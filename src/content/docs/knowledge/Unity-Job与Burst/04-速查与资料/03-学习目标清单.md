> 适用版本：以 Unity 6000.x 的 Burst 1.8.x / Collections 2.x / Mathematics 1.3.x 为主线；Unity 6.4 起 Collections 作为核心包随编辑器分发；本项目的 Unity 7000.0.0a8 中 Burst 2.0.0 与 Collections 6.7.0 是转发（shim）到引擎内置模块的壳包，API 仍在 `Unity.Burst` / `Unity.Collections` 命名空间，文档迁到了 Unity Manual。涉及版本差异处标"待核实"。

## 使用方法

- 每个阶段由“目标”“练习”“验收标准”三部分组成。括号里的“见 x.y”指向对应章节。
- 练习都落在本项目 `Assets/Scripts/WorldGen/` 的真实代码上。改动前先提交一个版本，方便对比优化前后的结果。
- 阶段 6 的验收要求每个阶段都留下优化前后的耗时表，所以从阶段 1 起就要记录基线数据。
- 本页是核对进度的清单，不含自测题。

## 阶段 1：Job 基础

目标

- [ ] 说清 Job 与主线程、`Task.Run` 的区别：谁调度、跑在哪个线程、如何同步（见 1.1、1.10）
- [ ] 会用 `IJob`、`IJobFor`、`IJobParallelFor`，并知道何时选哪个（见 1.2）
- [ ] 理解 `innerloopBatchCount` 对批大小的影响（见 1.8）
- [ ] 会用 `Schedule`、`ScheduleParallel`、`Run`，并知道三者的差别（见 1.2、1.3）
- [ ] 会用 `JobHandle`：`Complete`、依赖链、`CombineDependencies`（见 1.3）

练习（对应本项目）

- [ ] 阅读 `VoxelFaceVisibilityJob`（`IJobParallelFor`，输入 `Solid`、输出 `FaceMask`），把它改成只处理单个区块的版本，输入是一个 16 × 384 × 16 的区块数据（见 3.1）
- [ ] 分别用 `Run` 与 `Schedule(...).Complete()` 调用同一个 Job，在 Profiler 里对比（见 1.3、3.5）

验收标准

- [ ] 能画出一个区块从调度到完成经过哪些线程：主线程创建数据并调度，工作线程执行 `Execute`，主线程 `Complete` 后读取结果（见 1.1）
- [ ] 改造后的单区块 Job 输出的 `FaceMask` 与原版对应区域逐字节相同

## 阶段 2：Native 容器与安全系统

目标

- [ ] 掌握 `Allocator.Temp`、`TempJob`、`Persistent` 三种生命周期与 `Dispose` 时机（见 1.5）
- [ ] 会用 `NativeArray`、`NativeList`、`NativeParallelHashMap` 及 `ParallelWriter`（见 1.4、1.7）
- [ ] 会用 `[ReadOnly]`、`[WriteOnly]`、`[NativeDisableParallelForRestriction]`（见 1.6）
- [ ] 能读懂安全系统的报错和 Jobs Debugger 的提示（见 1.6）

练习（对应本项目）

- [ ] 把 `VoxelChunk.solid` 从 `byte[]` 改为 `Persistent` 的 `NativeArray<byte>`，并实现池化，让区块数据可复用而不是每次分配（见 1.5）
- [ ] 为 `VoxelChunk` 增加明确的释放路径，对应 `ChunkGenerationPipeline` 里区块被移出 `loaded` 的时机（见 1.5、3.5）
- [ ] 故意制造一次读写冲突（两个 Job 写同一个数组），观察并记录报错信息（见 1.6）

验收标准

- [ ] 反复生成、清除世界多次后，Console 没有 Native 内存泄漏警告（见 1.5）
- [ ] 能解释为什么不能把 `Allocator.Temp` 的数组传给跨帧的 Job（见 1.5）

## 阶段 3：Burst

目标

- [ ] 知道 Burst 支持的 C# 子集（HPC#）：哪些能写，哪些不能（见 2.2）
- [ ] 会用 Burst Inspector 看汇编，认出 SIMD 指令（见 2.5、2.4）
- [ ] 理解 `FloatMode`、`FloatPrecision` 与跨平台确定性的关系（见 2.6）
- [ ] 会用 `[NoAlias]`、`[SkipLocalsInit]`，知道函数指针的用法与代价（见 2.10、2.7）
- [ ] 熟悉 `Unity.Mathematics` 的 `float3`、`math` 函数（见 2.3）

练习（对应本项目）

- [ ] 用 Burst 重写 `ValueNoiseFunction` 的 hash 格点噪声：写成静态方法或 struct，输入整数格点坐标与种子，输出 `double` 或 `float`（见 3.2）
- [ ] 在 Burst Inspector 中检查该循环是否被向量化（见 2.5）
- [ ] 尝试不同的 `FloatMode`，比较结果差异与速度（见 2.6）

验收标准

- [ ] Burst 版与托管版在同一批输入上结果一致（整数哈希部分必须逐位一致；浮点部分需说明误差范围）
- [ ] 吞吐有量化提升，并记录为耗时表（见 3.5）

说明：该练习可以与阶段 1、2 交叉进行，因为它只需要一个最小的 Job 和 `NativeArray`。

## 阶段 4：密度函数 Burst 化

目标

- [ ] 方案 A，参数化 struct：把每种密度函数写成带参数的 struct，Job 中直接计算。通常最简单、运行时开销最小，以实测为准（见 3.2）
- [ ] 方案 B，压平成指令数组加解释器：把函数图展平为指令数组，Job 内用循环解释。灵活，但解释循环通常有额外开销（见 3.2）
- [ ] 方案 C，泛型结构体组合：用泛型 struct 组合函数，由单态化内联。写法优雅（见 2.9、3.2）
- [ ] 样条的 Burst 化：控制点放进 `NativeArray`，用二分查找段（见 3.2）
- [ ] 理解 `CubicSplineFunction` 在 Burst 下如何表示控制点与导数（见 3.2）

练习（对应本项目）

- [ ] 把 `ChunkDensitySampler` 的角点插值与同号填充移进 Job（见 3.3）
- [ ] 做一个二维场预计算 Job，取代现有的列缓存（`ColumnCacheFunction`、`CacheOnceFunction` 一类的缓存逻辑）（见 3.3）
- [ ] 先用方案 A 打通整条链路，再回头实现方案 C 并比较（见 3.2）

验收标准

- [ ] 1280 × 384 × 1280 的采样耗时与 `Task.Run` 版有量化对比数据（见 3.5）
- [ ] 生成的地形与托管版一致：固定种子下逐体素对比，差异数量为零或在说明的容差内
- [ ] 说清方案 A、B、C 各自的取舍

## 阶段 5：网格构建并行化

目标

- [ ] 会用 `Mesh.AllocateWritableMeshData` 与 `Mesh.ApplyAndDisposeWritableMeshData`（见 3.4、1.9）
- [ ] 理解 `VertexAttributeDescriptor` 与顶点布局（见 3.4）
- [ ] 掌握两遍法：第一遍数面，前缀和得到写入偏移，第二遍并行写入；单个区块的 MeshData 只需区块内的偏移，只有把多个区块合并成一个 Mesh 时才需要跨区块前缀和（见 3.4、1.7）
- [ ] 掌握顶点打包与 `UInt16` 索引的取舍，包括 65535 顶点上限（见 3.4）

练习（对应本项目）

- [ ] 把 `VoxelMeshBuilder.BuildChunk`（以及 `BuildChunkData`）改成 Burst Job，直接写入 `MeshData`（见 3.4）
- [ ] 对比现有的 `ChunkMeshData` 中间缓冲与 `MeshData` 直写的内存与耗时（见 3.4）

验收标准

- [ ] 主线程每帧只剩 `ApplyAndDisposeWritableMeshData` 的耗时（见 3.5）
- [ ] 生成的网格顶点数、三角形数与原版一致

## 阶段 6：调度与调优

目标

- [ ] 会用 Profiler Timeline 看并行度与 `Complete` 的等待（见 3.5、1.8）
- [ ] 能判断 Job 粒度是否合适（见 1.8）
- [ ] 知道何时不该用 Burst 或 Job：数据量小、对象图密集、需要大量 Unity API（见 0.2 与 1.9）

练习（对应本项目）

- [ ] 把 `ChunkGenerationPipeline` 中的 `Task.Run`（采样和建网格两处）换成 Job 链，用 `JobHandle` 表达“区块自身与四邻居采样完成后再建网格”的依赖（见 1.3、3.5）
- [ ] 保留背压逻辑（`maxLoadedChunks`、`maxSamplingInFlight`、`maxMeshingInFlight`）的等价实现（见 3.5）

验收标准

- [ ] 每个阶段都有优化前后耗时表，含测量方法、硬件与是否 Editor 环境（见 3.5）
- [ ] 能用 Timeline 截图说明瓶颈在哪一段，并据此做出一次有数据支撑的调整
