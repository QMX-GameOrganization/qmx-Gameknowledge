> 适用版本：以 Unity 6000.x 的 Burst 1.8.x / Collections 2.x 为主线；本项目的 Unity 7000.0.0a8 中 Burst 2.0.0 与 Collections 6.7.0 是转发（shim）壳包，API 仍在 `Unity.Burst` / `Unity.Collections` 命名空间。本章 API 签名以 Collections 2.5 文档为准，7000 上未逐项实测（待核实）。

## 要点

- 并行写入的核心矛盾：N 个工作项要往同一块输出里写，但写到哪里在运行前不知道（例如"每个暴露面追加一个顶点"）。
- 三条安全路线，按推荐顺序：
  1. 每个 index 只写属于自己的槽位（`IJobParallelFor` 天然安全，零同步）。
  2. 用容器自带的 `ParallelWriter`（内部有原子操作，写入顺序不确定）。
  3. 每线程或每批次各写各的缓冲，最后单线程合并。
- 需要"紧凑输出且顺序稳定"时，用两遍法（stream compaction）：第一遍计数，中间做前缀和（prefix sum），第二遍每个工作项按自己的偏移并行写。无锁、结果可复现。
- 归约（reduction，例如统计实心体素总数）：先每批次算部分和，再合并，不要让所有线程抢同一个计数器。
- 原子操作（`Interlocked`、`UnsafeAtomicCounter32`）可用，但高冲突下会成为瓶颈，仅作兜底。

## 原理

### 为什么不能直接并行 `list.Add`

`IJobParallelFor` 的安全系统只允许每个工作项访问 `NativeArray` 中属于自己 index 范围的元素。`NativeList<T>.Add` 会改长度字段，多个线程同时改就是数据竞争，所以安全系统直接拒绝在并行 Job 里使用普通 `NativeList`。Job 里能写的"共享追加"容器，必须是带原子语义的写入器。

```
普通 NativeList.Add            ParallelWriter.AddNoResize
  线程A: len=5 -> 写[5]          线程A: 原子取号 5 -> 写[5]
  线程B: len=5 -> 写[5]  冲突    线程B: 原子取号 6 -> 写[6]  安全
```

### 方式一：每 index 独占输出

输出数组长度与输入同长，`Execute(i)` 只写 `Output[i]`。体素场景里"每体素算一个面掩码"（本项目的 `VoxelFaceVisibilityJob`：`FaceMask[index] = mask`）就是这种。优点是最快、结果确定；缺点是输出是稀疏的（大部分体素没有面），后续要压缩。

### 方式二：ParallelWriter

通过容器的 `AsParallelWriter()` 取得写入器，传给 Job。以下类型与方法来自 Collections 2.5 API 文档（已核对）：

| 容器 | 写入器类型 | 关键方法 | 说明 |
|---|---|---|---|
| `NativeList<T>` | `NativeList<T>.ParallelWriter` | `AddNoResize(T)`、`AddRangeNoResize(void*, int)`、`AddRangeNoResize(NativeList<T>)` | 不会扩容，超过容量抛 `InvalidOperationException`，所以必须预先设好 `Capacity` |
| `NativeQueue<T>` | `NativeQueue<T>.ParallelWriter` | `Enqueue(T)` | 可无限追加，内部按块分配 |
| `NativeParallelHashMap<K,V>` | `NativeParallelHashMap<K,V>.ParallelWriter` | `TryAdd(K, V)`，属性 `ThreadIndex`、`Capacity` | key 已存在返回 `false`；不扩容，容量要预先设够（Collections 的 CHANGELOG 注明 `ParallelWriter` 的 `Add` / `TryAdd` 在容器已满时会抛异常） |
| `NativeStream` | `NativeStream.Writer` | `BeginForEachIndex(int)`、`Write<T>(T)`、`Allocate<T>()`、`EndForEachIndex()` | 每个 foreach 下标一块独立缓冲，天然无冲突 |

关于 `threadIndexOverride`：在 Collections 2.5 的文档里，`NativeList<T>.ParallelWriter`、`NativeQueue<T>.ParallelWriter`、`NativeParallelHashMap<K,V>.ParallelWriter` 都没有带该参数的公开重载，`ParallelWriter` 在 Job 中由作业系统自动注入线程下标（`NativeParallelHashMap` 的写入器暴露只读属性 `ThreadIndex`，文档说明"每个线程拿到自己的副本，job system 给每份赋上所在线程的下标"）。本项目的 Collections CHANGELOG 记录过：带线程下标参数的 `TryAdd` 曾一度公开，随后改为 internal，`m_ThreadIndex` 也改名为 `ThreadIndex`。所以不要依赖这类重载，直接调用 `TryAdd(key, value)` 即可。

`ParallelWriter` 的共同特点：

- 写入顺序不确定，同样的输入两次运行元素顺序可能不同。需要稳定顺序时要么事后排序，要么改用两遍法。
- 只能写，不能在同一个 Job 里读。
- 每次写入都有原子操作，写入量极大时有竞争开销。

`NativeStream` 的用法稍有不同：它以"foreach 下标"为单位分块，下标数在构造时固定，每个下标一块缓冲，适合"每个区块一个下标，往里写变长记录"。

```csharp
// 示例：每个 index 往自己的 NativeStream 缓冲里写若干条记录
[BurstCompile]
struct EmitFacesJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<byte> FaceMask;
    public NativeStream.Writer Writer;

    public void Execute(int index)
    {
        Writer.BeginForEachIndex(index);          // 每个 index 只开一次
        byte mask = FaceMask[index];
        for (int face = 0; face < 6; face++)
            if ((mask & (1 << face)) != 0)
                Writer.Write(new int2(index, face));
        Writer.EndForEachIndex();                 // 结束后才能读
    }
}
// 主线程：var stream = new NativeStream(count, Allocator.TempJob);   // 第一个参数是 buffer 数量
//        job.Writer = stream.AsWriter(); ... Complete 之后用 stream.AsReader() 或 stream.ToNativeArray<int2>(Allocator.TempJob) 读取，
//        用完 stream.Dispose()
```

`NativeStream` 与 `NativeStream.Writer` 的签名已按 Collections 2.5 文档核对：构造函数 `NativeStream(int bufferCount, AllocatorHandle allocator)`，`AsWriter()` / `AsReader()` 返回 `NativeStream.Writer` / `Reader`，`ToNativeArray<T>(AllocatorHandle)` 把各 buffer 依次拷成一个数组（buffer 0 在前，所以顺序与线程调度无关）。文档提醒两点：写入要在第一次读取之前全部完成；调用 `BeginForEachIndex` 之后传递写入器必须按引用传，不能按值拷贝，否则会抛 `ArgumentException`。

### 方式三：每线程 / 每批次独立缓冲

给每个批次（或每个线程）一块独立缓冲，Job 内互不干扰，Job 结束后单线程合并。合并是顺序的，所以如果缓冲按批次编号排列，合并结果的顺序是稳定的。代价是多一次拷贝和更多内存。

按线程分槽用 `[NativeSetThreadIndex]`：Job 结构体里声明一个 `int` 字段并打上这个特性，作业系统会在运行时把当前工作线程的下标注入进去。文档说明它"常用于实现原子容器，下标保证与其它并行运行的 Job 不重复"，对应的运行时值是 `JobsUtility.ThreadIndex`（在 Job 外读取返回 0）。分槽数组的长度用 `JobsUtility.ThreadIndexCount`（脚本 API 文档：能同时在一个 Job 上工作的最大工作线程数）。`JobsUtility.MaxJobThreadCount`（文档："Job 系统可创建的最大线程数"）在旧代码和旧版容器里更常见；两者在你的版本上数值关系请以实测为准（待核实），保守做法是取两者较大值。

## ParallelReader 概念与"确定性读写"

出处：Collections 2.5 手册 Parallel readers and writers 页。

### ParallelReader / ParallelWriter

官方的说法：好几个集合类型都带有嵌套类型，用来在并行 Job 里读或写。例如要在并行 Job 里安全地往 `NativeList<T>` 写，必须用 `NativeList<T>.ParallelWriter`（官方示例里它共享原列表的 `AtomicSafetyHandle`，每次调用 `AddNoResize(i)`）：

```csharp
NativeList<int> nums = new NativeList<int>(1000, Allocator.TempJob);
var job = new MyParallelJob { NumsWriter = nums.AsParallelWriter() };

public struct MyParallelJob : IJobParallelFor
{
    public NativeList<int>.ParallelWriter NumsWriter;
    public void Execute(int i) => NumsWriter.AddNoResize(i); // 只能追加，不能扩容
}
```

两点限制：

- 这些并行读写器只支持集合功能的一个子集。例如 `NativeList` 在并行 Job 里不能扩容，因为没有不引入同步开销的安全做法（所以前面强调 `AddNoResize` 要预留容量）。
- 官方页面标题是 "Parallel readers and writers"，正文只给了 `ParallelWriter` 的示例，把"并行读取"当作与写入对称的概念来谈（读取安全，但读取顺序不确定）。哪些容器有名为 `ParallelReader` 的具体类型，这一页没有列出，待核实；本章所有已核对的并行写入类型见上面"方式二"，只读访问通常用 `[ReadOnly]` 或 `AsReadOnly()`（见 1.4、1.6）。

### 为什么顺序不确定

`ParallelWriter` 保证并发写入的安全，但写入的先后顺序取决于线程调度，而线程调度由操作系统和程序之外的其它因素决定。`ParallelReader` 同理：并发读取是安全的，但读取顺序不确定，你无法知道哪个线程读到了哪个值。

### 确定性读写的三种手段

官方列出三种做法：

1. 用 `NativeStream`（或 `UnsafeStream`）。官方描述为：把读写拆到各自独立的缓冲里，从而避免不确定性。本页前面"方式二"里的 `NativeStream` 就是这条路：每个 foreach 下标一块缓冲，之后按下标顺序读。（官方这一页写的是"每个线程一个缓冲"，而 `NativeStream` 的 API 是"每个 foreach 下标一个缓冲"；要得到与线程调度无关的顺序，应以后者理解，这一点是我对两处文字的对照推断，待核实。）
2. 按范围划分：把读取确定性地分成若干范围，每个范围交给自己的线程处理。例如 `IJobParallelFor` 里每个 index 负责固定的一段 `[start, end)`，输出写进"每 index 独占"的槽位，再顺序合并。本页的"每批次部分和"与两遍法本质上都是这一类。
3. 写后排序：先让 `ParallelWriter` 无序写入，写完后对数据做确定性排序。排序工具见 1.4 的"排序与扩展方法"（`NativeSortExtension.Sort` / `SortJob`）。代价是多一次排序，且要排序键能唯一决定顺序，否则相同键的元素顺序仍然不确定。

对应本项目：区块网格的面列表如果需要在不同机器、不同线程数下完全一致（便于回归测试），不要直接用 `NativeList.ParallelWriter` 的输出；选"两遍法"（手段 2 的特例）或让每个区块写进自己的 `NativeStream` 下标。

## 两遍法：count - scan - write

目标：从逐体素的面掩码 `FaceMask` 压缩出一个紧凑的"面列表 + 三角形索引"，顺序按体素 index 稳定，不使用任何锁和原子操作。

```
体素 index :   0   1   2   3   4   5
FaceMask   :  0b0 0b11 0b0 0b1 0b111 0b0
counts     :   0   2    0   1   3     0        第一遍：每体素暴露面数 (popcount)
offsets    :   0   0    2   2   3     6        前缀和 (exclusive scan)，total = 6
                 |         |   |
          写入区间: [0,2)  -  [2,3) [3,6)       第二遍：体素 i 写到 offsets[i] 开始处
```

exclusive scan 的含义：`offsets[i]` 等于 `counts[0..i-1]` 之和（不含自己），所以体素 i 的输出区间正好是 `[offsets[i], offsets[i] + counts[i])`，区间两两不相交，并行写不会冲突。

前缀和有两种实现：

- 单线程 `IJob`：一个循环累加。对一个 16x16xH 区块（几万个体素）通常足够便宜，实现最简单。是否真是瓶颈要用 Profiler 看（见后续调度粒度一章）。
- 并行扫描：把数组切成若干块，各块并行求块内和，再扫描"块和数组"，最后各块并行加上块偏移。三段式，适合数据量大到单线程扫描成为瓶颈时。

### 完整示例

三个 Job 依次依赖：计数、扫描、写入。`FaceMask` 沿用本项目 `VoxelFaceVisibilityJob` 的位定义（bit0..bit5 对应 +X、-X、+Y、-Y、+Z、-Z）。

```csharp
using Unity.Burst;
using Unity.Collections;
using Unity.Jobs;
using Unity.Mathematics;

// 第一遍：每个体素统计暴露面数。每 index 独占输出，天然安全。
[BurstCompile]
struct CountFacesJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<byte> FaceMask;
    [WriteOnly] public NativeArray<int> Counts;

    public void Execute(int index)
    {
        Counts[index] = math.countbits((uint)FaceMask[index]);
    }
}

// 中间：exclusive scan。单线程 IJob，同时写出总数。
[BurstCompile]
struct ExclusiveScanJob : IJob
{
    [ReadOnly] public NativeArray<int> Counts;
    [WriteOnly] public NativeArray<int> Offsets;
    [WriteOnly] public NativeArray<int> Total;   // 长度 1

    public void Execute()
    {
        int running = 0;
        for (int i = 0; i < Counts.Length; i++)
        {
            Offsets[i] = running;     // 不含自己
            running += Counts[i];
        }
        Total[0] = running;
    }
}

// 第二遍：每个体素把自己的面写进 [Offsets[i], Offsets[i] + count) 区间。
// 写入位置不等于 index，需要 NativeDisableParallelForRestriction 关掉按 index 的范围检查；
// 安全性由"区间不相交"这一算法性质保证，而不是由安全系统保证。
[BurstCompile]
struct WriteFacesJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<byte> FaceMask;
    [ReadOnly] public NativeArray<int> Offsets;

    [NativeDisableParallelForRestriction] [WriteOnly] public NativeArray<int2> Faces;     // 长度 total
    [NativeDisableParallelForRestriction] [WriteOnly] public NativeArray<int> Indices;    // 长度 total * 6

    public void Execute(int index)
    {
        byte mask = FaceMask[index];
        if (mask == 0) return;

        int slot = Offsets[index];
        for (int face = 0; face < 6; face++)
        {
            if ((mask & (1 << face)) == 0) continue;

            Faces[slot] = new int2(index, face);

            // 每个面 4 个顶点（顶点缓冲里第 slot 个面占 [slot*4, slot*4+4)），2 个三角形共 6 个索引
            int v = slot * 4;
            int i = slot * 6;
            Indices[i + 0] = v; Indices[i + 1] = v + 1; Indices[i + 2] = v + 2;
            Indices[i + 3] = v; Indices[i + 4] = v + 2; Indices[i + 5] = v + 3;
            slot++;
        }
    }
}
```

主线程调度。注意总数 `total` 只有扫描完成后才知道，输出数组要等它，所以这里需要一个同步点（`Complete`）。想避免同步点，可以改按最坏情况（每体素 6 面）预分配，或改用 `NativeList` 加 `ResizeUninitialized` 的 Job 来延迟定长（本章不展开）。

```csharp
static void BuildFaces(NativeArray<byte> faceMask, out NativeArray<int2> faces, out NativeArray<int> indices)
{
    int n = faceMask.Length;
    var counts  = new NativeArray<int>(n, Allocator.TempJob, NativeArrayOptions.UninitializedMemory);
    var offsets = new NativeArray<int>(n, Allocator.TempJob, NativeArrayOptions.UninitializedMemory);
    var total   = new NativeArray<int>(1, Allocator.TempJob);

    var h1 = new CountFacesJob { FaceMask = faceMask, Counts = counts }.Schedule(n, 256);
    var h2 = new ExclusiveScanJob { Counts = counts, Offsets = offsets, Total = total }.Schedule(h1);
    h2.Complete();                                   // 必须先知道 total 才能分配输出

    int totalFaces = total[0];
    faces   = new NativeArray<int2>(totalFaces, Allocator.TempJob, NativeArrayOptions.UninitializedMemory);
    indices = new NativeArray<int>(totalFaces * 6, Allocator.TempJob, NativeArrayOptions.UninitializedMemory);

    new WriteFacesJob { FaceMask = faceMask, Offsets = offsets, Faces = faces, Indices = indices }
        .Schedule(n, 256).Complete();

    counts.Dispose(); offsets.Dispose(); total.Dispose();
    // faces 和 indices 以 TempJob 分配并交给调用方：用完后由调用方 Dispose，且要在 4 帧内
}
```

两遍法的性质：输出顺序按体素 index 升序，与线程数、调度顺序无关；同样输入永远得到同样输出，便于做回归测试和对比。

## 归约（reduction）

归约指把大量元素合成一个值：求和、计数、最大最小值。错误写法是所有工作项都对同一个计数器累加（要么被安全系统拒绝，要么靠原子操作串行化）。正确思路是"局部累加，最后合并"。

### 每批次部分和

让工作项的粒度变成"一块"而不是"一个体素"：每个工作项扫一块连续数据，把部分和写到自己的槽位，最后一个单线程 Job 合并（块数很少，几乎免费）。

```csharp
[BurstCompile]
struct CountSolidBlocksJob : IJobParallelFor
{
    public const int BlockSize = 1024;

    [ReadOnly] public NativeArray<byte> Solid;
    [WriteOnly] public NativeArray<int> Partials;   // 长度 = ceil(Solid.Length / BlockSize)

    public void Execute(int block)
    {
        int start = block * BlockSize;
        int end = math.min(start + BlockSize, Solid.Length);
        int sum = 0;
        for (int i = start; i < end; i++)
            sum += Solid[i] != 0 ? 1 : 0;
        Partials[block] = sum;                       // 每 index 独占输出
    }
}

[BurstCompile]
struct SumJob : IJob
{
    [ReadOnly] public NativeArray<int> Partials;
    [WriteOnly] public NativeArray<int> Result;      // 长度 1
    public void Execute()
    {
        int s = 0;
        for (int i = 0; i < Partials.Length; i++) s += Partials[i];
        Result[0] = s;
    }
}
// 调度：blocks = (n + BlockSize - 1) / BlockSize; Schedule(blocks, 1) 后接 SumJob.Schedule(handle)
```

这里 `Schedule(blocks, 1)` 的批大小设为 1 是合理的：每个工作项已经是 1024 个体素的活。粒度怎么选见下一章。

### 每线程槽位

不想自己切块、只想"每个线程一个累加器"时，用 `[NativeSetThreadIndex]` 加一个按线程分槽的数组。槽位之间要隔开至少一个缓存行（`JobsUtility.CacheLineSize`，常见为 64 字节，即 16 个 `int`），否则相邻线程写同一缓存行会产生伪共享（false sharing），反而变慢。

```csharp
using Unity.Collections.LowLevel.Unsafe;
using Unity.Jobs.LowLevel.Unsafe;

[BurstCompile]
struct CountSolidPerThreadJob : IJobParallelFor
{
    public const int Stride = 16;                    // 16 个 int = 64 字节

    [ReadOnly] public NativeArray<byte> Solid;

    [NativeDisableParallelForRestriction]
    public NativeArray<int> PerThread;               // 长度 = JobsUtility.ThreadIndexCount * Stride

    [NativeSetThreadIndex] int threadIndex;          // 运行时由作业系统注入

    public void Execute(int i)
    {
        if (Solid[i] != 0) PerThread[threadIndex * Stride]++;
    }
}
// 主线程：new NativeArray<int>(JobsUtility.ThreadIndexCount * Stride, Allocator.TempJob)
// 完成后遍历各槽求和。
```

要点：数组必须清零（`NativeArrayOptions.ClearMemory` 是默认值）；这种写法的输出只与"哪个线程处理了哪些 index"有关，整数求和结果不受影响，浮点求和则会受影响（见后文）。

## 原子操作

Burst 手册（System namespace support 一页）确认：Burst 支持 `System.Threading.Interlocked` 的全部方法（例如 `Interlocked.Increment`），前提是被操作的内存地址按类型自然对齐，否则行为未定义。另外 `Thread.MemoryBarrier` 与 `Volatile.Read/Write`（非泛型版本）也受支持。Job 里要对 `ref` 目标取非托管内存（例如指针指向的 `int`），不能对托管对象的字段做原子操作。

Collections 提供了对指针指向的整数做原子加减的包装：`Unity.Collections.LowLevel.Unsafe.UnsafeAtomicCounter32` 和 64 位版本 `UnsafeAtomicCounter64`（Collections 2.5 API 页都有；本项目的壳包 `AssemblyTypeForwarders.cs` 里两者都有 `TypeForwardedTo`，7000.0.0a8 上均可用）。

`UnsafeAtomicCounter32` 的特点（Collections 2.5 文档）：计数器本身不拥有整数，而是"指向"一个 `int`，让不同 Job 的计数器可以共享同一个底层整数。构造 `new UnsafeAtomicCounter32(void* ptr)`；方法 `Add(int)` / `Sub(int)` 返回修改前的原值，`AddSat` / `SubSat` 带上下限饱和，`Reset(int)` 是非原子赋值。

```csharp
using Unity.Collections.LowLevel.Unsafe;   // UnsafeAtomicCounter32、NativeArrayUnsafeUtility

[BurstCompile]
unsafe struct CountSolidAtomicJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<byte> Solid;
    // 指向一块在 Job 完成前一直有效的非托管内存，例如 NativeArray<int>(1, Allocator.TempJob) 的
    // NativeArrayUnsafeUtility.GetUnsafePtr(arr)；不要传局部变量的地址。
    [NativeDisableUnsafePtrRestriction] public int* Counter;

    public void Execute(int i)
    {
        if (Solid[i] == 0) return;
        var counter = new UnsafeAtomicCounter32(Counter);
        counter.Add(1);
    }
}
```

使用前提：`unsafe` 代码要在项目或 asmdef 中启用 Allow 'unsafe' Code。这种写法每个实心体素一次原子操作，所有线程争同一个缓存行，通常比"分块部分和"慢得多，只适合冲突很少的场合（例如罕见事件计数、错误标志）。

`NativeCounter` 是社区和 Unity 旧示例里常见的自定义容器模式：内部按线程下标分槽、槽间隔开缓存行，读总数时把各槽加起来。它本质就是上面"每线程槽位"的封装，不是 Collections 包的内置类型。

## 浮点归约的顺序依赖

浮点加法不满足结合律，分块或分线程的求和顺序不同，结果的最后几位就可能不同。需要跨机器或跨次运行完全一致的结果时，要固定块划分并按固定顺序合并（"每批次部分和"天然满足，"每线程槽位"不满足）。Burst 对浮点的优化选项另见 2.6 浮点模式与确定性。

## 选型表

| 场景 | 推荐方式 | 顺序稳定 | 同步成本 |
|---|---|---|---|
| 输出与输入一一对应（面掩码、密度值） | 每 index 独占输出 | 是 | 无 |
| 紧凑输出，顺序要可复现（顶点索引、面列表） | 两遍法 | 是 | 一个 `Complete` 取总数 |
| 紧凑输出，顺序无所谓（碰撞候选点、事件） | `NativeList.ParallelWriter` / `NativeQueue.ParallelWriter` | 否 | 原子取号 |
| 变长记录、按区块分组 | `NativeStream` | 组内是 | 无（每下标独立） |
| 计数、求和 | 分块部分和 | 是 | 一个合并 Job |
| 稀有事件计数 | `UnsafeAtomicCounter32` / `Interlocked` | 不适用 | 原子冲突 |

## 对应本项目

- `VoxelFaceVisibilityJob` 是方式一：`IJobParallelFor`，每个体素独占写 `FaceMask[index]`。
- `VoxelMeshBuilder.BuildWithJobs` 在 `Complete()` 之后用主线程三重循环把掩码转成 `List<Vector3>` 顶点，这一步正是两遍法能替代的部分：用上面的 `CountFacesJob` + `ExclusiveScanJob` + `WriteFacesJob` 可以把"掩码到面列表"也放进 Job。
- `ChunkGenerationPipeline` 里的 `SolidCount`：每个区块在后台任务里自己累加（`ChunkDensitySampler.Fill` 的局部变量 `solidCount`，最后 `SetSolidCount`），主线程再逐块相加。这是"每批次部分和"的一个手写版本：批次 = 区块，合并在主线程。
- 同一文件里的 `Interlocked.Add(ref sampleTicks, ...)` 是托管代码里用原子操作汇总耗时的例子，冲突频率是每区块一次，可以接受。

## 常见坑

- `AddNoResize` 容量不够：并行写入前必须 `Capacity` 足够。容量只能在主线程或单线程 Job 里扩，估算不准时宁可大一点。
- 以为 `ParallelWriter` 输出有序：写入顺序随调度变化。要可复现结果就用两遍法，或写完后排序。
- 绕过安全系统后写重叠：`[NativeDisableParallelForRestriction]` 之后不再有保护，偏移算错就是静默数据竞争。两遍法务必验证 `offsets[i] + counts[i] == offsets[i+1]` 以及末项等于 `total`。
- 分槽数组忘记隔开缓存行：功能正确但并行度被伪共享吃掉。
- 在 Job 里对 `NativeList` 直接 `Add`：并行 Job 里会被安全系统拒绝；单线程 `IJob` 里可以。
- 浮点求和结果每次不同：属于预期现象，见上节。

## 小结

- 先问"能不能让每个 index 只写自己的槽"，能就不要用别的。
- 需要紧凑输出：无序用 `ParallelWriter`，有序用两遍法。
- 归约用"分块部分和"，原子操作留给低冲突场景。
- 绕过安全检查的写入，正确性由算法不变式保证，必须自己验证。

## 自测题

1. `NativeList<T>.ParallelWriter.AddNoResize` 在容量不足时会怎样，使用前要做什么？
   答：抛 `InvalidOperationException`；使用前在主线程把 `Capacity` 设到足够大。
2. exclusive scan 与 inclusive scan 的区别是什么，两遍法为什么用前者？
   答：exclusive 的第 i 项不含自己，等于该工作项输出区间的起点；用它可以直接作为写入偏移。
3. 为什么两遍法的输出顺序与线程数无关？
   答：每个工作项的输出区间由前缀和决定，只取决于输入，不取决于调度。
4. 给每线程一个 `int` 累加槽时，为什么槽间要隔开 64 字节？
   答：避免相邻线程写同一缓存行造成伪共享。
5. Burst 里能用 `Interlocked.Increment` 吗，有什么前提？
   答：可以；被操作地址必须按类型自然对齐。
6. 官方给出的"确定性读写"有哪三种手段？
   答：用 `NativeStream` / `UnsafeStream` 分缓冲；把读写按确定的范围划分给各线程；写完后做确定性排序。
7. 为什么 `ParallelWriter` 的写入顺序不确定？
   答：顺序取决于线程调度，而调度由操作系统等程序之外的因素决定。
