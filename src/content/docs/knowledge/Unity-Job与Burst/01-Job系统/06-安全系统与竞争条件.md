> 适用版本：以 Unity 6000.x 的 Collections 2.x 为主线；Unity 6.4 起 Collections 作为核心包随编辑器分发；本项目的 Unity 7000.0.0a8 中 Burst 2.0.0、Collections 6.7.0 是转发壳包，API 仍在 `Unity.Collections` / `Unity.Burst` 命名空间。报错措辞按常见形式记录，具体类型名、字段名随你的代码而变，版本间可能有细微差异。编辑器菜单位置按 Unity 6000.5 / 6000.7 文档核对，7000.0.0a8 未逐项实测。

## 要点

- 竞争条件（race condition）：结果取决于线程执行的先后时序，偶发、难复现。Unity 的安全系统把它们变成确定的、带说明的异常。
- 规则只有两条：多个只读访问可以并行；任何写与同一容器上的其它读写冲突，必须用 `JobHandle` 依赖排序。
- 主线程同样受约束：Job 没完成就读写被占用的容器，会抛 `InvalidOperationException`，解法是先 `handle.Complete()`。
- `IJobParallelFor` 里每个 Job 只能访问自己的索引范围，越界会报错；`[NativeDisableParallelForRestriction]` 能关掉这层保护，风险由你自己承担。
- 安全检查只在编辑器和开发构建中启用，Release 构建里去除（由 `ENABLE_UNITY_COLLECTIONS_CHECKS` 等宏控制，具体宏列表待核实）。编辑器里报错一定要修；用了 Unsafe 或指针绕过检查的代码，检查不到不代表正确。
- `Unsafe*` 容器与裸指针绕过安全系统，出错表现为随机崩溃或脏数据。

## 竞争条件是什么，为什么难调

```
线程 A:  读 x -> x+1 -> 写回
线程 B:        读 x -> x+1 -> 写回      两次 +1 只生效一次
```

问题在于：结果取决于调度时序，同一份代码这次对、下次错；加日志或断点会改变时序，错误就消失。所以 Unity 的思路不是"事后调试"，而是在调度时就按"谁读谁写"做静态规则检查。

官方手册的描述：安全系统检测所有潜在的竞争条件；如果两个互不依赖的 Job 写同一个 `NativeArray`，无法预测谁先执行，所以在调度第二个 Job 时就抛出带清晰说明的异常。

## AtomicSafetyHandle 原理

每个 `Native*` 容器内部持有一个 `AtomicSafetyHandle`，指向一个由安全管理器维护的记录，大致包含：

- 当前的写版本号与读版本号（记录"最近有哪些 Job 在读/写"）。
- 允许标志（是否可读、可写、是否只写）。
- 释放标记：容器 `Dispose` 后，句柄失效，后续访问会报"已释放"。

调度 Job 时，系统检查 Job 里每个容器字段的访问方式（`[ReadOnly]` 或读写），与记录中仍未完成的 Job 做比较；冲突则抛异常。主线程访问容器时，同样检查是否有未完成的 Job 占用。

编译开关：这些检查由 `ENABLE_UNITY_COLLECTIONS_CHECKS` 等宏控制（Collections 包的 CHANGELOG 还提到部分检查在 `UNITY_DOTS_DEBUG` 下也会启用），编辑器和开发构建启用，Release 构建去除，所以发布版没有这部分开销（具体宏列表与默认定义位置待核实）。

补充说明：上面"写版本号与读版本号"是粗略的说法。官方 Copying NativeContainer structures 一页的描述更具体：每个容器背后有一条由安全系统维护的中心记录，记录里有一个版本号和一个可独立递增的次级版本号；每份 `AtomicSafetyHandle` 保存"指向中心记录的指针"加"这份拷贝能做什么的标志"，并带着创建时记下的版本号副本。下一节展开。

## 容器拷贝语义与 AtomicSafetyHandle 版本号机制

出处：Unity 手册 Copying NativeContainer structures（6000.6 版页面核对）。

### 拷贝的是结构，不是数据

`NativeContainer` 是值类型。把它赋给另一个变量、传进方法或放进 Job 字段时，复制的是容器结构本身，其中包含指向数据存放位置的指针和 `AtomicSafetyHandle`，不会复制容器里的全部内容。结果是同一个容器可以有多份结构拷贝：

- 所有拷贝指向同一块数据内存。
- 所有拷贝的 `AtomicSafetyHandle` 指向同一条中心记录。
- 每份拷贝的标志可以不同，表示"这份拷贝当前允许做什么"。例如交给 Job A 的那份是只读，交给 Job B 的那份是读写，主线程手上的是另一份。指针加标志合起来就是 `AtomicSafetyHandle`。

这也是官方在 Create and run a job 页写的那句话的原因：Job 拿到的是 Job 数据的拷贝，但 `NativeContainer` 的拷贝和原件指向同一块内存，所以 Job 完成后只有写进 `NativeContainer` 的数据才能在主线程看到。

### 主版本号：Dispose 让所有拷贝同时失效

容器被释放后，所有拷贝里保存的数据指针都成了悬空指针，继续用可能引发访问冲突。安全系统用版本号解决：

- 中心记录的内存从不释放，所以拷贝里的句柄永远不会指向已回收的内存。
- 释放容器时调用 `Release()`，把中心记录上的版本号加一，之后这条记录可以被别的 `NativeContainer` 复用。
- 每份 `AtomicSafetyHandle` 记着自己创建时的版本号，访问时与中心记录里的当前版本号比较，不相等就说明容器已释放。这个比较在 `CheckReadAndThrow`、`CheckWriteAndThrow` 这类方法里自动完成。

后果：对一个容器的任意一份拷贝调用 `Dispose`，其它拷贝下一次访问时都会抛 `ObjectDisposedException`（"has been deallocated"一类，见"常见报错逐条解读"第 4 条）。但 `IsCreated` 只在被调用 `Dispose` 的那份上变成 false，其它拷贝的 `IsCreated` 不反映这件事（见 1.5 的常见坑：对两份拷贝都 `Dispose` 会二次释放）。

### 次级版本号：扩容后视图失效

可变长容器（官方例子是 Collections 里的 `NativeList<T>`）和定长容器（`NativeArray<T>`）不同：可以不断追加元素。这类容器能给出"视图"（view）：不拷贝也不持有数据、直接别名容器数据的访问对象，例如枚举器和 `NativeList<T>.AsArray()`。官方说明，容器大小变化时 Unity 会把数据搬到内存的别处，视图里存的指针随之无效，所以视图在大小变化时通常不是线程安全的。

为此安全句柄里还有一个次级版本号，存在同一条中心记录里，可以独立于主版本号递增。官方列出的配套方法：

- `UseSecondaryVersion`：给"视图"用的句柄调用，让视图用次级版本号做有效性检查。
- `CheckWriteAndBumpSecondaryVersion`：改变容器大小或以其它方式使现有视图失效的操作，用它代替 `CheckWriteAndThrow`，检查写权限的同时把次级版本号加一，让已存在的视图作废。
- `SetBumpSecondaryVersionOnScheduleWrite`：在容器上设置后，每当有写这个容器的 Job 被调度，就自动使视图失效。
- `CheckGetSecondaryDataPointerAndThrow`：创建视图、把句柄拷给它之前，确认把数据指针拷进视图是安全的。

这四个方法在官方自定义容器示例里都出现了（见 1.11 自定义 NativeContainer），那里的 `AsArray()` 返回的就是带次级版本号的视图。

### 两个特殊句柄

给临时容器用的两个特殊句柄：`GetTempMemoryHandle` 用于 `Allocator.Temp` 分配的容器，当前临时内存作用域结束时 Unity 自动使其失效，不需要你释放，`IsTempMemoryHandle` 可判断某个句柄是不是它；`GetTempUnsafePtrSliceHandle` 是全局句柄，用于由不安全内存支撑的临时容器（例如用栈内存构造的 `NativeSlice`），使用它的容器不能传进 Job。

### 典型报错与排错

| 现象 | 常见原因 | 排错 |
|---|---|---|
| `ObjectDisposedException`（已释放） | 通过某份拷贝 `Dispose` 之后，另一份拷贝继续被访问；Job 还在跑就释放 | 找到所有持有同一容器的拷贝；谁创建谁释放，释放后把其它引用置为默认值或不再访问 |
| 访问 `AsArray()`、枚举器等视图时抛异常 | 视图创建后容器扩容，或调度了写该容器的 Job，视图已因次级版本号变化而作废 | 变更后重新取视图，不要长期保存视图（异常的具体措辞待核实，官方页面没有给出） |
| `IsCreated` 为 true 但访问报已释放 | `IsCreated` 只反映当前这份拷贝 | 不要用 `IsCreated` 判断别份拷贝，也不要对多份拷贝重复 `Dispose` |
| 用 `Unsafe*` 或指针别名后没有任何报错却读到脏数据 | 这些路径绕开了版本号检查 | 见 1.5 的别名一节与本章"Unsafe 容器与指针如何绕过安全系统" |

## 读写规则

| 情形 | 是否允许 |
|---|---|
| 多个 Job 都只读同一容器（`[ReadOnly]`） | 允许并行 |
| 一个 Job 写，另一个 Job 读或写同一容器 | 冲突，必须用依赖排序 |
| Job 运行中，主线程读/写被 Job 写的容器 | 抛异常，先 `Complete()` |
| Job 运行中，主线程写被 Job 只读的容器 | 抛异常 |
| 不同容器 | 互不影响 |

默认情况下 Job 对容器字段是读写权限，会占用写锁，削弱并行度。不写的字段务必加 `[ReadOnly]`；只写不读的加 `[WriteOnly]`（`NativeArray` 等容器支持，用于表明"不读旧值"，对它读取会被安全系统拒绝）。

```csharp
[BurstCompile]
struct DensityJob : IJobParallelFor
{
    [ReadOnly]  public NativeArray<float> Noise;   // 只读，可与其它只读 Job 并行
    [WriteOnly] public NativeArray<byte>  Solid;   // 只写
    public void Execute(int i) => Solid[i] = (byte)(Noise[i] > 0f ? 1 : 0);
}

// 两个 Job 写同一个 Solid：用依赖排序
JobHandle a = new DensityJob { Noise = n, Solid = s }.Schedule(s.Length, 128);
JobHandle b = new PostJob    { Solid = s }.Schedule(s.Length, 128, a); // 依赖 a
b.Complete();
```

## IJobParallelFor 的索引保护

`IJobParallelFor` 把 `[0, N)` 切成批次分给多个线程。对被标记为"支持最小/最大写入范围"的容器（`NativeArray` 属于此类，内部属性 `[NativeContainerSupportsMinMaxWriteRestriction]`），安全系统规定：`Execute(int index)` 中只能读写 `index` 这一个元素。

```csharp
public void Execute(int i)
{
    Data[i] = 1;       // 正确
    Data[i + 1] = 1;   // 越界保护：报 IndexOutOfRangeException
}
```

典型报错形如：`Index 5 is out of restricted IJobParallelFor range [0...3] in ReadWriteBuffer.`，后面通常还跟一句说明 ReadWriteBuffer 只允许读写与 Job 下标对应的元素、可以用双缓冲避免竞争。数字与容器名随实际情况变化。

### [NativeDisableParallelForRestriction]

关掉这层限制，让每个 Execute 能访问任意下标。适用于：

- 你有自己的划分约定，例如按区块写入互不重叠的区段：`index` 对应一个区块，写 `[index*size, (index+1)*size)`。
- 邻居数据只读（此时更好的做法是另开一个 `[ReadOnly]` 字段）。

风险：如果两个 `index` 实际写到了同一元素，这就是真正的竞争条件，且安全系统不再提示。

```csharp
[BurstCompile]
struct ColumnJob : IJobParallelFor
{
    public int SizeY;
    [NativeDisableParallelForRestriction] public NativeArray<byte> Solid; // 每个 index 写自己的一整列
    public void Execute(int column)
    {
        int start = column * SizeY;
        for (int y = 0; y < SizeY; y++) Solid[start + y] = 1;
    }
}
```

### 其它相关属性

| 属性 | 作用 |
|---|---|
| `[NativeDisableContainerSafetyRestriction]` | 关闭该容器字段上的容器安全限制（例如调度时的读写冲突/别名检查），常用于"我知道自己在干什么"的场景。它与 `[NativeDisableParallelForRestriction]` 不是同一个开关：需要放开 `IJobParallelFor` 的下标限制时用后者；两者的精确覆盖范围官方文档描述很少，使用时以实际行为为准（待核实） |
| `[NativeDisableUnsafePtrRestriction]` | 允许 Job 字段持有裸指针 |
| `[NativeSetThreadIndex]` | 把当前工作线程索引注入 Job 结构体里的 `int` 字段；官方说明该下标与可能并行运行的其它 Job 不重复，通常用于原子容器的实现 |
| `[NativeContainer]`、`[NativeContainerSupportsMinMaxWriteRestriction]`、`[NativeContainerIsReadOnly]`、`[NativeContainerIsAtomicWriteOnly]`、`[NativeContainerSupportsDeferredConvertListToArray]`、`[NativeContainerSupportsDeallocateOnJobCompletion]`、`[NativeSetClassTypeToNullOnSchedule]` | 自定义容器（或需要特殊处理的字段）声明自己的安全特性。只在这里点名，各自的作用与要求见 1.11 自定义 NativeContainer |

`[NativeSetThreadIndex]` 典型用法是"每线程一个缓冲区"，用 `JobsUtility.ThreadIndexCount`（官方：能同时在一个 Job 上工作的最大工作线程数）决定分配多少份：

```csharp
using Unity.Jobs.LowLevel.Unsafe;

[BurstCompile]
struct PerThreadCount : IJobParallelFor
{
    [NativeDisableParallelForRestriction] public NativeArray<int> Counters; // 长度 = ThreadIndexCount
    [NativeSetThreadIndex] int threadIndex;
    public void Execute(int i) { Counters[threadIndex]++; }  // 每线程只写自己那一格
}
// 创建: new NativeArray<int>(JobsUtility.ThreadIndexCount, Allocator.TempJob)
// 演示用：相邻格在同一缓存行，会有伪共享，实际做法见 1.7 并行写入与归约模式
```

注意线程索引不保证是 0 起连续编号。旧代码和旧版容器里更常见的上界是 `JobsUtility.MaxJobThreadCount`（官方：Job 系统可创建的最大线程数），两者数值关系以实测为准（待核实），拿不准时取较大者分配。

## 主线程访问被占用的容器

Job 已调度、尚未完成时，主线程读或写它占用的容器会抛 `InvalidOperationException`。解法：

```csharp
JobHandle h = job.Schedule(n, 64);
// var x = result[0];   // 抛异常：Job 可能还在写
h.Complete();           // 等待并让安全系统释放该 Job 对容器的占用
var x = result[0];      // 现在安全
```

要不阻塞主线程，就把依赖交给下一个 Job，最后一刻才 `Complete()`。官方手册同时说明：读写限制同样适用于主线程。

## 常见报错逐条解读

下面的措辞是常见形式，具体类型名、字段名随你的代码而变，版本间可能略有差别（待核实）。

1. 调度时冲突（写后又读/写）
   `InvalidOperationException: The previously scheduled job A writes to the Unity.Collections.NativeArray ... A.Data. You are trying to schedule the new job B that reads from the same ... (via B.Data). To guarantee safety, you must include A as a dependency of the newly scheduled job.`
   含义：A 还没完成，B 就要读或写同一容器。修复：`B.Schedule(..., handleOfA)`，或先 `A.Complete()`。

2. 主线程访问被占用的容器
   `InvalidOperationException: The previously scheduled job A writes to ... You must call JobHandle.Complete() on the job A, before you can read from the ... safely.`
   含义：主线程在 Job 完成前读或写。修复：先 `Complete()`。

3. 容器未创建
   `InvalidOperationException: The Unity.Collections.NativeArray ... has not been assigned or constructed. All containers must be valid when scheduling a job.`
   含义：Job 字段里有没赋值或默认构造的容器。修复：给每个字段赋值；可选字段也用空容器。

4. 容器已释放
   `ObjectDisposedException: The Unity.Collections.NativeArray ... has been deallocated, it is not allowed to access it.`
   含义：释放后继续用，或 Job 还在跑时就 `Dispose`。修复：改为 `Dispose(JobHandle)` 或 `Complete` 之后再释放。

5. 并行范围越界
   `IndexOutOfRangeException: Index N is out of restricted IJobParallelFor range [a...b] in ReadWriteBuffer.`
   含义：`Execute(i)` 访问了别人的元素。修复：只访问 `i`，或确认安全后加 `[NativeDisableParallelForRestriction]`，或改用双缓冲。

6. 泄漏
   `A Native Collection has not been disposed, resulting in a memory leak.`
   后面常跟一句提示去打开完整堆栈。含义：分配了没释放。修复：把 `Preferences ▸ Jobs ▸ Leak Detection Level` 设为 `Enabled With Stack Trace` 定位分配位置，补上 `Dispose`。

7. TempJob 超期
   这是引擎原生层的控制台警告，开头形如 `JobTempAlloc has allocations that are more than 4 frames old`（较新版本措辞可能不同，详见 1.5 内存分配器与生命周期）。含义：`TempJob` 分配超过 4 帧才释放，改 `Persistent` 或缩短生命周期。

8. 写入只读容器
   含义：对 `[ReadOnly]` 字段或 `AsReadOnly()` 视图执行写入会抛异常（措辞待核实）。

## 检查开关

| 开关 | 作用 |
|---|---|
| `Edit ▸ Preferences ▸ Jobs ▸ Enable Jobs Debugger` | 控制 Job 安全系统的竞争检测（6000.5 文档确认在 Preferences 的 Jobs 页，默认每次重启编辑器后为开启）。关掉后读写冲突不再报错，仅用于确认检查本身的开销，不应长期关闭。较早版本里它在顶部 `Jobs` 菜单 |
| `Jobs ▸ Burst ▸ Enable Safety Checks`（Off / On / Force On） | Burst 编译代码里的安全检查，如容器越界与依赖检查（6000.7 手册确认）；与 NativeContainer 在调度时的读写冲突检查是两套东西。Off 会在重载编辑器后恢复为 On，Force On 连 `DisableSafetyChecks = true` 的代码也强制检查 |
| `Jobs ▸ Burst ▸ Enable Compilation` | 关闭 Burst，Job 回退到托管 Mono/IL 执行，便于调试（6000.7 手册确认） |
| `Edit ▸ Preferences ▸ Jobs ▸ Leak Detection Level` | 泄漏检测级别：Disabled / Enabled / Enabled With Stack Trace，见上一章（6000.5 文档确认） |
| `Edit ▸ Preferences ▸ Jobs ▸ Use Job Threads` | 关闭后所有 Job 在调度时立即在主线程运行，用于排除并行因素 |
| Collections Checks | 由 `ENABLE_UNITY_COLLECTIONS_CHECKS` 宏控制 `Native*` 容器的边界/释放检查；编辑器菜单位置待核实 |

## Unsafe 容器与指针如何绕过安全系统

- `Unsafe*` 容器没有 `AtomicSafetyHandle`；`NativeArrayUnsafeUtility.GetUnsafePtr` 取出的指针也完全脱离安全系统。
- 把指针存进 Job 字段需要 `[NativeDisableUnsafePtrRestriction]`。
- 风险：两个 Job 同时写同一块内存不会有任何报错；释放后继续使用会读到垃圾或崩溃；Release 构建与编辑器行为一致，因为本来就没有检查。
- 正确用法：用依赖排序保证读写不重叠，或把写区域按索引严格分段，并写注释说明不变量。

## 如何复现和缩小问题

- 用 `Run()` 替代 `Schedule()`：Job 在主线程同步执行，调用栈完整，断点能命中；若同步版本不再报错，问题多半出在调度与依赖。
- 暂时关闭 Burst：`Jobs ▸ Burst ▸ Enable Compilation` 取消勾选，Job 变成托管代码，能用普通调试器。如果关掉 Burst 后异常消失，怀疑别名（aliasing）或 Burst 特有行为。
- 缩小范围：把 Job 拆小，逐个 `Complete()`，看哪一个先报错。
- 打开泄漏完整堆栈，定位分配位置。

## 排错流程图

```
报错了
 |
 +-- 提示 "previously scheduled job ... writes/reads"?
 |      |-- 在调度 Job 时报 -> 缺依赖: 把前一个 JobHandle 传给后一个 Schedule
 |      '-- 在主线程读写时报 -> 先 handle.Complete()
 |
 +-- 提示 "has been deallocated"?
 |      '-- 检查 Dispose 位置: 改为 Dispose(handle) 或 Complete 后再 Dispose
 |
 +-- 提示 "has not been assigned or constructed"?
 |      '-- 给所有 Job 字段赋值, 检查 IsCreated
 |
 +-- 提示 "out of restricted IJobParallelFor range"?
 |      '-- 只访问 index; 确有分区约定再加 [NativeDisableParallelForRestriction]
 |
 +-- 无报错但结果偶发错误?
        |-- 是否用了 Unsafe 容器/指针/[NativeDisable...]? -> 逐项核对读写区域是否重叠
        |-- 用 Run() 复现 -> 同步正确则问题在并行
        '-- 关闭 Burst 复现 -> 排除编译差异
```

## 常见坑

- 忘记 `[ReadOnly]`：两个本可并行的读 Job 被串行化，或误报冲突。
- 在 `IJobParallelFor` 里对共享计数器 `count++`：这是真正的竞争条件，用 `NativeStream`、每线程缓冲或原子计数器（`UnsafeAtomicCounter32`）。
- 用 `[NativeDisableParallelForRestriction]` 消除报错但没真正理解冲突：错误只是被藏起来。
- 在 Job 运行期间对同一 `NativeArray` 调用 `ToArray()`、`CopyTo` 或读元素。
- 把 `NativeList` 的 `AsArray()` 视图当长期引用，扩容后失效。
- 以为 Release 构建同样有保护：发布版没有这些检查，错误会变成静默的数据损坏。

## 小结

- 安全系统靠每个容器内的 `AtomicSafetyHandle` 记录读写，调度时检查冲突。
- 规则：只读可并行，写必须排序；主线程访问也要遵守，用 `Complete()` 解锁。
- `IJobParallelFor` 默认只让你访问自己的 index，`[NativeDisableParallelForRestriction]` 要自担风险。
- `Unsafe*` 与指针绕过全部检查，要有自己的不变量。
- 报错信息通常直接告诉你缺哪个依赖，先读完整文本再动手。

## 自测题

1. 两个都标了 `[ReadOnly]` 的 Job 读同一个 `NativeArray`，会冲突吗？
   答：不会，可以并行。
2. 主线程在 Job 未完成时读取 Job 写的 `NativeArray`，会发生什么，怎么解？
   答：抛 `InvalidOperationException`；先 `JobHandle.Complete()`。
3. `[NativeDisableParallelForRestriction]` 关掉了什么，代价是什么？
   答：关掉"只能访问自己 index"的限制；两个 index 写同一元素时不会再报错，变成真正的竞争条件。
4. 为什么安全检查在 Release 构建里不会拯救你？
   答：它们只在编辑器和开发构建启用，发布版去除；所以必须在编辑器里修掉所有报错。
5. 一个 Job 结果偶发不对，又没有任何报错，先做什么？
   答：确认是否使用了 Unsafe/指针/Disable 属性；用 `Run()` 与关闭 Burst 做对照复现。
6. 把一个 `NativeArray` 赋给另一个变量，复制了什么？
   答：复制的是容器结构（数据指针加 `AtomicSafetyHandle`），不复制数据；所有拷贝指向同一块内存和同一条中心记录，各自的标志可以不同。
7. 一份拷贝 `Dispose` 之后，另一份拷贝为什么能知道自己已失效？
   答：`Release()` 把中心记录上的版本号加一，每份句柄访问时比较自己保存的版本号与记录里的当前版本号。
8. 次级版本号解决什么问题？
   答：可变长容器扩容会搬走数据，`AsArray()`、枚举器这类视图里的指针随之无效；视图用次级版本号做检查，改变大小的操作用 `CheckWriteAndBumpSecondaryVersion` 让它们作废。
