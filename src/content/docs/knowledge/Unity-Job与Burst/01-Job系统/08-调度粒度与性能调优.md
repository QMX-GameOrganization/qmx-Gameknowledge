> 适用版本：以 Unity 6000.x 的 Burst 1.8.x / Collections 2.x / Mathematics 1.3.x 为主线；本项目的 Unity 7000.0.0a8 中 Burst 2.0.0 与 Collections 6.7.0 是转发（shim）壳包，API 仍在 `Unity.Burst` / `Unity.Collections` 命名空间。编辑器菜单与偏好设置的位置随版本变动，下文逐项标注了核对来源与版本。

## 要点

- 并行 Job 的速度由三件事决定：每个工作项的活够不够大（调度开销能否摊薄）、负载是否均匀（尾部效应）、数据是否在内存里顺序访问（带宽与缓存）。
- `innerloopBatchCount` 没有通用最优值。Unity 手册给出的做法是：从 1 开始，逐步增大，直到性能收益可以忽略为止。
- 先测再改。Deep Profile、Safety Checks、Jobs Debugger、Leak Detection 都会扭曲计时，测性能前要按清单关掉。
- 本章不给具体的"调度一个 Job 要花多少微秒"数字：它随平台、Job 类型、依赖链长度而变，请在你的机器上用 Profiler 实测。

## 原理

### innerloopBatchCount 是什么

`IJobParallelFor` 的 `Schedule(arrayLength, innerloopBatchCount)` 中，第二个参数是批大小：一个批次包含多少个连续的 `Execute(index)`。Unity 手册（Parallel jobs 页）的描述：作业系统把工作分成批次分发给各核心；每个 CPU 核心对应一个原生 Job，原生 Job 处理分到的批次；先做完的原生 Job 会从别的 Job"偷"（steal）剩余批次，一次只偷对方剩余批次的一半，以保持缓存局部性。

```
arrayLength = 16, batch = 4  ->  4 个批次
 批次0 [0..3]  批次1 [4..7]  批次2 [8..11]  批次3 [12..15]
 worker A 取批次0，worker B 取批次1 ...；A 先做完 -> 偷 B 或 C 剩余批次的一半
```

| 批大小 | 好处 | 坏处 |
|---|---|---|
| 1 | 分配最均匀，最容易负载均衡 | 每个批次都有取任务的开销；工作项很小时开销占比高 |
| 32 / 64 一类的小常数 | 开销摊薄，仍有足够多的批次可偷 | 工作项耗时差异大时尾部不均 |
| 按数据块（如一个区块、一列） | 一次处理一段连续内存，缓存友好 | 批次数太少时核心吃不满 |

选择方法：

- 工作项很轻（几十条指令，如按体素算面掩码）：批大小取几十到几百，保证批次总数仍然显著多于核心数。
- 工作项很重（如一个区块采样几十万次噪声）：批大小 1，让作业系统均衡。
- 批次总数 = `ceil(arrayLength / batch)`，至少应是工作线程数的数倍，否则吃不满核心。可以用 `JobsUtility.JobWorkerCount`（当前可用工作线程数）和 `JobsUtility.JobWorkerMaximumCount` 查看。

### Job 粒度：区块、体素还是列

体素世界里有三种常见的工作项粒度：

| 粒度 | 工作项数量（16x16x128 区块为例） | 适合 | 风险 |
|---|---|---|---|
| 每区块一个 Job | 1 个 Job，内部循环 | 每块工作量大且独立（密度采样、整块网格化） | 区块数少于核心数时吃不满；一块很慢会拖尾 |
| 每体素一个工作项 | 32768 个 | 每体素算一点点（面掩码） | 工作项太小；除法/取模解下标有成本；需要大批大小 |
| 每列（XZ 一根）一个工作项 | 256 个 | 以列为单位有依赖（高度图、从上往下扫、光照传播） | 列内部串行；Y 方向放内层时访存连续 |

经验：让每个工作项的耗时远大于"取一个批次"的开销，同时让批次总数远大于核心数，两者之间取平衡。本项目的 `VoxelFaceVisibilityJob` 是"每体素"粒度，`VoxelMeshBuilder.BuildWithJobs(volume, voxelSize, batchSize = 64)` 默认批大小 64，这是一个起点而不是结论，值得用下面的方法做一次扫描实验（32 / 64 / 256 / 1024）。

调度本身也有成本：每次 `Schedule` 要写入作业队列、做安全系统的依赖登记。很多个很小的 Job 通常不如一个循环更大的 Job 划算；反过来一个超大的 `IJob` 又会独占一个核心。具体"多小算小"没有固定数字，请实测。

### 负载均衡与尾部效应

尾部效应（tail effect）：并行段的总时间由最慢的那个工作线程决定。常见成因：

- 批次太少或太粗，最后一个大批次只能由一个线程做完，其它线程空等。
- 工作项耗时差异大（比如整块是空气与整块是复杂地形），静态等分失衡。
- 并行段之后紧跟着单线程段（例如前缀和或主线程合并），相当于阿姆达尔定律的串行部分。

对策：批次更细、让作业系统偷任务；把大块工作拆成更多独立 Job 让它们交错调度；用 Profiler 的 Timeline 看最后一段时间里是不是只剩一个 worker 在跑。

### memory-bound 与 compute-bound

- compute-bound：瓶颈在算术。例如多层噪声叠加的密度函数，每个采样点要算很多浮点运算。优化手段：减少运算、SIMD（`Unity.Mathematics` 的向量类型）、Burst 的浮点选项。
- memory-bound：瓶颈在读写内存。例如"每体素读 6 个邻居，写 1 字节"，运算极少，时间花在把数据搬进缓存。这种 Job 加线程数收益会很快饱和，因为内存带宽是共享的。优化手段：缩小数据类型（`byte` 而不是 `int`）、提高访问连续性、合并相邻 Job 减少遍历次数。

快速判断：把线程数调高，如果耗时基本不降，多半是 memory-bound；如果近似线性下降，多半是 compute-bound。

### 访问局部性：x + W*(y + H*z) 的遍历顺序

本项目的体素线性化是 `index = x + SizeX * (y + SizeY * z)`（见 `VoxelChunk.Get`）。x 变化 1，地址变 1 字节；y 变化 1，地址变 `SizeX`（16）字节；z 变化 1，地址变 `SizeX * SizeY` 字节。

```
内存布局：x 最快，其次 y，z 最慢
  地址 = x + 16*(y + H*z)
  遍历顺序 z(外) -> y -> x(内)   顺序访问，缓存行（常见 64B）一次带进来 4 行 x
  遍历顺序 x(外) -> z -> y(内)   y 步长 16B，尚可
  遍历顺序 x(外) -> y -> z(内)   z 步长 16*H B，每次访问几乎都换一个缓存行
```

原则：让最内层循环对应地址变化最小的那个维度。注意有时"访问顺序"和"业务顺序"冲突：`VoxelChunk.Fill` 的注释写明为了让二维噪声的列缓存命中，故意把 Y 放最内层（x、z、y 的循环顺序），这是用写入的不连续换取采样的缓存命中，是有意取舍；`ChunkDensitySampler.Fill` 逐 cell 填充的最内层循环是 z（步长 `sx*sy`），这对写入的局部性并不友好。这些是否构成实际瓶颈，需要用 Profiler 在真实参数下确认，不要凭直觉改。

`VoxelFaceVisibilityJob` 的 `index % Width`、`index / Width`、`yz % Height`、`yz / Height` 每个工作项做 4 次整数除法/取模，在 memory-bound 的轻量 Job 里这些整数运算可能被内存延迟掩盖，也可能不被掩盖；想优化时可以改成"每列一个工作项"，在 Job 内用累加代替除法。同样是待测量的假设。

### false sharing 与输出分块

伪共享（false sharing）：两个线程写同一个缓存行里的不同字节。缓存行常见为 64 字节，`JobsUtility.CacheLineSize` 可读到引擎认为的值。每个核的缓存要为这条线来回抢所有权，性能会掉得很厉害，而代码逻辑完全正确，不会有任何报错。

- 每 index 写不同 `byte` 的 `IJobParallelFor`：批大小太小时，相邻批次的边界可能落在同一缓存行上。批大小取 64 的倍数，能让每个批次覆盖整数个缓存行（对 `byte` 数组而言）；但批次起点是否正好落在缓存行边界，还取决于数组起始地址，`NativeArray` 的起始地址不保证 64 字节对齐，所以这只是降低相邻批次共享缓存行的概率，不是保证。
- 每线程累加器数组：槽间距至少一个缓存行（见上一章的 `Stride = 16` 示例）。
- 输出分块对齐：把输出按"每批一块、块大小是缓存行的整数倍"划分。

### 数据布局：AoS 与 SoA

- AoS（Array of Structs）：`struct Voxel { byte id; byte light; byte meta; }` 的数组。一次读一个体素的全部字段，字段都用到时很划算。
- SoA（Struct of Arrays）：`NativeArray<byte> Id; NativeArray<byte> Light; ...`。只遍历某一个字段时（例如只看"是否实心"），读入缓存的全是有用数据，也更容易被 Burst 向量化。

本项目当前只有 `byte[] solid` 一个字段，天然是 SoA 形态。将来加光照、群系等字段时，倾向"一个字段一个数组"，面掩码计算只碰 `Solid` 数组。

### 避免在 Complete 上阻塞主线程

`handle.Complete()` 会让主线程等待 Job 完成。本项目 `BuildWithJobs` 在 `Schedule` 后立刻 `Complete()`，并行只发生在 Job 内部，主线程这段时间是空等的。更好的模式：

- 本帧 Schedule，下一帧或之后再 Complete，中间主线程做别的事。
- 用 `JobHandle.IsCompleted` 轮询，完成了才 `Complete()`（此时不会真的阻塞）。
- 用依赖链串联 Job，只在最后一个需要读结果的地方 Complete 一次。

## 用 Profiler 看清发生了什么

### Timeline 视图

在 Profiler 的 CPU Usage 模块里切到 Timeline 视图，可以按线程横向看时间线：

- 主线程那一行：看 Job 调度、`Complete` 等待占了多长。主线程在等 Job 时会出现一段等待类标记（Unity 论坛和 Issue Tracker 的帖子里能见到 `WaitForJobGroup`、`WaitForJobGroupID` 这类名字，具体标记名随版本变化，待核实）。
- 工作线程（worker）那几行：看你的 Job 是否真的铺满了多个核心；中间有大段空白说明并行度不足或批次太粗；最后只剩一两行有活说明有尾部效应。
- Job 之间的依赖等待：一个 Job 在等另一个时，它的 worker 行上看不到它，要回到依赖链上找。

### ProfilerMarker 自定义标记

`Unity.Profiling.ProfilerMarker` 是最高效的自定义标记（API 文档已核对）：构造时给名字，`Begin()` / `End()` 或 `using (marker.Auto())`。文档明确说明可以用在 Job 化代码中，并且 `Begin` / `End` 带 `ConditionalAttribute`，在非 Development 构建里被编译掉，零开销。与 `Profiler.BeginSample` 相比，`ProfilerMarker` 只传整数标识而不是整条字符串，数据量更小。

```csharp
using Unity.Profiling;

static readonly ProfilerMarker s_BuildFaces = new ProfilerMarker("VoxelMesh.BuildFaces");

void Build()
{
    using (s_BuildFaces.Auto())
    {
        // 调度、Complete、拷贝结果
    }
}
```

在 Burst Job 内部使用 `ProfilerMarker` 时，标记会显示在执行该 Job 的 worker 线程行上；是否有额外限制（如 static 字段的初始化方式）请以 Burst 手册为准（待核实）。

### Deep Profile 的失真

Deep Profile 会给每一次托管方法调用插桩，开销随调用次数线性增长，会让小函数多的代码显得特别慢，改变热点排序。它也不能对 Burst 编译后的代码插桩。用它定位"哪些托管调用多"可以，用它比较优化前后的耗时不行。比较耗时应当用 `ProfilerMarker` 加普通 Profiler 或 Stopwatch。

### Profile Analyzer

Profile Analyzer（包名 `com.unity.performance-profile-analyzer`，待核实当前包名）可以把多帧 Profiler 数据汇总，给出中位数、最大值、分布，并对比两次采集。适合做"优化前 vs 优化后"的对比，比肉眼看单帧可靠。

## 测性能前要先关掉什么

下表中的开关位置按所述文档版本核对；你的 Unity 7000.0.0a8 菜单位置未逐项实测（待核实）。

| 开关 | 位置（文档版本） | 对计时的影响 | 测性能前 |
|---|---|---|---|
| Burst Enable Compilation | Jobs > Burst > Enable Compilation（6000.7 手册） | 关闭后 `[BurstCompile]` 的 Job 退回 Mono 执行，通常慢得多，差距随代码而定，请自己测 | 保持开启 |
| Burst Enable Safety Checks | Jobs > Burst > Enable Safety Checks：Off / On / Force On（6000.7 手册） | On 时 Burst 生成的代码带容器越界和依赖检查，更慢。手册说明 Off 适合"更真实的编辑器内性能剖析"，且重载编辑器后会自动恢复为 On | 设为 Off，或直接测构建版 |
| Synchronous Compilation | Jobs > Burst > Synchronous Compilation（6000.7 手册） | 关闭时 Burst 在后台异步编译，编译完成前 Job 会先用 Mono 版本运行，首批计时是错的 | 测量前确保已编译完成（预热） |
| Native Debug Mode Compilation | Jobs > Burst > Native Debug Mode Compilation（6000.7 手册） | 关闭 Burst 编译时的所有优化，便于原生调试器调试 | 保持关闭 |
| Use Job Threads | Edit > Preferences > Jobs（6000.5 文档） | 关闭则所有 Job 在调度时立即在主线程运行（与把 `JobsUtility.JobWorkerCount` 设为 0 是否等价，官方没写，待核实） | 保持开启 |
| Enable Jobs Debugger | Edit > Preferences > Jobs（6000.5 文档） | 提供 Job 竞争检测，有开销；文档建议想监测性能时关闭它 | 关闭 |
| Leak Detection Level | Edit > Preferences > Jobs（6000.5 文档） | Disabled / Enabled / Enabled With Stack Trace 三档，最后一档会给分配增加开销 | 设为 Disabled 或 Enabled，别用 With Stack Trace |
| Deep Profile | Profiler 工具栏 | 见上节 | 关闭 |
| Editor 本身 | - | Scene/Game 视图、Inspector、Console 日志刷新都占主线程 | 关闭无关窗口，减少 `Debug.Log` |

运行时脚本里也有对应的属性：`JobsUtility.JobCompilerEnabled`（Job 跑 Mono 还是 Burst）、`JobsUtility.JobDebuggerEnabled`（运行时是否启用 Job 调试器）、`JobsUtility.JobWorkerCount`。较早的 Unity 版本里这些开关在顶部的 Jobs 菜单中，现在的位置见上表。

## 正确的基准方法

- 预热：第一次调用包含 Burst JIT 编译、缓存冷启动、分配器首次扩容。先丢弃若干次。
- 多次取中位数：取 N 次（如 20 次）的中位数和最大值，而不是平均数或单次最小值。
- 控制变量：一次只改一个参数（批大小、粒度、布局）。
- 环境：编辑器里的数字只适合比较相对变化。绝对数值要在 Development 构建或 Release 构建里测；Release 构建没有安全检查，也没有 Profiler 开销。
- 计时工具：简单场景用 `System.Diagnostics.Stopwatch` 包住 `Schedule` 到 `Complete`；需要自动化与统计时用 Unity Performance Testing 包（`com.unity.test-framework.performance`，待核实包名与当前版本），典型写法是在带 `[Performance]` 的测试里用 `Measure.Method(...).WarmupCount(n).MeasurementCount(m).Run()`（API 形态待核实）。
- 区分墙钟时间与 CPU 时间：多线程下总 CPU 时间可能上升而墙钟时间下降。本项目 `ChunkGenerationPipeline` 的 `SampleMilliseconds` / `MeshMilliseconds` 是所有后台线程耗时之和（CPU 时间），`ElapsedMilliseconds` 才是墙钟时间，对比时不要混用。

```csharp
// 最小基准骨架：预热 + 多次测量 + 中位数
static double MedianMs(System.Action run, int warmup = 5, int samples = 21)
{
    for (int i = 0; i < warmup; i++) run();
    var times = new double[samples];
    var sw = new System.Diagnostics.Stopwatch();
    for (int i = 0; i < samples; i++)
    {
        sw.Restart();
        run();                                   // 内部包含 Schedule 与 Complete
        sw.Stop();
        times[i] = sw.Elapsed.TotalMilliseconds;
    }
    System.Array.Sort(times);
    return times[samples / 2];
}
```

## 调优检查表

1. 已关闭 Deep Profile、Jobs Debugger、Leak Detection 堆栈、Burst Safety Checks，并预热过 Burst 编译。
2. 先用 Timeline 确认瓶颈：是主线程 `Complete` 等待、并行度不足、还是单个 Job 本身慢。
3. 判断 memory-bound 还是 compute-bound（改线程数观察缩放）。
4. 调批大小：从 1 开始往上扫，直到收益可忽略。
5. 检查批次总数是否显著多于工作线程数。
6. 检查最内层循环是否对应地址变化最小的维度。
7. 检查并行输出的相邻写入是否会落在同一缓存行。
8. 能否缩小数据类型、合并相邻遍历、改为 SoA。
9. 能否把 `Complete` 推迟，或用依赖链避免提前阻塞。
10. 每次改动单独测量，记录中位数，保留对照版本。

## 常见坑

- 在编辑器里用开着 Safety Checks 的 Burst 代码得出"Burst 没有想象中快"的结论。
- 首次运行的数字被 Burst 异步编译污染。
- 用平均值：一次 GC 或编辑器卡顿就把平均数带歪，用中位数。
- 只看总耗时不看 Timeline，错过空闲 worker 和尾部效应。
- 把 CPU 时间之和当成墙钟时间。

## 小结

- 粒度选择就是在"调度开销"和"负载均衡"之间找平衡，批大小靠扫描实验确定。
- 轻量 Job 通常 memory-bound，重点是访问连续、数据小、遍历次数少。
- 先关掉会扭曲计时的开关，预热，取中位数，再下结论。

## 自测题

1. Unity 手册建议怎么确定 `innerloopBatchCount`？
   答：从 1 开始，逐步增大，直到性能收益可以忽略。
2. 为什么批大小为 1 对重活合适，对轻活不合适？
   答：每个批次有取任务的开销；重活里这点开销可忽略，轻活里占比会很高。
3. `index = x + W*(y + H*z)` 下，最内层应遍历哪个维度？
   答：x，它的地址步长最小。
4. 什么是伪共享，怎么避免？
   答：多个线程写同一缓存行的不同字节；让每线程的写入区域至少隔开一个缓存行（`JobsUtility.CacheLineSize`），批大小取缓存行的整数倍。
5. 为什么在编辑器里刚进入播放模式时的 Job 耗时可能偏大？
   答：Burst 可能还在异步编译（回退到 Mono），且缓存、分配器处于冷状态，需要预热。
