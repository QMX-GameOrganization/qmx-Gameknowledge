> 适用版本：以 Unity 6000.x 的 Collections 2.x 为主线；Unity 6.4 起 Collections 作为核心包随编辑器分发；本项目的 Unity 7000.0.0a8 中 Collections 6.7.0 是转发壳包，API 仍在 `Unity.Collections` 命名空间。菜单名称随编辑器版本有变化，处已标"待核实"。

## 要点

- Native 内存不归 GC 管，谁分配谁释放；漏了就是内存泄漏，编辑器会报警告。
- 三个常用分配器：`Temp`（本帧/本 Job 内，不能跨 Job 传递）、`TempJob`（Job 期间，须在 4 帧内释放）、`Persistent`（想留多久留多久，必须手动释放）。
- 释放写法首选 `using` 或 `try/finally`（同步场景）与 `Dispose(JobHandle)`（异步场景，在 Job 之后释放）。
- 泄漏检测在编辑器偏好设置里开，打开"完整堆栈"后能看到分配位置；退出 Play Mode 后残留会在控制台报告。
- 长生命周期缓冲应池化复用，而不是每次 `new`/`Dispose`；复用时要决定是否清零。
- `NativeArray` 长度是 `int`，且总字节数有 2 GiB 级上限，更大的数据要分块。

## 为什么要关心分配器

托管对象由 GC 回收，Native 容器没有终结器兜底。一个 `NativeArray` 变量离开作用域后内存不会释放，只会泄漏。分配器决定三件事：分配速度、允许的生命周期、能否传给 Job。

| 分配器 | 速度 | 生命周期 | 能传给 Job | 要不要手动释放 |
|---|---|---|---|---|
| `Allocator.Temp` | 最快 | 帧内（主线程）或 Job 结束前（Job 内） | 否 | 不需要，调用 `Dispose` 无实际效果 |
| `Allocator.TempJob` | 较快 | 须在创建后 4 帧内释放 | 是 | 必须 |
| `Allocator.Persistent` | 最慢 | 不限 | 是 | 必须 |

数据来自 Collections 手册的 Allocator overview 页：Temp 每帧由主线程创建并整体丢弃，每个 Job 也为每个线程创建 Temp 分配器并在 Job 结束时整体丢弃；Temp 最小对齐 64 字节，TempJob 与 Persistent 为 16 字节。

## 各分配器细节

### Allocator.Temp

- 主线程里分配的 Temp 容器不能放进 Job 的字段（官方手册：不能用 Temp 把分配传给存放在 Job 成员字段里的 `NativeContainer`）。
- 在 Job 内部分配 Temp 容器是允许的，Job 结束时整体回收。
- 手册说明对 Temp 调用释放"什么也不做"。但对 `Native*` 容器，`Dispose` 还负责释放安全检查句柄，所以习惯上仍写 `using`/`Dispose`，保持与其它分配器一致（这是建议而非手册硬性要求）。

### Allocator.TempJob

超过 4 帧未释放，`Native-` 容器的释放安全检查会抛异常；`Unsafe-` 容器同样必须在 4 帧内释放，但没有检查，不会提醒你。控制台里常见的是引擎原生层的警告，开头为 "JobTempAlloc has allocations that are more than 4 frames old"（来自 Unity 论坛与 Issue Tracker 的帖子，较新版本措辞改为 "more than the maximum lifespan of 4 frames"，随版本略有差异）；排查时可给编辑器或 Player 加命令行参数 `-diag-job-temp-memory-leak-validation` 打印泄漏分配的调用栈（来自论坛讨论，待核实）。

### Allocator.Persistent

手册原话：Persistent 的分配可以无限期存在，安全检查无法发现它是否超出预期寿命，所以必须自己释放。它基本等于 `malloc`，分配慢，不要放在逐帧热路径里。

### 其它枚举值

| 值 | 含义 |
|---|---|
| `Allocator.Invalid` | 无效分配器，默认值；`NativeList.AsDeferredJobArray()` 返回的数组用它标记"列表模式"（来自 Collections 1.2.x 更新日志） |
| `Allocator.None` | 不拥有内存，用于包装别人分配的内存（如 `NativeArrayUnsafeUtility.ConvertExistingDataToNativeArray`），`Dispose` 不会释放 |
| `Allocator.AudioKernel` | 音频内核专用（待核实具体用途与可用范围） |
| 用户自定义分配器 | `AllocatorManager` 注册后得到的句柄，隐式转换为 `Allocator` |

## Collections 2.x 的分配器体系

Collections 把分配器抽象成 `AllocatorManager`，允许注册自定义分配器；`Allocator` 枚举可以隐式承载这些句柄。手册另列出几个相关页面：别名分配器（Aliasing allocators）、可回绕分配器（Rewindable allocators）、自定义分配器（Define a custom allocator）。类型转发列表里能确认存在的相关类型：`AllocatorManager`、`AllocatorHelper<>`、`RewindableAllocator`、`DoubleRewindableAllocators`、`UnsafeScratchAllocator`。

`RewindableAllocator` 是类似线性分配器的自定义分配器：快、线程安全，预先分配成块，按需从块里划出一段给调用者。适合"每帧/每批次产生一堆临时容器，批次结束一次性丢掉"。它的完整行为见下面的"RewindableAllocator"一节，旧稿里"不能单独释放，只能整体 `Rewind()`"的说法不准确，已在那一节纠正。

自定义分配器与别名的细节分别见下面三小节：别名与 `Reinterpret<T,U>()`、`RewindableAllocator`、自定义分配器的注册与销毁。容器会记住自己的分配器，释放时用同一个分配器。

### 别名（alias）与 Reinterpret&lt;T,U&gt;()

出处：Collections 2.5 手册 Aliasing allocators 页。

别名是这样一种集合：它没有自己的分配，而是整体或部分共享另一个集合的分配。例如可以建一个不分配内存、直接使用某个 `NativeList` 内存的 `UnsafeList`，通过它写入会影响原 `NativeList` 的内容，反之亦然。规则：

- 别名不需要释放，对别名调用 `Dispose` 什么也不做。
- 原件一旦被释放，别名就不能再用（原件释放把共享的内存也释放了）。
- 用途有三类：不拷贝地把数据换成另一种集合类型（如让 `UnsafeList` 别名一个 `NativeArray`）；不拷贝地取子区间；数组重解释。
- `Unsafe-` 集合可以别名 `Native-` 集合，但这会绕开安全检查：比如 `UnsafeList` 别名了 `NativeList`，同时调度一个访问前者的 Job 和一个访问后者的 Job，安全检查抓不到这种冲突。

```csharp
// 官方示例的精简：别名与原件
NativeList<int> nums = new NativeList<int>(10, Allocator.TempJob);
nums.Length = 5;

NativeArray<int> aliasedNums = nums.AsArray(); // 别名：与列表共享内存
aliasedNums[0] = 99;                           // 同时改了列表的第一个元素

nums.Dispose();                                // 只需要释放原件
aliasedNums[0] = 99;                           // 抛 ObjectDisposedException
```

数组重解释（reinterpretation）是一种特殊的别名：同一块字节按另一种元素类型读写。官方例子：`NativeArray<int>` 重解释为 `NativeArray<short>`，每个 `int` 对应两个 `short`，长度变为原来的两倍（10 个 `int` 变成 20 个 `short`）；写 `shorts[0]=1`、`shorts[1]=1` 后 `ints[0]` 等于 65537。API 是 `NativeArrayExtensions.Reinterpret<T, U>(this NativeArray<T> array)`，两个类型都要 `unmanaged`，容量不能被 `sizeof(U)` 整除时抛 `InvalidOperationException`（API 页）。与 1.4 里 `array.Reinterpret<U>(expectedTypeSize)` 的成员方法写法是两种入口，语义相同。

```csharp
NativeArray<int> ints = new NativeArray<int>(10, Allocator.Temp);
NativeArray<short> shorts = ints.Reinterpret<int, short>(); // 长度 20
shorts[0] = 1; shorts[1] = 1;
int val = ints[0];   // 65537
ints.Dispose();      // 只释放原件
// shorts[0] = 1;    // 之后再用会抛 ObjectDisposedException
```

对应本项目：用 `byte` 存体素类型、要一次按 `uint` 批量比较或清零时，别名比拷贝省一次内存。注意官方只明确说了一点：用 `Unsafe*` 去别名 `Native*` 会绕开安全检查，别名与原件之间的读写冲突不会被抓到，所以别名最好仍用 `Native*` 视图。

### RewindableAllocator

出处：Collections 2.5 手册 Rewindable allocator overview 页。

行为要点：

- 它是一种自定义分配器，工作方式类似线性分配器，快且线程安全；预先分配内存块，请求时从块里划一段，最小对齐 64 字节。
- 现有块用完就再分配一块：新块大小先翻倍，直到达到最大块大小，之后改为在前一块大小上加最大块大小，线性增长。
- 可以整体 `Rewind()`，一次性释放所有分配。`Rewind` 时它保留之前用过的块以提高性能，释放其余的块。
- 纠错：单个 `Free` / `Dispose` 默认是空操作（no-op），而不是"不能单独释放"。只有创建时打开 enable block free 标志，它才会在释放某个块的最后一个分配时回绕（rewind）那一块。
- `Rewind` 会使其子分配器失效并注销，并使所有子安全句柄失效；对 `Native-` 容器，之后再访问，释放安全检查会抛 `ObjectDisposedException`（需要检查开启的构建）。

创建：需要为分配器本身分配内存、在全局分配器表登记、预分配第一块。官方建议用封装 `AllocatorHelper<T>`，初始化的签名是 `Initialize(int initialBlockSize, bool enableBlockFree = false)`（官方示例里 `enableBlockFree` 默认 false），旧稿的"待核实"据此去掉。

```csharp
// 取自官方示例的精简；同样是教学用，未在 Unity 内编译
AllocatorHelper<RewindableAllocator> rwdAllocatorHelper =
    new AllocatorHelper<RewindableAllocator>(Allocator.Persistent); // 参数是"后台分配器"
ref RewindableAllocator rwd = ref rwdAllocatorHelper.Allocator;
rwd.Initialize(128 * 1024, false);        // 初始块大小（字节），是否开启块级释放

// Native 数组：必须经 CollectionHelper 创建，无需单个 Dispose
NativeArray<int> arr = CollectionHelper.CreateNativeArray<int, RewindableAllocator>(100, ref rwd);

// NativeList：用分配器句柄构造
NativeList<int> list = new NativeList<int>(rwd.Handle);

// Unsafe 容器或原始内存：用 AllocatorManager.Allocate
// unsafe { byte* p = (byte*)AllocatorManager.Allocate(ref rwd, sizeof(byte), sizeof(byte), 10); }

rwd.Rewind();                // 整体回收；之后 arr、list 都不能再用
rwd.Dispose();               // 释放分配器的所有内存块
rwdAllocatorHelper.Dispose();// 注销分配器并释放存放它自己的内存
```

官方明确要求：从可回绕分配器创建 `NativeArray` 必须用 `CollectionHelper.CreateNativeArray`（`NativeList` 用句柄构造即可）；并说明用它创建 `Native-` 容器时，容器的安全句柄会加入分配器的子安全句柄列表，这正是 `Rewind` 之后旧容器访问会抛 `ObjectDisposedException` 的机制。直接 `new NativeArray<T>(n, rwd.Handle)` 是否可行官方页面没写，待核实。

对应本项目：每帧建网格要用到的一堆 `NativeList`、临时 `NativeArray`，可以全部从一个 `RewindableAllocator` 分配，帧末（或该批 Job 全部 `Complete` 之后）一次 `Rewind()`。注意 `Rewind` 之前必须保证没有 Job 还在用这些容器，否则等于提前释放（见"常见坑"）。该机制在 Unity 6.x / 7000 里是否有变化，我没有核实（待核实）。

### 自定义分配器的注册与销毁（概览）

出处：Collections 2.5 手册 Custom allocator overview 页。

自定义分配器是一个结构，满足两条：

- 内含一个 `AllocatorManager.AllocatorHandle` 字段。句柄含 `Version`（2 字节无符号，只有低 15 位有效）、`Index`（登记时得到的全局分配器表下标），以及登记子安全句柄、子分配器、回绕（使所有子分配器与子安全句柄失效并递增版本）的方法。
- 实现 `AllocatorManager.IAllocator`：`Function`（返回 `TryFunction` 委托，分配器函数，可分配、释放、重新分配）、`Try(ref Block)`（分配器函数调用的方法）、`Handle`、`ToAllocator`（把句柄下标转成 `Allocator` 枚举）、`IsCustomAllocator`（句柄 `Index` 大于等于 `AllocatorManager.FirstUserIndex` 即为自定义）、`IsAutoDispose`（释放单个分配是否是空操作；默认实现返回 false）。因为 `IAllocator` 继承 `IDisposable`，还要实现 `Dispose`。

登记：实例化之后必须登记到 `AllocatorManager` 的全局分配器表。表里存：分配器实例的指针、分配器函数指针、当前官方版本号（2 字节的低 15 位）、用该分配器创建的 Native 容器的子安全句柄列表、子分配器列表，以及一个标志位表明是否能释放单个分配。官方示例里分配器函数是静态方法，标 `[BurstCompile(CompileSynchronously = true)]` 和 `[MonoPInvokeCallback(typeof(AllocatorManager.TryFunction))]`，内部把传入指针转回分配器结构再调用 `Try`。官方示例的 `Try` 用 `Allocator.Persistent` 分配，并在成功后用指定值初始化内存、增加计数；释放时减计数；`Dispose` 里断言计数为 0 来检查泄漏。

具体怎样把自定义分配器注册进表（官方在另一页 "Use a custom allocator" 讲，我没有读到）待核实；`RewindableAllocator` 的做法是用 `AllocatorHelper<T>` 一步完成"分配存放分配器的内存、登记、销毁时注销并释放"，普通场景用它即可。销毁顺序：先释放分配器自己的内存块（`RwdAllocator.Dispose()`），再 `AllocatorHelper.Dispose()` 注销并释放分配器本体。

该概览的内容面向进阶需求，体素项目起步阶段只用内置的 `Temp` / `TempJob` / `Persistent` 即可。

## Dispose 的几种写法

### using / try-finally

同步场景最稳妥：

```csharp
using (var results = new NativeArray<int>(n, Allocator.TempJob))
{
    new MyJob { Results = results }.Schedule(n, 64).Complete();
    // 读取 results ...
} // 出作用域自动 Dispose
```

`using` 要求 `Complete()` 在作用域内完成，否则 Job 还在跑时内存就被释放，会触发安全异常。

### Dispose(JobHandle)

Job 异步运行、不想阻塞主线程时，把释放也变成一个依赖 Job：

```csharp
var nums = new NativeArray<int>(10, Allocator.TempJob);
JobHandle h = new ExampleJob { Nums = nums }.Schedule();
h = nums.Dispose(h);   // 返回"释放 Job"的句柄，在 ExampleJob 之后执行
// 之后仍需有人对 h 调用 Complete 或把它作为后续依赖
```

这是 Collections 手册给出的标准写法。

### [DeallocateOnJobCompletion]

给 Job 字段加该属性，Job 完成后自动释放容器。我在 Unity 6.6 的脚本 API 页面确认它仍存在、未标记弃用，描述为"Job 完成时自动释放原生容器"；字段所属容器类型须带 `NativeContainerSupportsDeallocateOnJobCompletion`，实际主要是 `NativeArray`。新代码更推荐 `Dispose(JobHandle)`，适用范围更广，意图也更显式。

```csharp
struct SumJob : IJob
{
    [ReadOnly, DeallocateOnJobCompletion] public NativeArray<int> Input;
    public void Execute() { /* ... */ }
}
```

### 选择建议

| 场景 | 推荐 |
|---|---|
| 同帧调度并 Complete | `using` |
| 跨帧、不阻塞主线程 | `Dispose(JobHandle)` |
| 只想少写一行、容器是 NativeArray | `[DeallocateOnJobCompletion]` |
| 池化的 Persistent 缓冲 | 不释放，由池在退出时统一释放 |

## Job 内部创建临时容器

Job 里可以用 `Allocator.Temp` 创建容器做草稿，Job 结束时随线程的 Temp 分配器整体回收：

```csharp
[BurstCompile]
struct MeshColumnJob : IJobParallelFor
{
    public int SizeY;
    public void Execute(int column)
    {
        var scratch = new NativeList<int>(64, Allocator.Temp); // Job 内的 Temp
        for (int y = 0; y < SizeY; y++) { /* 收集可见面 ... */ }
        scratch.Dispose(); // 对 Temp 不是必须，但保持习惯，并释放安全句柄
    }
}
```

不要把 Job 内创建的 Temp 容器通过字段带出 Job，也不要把主线程的 Temp 容器放进 Job 字段。

## 泄漏检测

典型警告：`A Native Collection has not been disposed, resulting in a memory leak. Enable Full StackTraces to get more details.`（我在 Unity Discussions 的讨论串中见到该文本）。

开关位置：

- 较新的版本位于 `Edit ▸ Preferences ▸ Jobs ▸ Leak Detection Level`（6000.5 手册的 Preferences ▸ Jobs 页面确认，见 1.6、1.8；在 7000.0.0a8 里的位置待核实）。
- 更早的版本是顶层 `Jobs ▸ Leak Detection` 菜单，并有一个 `Enable Full Stack Traces` 选项（待核实）。

建议：定位泄漏时临时把级别设为带完整堆栈的选项，排查完再调回，因为捕获堆栈有额外开销。

泄漏检测对 `Native*` 容器有效；`Unsafe*` 容器没有句柄，手册说明它们不被安全检查跟踪，泄漏只能靠自己的纪律与内存分析器发现。

## Domain Reload 与退出 Play Mode

- 退出 Play Mode 时，静态字段里的 `Persistent` 容器如果没有被 `OnDestroy`、`OnDisable` 或 `[RuntimeInitializeOnLoadMethod]` 配套逻辑释放，会在重新加载域时留下泄漏警告。
- 关闭 Domain Reload（Enter Play Mode Options）时，静态状态不会重置，上一轮 Play 创建的静态 `NativeArray` 可能仍"活着"，下一轮再分配就会叠加，需要手动在进入时清理。
- 约定：谁创建谁释放，成对写在 `OnEnable/OnDisable` 或 `Awake/OnDestroy`；静态池提供显式的 `Shutdown()`。

```csharp
sealed class ChunkBufferPool : System.IDisposable
{
    NativeArray<byte> buffer;
    public ChunkBufferPool(int bytes) =>
        buffer = new NativeArray<byte>(bytes, Allocator.Persistent, NativeArrayOptions.UninitializedMemory);
    public void Dispose() { if (buffer.IsCreated) buffer.Dispose(); }
}
```

## 对象池与复用 Persistent 缓冲

频繁 `new NativeArray(..., Persistent)` 又 `Dispose` 有两个代价：分配本身慢（接近 `malloc`），以及构造时的清零。池化模式：

```csharp
sealed class NativeBytePool : System.IDisposable
{
    readonly Stack<NativeArray<byte>> free = new();
    readonly int bytesPerBuffer;
    public NativeBytePool(int bytesPerBuffer, int prewarm)
    {
        this.bytesPerBuffer = bytesPerBuffer;
        for (int i = 0; i < prewarm; i++) free.Push(Create());
    }
    NativeArray<byte> Create() => new NativeArray<byte>(
        bytesPerBuffer, Allocator.Persistent, NativeArrayOptions.UninitializedMemory);

    public NativeArray<byte> Rent() => free.Count > 0 ? free.Pop() : Create();
    public void Return(NativeArray<byte> b) => free.Push(b);
    public void Dispose() { while (free.Count > 0) free.Pop().Dispose(); }
}
```

要点：

- 预分配：启动时按预期并发量先造好，避免运行时抖动。
- 容量策略：每个缓冲固定大小（如一个区块），借出多于预热数量时再增长，设置上限防止无限增长。
- 清零 vs 不清零：`UninitializedMemory` 快，但借出的缓冲带着上一轮的旧数据。如果后续 Job 会写满整个缓冲（如密度采样覆盖每个体素），可以不清零；如果依赖初始为 0，则必须 `UnsafeUtility.MemClear` 或在 Job 里显式写。
- 池里的缓冲被 Job 使用时不要归还；归还应发生在对应 `JobHandle` 完成之后。
- 池本身要在退出时 `Dispose`，否则触发泄漏警告。

## 对齐与大小

Native 内存的对齐会影响 SIMD 加载和跨平台行为。`UnsafeUtility.SizeOf<T>()` 返回类型大小，`UnsafeUtility.AlignOf<T>()` 返回对齐要求。

```csharp
using Unity.Collections.LowLevel.Unsafe;
int size  = UnsafeUtility.SizeOf<Unity.Mathematics.float4>();   // 16
int align = UnsafeUtility.AlignOf<Unity.Mathematics.float4>();  // 通常 4 或 16，以实际为准
```

分配器给出的最小对齐：Temp 64 字节，TempJob 与 Persistent 16 字节（手册）。结构体字段排布也有填充，`SizeOf` 比字段字节和更大是正常的。需要更严格对齐时，用 `UnsafeUtility.Malloc(size, alignment, allocator)` 自己分配并 `Free`。

## NativeArray 的大小上限

`NativeArray<T>` 的长度是 `int`，所以元素数不超过约 21.4 亿；另外构造时会检查总字节数（`Length * sizeof(T)`）是否超过 `int.MaxValue`，超了抛异常（该检查的存在来自我对源码的记忆，待核实）。这意味着：

- `byte` 体素最多约 2 GiB 一块；`int` 或 `float` 只能约 5.4 亿个元素。
- 更大的数据要分块：多个 `NativeArray` 或一个 `UnsafeList<T>`/指针（`long` 索引），并自行管理索引。

## 对应本项目：流式区块与内存估算

下面是估算，不是实测。

- 区块：16×16×384 = 98 304 字节（每体素 1 字节）。
- 总世界 6.3 亿体素：例如 1280×1280×384 = 629 145 600 体素，即 80×80 = 6 400 个区块，约 600 MiB（629 145 600 / 1 048 576 ≈ 600）。
- 若体素是 `int`（4 字节）则约 2.3 GiB，超出单数组字节上限；即便是 `byte`，一次装 600 MiB 并整块做 Job，也不利于流式加载与卸载。
- 采用流式区块：只保留玩家附近的区块。若可视半径 8 个区块，则 (2×8+1)² = 289 块，289 × 98 304 ≈ 28.4 MB（约 27 MiB）；半径 16 则 1 089 块，约 107 MB（约 102 MiB）。
- 再加上池里预留的"正在生成/正在建网格"的缓冲，总体仍在百兆量级。

结论：区块级 `Persistent` 缓冲池 + 流式加载，既不触碰单数组上限，也让内存与可视范围成正比，而与世界总大小无关。这与 `VoxelChunk` 注释中"世界总大小不再受单块连续内存限制"的设计一致。

## 常见坑

- `using` 块里 `Schedule` 但没 `Complete`：作用域结束就释放，Job 还在用。
- 把 `Allocator.Temp` 的容器放进 Job 字段：不允许。
- TempJob 持有超过 4 帧：触发警告或异常；跨帧的缓冲用 `Persistent`。
- 对同一容器的两个拷贝都调用 `Dispose`：`IsCreated` 只在被调用的那份上变 false，另一份会二次释放（手册指出 `IsCreated` 不反映别份拷贝）。
- 静态 `Persistent` 容器在关闭 Domain Reload 时没有清理。
- 池化缓冲归还过早（Job 还在读）或忘记归还。
- 池中使用 `UninitializedMemory` 却依赖零初值。
- 忽略 `Unsafe*` 容器的 4 帧规则：没有检查不代表没有问题。
- `RewindableAllocator.Rewind()` 之后继续使用旧容器：`Native-` 容器在检查开启时抛 `ObjectDisposedException`，`Unsafe-` 容器和裸指针没有检查，读到的是已回收的内存。`Rewind` 前要确认没有 Job 还在使用。
- 以为 `RewindableAllocator` 的单个 `Dispose` 会释放内存：默认是空操作，要么整体 `Rewind`，要么创建时开启 enable block free。
- 对别名调用 `Dispose` 或在原件释放后继续使用别名：前者无效果，后者抛 `ObjectDisposedException`。

## 小结

- Native 内存不归 GC，要有明确的所有者和释放点。
- `Temp` 最快但不能传给 Job；`TempJob` 须 4 帧内释放；`Persistent` 随用随放但慢。
- 释放写法：同步用 `using`，异步用 `Dispose(JobHandle)`，`[DeallocateOnJobCompletion]` 仍可用但覆盖面窄。
- 泄漏检测在编辑器偏好中开启，配合完整堆栈定位。
- 大数据靠分块与流式池化，而不是单个巨型数组。

## 自测题

1. 为什么 `Allocator.Temp` 的 `NativeArray` 不能传给 Job？
   答：Temp 内存属于创建它的线程与帧，Job 在其它线程异步运行，生命周期无法保证。
2. TempJob 的最长生命周期是多少，超出会怎样？
   答：4 帧；`Native-` 容器的释放检查会报告，`Unsafe-` 容器没有检查。
3. 怎样在不阻塞主线程的前提下，在 Job 之后释放一个 `NativeArray`？
   答：`handle = array.Dispose(handle)`，并让后续代码依赖这个新句柄。
4. 区块 16×16×384 每体素一字节是多少字节？
   答：98 304 字节（估算，不含对象头和池的额外开销）。
5. 池化 `Persistent` 缓冲时，清零与不清零各有什么取舍？
   答：不清零更快但带旧数据，须保证写满再读；清零安全但多一次内存写。
6. `RewindableAllocator` 里单个容器 `Dispose` 会发生什么？
   答：默认是空操作；开启 enable block free 后，释放某块的最后一个分配时才回绕那一块；通常靠整体 `Rewind()`。
7. `ints.Reinterpret<int, short>()` 得到的数组多长，怎么释放？
   答：长度翻倍（一个 `int` 对应两个 `short`）；它是别名，只释放原件，释放后别名不能再用。
8. 为什么从 `RewindableAllocator` 创建 `NativeArray` 要用 `CollectionHelper.CreateNativeArray`？
   答：官方要求；创建时容器的安全句柄会登记为分配器的子句柄，`Rewind` 时才能使其失效。
