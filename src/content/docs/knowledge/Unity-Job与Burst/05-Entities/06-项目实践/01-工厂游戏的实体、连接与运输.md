## 推荐的运行时实体

```text
Producer Entity
  Producer + RecipeRef + PendingOutput

BeltPath Entity
  BeltPath + DynamicBuffer<BeltItem>

Receiver Entity
  Receiver + InputBuffer
```

单段传送带可以先对应一个 Entity；连续传送带稳定后，再像 shapez.io 一样合并为 `BeltPath` 聚合实体。

## Entity 连接

端口组件保存目标 Entity 和目标槽位：

```csharp
public struct OutputPort : IComponentData
{
    public Entity Target;
    public ushort TargetSlot;
}
```

连接在拓扑改变时建立，普通 tick 只使用缓存。Entity 句柄不是永久业务编号；存档需要单独保存稳定 ID 和端口关系。

## 单 tick 数据流

```text
ProductionSystem
  → OutputInsertSystem
  → BeltMovementSystem
  → BeltTransferSystem
  → ReceiverConsumeSystem
```

传送带入口采用“尝试接收”：没有间距时生产器保留输出；出口接收失败时，物品停在路径末端，阻塞自然向上游传播。

## 速率模型

```text
BeltThroughput ≈ MovementSpeed / ItemSpacing
EffectiveRate = min(ProducerRate, BeltRate, ReceiverRate)
```

容量和速度分别建模。容量决定能否继续存入，速率决定固定 tick 内最多推进多少。

## 多路竞争

一个接收器被多个生产器连接时，不要让并行系统直接写库存：

```text
TransferProposal
  → ArbitrationSystem（优先级/轮询）
  → TransferCommitSystem
```

这样可以把“实体如何访问”与“谁获得容量”分开。

## 迁移顺序

1. 先用 `SystemAPI.Query` 在主线程实现单链。
2. 加入固定步、容量、速率和阻塞测试。
3. 把路径内移动改成 `IJobEntity` + Burst。
4. 最后才做多路仲裁、拓扑重建和路径合并。

## 与前面接口章节的对应

本章不是另一套 ECS API，而是把前面章节组合起来：

| 工厂问题 | Entities 机制 | 负责者 |
| --- | --- | --- |
| 设备身份 | `Entity` | World / EntityManager |
| 生产器状态 | `IComponentData` | `ProductionSystem` |
| 传送带物品列表 | `IBufferElementData` + `DynamicBuffer` | `BeltMovementSystem` |
| 生产器连接接收器 | 组件中的 `Entity` 引用 | `TopologySystem` |
| 运行时放置设备 | `EntityCommandBuffer` | `BuildSystem` |
| 批量移动物品 | `IJobEntity` + Burst | `BeltMovementSystem` |
| 场景初始设备 | `Authoring` + `Baker` | Baking 阶段 |

阅读这张表时可以回到 [ECS 核心接口与运行时类型](../../01-ECS核心/03-ECS%20核心接口与运行时类型) 查看接口职责，再回到本章看它们如何共同完成一条工厂链。
