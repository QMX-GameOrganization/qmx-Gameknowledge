## 推荐的运行时实体

```text
Producer Entity
  Producer + RecipeRef + PendingOutput

BeltPath Entity
  BeltPath + DynamicBuffer<BeltItem>

Receiver Entity
  Receiver + InputBuffer
```

单段传送带可以先对应一个 Entity；连续传送带稳定后，再像 shapez.io 一样合并为 `BeltPath` 聚合实体。

## Entity 连接

端口组件保存目标 Entity 和目标槽位：

```csharp
public struct OutputPort : IComponentData
{
    public Entity Target;
    public ushort TargetSlot;
}
```

连接在拓扑改变时建立，普通 tick 只使用缓存。Entity 句柄不是永久业务编号；存档需要单独保存稳定 ID 和端口关系。

## 单 tick 数据流

```text
ProductionSystem
  → OutputInsertSystem
  → BeltMovementSystem
  → BeltTransferSystem
  → ReceiverConsumeSystem
```

传送带入口采用“尝试接收”：没有间距时生产器保留输出；出口接收失败时，物品停在路径末端，阻塞自然向上游传播。

## 速率模型

```text
BeltThroughput ≈ MovementSpeed / ItemSpacing
EffectiveRate = min(ProducerRate, BeltRate, ReceiverRate)
```

容量和速度分别建模。容量决定能否继续存入，速率决定固定 tick 内最多推进多少。

## 多路竞争

一个接收器被多个生产器连接时，不要让并行系统直接写库存：

```text
TransferProposal
  → ArbitrationSystem（优先级/轮询）
  → TransferCommitSystem
```

这样可以把“实体如何访问”与“谁获得容量”分开。

## 迁移顺序

1. 先用 `SystemAPI.Query` 在主线程实现单链。
2. 加入固定步、容量、速率和阻塞测试。
3. 把路径内移动改成 `IJobEntity` + Burst。
4. 最后才做多路仲裁、拓扑重建和路径合并。

## 与前面接口章节的对应

本章不是另一套 ECS API，而是把前面章节组合起来：

| 工厂问题 | Entities 机制 | 负责者 |
| --- | --- | --- |
| 设备身份 | `Entity` | World / EntityManager |
| 生产器状态 | `IComponentData` | `ProductionSystem` |
| 传送带物品列表 | `IBufferElementData` + `DynamicBuffer` | `BeltMovementSystem` |
| 生产器连接接收器 | 组件中的 `Entity` 引用 | `TopologySystem` |
| 运行时放置设备 | `EntityCommandBuffer` | `BuildSystem` |
| 批量移动物品 | `IJobEntity` + Burst | `BeltMovementSystem` |
| 场景初始设备 | `Authoring` + `Baker` | Baking 阶段 |

阅读这张表时可以回到 [ECS 核心接口与运行时类型](/qmx-Gameknowledge/knowledge/unity-job与burst/05-entities/01-ecs核心/03-ecs-核心接口与运行时类型/) 查看接口职责，再回到本章看它们如何共同完成一条工厂链。

## 从当前网格到工厂链：每一步由谁触发

当前项目已有网格和占格能力，以下建造与物流链是后续接线目标，不代表已经全部实现：

```text
MonoBehaviour 输入与预览
  → 创建目标 Entity 和 GridOccupancyRequest
GridOccupancySystem
  → 全范围冲突检查 → 成功登记并写入 GridOccupancyState
建造结果处理
  → 成功才展示已建模型；读取结果后销毁请求 Entity
拓扑系统
  → 根据占地与端口建立连接缓存
固定步生产 / 运输 / 接收系统
  → 查询上述数据，推进模拟
表现层
  → 读取结果更新画面
```

GridPose / GridFootprint 只有范围描述；GridOccupancyState 才表示已登记。GridOccupancyIndex 是系统的运行时缓存，生命周期属于该 World，不是需要挂到场景的 MonoBehaviour。

当前 GridOccupancySystem 在 SimulationSystemGroup 前部；输入收集、请求提交和结果消费应明确约定先后。不要只因为都在模拟组里，就假设放置请求一定同帧生效。后续高频运输使用固定步，并不要求低频占格也每个固定 tick 重跑。

初始对象有两条落地方式：SubScene 加载后由初始化系统提交占格请求；运行时创建对象时直接提交请求。Baker 写出 GridPose/Footprint 不会自动调用托管占用索引。

Entity 数据也不会自动获得 GameObject 模型。先决定 Entities Graphics 或表现桥接，再实现显示。完整机制对照见 [00.2 完整链路与最小示例](/qmx-Gameknowledge/knowledge/unity-job与burst/05-entities/00-导读/02-从场景到运行时ecs的完整链路/)。
