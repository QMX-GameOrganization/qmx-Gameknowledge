> 适用版本：本章讲的是硬件与运行时通用原理，与具体包版本基本无关。涉及 Unity 6000.x 的 Burst 1.8.x / Collections 2.x 与本项目 Unity 7000.0.0a8（Burst 2.0.0 / Collections 6.7.0 壳包）的差异见“学习路线与版本说明”一章。

## 要点

- 现代 CPU 的瓶颈常常是内存访问而不是算术。顺序、紧凑、无指针追逐的数据访问通常比散乱访问快得多。
- 加速有三个来源，可以叠加：多线程（利用多核）、SIMD（一条指令处理多个数据）、去掉托管开销（编译为本机代码、无 GC 压力、无虚调用）。具体倍数视情况而定，必须自己测量。
- Job 不是线程，Burst 不是万能加速器。数据量小、逻辑分支多、频繁访问托管对象时，用它们可能更慢。
- 体素生成是理想负载：数据量按亿计，每个体素的计算简单且互相独立。

## 原理

### CPU 缓存与内存延迟

CPU 访问主存比访问寄存器慢得多，所以中间有多级缓存（L1、L2、L3）。缓存按“缓存行”（cache line）为单位搬运数据，常见大小为 64 字节。读取一个字节，会把它所在的 64 字节一起读进缓存。

```
内存:  | 64B 行 0 | 64B 行 1 | 64B 行 2 | ...
访问 a[0]  -> 整行 0 进入缓存
访问 a[1..63 字节内] -> 命中，几乎免费
```

- 顺序访问：一次行加载服务后续多次访问，硬件预取器还能提前读下一行。
- 随机访问：每次访问可能落在不同行，每次都付出一次缓存未命中的代价。

对 `byte` 数组：一行 64 字节可以容纳 64 个体素的标志，顺序扫描时几乎总是命中。对每个体素都是独立堆对象的布局，情况完全相反。

### 托管堆、GC 与指针追逐

C# 的引用类型对象放在托管堆上，变量里存的是指针。

- 指针追逐：`List<Foo>` 其中 `Foo` 是 class 时，元素在内存中不一定相邻，遍历要一次次跳转到各自的对象，缓存局部性差。
- 垃圾回收（GC）：大量短命对象会触发 GC，造成帧时间尖峰。Unity 使用的 GC 在回收时可能暂停托管线程（具体行为随版本与设置而异，待核实）。
- 虚调用：通过接口或虚方法调用，运行时要查表间接跳转，编译器难以内联，也就难以向量化。

本项目的密度函数图正是这种结构：`IDensityFunction.Sample(in DensityContext)` 是接口虚调用，函数图由多个托管对象组合，每次采样沿对象图追逐指针并多次虚调用。

### 多核与 Amdahl 定律

多核加速的上限由串行部分决定。Amdahl 定律：设并行部分占比为 p，核心数为 N，理论加速比为

```
speedup = 1 / ((1 - p) + p / N)
```

例：p = 0.9，N = 8，上限约 4.7 倍；p = 0.5，N = 8，上限不到 2 倍。这说明：

- 并行化之前先看串行部分有多大，主线程上的 `Apply`、调度、等待都算串行。
- 核心数增多，收益也会递减，同时还有调度与内存带宽的限制。

### 数据导向：AoS 与 SoA

| 布局 | 含义 | 特点 |
| --- | --- | --- |
| AoS（Array of Structures，结构体数组） | 每个元素把所有字段放一起 | 按对象访问方便；只用到部分字段时浪费缓存 |
| SoA（Structure of Arrays，数组的结构） | 每个字段单独一个数组 | 只读用到的字段时紧凑，易于向量化 |

本项目中，`FaceMask` 与 `Solid` 各自是一个 `NativeArray<byte>`，就是 SoA 的简单形式：扫描时只带入需要的数据。

## Job + Burst 的三个加速来源

| 来源 | 机制 | 合理预期 | 如何验证 |
| --- | --- | --- | --- |
| 多线程 | Job 把工作分给多个工作线程 | 通常随核心数增长但低于线性，受串行部分与内存带宽限制 | 对比相同 Job 的单线程（`Run`）与并行调度（`IJobFor.ScheduleParallel` 或 `IJobParallelFor.Schedule`）耗时 |
| SIMD | Burst 自动向量化，一条指令处理多个数据 | 视循环是否可向量化而定，可能很明显，也可能完全没有 | 在 Burst Inspector 里看汇编是否出现向量指令 |
| 去托管开销 | 编译为本机代码，Job 内无托管分配（无 GC），可直接内联调用 | 对计算密集的小循环通常显著，对本来就受内存限制的代码有限 | 对比同一段代码有无 `[BurstCompile]` |

三者的收益不是简单相乘。例如受内存带宽限制的循环，SIMD 与多线程的收益都会被带宽卡住。

测量方法：

1. 用 `Stopwatch` 或 Profiler 的 Timeline 测同一批输入。
2. 先 Warm up，Editor 中 Burst 默认在首次调用时同步或异步编译，首次计时会包含编译时间（具体行为取决于 `CompileSynchronously` 等设置，见 Burst 一章）。
3. 多次取中位数，并与托管版结果逐元素对比，确认答案一致后再比较速度。
4. 在目标平台的构建上再测一次，Editor 里的数字不代表发布版。

## 适合与不适合的场景

| 场景 | 适合 Job + Burst | 原因 |
| --- | --- | --- |
| 大量同构数据的逐元素计算（噪声采样、体素扫描） | 适合 | 独立、可并行、可向量化 |
| 网格顶点与索引生成 | 适合 | 数据量大，可用 `MeshData` 直接写 |
| 少量元素（几十个）的逻辑 | 不适合 | 调度开销可能超过计算本身 |
| 大量分支与对象图遍历 | 不太适合 | 分支预测失败、指针追逐，难向量化 |
| 要频繁调用 `UnityEngine.Object` API 的逻辑 | 不适合 | Job 内不能访问大部分 Unity 对象 API |
| 一次性、不在热路径的代码 | 不值得 | 复杂度增加，收益可忽略 |
| 有严格顺序依赖的流程 | 视情况 | 依赖链会限制并行度，可能只能拆成多阶段 |

## 用本项目做数量级估算

以下是估算，用来判断“是否值得”，不是测量值。

世界尺寸 1280 × 384 × 1280 体素：

```
1280 * 384 * 1280 = 629,145,600 ≈ 6.3 亿 体素
```

区块是 16 × 384 × 16，每块 98,304 个体素，共 80 × 80 = 6,400 个区块（与 `ChunkGenerationPipeline.ChunkSize = 16` 一致）。

如果每个体素需要 N 次基础运算（噪声、插值、比较等），总运算量约为 6.3 亿 × N：

| N | 总运算量（约） |
| --- | --- |
| 10 | 63 亿 |
| 100 | 630 亿 |
| 1000 | 6300 亿 |

再假设单核每秒能做的有效运算在 10 亿量级（只是量级假设，实际随指令、缓存情况差异很大），那么：N = 100 时单核约需几十秒到一分钟的量级，N = 1000 时可到十分钟的量级。这解释了为什么逐体素调用接口、对象图、再做插值的路径在大世界上很慢，也说明三个加速来源都值得用上。

另一个视角是内存：每体素 1 字节时，整个世界的 `solid` 约 600 MB，所以项目才用区块流式处理，只让必要的区块驻留（见 `ChunkGenerationPipeline` 里的 `maxLoadedChunks` 背压逻辑）。

本项目现状：`VoxelChunk.Fill` 对每个体素创建 `DensityContext` 并调用 `density.Sample`，这是上文“托管 + 虚调用 + 逐点”的典型路径，是 Burst 化的主要收益点。

## 常见误区

- Job 不是线程。Job 是一个待执行的数据加代码单元，由 Unity 的工作线程池取走执行。你不创建线程，也不决定它在哪个线程上跑。
- Burst 不是万能加速。它只加速可编译的 C# 子集，访问托管对象、字符串、异常等不被支持或会限制优化。
- 小数据可能更慢。调度、依赖管理、安全检查都有固定成本。几百个元素的循环放在主线程可能更快。
- 只加 `[BurstCompile]` 不等于被向量化。是否向量化取决于循环结构、别名、数据类型，要看 Burst Inspector。
- 在 Editor 测速不等于发布版速度。安全检查、Leak Detection、Jobs Debugger 在 Editor 中默认可能开启，会拖慢速度（各开关默认值待核实）。
- “并行了”不等于“变快了”。要看 Timeline 里的并行度和 `Complete` 的等待时间。

## 小结

- 内存访问模式往往决定性能，Job + Burst 要求你把数据做成紧凑的、无指针的数组。
- 加速来源是多线程、SIMD、去托管开销，收益互相制约，需要实测。
- 体素生成数据量大、逻辑独立，适合 Job + Burst；小数据与对象图密集的逻辑不适合。
- 估算只用来决定方向，决策要靠 Profiler 数据。

## 自测题

1. 缓存行通常是多少字节？它对顺序访问意味着什么？
   答：常见为 64 字节；顺序访问时一次加载可服务后续多次访问，命中率高。
2. 若程序 90% 可并行，8 核的理论加速上限约是多少？
   答：约 1 / (0.1 + 0.9 / 8) ≈ 4.7 倍。
3. 为什么 `IDensityFunction.Sample` 这种接口虚调用会妨碍加速？
   答：间接跳转难以内联和向量化，函数图还涉及托管对象指针追逐，缓存局部性差。
4. 1280 × 384 × 1280 的世界有多少体素，按每块 16 × 16 分，多少个区块？
   答：约 6.29 亿体素，80 × 80 = 6400 个区块。
5. 为什么说 Job 不是线程？
   答：Job 只是任务单元，由工作线程池调度执行，开发者不创建或控制线程。
