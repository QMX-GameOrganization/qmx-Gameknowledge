> 适用版本：以 Unity 6000.x 的 Burst 1.8.x 为主线（本章取自 Burst 1.8.31 手册 "Function pointers"）；本项目 Unity 7000.0.0a8 的 Burst 2.0.0 壳包在 `TypeForwarders.cs` 中确认转发了 `Unity.Burst.FunctionPointer<>`、`IFunctionPointer`、`BurstCompiler`。Burst 2.0 是否新增了更方便的函数指针语法，待核实。

## 要点

- Burst 不支持 C# 委托（delegate）和虚调用，因为它们是托管对象。需要"运行时选一个函数来调用"时，用 `FunctionPointer<T>`。
- 流程：给静态方法和所在类型都加 `[BurstCompile]` -> 声明非泛型委托类型 -> `BurstCompiler.CompileFunctionPointer<T>(method)` -> 把返回的 `FunctionPointer<T>` 存下来 -> 在 Job 里 `.Invoke(...)`。
- 间接调用不能内联，也阻碍向量化，别在最内层标量循环里每个元素调一次。要按批（batch）调用，让函数内部自己循环。
- 手册的建议很直接：能用 Job 就用 Job，Job 的别名信息和安全系统让 Burst 优化得更好。函数指针是没有更好办法时才选。
- 函数本身必须无共享可变状态，否则多线程调用会出数据竞争。

## 为什么需要间接调用

Burst 编译的是"一个已知的调用图"：它从入口点出发，静态地找到所有被调函数并一起编译、内联。C# 里的这些东西无法在这张图里表达：

- `interface` 虚调用与 `virtual` 方法需要托管类型实例；
- `Func<>`、`Action<>` 等委托是托管对象；
- 反射、动态加载的代码。

但程序又常需要"同一个循环，不同的行为"，比如密度函数图里每个节点做不同的运算。方案有几种（见后文对比表），函数指针是其中"最灵活、最慢"的一档。

## 基本用法

### 要求

- 目标方法必须是 `static`，加 `[BurstCompile]`，其所在类型也要加 `[BurstCompile]`（让 Burst 能找到这些静态方法）。
- 委托类型不能是泛型。不要把 `CompileFunctionPointer<T>` 包进另一个开放泛型方法里，否则 Burst 无法给委托加属性、做额外安全分析与优化（手册）。
- 参数与返回值受与 `DllImport` 和内部调用相同的限制，也就是只能用 blittable 类型（基元、指针、不含托管引用的结构体）。
- 不能直接传 `NativeArray<T>` 等容器，需要取出指针再传（容器里有托管对象用于安全检查，Job 能绕开，函数指针不能）。

### 示例

```csharp
using AOT;                       // MonoPInvokeCallback 在 AOT 命名空间
using Unity.Burst;
using Unity.Collections;
using Unity.Collections.LowLevel.Unsafe;
using Unity.Jobs;

[BurstCompile]                   // 类型上也要加
public static class Ops
{
    // 委托类型：函数指针的"接口"
    public unsafe delegate void BatchOp(int count, float* input, float* output);

    [BurstCompile]
    [MonoPInvokeCallback(typeof(BatchOp))]   // IL2CPP 兼容
    public static unsafe void Square(int count, float* input, float* output)
    {
        for (int i = 0; i < count; i++) output[i] = input[i] * input[i];
    }

    [BurstCompile]
    [MonoPInvokeCallback(typeof(BatchOp))]
    public static unsafe void Negate(int count, float* input, float* output)
    {
        for (int i = 0; i < count; i++) output[i] = -input[i];
    }
}

[BurstCompile]
struct ApplyJob : IJobParallelForBatch
{
    public FunctionPointer<Ops.BatchOp> Op;      // 把指针作为 Job 字段
    [ReadOnly]  public NativeArray<float> Input;
    [WriteOnly] public NativeArray<float> Output;

    public unsafe void Execute(int startIndex, int count)
    {
        float* inp = (float*)Input.GetUnsafeReadOnlyPtr() + startIndex;
        float* outp = (float*)Output.GetUnsafePtr() + startIndex;
        Op.Invoke(count, inp, outp);
    }
}

public static class Runner
{
    // 缓存：只编译一次，并保持存活
    static FunctionPointer<Ops.BatchOp> s_square;

    public static void Init()
    {
        s_square = BurstCompiler.CompileFunctionPointer<Ops.BatchOp>(Ops.Square);
    }
}
```

### 缓存与保活

- `CompileFunctionPointer` 有编译成本，应在启动时调用一次，把返回的 `FunctionPointer<T>` 存进静态字段或你的系统对象里，不要每帧、每个区块重新编译。
- 如果还要从普通 C# 代码里调用，手册建议把 `FunctionPointer<T>.Invoke`（即委托实例）缓存到静态字段，这样最快：

```csharp
static readonly Ops.BatchOp s_squareInvoke =
    BurstCompiler.CompileFunctionPointer<Ops.BatchOp>(Ops.Square).Invoke;
```

- 关于"是否需要额外持有原始委托实例以防 GC 回收"：手册示例并没有这样做，只是缓存 `FunctionPointer` 或其 `Invoke`。把 `FunctionPointer` 与（若创建过的）委托都放在静态字段里是稳妥做法，具体 GC 保活语义待核实。
- Burst 默认对 Job 里的函数指针做异步编译。需要首次调用就是 Burst 版本，用 `[BurstCompile(CompileSynchronously = true)]`。注意：1.8.31 的 "Function pointers" 手册页写的是 `SynchronousCompilation = true`，但 `BurstCompileAttribute` 的 API 页只列出 `CompileSynchronously`（以及 `Debug`、`DisableDirectCall`、`DisableSafetyChecks`、`FloatMode`、`FloatPrecision`、`OptimizeFor`），没有 `SynchronousCompilation`，所以应以 API 为准，手册那处应是笔误。

### 关于 IL2CPP 与 UnmanagedFunctionPointer

IL2CPP 下函数指针与委托互操作需要委托类型带 `System.Runtime.InteropServices.UnmanagedFunctionPointerAttribute`，调用约定为 `CallingConvention.Cdecl`。手册说明：用于 `CompileFunctionPointer<T>` 的委托，Burst 会自动加上这个属性，所以一般不用手写。静态方法上的 `[MonoPInvokeCallback]` 则需要自己加（`AOT` 命名空间里有；若不可用，手册给出了自己声明一个同名空特性类的退路）。

### 间接调用的开销

- 每次调用是一次 `call reg`，目标在别处，CPU 分支预测要猜；
- 函数体不能内联进调用点，调用点与函数体之间的常量传播、别名分析都断了；
- 标量逐元素调用时，循环无法向量化。手册示例（对 `math.sqrt` 的一次计算）：批量函数指针比逐元素函数指针快约 1.53 倍；直接写成 Job 比批量函数指针再快约 1.26 倍，比逐元素函数指针快约 1.93 倍。这是手册特定示例的数据，具体倍数随场景变化，要以自己的测量为准。

所以要把粒度放大：每次调用处理一批数据（一整列方块、一整个区块的某一层），把间接调用的开销摊薄，并让函数内部的循环可以向量化。

### 从普通 C# 调用

Burst 编译的函数指针从托管代码调用要经过 P/Invoke 式互操作，函数太小的话，可能比纯 C# 版本还慢。编辑器里若关闭了 Burst（`Jobs > Burst > Enable Compilation` 取消），`CompileFunctionPointer` 返回的指针会走托管回退路径；回退时抛出异常的行为（是否会跨越互操作边界、能否被外层 `try/catch` 捕获）本文没有核实，待核实。建议不要依赖异常在函数指针内外传播，用错误码或输出参数报告失败。

## 几种动态分发方案对比

场景：同一个 Job 要根据"节点类型"做不同计算。

| 方案 | 做法 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| switch（枚举）分发 | Job 内 `switch (node.Type)` 调用各静态方法 | 全部可内联，可向量化，最快，Inspector 里一眼看清 | 新增类型要改 switch；类型集合需编译期已知 | 节点种类有限（十几到几十种）、热点路径 |
| 泛型单态化 | `Job<TNode> where TNode : struct, INode`，每种节点生成一份专门的 Job | 零开销，节点逻辑可完全内联 | 组合爆炸；泛型 Job 要提前实例化 | 静态已知的少量组合 |
| 函数指针表 | `NativeArray` 或字段里存 `FunctionPointer`，运行时按索引调用 | 可在运行时选择与扩展，Job 代码不变 | 无法内联、阻碍向量化，需按批调用 | 插件式节点、配置驱动、种类很多且每次调用工作量大 |
| 指令数组 + 解释器 | 把表达式编成字节码数组，Job 里一个循环解释执行 | 完全数据驱动，可序列化，不依赖函数指针 | 解释器分支多，单条指令慢；要自己写 VM | 表达式图在运行时才定，如数据包定义的世界 |

选择顺序建议：能 `switch` 就 `switch`；类型多且稳定再考虑泛型；运行时需要扩展才用函数指针；结构完全由数据决定才写解释器。

## 应用示例：可替换的密度节点

本项目现在用 `IDensityFunction.Sample(in DensityContext)` 做虚调用（每个节点是托管类）。Burst 里没法这样写，需要把节点改成数据加分发。下面用"批量版"的密度节点说明两种写法。为保持示例短小，节点参数放在一个 `float` 数组里，`param` 指向它。

### 函数指针表版本

```csharp
using AOT;
using Unity.Burst;
using Unity.Collections;
using Unity.Collections.LowLevel.Unsafe;
using Unity.Jobs;

[BurstCompile]
public static unsafe class DensityNodes
{
    // 对一行 count 个 x 采样：y、z 固定
    public delegate void NodeFn(int count, int x0, int y, int z, float* param, float* output);

    [BurstCompile, MonoPInvokeCallback(typeof(NodeFn))]
    public static void Constant(int count, int x0, int y, int z, float* param, float* output)
    {
        for (int i = 0; i < count; i++) output[i] = param[0];
    }

    [BurstCompile, MonoPInvokeCallback(typeof(NodeFn))]
    public static void YGradient(int count, int x0, int y, int z, float* param, float* output)
    {
        // param[0]=起点y，param[1]=终点y，param[2]=起点值，param[3]=终点值
        float t = math.saturate((y - param[0]) / (param[1] - param[0]));
        float v = param[2] + (param[3] - param[2]) * t;
        for (int i = 0; i < count; i++) output[i] = v;
    }
}

[BurstCompile]
struct NodeJob : IJob
{
    public FunctionPointer<DensityNodes.NodeFn> Fn;   // 运行时选的节点
    [ReadOnly] public NativeArray<float> Param;
    public NativeArray<float> Output;
    public int X0, Y, Z;

    public unsafe void Execute()
    {
        Fn.Invoke(Output.Length, X0, Y, Z,
            (float*)Param.GetUnsafeReadOnlyPtr(), (float*)Output.GetUnsafePtr());
    }
}
// 启动时：
// var yGrad = BurstCompiler.CompileFunctionPointer<DensityNodes.NodeFn>(DensityNodes.YGradient);
```

（示例里的 `math` 需要 `using Unity.Mathematics;`。）

### switch 版本

```csharp
public enum NodeType : byte { Constant, YGradient }

[BurstCompile]
struct SwitchNodeJob : IJob
{
    public NodeType Type;
    [ReadOnly] public NativeArray<float> Param;
    public NativeArray<float> Output;
    public int Y;

    public void Execute()
    {
        var p = Param;
        var o = Output;
        switch (Type)
        {
            case NodeType.Constant:
                for (int i = 0; i < o.Length; i++) o[i] = p[0];
                break;
            case NodeType.YGradient:
                float t = math.saturate((Y - p[0]) / (p[1] - p[0]));
                float v = p[2] + (p[3] - p[2]) * t;
                for (int i = 0; i < o.Length; i++) o[i] = v;
                break;
        }
    }
}
```

对比：`switch` 版本里两个分支都在同一个编译单元，Burst 能把循环填充向量化，也能直接用 `NativeArray`；函数指针版本要用指针，别名信息丢失，每次节点调用有间接调用成本。在节点图里每个节点的计算量大（整行、整层）时差距不明显，节点很多且每个很小的时候，`switch` 明显更好。

对本项目的建议（只给方向）：节点种类数量有限且已知，优先 `switch` 加扁平化的节点数组；样条等需要子节点的结构见 2.8 与 3.2 的做法。

## 线程安全

函数指针会被多个 Job 线程同时调用，因此：

- 函数只依赖入参（指针指向的数据）与局部变量；
- 不写静态可变状态（Burst 本来也不允许可写静态字段，见 2.8）；
- 多线程各写各的输出区间，不能写同一块输出；
- 需要共享可变数据时，用 `SharedStatic<T>` 并自己保证同步（见 2.8），或者改成每线程一份。

## 常见坑

- 忘了给类型加 `[BurstCompile]`，函数指针没被 Burst 编译，运行退回托管，会慢很多且不一定报错。用 Inspector 确认目标不是灰色。
- 委托签名里用了 `NativeArray<T>` 或托管类型。参数与返回值的限制与 `DllImport` 相同（手册 "DllImport and internal calls"），`bool` 能否直接用以该页为准（待核实），保守起见可改用 `byte` 或 `int`。
- 在热循环里按元素调用函数指针，失去向量化。
- 每帧重复 `CompileFunctionPointer`。
- 把函数指针包进泛型方法里再编译，Burst 无法优化。

## 小结

函数指针是 Burst 里的动态分发手段，使用门槛不高但代价明确：不可内联，不可向量化，不能传容器。按批调用才合理。能用 `switch` 或泛型就别用函数指针；节点由数据驱动、数量多且运行时扩展时，才选函数指针表或解释器。

## 自测题

1. 为什么 Burst 里不能直接用 C# 委托？答：委托是托管对象，Burst 不支持托管引用类型。
2. 使用 `CompileFunctionPointer` 时，目标方法和所在类型需要什么标注？答：两者都要 `[BurstCompile]`；方法是 `static`，委托类型非泛型。
3. 为什么函数指针要按批调用？答：每次间接调用不能内联，开销固定；批量处理摊薄开销，也让函数内部循环可以向量化。
4. 函数指针为什么不能直接收 `NativeArray`？答：容器内含用于安全检查的托管对象，函数指针无法像 Job 那样绕开，需传裸指针。
5. 列出四种动态分发方案并各举一个适用场景。答：switch（节点种类少）、泛型单态化（静态已知组合）、函数指针表（运行时扩展）、指令数组加解释器（数据完全驱动）。
