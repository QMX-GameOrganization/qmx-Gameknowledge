> 适用版本：以 Unity 6000.x 的 Burst 1.8.x / Collections 2.x 为主线（手册取自 Burst 1.8.31）；本项目 Unity 7000.0.0a8 中 Burst 2.0.0 与 Collections 6.7.0 是转发（shim）到引擎内置模块的壳包，API 仍在 `Unity.Burst` / `Unity.Collections` 命名空间。错误码文本以 1.8.x 为准，2.0.0 是否有增删待核实。

## 要点

- Burst 的错误码很少有集中的官方清单。官方手册只在各专题页里提到少数几个（`BC1361`、`BC1370`、`BC1371`、`BC1321`），更新日志里还出现了 `BC1054`、`BC1055`、`BC1091`。本章其余编号的消息原文来自 Unity 论坛和 GitHub 的真实报错贴，来源在表里逐条标注，没有核实的编号一律不写。
- 绝大多数 `BC1xxx` 错误的根因只有一类：Burst 代码路径碰到了托管对象、托管数组、`string`、`class`、非 `readonly` 静态字段。修法几乎都是换成 unmanaged 数据（`NativeArray<T>`、`FixedString`、`struct`）。
- 报错要先看三样东西：错误码和消息、`文件(行,列)`、下面的调用栈。调用栈的最后几行常常指向你没想到的库代码。
- "Burst 没变快"的第一步是确认它真的在跑，而不是调优：看 Burst Inspector、关掉 `Safety Checks` 再比、用 Player 构建测。
- "结果与 Mono 不同"先查未初始化内存、浮点模式、数据竞争和越界，这四类占绝大多数。
- 提问时附上 Unity 与 Burst 版本、完整的报错文本（含调用栈）和 Editor.log 的 Burst 片段，本章末尾给了清单。

## 先读懂一条 Burst 报错

典型的错误长这样（节选自论坛真实报错，路径为示例）：

```
Assets/Scripts/ChunkJob.cs(42,13): Burst error BC1016: The managed function
`System.String.get_Length(System.String* this)` is not supported

at System.String.IsNullOrEmpty(System.String value)
at ChunkJob.Execute()
```

各部分的含义：

| 部分 | 含义 |
| --- | --- |
| `Burst error` / `Burst warning` | 错误会让该入口编不过；警告不会，但可能暗示 Player 里会出事 |
| `BC1016` | 错误码，用来在文档和论坛里检索 |
| `: The managed function ...` | 消息，其中用反引号括起来的是出问题的成员或类型 |
| `文件(行,列)` | 来自调试信息，只有编译时能拿到源码位置才有 |
| `at ...` 调用栈 | 从出错点往回追到 Burst 入口，最底下一行通常是你的 `Execute` |

### 同一类问题在不同场景的表现

- 编辑器里的 Job：首次调度（Schedule / Run）时 Burst 编译，失败会在 Console 里出现 `Burst error`。编辑器下失败后 Job 会不会回退到托管（Mono）版本继续跑，我没有在手册里找到明确说明，待核实。排查时不要依赖"回退后能跑"，要把 Console 里的每一条 Burst error 都当作需要修的问题。
- 函数指针与直接调用：失败时会抛 `InvalidOperationException`，消息为 `Burst failed to compile the function pointer ...`（或更老版本的 `... the given delegate ...`）。这是论坛里反复出现的写法，真正原因在这条异常之前的 `Burst error BCxxxx`，一定要往上翻。
- Player 构建（AOT）：编译失败会作为构建期错误出现在构建日志里；另外，如果平台工具链缺失，Burst 会静默跳过而构建仍成功，见"构建发布与平台差异"一章。
- 原生链接阶段失败：消息形如 `AotLinkerException: The native link step failed`，通常与平台工具链、NDK / Xcode 版本相关，而不是你的代码。

### 去哪里找完整日志

1. Console 窗口：适合看最近的错误，但可能被折叠，用右键复制全文。
2. Editor.log：Windows 默认在 `%LOCALAPPDATA%\Unity\Editor\Editor.log`，搜索 `Burst`、`BC1` 和 `error`。
3. Burst Inspector（`Jobs > Burst > Open Inspector`）：看某个目标能否编译、生成的汇编与 IR。
4. `Jobs > Burst > Show Timings`：在 Console 里输出每个库的编译耗时，定位编译特别慢的入口。

## 错误码速查表

来源列：手册 = Burst 1.8.31 官方手册；日志 = 官方 CHANGELOG 里出现该编号；论坛 / GitHub = 真实报错贴中的消息原文（措辞可能随版本略有不同）。

| 编号 | 消息要点 | 典型触发 | 修复方向 | 来源 |
| --- | --- | --- | --- | --- |
| `BC1016` | The managed function `...` is not supported | 在 Burst 里调用托管方法，如 `string.IsNullOrEmpty`、`List<T>` 方法 | 换成 unmanaged 等价物，或移出 Burst 路径 | 论坛 |
| `BC1028` | Creating a managed array `T[]` is not supported | 在 Job 里 `new int[n]`、`new string[]` | 用 `NativeArray<T>`、`stackalloc` 或 `FixedList` | 论坛 |
| `BC1033` | Loading a managed string literal is not supported | 旧版本里把字符串用于 `ProfilerMarker`、拼接 | 用 `FixedString`；现在手册已支持部分场景，见下 | 论坛 |
| `BC1042` | The managed class type `X` is not supported. Loading from a non-readonly static field ... | 读取非 `readonly` 的静态字段 | 改 `static readonly`、`SharedStatic<T>`，或通过 Job 字段传入 | GitHub |
| `BC1045` | Struct `X` with auto layout is not supported | `LayoutKind.Auto` 的结构体，如 `ValueTuple` | 自定义 `Sequential` 结构体 | 论坛 |
| `BC1051` | Invalid managed type found for the field `f` of the struct `S` | Job 或数据结构里有 `int[]`、`class`、委托字段 | 字段改成 `NativeArray<T>` 等 unmanaged 类型 | 论坛 |
| `BC1054` | （编译器内部问题）带指向泛型参数指针字段的结构体用作接口泛型实参 | 复杂泛型 + 指针 | 升级 Burst；日志称已修复 | 日志 |
| `BC1055` | Unable to resolve the definition of the method ... | 含 `in` 参数的方法，多 CPU 目标 | 升级 Burst；日志称已修复 | 日志 |
| `BC1091` | External and internal calls are not allowed inside static constructors | 静态初始化里调用了外部函数 | 把初始化挪到运行时，或用 `SharedStatic` | 论坛 + 日志 |
| `BC1321` | 循环没有被向量化，而你声明了期望 | `Loop.ExpectVectorized()` 的循环里加了 `break` 等 | 去掉阻碍向量化的控制流，或去掉断言 | 手册 |
| `BC1361` | 不被支持的静态构造 | `static readonly` 数组用了不可求值的初始化 | 简化成数组初始化器 | 手册 + 日志 |
| `BC1370` | 警告：异常抛出点没有 `[Conditional("ENABLE_UNITY_COLLECTIONS_CHECKS")]` 保护 | 直接在 Burst 方法里 `throw` | 放进带该特性的检查方法；有意崩溃用 `[IgnoreWarning(1370)]` | 手册 |
| `BC1371` | 警告：对 `[BurstDiscard]` 方法的调用被丢弃 | 只把计算结果传给 `[BurstDiscard]` 方法 | 让变量有其它用途，或 `[IgnoreWarning(1371)]` | 手册 |

下面对常见几条给出可复现的触发代码和修复。

### BC1016 与 BC1028：托管函数与托管数组

```csharp
using Unity.Burst;
using Unity.Collections;
using Unity.Jobs;

[BurstCompile]
public struct BadJob : IJob
{
    public NativeArray<int> Output;
    public void Execute()
    {
        var tmp = new int[16];                // BC1028: 托管数组
        string name = "chunk";
        if (string.IsNullOrEmpty(name)) { }   // BC1016: 托管方法
    }
}

[BurstCompile]
public struct GoodJob : IJob
{
    public NativeArray<int> Output;
    public void Execute()
    {
        // 小的固定大小缓冲放栈上; 大小不确定或较大时用 Allocator.Temp 的 NativeArray
        var tmp = new NativeArray<int>(16, Allocator.Temp);
        // ...
        tmp.Dispose();
    }
}
```

调试时注意：错误往往不在你的 Job 里，而在库代码。论坛上有人在 Netcode 库里遇到 `String.get_Length`，调用栈里才能看到是谁调的。

### BC1042：读取非 readonly 静态字段

手册说明：Burst 在编译期对静态字段求值，只支持 `readonly` 的静态字段，在 Burst 编译的结构体里出现非 `readonly` 的静态字段会导致编译错误。

```csharp
[BurstCompile]
public struct StaticJob : IJob
{
    static int s_counter;                       // 非 readonly: 会触发错误
    static readonly int[] s_table = { 1, 2, 3 }; // 只读数组: 有限支持, 只能直接用

    public void Execute()
    {
        s_counter++;                            // 错误
        int x = s_table[0];                     // OK
    }
}
```

修复：需要共享可变的静态数据时用 `SharedStatic<T>`（详见"静态数据与 SharedStatic"一章）；一次性的配置值通过 Job 字段传入。

### BC1051：托管类型出现在结构体字段里

```csharp
public struct ChunkData
{
    public int[] Heights;     // BC1051: `int[]` is a managed type
    public Material Mat;      // BC1051: 引用类型
}

public struct ChunkDataFixed
{
    public NativeArray<int> Heights;  // Job 内可用
}
```

这个错误的消息会点出字段名和结构体名，直接按提示改字段类型。注意含托管字段的结构体即使没有被你标 `[BurstCompile]`，只要被某个 Burst 入口用到就会报。

### BC1091：静态构造里的外部调用

触发形式是 `static readonly` 字段的初始化表达式调用了外部（`extern`）函数，例如分配内存的 `UnsafeUtility.Malloc` 类方法。论坛一例里，原因是一个 `static readonly` 字段的初始化链上用到了这类调用，并且这个错误在 Player 构建中还会表现为只在独立构建里崩溃。修复：不要在静态初始化里做分配或外部调用，改成运行时显式初始化。

### BC1361、BC1370、BC1371、BC1321

这几条已在"支持的 C# 子集"与"SIMD 与自动向量化"两章展开，此处只补两点：

- `BC1361` 的更新日志条目写道，曾经因为超大 `static readonly` 数组导致此错误，后续版本已修复，所以遇到时先确认 Burst 版本。
- `BC1370` 是警告而不是错误：编辑器里 `throw` 会被捕获并在 Console 里打印，Player 里 `throw` 变成 abort，应用崩溃。

## 其它没有编号但常见的报错

| 现象 | 原因 | 修复 |
| --- | --- | --- |
| `Can't call the method ... on the generic interface object type ...` | 手册列出的限制：泛型方法的参数 `T : IEnumerable<U>` 在方法体里 `foreach` | 用具体的集合类型，或自己写索引循环 |
| 泛型 Job 在编辑器里很快，Player 里很慢 | 手册说明：通过泛型参数间接使用的泛型 Job，构建时 Burst 发现不了，不会 AOT 编译 | 只用已完全确定类型实参的泛型 Job，如 `MyJob<int>`；不要用泛型方法去调度泛型 Job |
| `Burst failed to compile the function pointer ...` | 函数指针目标编译失败，真正原因在前面的 `Burst error` | 先修前面的错误；泛型委托不能用于函数指针 |
| `The type initializer for 'X$BurstDirectCall' threw an exception` | 论坛里的同类报错，内层异常就是上一行的 `Burst failed to compile the function pointer` | 看内层异常和它之前的 `Burst error`，不要只盯着外层 |
| `Failed to find entry-points` | 更新日志 1.8.30 修复了 Burst 与编辑器编译流程之间的竞态 | 升级 Burst，或重启编辑器 |
| `AotLinkerException: The native link step failed` | 平台链接器问题 | 检查 NDK / Xcode / 平台 SDK，参见"构建发布与平台差异"一章 |

`BC1033` 补充说明：它出自较老的版本，常见于把 `ProfilerMarker` 或字符串拼接用到 Burst 里。当前手册已写明 Burst 可以使用 `ProfilerMarker`，也支持字符串字面量、插值字面量和 `FixedString`，`Debug.Log` 是唯一能直接接收托管 `string` 的调用。所以现在若仍遇到，大概率是字符串被传进了自定义方法或存进了结构体字段；按手册，需要传递或存储字符串时用 `FixedString128Bytes` 等类型。

## Burst 没变快或没生效：排查清单

按成本从低到高排查，前三项最常见。

| 序号 | 检查项 | 怎么确认 | 处理 |
| --- | --- | --- | --- |
| 1 | Burst 总开关 | 编辑器看 `Jobs > Burst > Enable Compilation`；Player 看 `Burst AOT Settings` 的 `Enable Burst Compilation` | 打开 |
| 2 | Job 是否带 `[BurstCompile]` | Burst Inspector 左侧列表里没有 `[BurstCompile]` 的目标是灰色 | 补上特性；静态方法需要方法和所在类型都标 |
| 3 | 是否回落到 Mono 或在编译中 | 首帧慢、后面快 | 编辑器默认异步编译，编译完成前跑托管版本；用 `Synchronous Compilation` 或 `[BurstCompile(CompileSynchronously = true)]` 验证（手册提醒会造成卡顿，只用于验证） |
| 4 | 编辑器的安全检查 | `Jobs > Burst > Enable Safety Checks` 是 `On` | 测性能时切 `Off`；手册说明重启编辑器后会复位为 `On` |
| 5 | Leak Detection、Jobs Debugger | 编辑器 `Jobs` 菜单里的相关开关 | 关闭再比（具体菜单项名称随版本，待核实） |
| 6 | 挂了调试器 | 手册：挂托管调试器并在 Burst 代码路径下断点时，Burst 会对该路径自动关闭 | 移除断点或不挂调试器 |
| 7 | 用了 `Native Debug Mode` 或 `Debug = true` | 对应菜单项被勾选，或特性里有 `Debug = true` | 取消；这会关掉优化 |
| 8 | Profiler 的 Deep Profile | Profiler 窗口里开着 | 关闭，Deep Profile 本身开销很大（这是通用经验，非 Burst 手册内容） |
| 9 | 域重载刚发生 | 刚改完脚本 | Burst 要重新编译受影响的代码，等待后再测 |
| 10 | 不是在 Player 里测 | 在编辑器 Play 模式测的 | 用 Release 构建的 Player 测，见"构建发布与平台差异"一章 |
| 11 | 泛型 Job 没被 AOT | Player 里慢、编辑器里快 | 见上表，用完全确定类型的泛型 Job |
| 12 | 优化级别被调低 | 程序集或 Job 上有 `OptimizeFor = FastCompilation`，或 AOT 设置里 `Optimize For` 不对 | 改回 `Performance` 或 `Balanced`；`Fast Compilation` 不做向量化、内联和循环优化 |
| 13 | 没有向量化 | Burst Inspector 汇编里全是标量指令 | 见"SIMD 与自动向量化"一章，使用 `[NoAlias]`、避免循环中的 `break` |
| 14 | 数据量太小 | 一次只处理几十个元素 | 调度、同步与线程唤醒的开销会盖过计算，攒批后再调度 |
| 15 | 被内存带宽限制 | 计算很简单、数据量很大 | 此时算力不是瓶颈，减少访存、改善布局才有用 |
| 16 | 平台工具链缺失 | Player 的 Plugins 下没有 `lib_burst_generated` | 手册：目标无效时不会用 Burst 但仍构建 |

一个实用的二分法：同一份 Job 分别在 Burst 开与关两种状态下计时（用 `Enable Compilation` 开关或 `--burst-disable-compilation` 命令行参数）。如果差距接近零，说明 Burst 根本没生效；如果差距巨大但帧率没变，说明瓶颈在别处，而不是这个 Job。

## 结果与 Mono 不同：排查清单

先建立可复现的对比：同一份输入，分别在 Burst 开与关下跑，再在 `Safety Checks` 为 `On` 的编辑器里跑一次。编辑器的安全检查能直接抓住很多问题，是最便宜的诊断工具。

### 1. 读了未初始化的内存

```csharp
// 不清零: 申请快, 但内容是上一次留下的垃圾值
var heights = new NativeArray<int>(
    4096, Allocator.TempJob, NativeArrayOptions.UninitializedMemory);

// 默认 ClearMemory 会清零; 用 UninitializedMemory 后必须保证每个元素先写后读
```

垃圾值在 Burst 和 Mono 下不同，所以表现为"结果不一致"。只有确认整块都会被写入时才用 `NativeArrayOptions.UninitializedMemory`。

`stackalloc` 也一样：.NET 会把 `stackalloc` 的内存清零，更新日志记录 Burst 早期修过"没有清零"的差异。手册说明 `[SkipLocalsInit]`（`Unity.Burst.CompilerServices.SkipLocalsInitAttribute`）会让 Burst 跳过栈分配的清零，这时必须自己保证先写后读。

### 2. 浮点差异

- 默认 `FloatMode.Strict`：Burst 不重排计算，遵守 NaN 与非规格化数。`FloatMode.Fast` 允许重排与使用精度更低的 SIMD 指令，结果与 Mono 会有微小差别。
- 数学函数精度由 `FloatPrecision` 控制：`Standard` 等同 `Medium`，为 3.5 ulp；`High` 为 1.0 ulp；`Low` 对 `sin`、`cos`、`exp`、`log`、`pow`、`fmod` 等为 350 ulp。托管的 .NET 数学库和 Burst 的实现不是同一份，所以逐位相同本来就不能期待。
- 需要跨平台一致用 `FloatMode.Deterministic`（1.8.25 加入，仅 64 位架构）。它会把非规格化数刷成零，也可能降低性能。
- 详见"浮点模式与确定性"一章。判断是否属于这类：把差异量级与 ulp 比较，只差最后几位的是浮点差异，差几个数量级的是别的问题。

### 3. 数据竞争

并行 Job 里多个线程写同一个位置，结果取决于调度，Burst 与 Mono 的时序不同就会出现差异。检查：

- `IJobParallelFor` 中是否只写 `[index]`；写别的下标需要 `[NativeDisableParallelForRestriction]`，加了它就等于你自己保证无冲突。
- `[NativeDisableContainerSafetyRestriction]` 会关掉编辑器的检查，试着去掉它看是否报错。
- 别名问题：更新日志 1.8.22 说明，Job 结构体里 `NativeContainer` 字段通过 `GetUnsafePtr()` 取得的指针被假定与同一 Job 里其它容器互不重叠（`[NoAlias]`）。如果你让两个字段指向同一块内存，结果可能因优化而变。需要时可以用 `[Alias]`（1.8.21 加入，实验性）标注。

### 4. 越界读写

- 编辑器里 `NativeArray<T>` 的越界会抛异常，前提是 `Safety Checks` 打开。
- 用原始指针、关掉安全检查、或 Player 里则没有保护：越界读到别处的数据，越界写直接破坏内存，表现为诡异的结果或崩溃。
- 更新日志记录过 `Span<T>.Fill` 对小于 int 的整数类型会越界写（1.8.27 修复）、`Span` 切片的安全检查误报（已修复）。这类问题靠升级解决。

### 5. 静态只读数组的拷贝

手册提醒：Burst 在编译时把 `static readonly` 数组拷成只读数据。如果非 Job 的 C# 代码在运行时修改了这个数组，Burst 里看不到修改。不要在运行时改它。

## 崩溃与卡死排查

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| 编辑器直接崩溃或 Player 闪退，无托管异常 | 指针越界读写、使用已释放的内存、栈溢出 | 先在编辑器里开 `Safety Checks`；再用 `Native Debug Mode Compilation` 或 `Debug = true` 挂原生调试器 |
| 只在 Player 崩溃 | 编辑器的检查把问题掩盖了；`throw` 在 Player 里是 abort（见 `BC1370`） | 检查异常路径与指针；把 `throw` 放进条件保护的检查方法 |
| 栈溢出 | 栈上放了大数组：大的 `stackalloc`、大的固定缓冲、`FixedList4096Bytes<T>` 一类大型栈结构，或递归过深 | 大块数据放 `NativeArray<T>` 或 `Allocator.Temp`；递归改迭代。Job 工作线程的栈大小我没有核实到，待核实 |
| 循环里反复 `stackalloc` | 栈内存要到函数返回才释放，在循环里反复分配会耗尽栈 | 在循环外分配一次，循环内复用 |
| 编辑器编译时卡死 | 更新日志 1.8.25：带 `[MethodImpl(MethodImplOptions.AggressiveInlining)]` 的（间接）递归方法会导致编译死循环和内存暴涨 | 去掉递归方法上的强制内联，并升级 Burst |
| 运行卡死 | Job 内死循环，主线程 `Complete()` 在等它 | 给循环加上界；用 Burst 关闭对比看是否是同一处 |
| 加载 JIT 库失败 | 更新日志 1.8.30：Windows Smart App Control 或 WDAC 策略可能在加载时拦截 JIT 编译出的库，Burst 会记录警告并删除该库，下次重新编译 | 检查系统安全策略与 Editor.log 里的相关警告 |

调试手段：

- `System.Diagnostics.Debugger.Break()` 可在 Burst 代码里放代码断点，手册说明不论是否挂了调试器它都会触发。
- 想知道是不是栈缓冲溢出，可以在 Player 的 `Burst AOT Settings` 里打开 `Stack Protector`（`Basic`、`Strong`、`All`），它会在函数返回时检查栈金丝雀值。
- Player 里的原生调试需要符号：开 `Development Build` 或 `Force Debug Information`，并关掉 `Enable Optimizations` 或使用 `Debug = true`；调试器要指向含 `lib_burst_generated` 文件的目录（通常是 `Plugins`）。

## 版本升级注意事项

我能核实到的事实：

- 项目里的 `com.unity.burst` 是 `2.0.0`，`package.json` 的 `type` 为 `shim`，`packages-lock.json` 里来源是 `builtin`。包内只有类型转发（`TypeForwarders.cs`）和一个程序集定义，真实实现随编辑器发布，不再由你在 Package Manager 里单独升级。

- 手册首页提醒：升级 Burst 包版本后需要关闭并重启编辑器。

我没能核实到的：

- Burst 2.0.0 相对 1.8.x 的变更说明（What's new / 升级指南）。我读到的 1.8 手册、更新日志和 Unity 6.7 手册里都没有 2.0 的升级页面，所以 1.8 到 2.0 的行为变化、错误码增删，全部待核实。
- 7000.0.0a8 是 alpha 版本，行为可能与已发布版本不同。遇到差异以实机为准，并在升级编辑器后重新跑一遍性能基线和结果对比。

升级后建议的检查：

1. 清掉所有 Burst 相关的编译警告和错误，特别是新增的警告。
2. 用固定输入对关键 Job 做"Burst 开与关"的结果比对，防止优化器变化带来的数值差异。
3. 在 Burst Inspector 里确认热点循环仍然向量化；必要时用 `Loop.ExpectVectorized()`（需定义 `UNITY_BURST_EXPERIMENTAL_LOOP_INTRINSICS`）把这个预期写进代码，退化时由编译器直接报 `BC1321`。
4. 重新做一次 Player 构建，确认 `lib_burst_generated` 仍在产物里。
5. 更新日志中有若干"编译器误编译或崩溃"类修复（例如 1.8.28 的特定算术误编译），遇到无法解释的错误结果时，把 Burst 升到包含修复的版本也是一个排查方向。

## 提问或提 bug 时附带的信息

1. Unity 完整版本号（如 `7000.0.0a8`）和 Burst 版本（项目里是壳包 `2.0.0`，同时说明你读的是哪套手册）。
2. 目标平台、脚本后端（Mono 或 IL2CPP）、是编辑器还是 Player、是 Development 还是 Release。
3. 完整的 Console 报错文本，包含错误码、`文件(行,列)` 和调用栈，不要只贴最后一行。
4. Editor.log 中与 Burst 相关的片段（搜索 `Burst`、`BC1`），以及是否有 `Burst failed to compile` 之类的异常。
5. 最小复现：一个 Job 加几行输入数据，能复现的就够。
6. Burst Inspector 里该目标的文本（汇编或 IR）：复制 Assembly 或 `.NET IL` 视图的内容，说明选的架构和 `Safety Checks` 状态。
7. 你已经尝试过的开关：Burst 开关、`Safety Checks`、`Synchronous Compilation`、`FloatMode`、`OptimizeFor`。
8. 性能问题还要附上数据规模、测量方式（编辑器或 Player）和前后对比数字。
9. 编译慢的问题附上 `Show Timings` 的输出。

## 常见坑

- 只看最后一行报错：真正的原因常在上面一两行，或在调用栈的库代码里。
- 把 `BC1042` 理解成"类不能用"：它也可能是读取了非 `readonly` 的静态字段。
- 在 Job 里 `throw` 当作正常控制流，Player 里会直接崩溃。
- 用 `UninitializedMemory` 又没写满就读。
- 关掉安全检查后才发现的越界，已经破坏了别处的内存，崩溃点和真正出错点相距很远。
- 在编辑器里就下"Burst 没用"的结论：先排除异步编译、Safety Checks 和 Deep Profile。
- 把泛型 Job 通过泛型方法调度，导致 Player 里没有 AOT 编译。

## 小结

- 先读完整的报错：错误码、消息里的反引号成员、文件行号、调用栈。
- 大多数 `BC1xxx` 都是"用了托管的东西"，修法是换成 unmanaged 数据，或把代码移出 Burst 路径。
- "没变快"先确认 Burst 真的在跑，再依次排除安全检查、调试器、Profiler、异步编译、测试环境。
- "结果不一致"查四件事：未初始化内存、浮点模式、数据竞争、越界。
- 崩溃卡死多与指针、栈和无限循环有关；原生调试需要符号和关闭优化。
- 2.0.0 的变更说明没能核实，升级后要自己做对比验证。

## 自测题

1. 看到 `InvalidOperationException: Burst failed to compile the function pointer ...`，应该先看哪里？
   答：看它之前的 `Burst error BCxxxx`，那才是真正的编译失败原因。
2. 如何区分 `BC1370` 与 `BC1016`，哪个是警告？
   答：`BC1370` 是警告，指 `throw` 所在方法没有 `[Conditional("ENABLE_UNITY_COLLECTIONS_CHECKS")]` 保护，Player 里会变成 abort；`BC1016` 是错误，指调用了不受支持的托管函数。
3. Job 在编辑器里很快、Player 里很慢，首先怀疑什么？
   答：手册指出的泛型 Job 问题：通过泛型参数间接使用的泛型 Job 在构建时不会被 AOT 发现；其次是平台工具链缺失导致 Burst 被静默跳过。
4. 为什么 `NativeArrayOptions.UninitializedMemory` 会造成 Burst 与 Mono 结果不同？
   答：垃圾值在两种运行方式下不同，没写先读就得到不同结果。
5. 提问时为什么要附上 Burst 版本？
   答：错误码文本与修复随版本变化，许多问题（如 `BC1054`、`BC1055`、`BC1361`）在更新日志里写明了修复版本。
