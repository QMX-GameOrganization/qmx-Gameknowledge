> 适用版本：以 Unity 6000.x 的 Burst 1.8.x（选项名取自 1.8.31 手册）为主线；本项目 Unity 7000.0.0a8 中 Burst 2.0.0 是转发（shim）到引擎内置模块的壳包，API 仍在 `Unity.Burst` 命名空间，文档迁到了 Unity Manual。两者在设置项上的差异已逐处注明，核实不了的标"待核实"。

## 要点

- 编辑器里 Burst 是 JIT（即时编译），Player 里是 AOT（Ahead-of-Time，提前编译）：构建时把所有可编译代码编成一个原生库，随游戏发布，运行时不再编译。
- Windows 构建的产物是 `Data/Plugins/lib_burst_generated.dll`；iOS 为满足 Apple 提交要求改为静态库。运行时第一次调用 Burst 方法时才加载这个库。
- 配置入口只有一个：`Edit > Project Settings > Burst AOT Settings`（1.8.31 手册的 AOT 设置页这样写；同版本的 "Building your project" 页写成 `Edit > Player Settings > Burst AOT Settings`，两页不一致，以编辑器里实际能找到的为准），它只管 Player 构建；编辑器内的行为由 `Jobs > Burst` 菜单管。两者互不影响。
- 目标平台无效（缺工具链或不支持）时，Unity 不会让构建失败，而是不用 Burst 继续构建。性能骤降却没有报错，往往就是这个原因。
- 容器安全检查（越界、依赖检查）是编辑器功能，Player 构建里没有"Enable Safety Checks"选项。性能测试应该用 Player 构建，不要在编辑器里测。
- 手册里没有名为 "Enable Debug Mode / Force Debug Mode / Disable Warnings" 的 AOT 选项。与调试和警告相关的实际选项是 `Force Debug Information`、`Enable Optimizations`（关掉它用于原生调试）和 `Disabled Warnings`，下文逐项说明。

## 构建时发生了什么

```
Player 构建
  |
  +-- 脚本编译 (C# -> IL)
  |
  +-- Burst AOT: 找出所有 [BurstCompile] 入口
  |     |-- 对每个选中的 CPU 目标各做一次独立编译 (X64_SSE2、X64_SSE4 ...)
  |     |-- 链接成 lib_burst_generated (Plugins 目录)
  |
  +-- 打包; 运行时首次调用 Burst 方法时加载该库
```

几点需要知道：

- Burst 会为每个 CPU 目标单独编译一遍。手册举例：同时选 `X64_SSE2` 与 `X64_SSE4`，就要做两次独立编译。选的目标越多，构建越慢，生成的库也越大。（库体积的具体增幅手册没有给数字，需要自己看产物大小。）
- 桌面平台（Windows、macOS、Linux）之间默认支持交叉编译，不需要外部工具链。非桌面平台需要对应的平台工具链，例如 Android 要 NDK。
- 1.8.31 手册还有一个 `Use Platform SDK Linker` 选项（仅桌面）：开启后关闭交叉编译，必须使用目标平台的原生工具。手册建议仅在调试时开启。Unity 6.7 手册的 AOT 设置页里没有列出这个选项（待核实它在 7000.0.0a8 中是否还在）。

## Burst AOT Settings 逐项

下表以 Burst 1.8.31 手册为准，括号里是 Unity 6.7 手册的差异。

| 选项 | 含义 | 备注 |
| --- | --- | --- |
| `Target Platform` | 显示当前平台 | 6 及以上在 `File > Build Profiles` 切换，更早版本在 `File > Build Settings`。每个平台可以有各自的 Burst AOT 设置 |
| `Enable Burst Compilation` | Burst 总开关（按平台） | 关闭后该平台的 Player 完全走托管代码 |
| `Enable Optimizations` | 启用 Burst 优化 | 关闭会让所有 Job 变慢，仅用于原生调试 |
| `Force Debug Information` | 让 Burst 生成调试信息 | 即使 Release 构建也带符号，方便调试器显示文件和行号 |
| `Use Platform SDK Linker` | 见上，关闭交叉编译 | 仅 Windows/macOS/Linux 构建；6.7 手册未列 |
| `Target 32Bit CPU Architectures` | 32 位构建的 CPU 目标 | 默认勾选 SSE2 与 SSE4；只有架构受支持时才显示 |
| `Target 64Bit CPU Architectures` | x64 构建的 CPU 目标 | 默认 SSE2 与 SSE4；平台表里还列出 AVX、AVX2 |
| `Target Arm 64Bit CPU Architectures` | Arm64 构建的 CPU 目标 | 默认 `ARMV8A` |
| `Optimize For` | 全局默认优化目标 | `Performance`、`Size`、`Fast Compilation`、`Balanced`（默认） |
| `Floating Point Mode` | 全局默认浮点模式 | 1.8.24 加入；可被 `[BurstCompile(FloatMode = ...)]` 覆盖 |
| `Disabled Warnings` | 要屏蔽的 Burst 警告编号，分号分隔 | 只对 Player 构建生效，所有平台共享 |
| `Stack Protector` | 栈保护级别 | 1.8.21 加入；`Off`、`Basic`、`Strong`、`All`，对应 clang 的 `--fstack-protector` 系列 |
| `Stack Protector Buffer Size` | 栈保护启发式的缓冲区大小阈值 | 同上 |

### Optimize For 的覆盖关系

`Optimize For` 只是全局默认值。程序集级 `[assembly: BurstCompile(OptimizeFor = ...)]`、单个 Job 或函数指针上的 `OptimizeFor` 都会覆盖它。四个取值：

- `Performance`：尽可能快。
- `Size`：生成代码尽可能小。
- `Fast Compilation`：几乎不优化，不做向量化、内联和循环优化。编译最快，运行最慢。
- `Balanced`：运行快的同时尽量控制编译时间，是默认值。

```csharp
using Unity.Burst;
using Unity.Jobs;

// 只想让这个 Job 在发布构建里全力优化, 不受全局 Balanced 影响
[BurstCompile(OptimizeFor = OptimizeFor.Performance)]
public struct MeshBuildJob : IJob
{
    public void Execute() { /* ... */ }
}
```

### 关于"Enable Safety Checks"

Burst 1.6.0-pre.3 的更新日志写明：移除了 Player 构建的 `Enable Safety Checks` 选项，因为它实际上并不能打开容器的安全检查，而容器检查在 Unity 里只存在于编辑器。所以：

- 编辑器：`Jobs > Burst > Enable Safety Checks` 有 `Off`、`On`、`Force On` 三档，`On` 是默认值。
- Player：没有这个开关。`NativeArray<T>` 之类容器的越界和依赖检查是否存在，取决于 `ENABLE_UNITY_COLLECTIONS_CHECKS` 这类脚本符号在构建中是否定义（Development Build 是否默认定义它，我没有在手册里核实到，待核实）。

这也是 `BC1370` 的来源：Player 里 `throw` 会变成 abort，应用直接崩溃，所以 Burst 要求把异常放进带 `[Conditional("ENABLE_UNITY_COLLECTIONS_CHECKS")]` 的方法里。详见"常见编译错误与排错"一章。

## 多 CPU 目标与运行时选择

### 选哪些目标

`Target 64Bit CPU Architectures` 的几档是累积的指令集门槛：

- `SSE2`：x64 的基线，所有 x64 CPU 都有。
- `SSE4`：门槛是 SSE4.2 加 `POPCNT`。
- `AVX2`：门槛是 `AVX2`、`FMA`、`F16C`、`BMI1`、`BMI2` 同时具备。
- Arm 方面：`ARMV8A` 是基础 Armv8-A；`ARMV8A_HALFFP` 额外要求 `fullfp16`、`dotprod`、`crypto`、`crc`、`rdm`、`lse`（实际对应 Cortex A75/A55 及更新的核）；`ARMV9A` 再加 SVE2，手册标注"目前是实验性"。

### 运行时怎么挑变体

手册描述：构建时 Burst 在模块里生成一段分发（dispatch）代码，运行时检测当前 CPU，选出已编译的合适版本。适用范围是 x86/x64 桌面平台以及 Android 上的 64 位 Arm。`CPU Architecture` 这个设置只支持 Windows、macOS、Linux、Android。

手册给出的例子：CPU 只支持 SSE3 及以下时，Burst 自动选 `SSE2`。另有一句写明 x86/x64 在运行时只支持 `SSE2` 与 `SSE4` 两种指令集。但同一页的平台表又列了 AVX 与 AVX2 目标，这两句话如何对应（AVX2 变体是否真的会在运行时被选中）手册没有说清，待核实。想确认就在 Burst Inspector 里切换 Architecture 看生成的汇编，并在目标机器上实测。

### 取舍

| 做法 | 构建时间 | 包体 | 运行表现 |
| --- | --- | --- | --- |
| 只选 `SSE2` | 最短 | 最小 | 老 CPU 兼容最好，但用不到 SSE4 以上的指令 |
| `SSE2` + `SSE4`（默认） | 约两倍编译 | 约两份代码 | 现代 PC 基本都走 `SSE4` 版本 |
| 再加 `AVX2` | 再多一次编译 | 再多一份 | 支持的 CPU 上向量更宽，收益取决于代码能否向量化 |

"约两倍"是按手册"每个目标独立编译一次"推出的，不是测量值。对本项目这种体素 Job，建议先用默认值，需要时再用 Player 构建实测 `AVX2` 的收益。

## 平台支持矩阵

以下取自 1.8.31 手册的"Building your project"页（该页按宿主编辑器平台分行，下表只摘录 Windows 宿主下的行，macOS 与 Linux 宿主的差异见原页；原页还列有 Magic Leap 2 与 visionOS Simulator）：

| 目标平台 | 支持的 CPU 架构 | 外部要求 |
| --- | --- | --- |
| Windows | x86（SSE2、SSE4）、x64（SSE2、SSE4、AVX、AVX2） | 无 |
| macOS | x64（SSE2、SSE4、AVX、AVX2）、Apple Silicon | 无 |
| Linux | x64（SSE2、SSE4、AVX、AVX2） | 无 |
| Android | x86 SSE2、ARMv7（Thumb2、Neon32）、ARMv8 AArch64（含 `ARMV8A`、`ARMV8A_HALFFP`、`ARMV9A`） | Android NDK（用 Unity Hub 安装的；回退用 `ANDROID_NDK_ROOT`） |
| iOS / tvOS / visionOS | ARMv8 AArch64 | 构建 Xcode 工程需要 macOS 与 Xcode |
| UWP | x86、x64、ARM32、ARMv8 AArch64 | 总是编译四个目标；需要 Visual Studio 与 UWP 工作负载 |
| Xbox One / Series | x64 SSE4 / x64 AVX2 | Microsoft GDK |
| PlayStation 4 / 5 | x64 SSE4 / x64 AVX2 | PS4 SDK 8.00+ / PS5 SDK 2.00+ |
| Nintendo Switch | ARMv8 AArch64 | 无 |

注意事项：

- 手册注明主机等平台的"最大 CPU 目标"是写死的；只有桌面独立构建才能在 AOT 设置里自选目标。
- 不能使用 Burst 的工程：从 Linux 编辑器构建 Android；用 `Create Xcode Project` 选项生成的 Xcode 工程。
- Web（WebGL / WebAssembly）：平台表没有列出 Web，但更新日志里有线索：1.8.26 写有 "Enable Burst on Web Platform"，1.8.30 加入 Wasm64 目标并修复了"启用线程的 Web 平台不生成原子操作"。据此可判断 Web 上 Burst 已可用，但它的限制（线程、SIMD 等）我没有读到手册页面，待核实。更早的版本日志还提到过 WASM 的反汇编语法着色与 `Sleef` 数学回退，说明 Burst 对 WASM 的底层支持由来已久。
- 本项目是 PC 独立构建（Windows），表中这一行是你最关心的：无需外部工具链。

## 脚本后端：Mono 与 IL2CPP

- Unity 6.7 手册的 Burst 简介明确写到：Burst 不是完整的脚本后端，无法取代 Mono 或 IL2CPP，而是对两者的补充；脚本后端照常编译，Burst 只编译标记了的部分。
- 手册说非桌面平台的 Burst 编译"需要平台工具链（类似 IL2CPP）"，但没有说 AOT 必须搭配 IL2CPP。
- 更新日志 1.8.21 提到：Android 用 Mono 脚本后端时，arm64-v8a 符号可能被错误打进产物，因为 Mono for Android 只支持 armv7。这说明 Mono 后端下 Burst AOT 也会跑。
- 桌面独立构建在 Mono 后端下使用 Burst 是常见做法，但手册没有单独声明，待核实。
- 与 IL2CPP 的交互主要在函数指针：用 `BurstCompiler.CompileFunctionPointer` 的目标方法在 IL2CPP 下需要 `[MonoPInvokeCallback]`（更新日志多处提到缺失时的提示）。详见"函数指针与间接调用"一章。
- 1.8.29 修复：开启高强度托管代码裁剪（managed stripping）时，仅通过 `[BurstCompile]` 使用 Burst 可能被裁掉。如果在发布构建里发现 Burst 莫名消失，把裁剪级别作为排查项。

## 编辑器 JIT 设置与 Enter Play Mode Options

编辑器里的 Burst 设置在 `Jobs > Burst` 菜单（只影响编辑器）：

| 菜单项 | 作用 |
| --- | --- |
| `Enable Compilation` | 编辑器内 Burst 总开关 |
| `Enable Safety Checks` | `Off` / `On`（默认）/ `Force On`；重载编辑器后 `Off` 会复位为 `On` |
| `Synchronous Compilation` | 同步编译；默认是异步，编译完成前先跑 JIT 的托管版本 |
| `Native Debug Mode Compilation` | 关掉所有优化，便于原生调试器 |
| `Show Timings` | 在 Console 输出每个库的 JIT 编译耗时 |
| `Open Inspector` | 打开 Burst Inspector |

和 Enter Play Mode Options（关闭 Domain Reload）的关系：

- 官方 Burst 手册没有专门讲这个组合，我读到的页面里没有相关表述，所以这部分只能给出已知事实和推论，具体行为待核实。
- 已知事实一：Burst 在域重载后需要重新处理被改动的代码，更新日志多次优化了"域重载时的 Burst 初始化成本"（例如 1.8.1 的日志写到调整了域重载的处理方式，避免每次域重载付出约 250ms 的开销）。
- 已知事实二：1.8.18 修复过"设为同步编译时，域重载期间编辑器卡在加载"的问题。
- 推论：关闭 Domain Reload 后，进入 Play Mode 不再触发域重载，静态字段（包括普通 `static` 与 `SharedStatic`）里的值会跨次 Play 保留。这是 Unity 本身的行为，与 Burst 无关，但 Job 里依赖静态数据时要自己在进入 Play 时重置。参见"静态数据与 SharedStatic"一章。
- 如果怀疑是缓存导致的怪问题：更新日志记录过缓存相关的修复，例如项目被复制到别的目录或 Unity 升级后可能用到过期的缓存库（已修复），以及 PDB 缓存过期导致 Inspector 显示错误源码信息（已修复）。遇到无法解释的编辑器内异常，可以先重启编辑器；Burst 的编辑器缓存位于 `Library/Burst/JitCache`（路径来自更新日志对 PDB 位置的描述），是否需要手动清理没有官方说明，待核实。

## CI 与 batchmode 构建

可用的开关（均来自更新日志）：

- 命令行 `--burst-disable-compilation`：完全关闭 Burst。
- 命令行 `--burst-force-sync-compilation`：强制同步编译。
- 环境变量 `UNITY_BURST_DISABLE_COMPILATION`（1.8.18 加入），效果等同第一项；1.8.22 起它也会关闭 Burst 的 IL 后处理。

CI 上要注意的点：

1. 平台工具链：Android 要装对应 NDK（优先 Unity Hub 安装的，退而用 `ANDROID_NDK_ROOT`）；Apple 平台要 Xcode。缺工具链时 Burst 会被静默跳过，构建仍然成功。CI 上必须检查构建日志，确认有 Burst 的编译输出，并检查产物里存在 `lib_burst_generated`。
2. 警告：想屏蔽噪声可以在 AOT 设置的 `Disabled Warnings` 里填编号（分号分隔）；代码里可以用 `[IgnoreWarning(1370)]`。"把 Burst 警告当错误"有没有官方开关，我没有核实到，待核实；稳妥的做法是在 CI 里 grep 构建日志里的 `Burst error` 或 `BC1` 开头条目。
3. 多目标构建慢：每个 CPU 目标一次独立编译。CI 上若只验证流程，可以临时减少目标或用 `Fast Compilation`，但发布构建要用正式配置。
4. 符号文件：Embedded Linux 与 QNX 的 `BurstDebugInformation_DoNotShip` 文件夹按玩家构建目录名加前缀（1.8.23）。其它平台的符号输出位置待核实；发布时不要把这类目录打进包。
5. 1.8.30 修复了 Embedded Linux/QNX 用 Build Profiles 时在 batchmode 与 CI 中读取过期架构设置的问题。如果你的 CI 用 Build Profiles，请确认 Burst 版本不低于该修复。
6. 并发构建：更新日志提到过无头构建下，两个编译任务靠得很近时，Burst 缓存文件被锁住的罕见问题（已修复）。不要在同一个工程目录同时开两个 Unity 实例构建。

## Development Build 与 Release 的差异

| 项目 | Development Build | Release |
| --- | --- | --- |
| Burst 符号 | 会生成调试符号（调试页明确写：启用 `Development Build` 可得到符号） | 默认不带；开 `Force Debug Information` 可补上 |
| 优化 | 与 Release 相同，除非关了 `Enable Optimizations` | 相同 |
| 容器安全检查 | 编辑器才有；Development Build 是否定义检查符号待核实 | 无 |
| 异常（`throw`） | Player 里仍是 abort | 同左 |
| 原生调试 | 配合 `Debug = true` 或关优化可用 | 同左，但无符号需手动开 |

结论：Burst 本身的"优化级别"不随 Development / Release 变化，真正的差别是调试符号和脚本层的检查代码。所以用 Development Build 做性能分析大体可信，但要留意附带的 Profiler、Deep Profile 等因素。

## 构建失败时的表现与排查

典型表现有三类：

1. 构建成功但 Burst 没生效：目标无效被静默跳过、`Enable Burst Compilation` 被关、被裁剪掉。检查 Player 日志与构建日志，确认存在 Burst 库。
2. 构建报 Burst 编译错误（`Burst error BCxxxx`）：某个入口无法编译。Console 里能看到文件、行号和错误编号。编号含义见"常见编译错误与排错"一章。
3. 链接或工具链错误：例如 NDK 路径、Xcode 版本、桌面上开了 `Use Platform SDK Linker`。先关掉 `Use Platform SDK Linker` 恢复交叉编译，再对照平台要求。

排查路径：

```
构建结果异常
  |
  +-- 有 Burst error ?  --是--> 看编号和调用栈 -> 修代码 (见排错一章)
  |
  +-- 无报错但变慢 ?   --是--> 确认 lib_burst_generated 在 Plugins 下
  |                              确认 AOT 设置里 Enable Burst Compilation 为开
  |                              确认目标平台工具链齐全
  |
  +-- 仅某平台失败 ?   --是--> 对照平台表; 试 Fast Compilation 排除优化器问题
```

## 性能测试要用 Player 构建

编辑器里测出来的数字和 Player 差别很大，原因都能在上面找到：

- 编辑器默认异步编译，前几帧可能在跑托管版本，需要预热或开 `Synchronous Compilation`；手册建议计时时丢弃第一次调用，因为它包含编译时间。
- 编辑器里容器安全检查默认开着（`Enable Safety Checks` 为 `On`），Player 里没有。手册说 `Off` 可以得到"更接近真实的编辑器内性能数据"，但仍然不等于 Player。
- 编辑器里还有 Jobs Debugger、Leak Detection 等检查，Player 没有。
- 编辑器只用本机 CPU 的 JIT 结果，Player 是多目标 AOT 加运行时分发。

建议的测量流程：

1. 用 Release（非 Development）Player 构建，`Enable Burst Compilation`、`Enable Optimizations` 都开，`Force Debug Information` 关。
2. 固定 `Optimize For` 与 `Floating Point Mode`，避免在对比中悄悄变化。
3. 先跑若干帧预热，再计时。在目标硬件（含低端机）上跑，必要时在 Player 里用 `ProfilerMarker` 打点（Burst 里可以创建 `ProfilerMarker`）。
4. 要附带 Profiler 时用 Development Build，并记住 Profiler 与 Deep Profile 本身有开销，对比数据要用同一种构建。

## Burst 2.0.0 壳包后配置入口有变化吗

已确认的事实：

- 项目 `Library/PackageCache/com.unity.burst@626e66ab421b/package.json` 中 `version` 是 `2.0.0`，`type` 是 `shim`。
- `Packages/packages-lock.json` 里 `com.unity.burst` 与 `com.unity.collections` 的 `source` 都是 `builtin`（版本分别为 2.0.0 与 6.7.0）。
- 包里只有 `Runtime/TypeForwarders.cs` 与 `Unity.Burst.asmdef`；`TypeForwarders.cs` 把 `Unity.Burst` 下的 `BurstCompileAttribute`、`BurstCompiler`、`OptimizeFor`、`FloatMode`、`FloatPrecision`、`SharedStatic<>` 等，以及 `Unity.Burst.CompilerServices` 与 `Unity.Burst.Intrinsics` 下的类型转发到引擎内置模块。
- Unity 6.7（6000.7）手册已把 Burst 页面放进 Unity Manual（路径 `Script compilation > Burst compilation`），菜单页 `Jobs > Burst` 与 AOT 设置页 `Edit > Project Settings > Burst AOT Settings` 的入口与 1.8 一致，选项名仍是 `Enable Burst Compilation`、`Enable Optimizations`、`Force Debug Information`、`Optimize For`、`Floating Point Mode`、`Disabled Warnings`、`Stack Protector` 等。

与 1.8.31 手册的措辞差异（来自 6.7 手册，非 7000.0.0a8 本身）：

- AOT 设置页未列出 `Use Platform SDK Linker`，且 `Target Platform` 只提 `File > Build Profiles`。
- 平台页改名为"Platform build support reference"，对 iOS/tvOS/visionOS 的说明改为"可从其它宿主编译，但构建 Xcode 工程要 macOS 与 Xcode"。
- 平台表中仍没有 Web 一行。

无法核实的部分：7000.0.0a8 的实际界面和上述 6.7 手册是否完全一致，Web 平台限制是否有变化，壳包下 Burst 的缓存与更新日志机制是否变化，都待核实。结论：配置入口按 1.8 / 6.7 的位置找，遇到差异以编辑器实际界面为准。

## 常见坑

- 以为勾了 `[BurstCompile]` 发布版就一定快：目标平台工具链缺失或设置里关了 Burst，构建不报错却没有优化。
- 把 `Enable Optimizations` 关了做调试，忘了打开就发布。
- `Disabled Warnings` 是所有平台共享的，屏蔽后别忘了清理。
- 在编辑器里测完性能就下结论，Player 里行为不同。
- 选了很多 CPU 目标，构建时间翻倍却没测过收益。
- 在 CI 上没检查产物里是否存在 `lib_burst_generated`。
- 开着 `Use Platform SDK Linker` 提交构建配置，导致 CI 机器缺工具链而失败。

## 小结

- Player 用 AOT，生成 `lib_burst_generated`，设置只在 `Burst AOT Settings`；编辑器用 JIT，设置在 `Jobs > Burst`。
- 多 CPU 目标靠运行时分发选变体，代价是构建时间与包体；默认 `SSE2` + `SSE4` 够用。
- 目标无效时 Burst 静默跳过，CI 上必须检查产物与日志。
- 性能测试用 Release Player 构建，并预热。
- 壳包 2.0.0 的入口与 1.8 一致，细节差异以实机为准。

## 自测题

1. Burst AOT 的产物在 Windows 上叫什么，放在哪里？
   答：`lib_burst_generated.dll`，在 `Data/Plugins/` 下；运行时首次调用 Burst 方法时加载。
2. 在 Player 构建里有 `Enable Safety Checks` 选项吗？为什么？
   答：没有。更新日志说该选项不能真正打开容器安全检查，而容器检查只在编辑器存在，所以在 1.6.0-pre.3 被移除。
3. 构建 Android 但没有装 NDK，会发生什么？
   答：手册说无效目标时 Unity 不使用 Burst 但仍构建，所以构建不一定失败，但没有 Burst 优化。
4. 同时勾选 `SSE2` 与 `SSE4` 对构建和运行时分别有什么影响？
   答：构建要为两个目标各编译一次，库更大；运行时按 CPU 能力选版本，CPU 只支持 SSE3 及以下时选 `SSE2`。
5. 为什么编辑器里的计时不能代表 Player？
   答：异步编译与预热、容器安全检查、Jobs Debugger 等编辑器检查，以及 JIT 与多目标 AOT 的差异。
