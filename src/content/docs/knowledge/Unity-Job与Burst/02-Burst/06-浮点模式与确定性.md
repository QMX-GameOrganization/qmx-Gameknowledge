> 适用版本：以 Unity 6000.x 的 Burst 1.8.x / Mathematics 1.3.x 为主线（本章枚举含义取自 Burst 1.8.31 手册）；本项目 Unity 7000.0.0a8 的 Burst 2.0.0 为转发壳包，`FloatMode`、`FloatPrecision` 在 `TypeForwarders.cs` 中确认仍转发到 `Unity.Burst`。`FloatMode.Deterministic` 这个枚举值在很早的版本里就以"早期预览"形式出现，Burst 1.8 更新日志明确写到 1.8.25（2025-09-16）起 "`FloatMode.Deterministic` is now supported"，所以文中把它当作 1.8.25 及以后可用的正式模式。

## 要点

- `FloatMode` 决定编译器可以怎样"改写"你的浮点算式：`Strict`（默认）不重排；`Fast` 允许重排、融合与忽略特殊值；`Deterministic` 要求跨平台一致。
- `FloatPrecision` 决定 `sin`、`cos`、`exp`、`pow` 等数学函数的误差上限（ULP）。`Standard` 等同 `Medium`，约 3.5 ULP。
- 同一份浮点代码在 Mono、IL2CPP、Burst、x64、ARM 上可以相差几个 ULP。整数与位运算没有这个问题。
- 对"种子可复现世界"：核心随机性用整数哈希，浮点只做平滑插值，并用 golden test 锁住输出。
- Burst 支持 `double`，但 SIMD 宽度减半，吞吐大约降一半（原理推断，非手册数据，见下文）。

## FloatPrecision

ULP（unit in the last place）是相邻两个浮点数之间的间距，用来衡量数学函数结果的误差。

| 取值 | 精度（手册） | 说明 |
| --- | --- | --- |
| `Standard` | 3.5 ULP | 默认，等同 `Medium` |
| `High` | 1.0 ULP | 精度最高，可能更慢 |
| `Medium` | 3.5 ULP | |
| `Low` | 按函数而定 | 下列函数为 350 ULP，其余沿用 `Medium` |

`Low` 下 350 ULP 的函数：`math.sin`、`math.cos`、`math.exp`、`math.exp2`、`math.exp10`、`math.log`、`math.log2`、`math.log10`、`math.pow`（负底数配小数指数不支持）、`math.fmod`。这个模式用来换速度，只适合视觉效果，不适合需要复现的逻辑。旧版 API 里这个枚举叫 `Accuracy`。

## FloatMode

| 取值 | 含义（手册） |
| --- | --- |
| `Default` | 等同 `Strict` |
| `Strict` | 不重排计算，遵守 NaN、非规格化数（denormal）等特殊值 |
| `Fast` | 允许指令重排，可用专用或精度较低的硬件 SIMD 指令 |
| `Deterministic` | 保证 Burst 内浮点计算在所有支持的平台一致，仅 64 位架构支持 |

`Fast` 允许的典型变换（编译器行为，手册只概述为"重排与更低精度指令"）：

- 重结合：`(a + b) + c` 改成 `a + (b + c)`，这样才能把求和循环向量化，但改变了舍入。
- 乘加融合（FMA，fused multiply-add）：`a * b + c` 合成一条指令，只舍入一次。手册明确说 `Fast` 可以启用这类 mad 优化，精度可能不同。
- 假定没有 NaN 与 Inf，从而删除相关检查。若数据里真的有 NaN，结果不可预期。

`Deterministic` 的行为（手册）：

- 使用确定性的数学函数实现；
- 关闭会导致平台差异的浮点优化；
- 所有平台上把非规格化数刷成 0；
- 不保证 NaN 的位模式一致，只保证"是 NaN"；
- 可能有性能代价，大小取决于场景。

手册同时指出它的边界：只作用于 Burst 编译的代码；输入若本身含有非确定的浮点计算，则无法保证；把未设 Deterministic 的函数指针传进设了的代码，也会破坏确定性；硬件特定 intrinsics 同样可能破坏确定性。

## 设置位置

```csharp
using Unity.Burst;
using Unity.Jobs;

// 1) 在单个 Job 上
[BurstCompile(FloatPrecision.High, FloatMode.Deterministic)]
public struct TerrainJob : IJobParallelFor
{
    public void Execute(int index) { /* ... */ }
}

// 2) 命名参数写法，只改其一
[BurstCompile(FloatMode = FloatMode.Fast)]
public struct ParticleJob : IJob
{
    public void Execute() { }
}

// 3) 整个程序集的默认值
// [assembly: BurstCompile(FloatMode = FloatMode.Deterministic)]
```

程序集级写法见手册 "Defining Burst options for an assembly"（本文未逐字核实示例，待核实）。静态方法与函数指针也用同样的属性参数。

Burst Inspector 上没有 `FloatMode` 与 `FloatPrecision` 的开关（1.8.31 手册的显示选项里没有列出），它们只通过属性设置。（Inspector 是否在 Burst 2.0 增加了此类开关待核实。）旧属性 `BurstCompilerOptions.EnableFastMath` 已弃用，改用 `FloatMode.Fast`。

## 为什么同一段浮点代码会不一样

下面是行业通用的原理，手册只给出结论性的描述，具体平台行为依赖编译器与硬件。

| 来源 | 机制 |
| --- | --- |
| FMA 融合 | `a*b+c` 若被编译成 FMA，只舍入一次，结果与"先乘后加"（两次舍入）不同。有的 CPU 或编译选项融合，有的不融合 |
| 浮点宽度 | 老式 x87 用 80 位中间精度；现代 x64 默认用 SSE 的 32/64 位。不同运行时选择不同 |
| 超越函数实现 | `sin`、`cos`、`exp`、`pow` 在 .NET 的 `Math`、Burst 内置实现、平台 libm 里算法不同，只保证一定 ULP 内正确，不保证逐位相同 |
| 向量化改变求和顺序 | 浮点加法不满足结合律，把循环按 4 或 8 路并行累加，再合并，总和与顺序累加不同。`Strict` 下 Burst 不会这样做，`Fast` 会 |
| 非规格化数处理 | 有的平台把极小数刷成 0，有的保留 |
| 浮点转整数 | `(int)` 对越界或 NaN 的结果在 x86 与 ARM 上不同（C# 规范认为这是未指定行为） |

不会漂移的内容：整数加减乘、位移、异或、与或、比较。无符号整数溢出回绕（`unchecked`）在所有平台上语义一致。

## 双精度 double

- Burst 支持 `double`、`double2/3/4`（`Unity.Mathematics`），`math.floor`、`math.sqrt` 等都有 `double` 重载。
- 128 位寄存器能放 4 个 `float` 但只能放 2 个 `double`；AVX 下 256 位为 4 个 `double`。所以同样的向量化循环，`double` 吞吐约为 `float` 的一半（结论来自寄存器宽度，非手册数据）。内存带宽也翻倍。
- `double` 不会因此自动更"确定"。FMA、重排等问题同样存在，只是误差更小，让问题更不容易暴露。
- GPU、部分移动端 ARM 对 `double` 支持差；Burst 路径下的 CPU `double` 一般没问题，但要在目标平台实测。

## 种子可复现世界的实践建议

1. 核心随机性用整数哈希：坐标和种子经过 `uint` 乘法、异或、移位得到格点值，整数运算在所有平台逐位相同。
2. 浮点只用于平滑插值：把哈希结果转成浮点后，只做乘、加、减、比较这类 IEEE 754 要求"正确舍入"的基本运算（单次舍入，结果唯一）。
3. 避免依赖超越函数（`sin`、`cos`、`exp`、`pow`、`log`）。需要时用查表（整数索引）或多项式近似，自己写并锁死运算顺序。
4. 浮点转整数前先 `floor`，再转 `int`，并保证值在 `int` 范围内：`floor` 本身是精确的，但越界转换是未指定行为。体素坐标一般远小于 2^31，把输入范围作为约定写进注释或断言。
5. 相邻区块要在不同线程、不同路径（编辑器 Mono 对 Burst）算同一个格点，得到逐位相同的值。因此区块边界的采样必须用全局世界坐标，调用同一份代码，不要在两个实现里各写一遍。
6. 整个生成流程的 Burst 代码设 `FloatMode.Strict`（默认）或 `Deterministic`，不要用 `Fast`。`Fast` 允许重排和融合，会让"同一份代码在编辑器与玩家里不同"。
7. 加 golden test：固定种子，采样一批坐标（含负坐标、区块边界、大坐标），把结果的位模式做哈希，保存在测试里。

```csharp
using NUnit.Framework;
using System;

public class NoiseGoldenTests
{
    // 固定种子 + 固定坐标集，把 double 的原始位模式混进 FNV-1a 哈希
    static ulong HashSamples(Func<int, int, int, double> sample)
    {
        ulong h = 14695981039346656037UL;
        for (int x = -64; x <= 64; x += 7)
        for (int y = 0; y < 256; y += 13)
        for (int z = -64; z <= 64; z += 7)
        {
            ulong bits = (ulong)BitConverter.DoubleToInt64Bits(sample(x, y, z));
            h = (h ^ bits) * 1099511628211UL;
        }
        return h;
    }

    [Test]
    public void SeedIsReproducible()
    {
        // 首次运行把 expected 记录下来并写进测试（此处的数值仅为占位）
        const ulong expected = 0UL;
        ulong actual = HashSamples((x, y, z) => 0.0 /* 替换为被测采样函数 */);
        Assert.AreEqual(expected, actual);
    }
}
```

逐位哈希适合"整数哈希 + 简单插值"的路径；一旦必须用超越函数，就改成容差比较（例如 `Assert.AreEqual(a, b, 1e-9)`），并明确这条路径不承诺跨平台逐位相同。

## 本项目对照

只分析，不改代码。涉及文件在 `D:\UnityHub\Project\程序化生成\Assets\Scripts\WorldGen\Density\`。

### ValueNoiseFunction.cs

- 第 24 到 26 行：`context.X * scale`，`int` 乘 `double`。`int` 到 `double` 转换是精确的，乘法单次舍入，本身确定。
- 第 27 行与第 50 行：`FloorToInt` 的实现是 `(int)Math.Floor(value)`。`floor` 是精确运算，没有舍入差异；风险在转换边界：当 `x * scale` 超出 `int` 范围或为 NaN，C# 下结果未指定，x86 与 ARM 可能不同。当前调用方限制了频率与坐标，正常世界范围内不会触发，迁移到 Burst 时建议显式 `math.floor` 加范围约束，或用 `(long)` 兜底。
- 第 28 行：`Smooth(x - x0)` 里 `x0` 是 `int`，`x - x0` 先转 `double` 再减，精确且确定。
- 第 37 到 49 行 `Lattice`：`uint` 乘法、异或、移位，在 `unchecked` 下语义完全确定。这是整个文件里最可靠的部分，对应上文第 1 条。最后一步 `h / (double)uint.MaxValue * 2.0 - 1.0` 是 IEEE 除法和乘减，单次舍入、结果唯一，确定。
- 第 51 行 `Smooth`：`value * value * (3.0 - 2.0 * value)` 含 `3.0 - 2.0*value` 这类"乘后加减"结构，第 52 行 `Lerp` 的 `a + (b - a) * t` 也是典型的 FMA 候选。在 `Strict` 下不应融合（待核实 Burst 在 `Strict` 下对 `fp-contract` 的具体处理）；若开 `Fast` 则融合与否由编译器决定，同一份代码在不同 CPU 上可能不同，这是迁移后最需要锁住的风险点。
- 第 29 到 35 行：三线性插值，求和顺序在源码里固定。若 Burst 以 `FloatMode.Fast` 把相邻运算打包成 SIMD，顺序可能变。

### OctaveNoiseFunction.cs

- 第 15 行：`Math.Pow(2, octaves - 1)` 只用于构造时的合法性检查，不进入采样。底数为 2 的整数次幂在大多数实现中是精确的，但 `pow` 的精确性不由规范保证，换成 `1 << (octaves - 1)` 可彻底消除这个依赖。
- 第 21 行：`unchecked(seed + i * 1013)`，整数运算，确定。
- 第 22 到 24 行：`weight *= 0.5` 与 `frequency *= 2` 是 2 的幂次缩放，二进制浮点下精确，无舍入误差。`weightSum` 累加的是 2 的幂，也是精确的。
- 第 29 到 31 行：`foreach` 顺序累加各层再除以 `weightSum`。顺序固定，所以确定；如果迁移后把各层改成并行计算再合并，或在 Burst 里被重排，总和会变。保持顺序累加，或在 `Deterministic` 下实现。

### 迁移到 Burst 的关注点汇总

| 位置 | 风险 | 建议 |
| --- | --- | --- |
| `FloorToInt` | 越界或 NaN 转 `int` 未指定 | 限制输入范围，转换前断言 |
| `Smooth`、`Lerp` | FMA 融合差异 | 用 `Strict` 或 `Deterministic`，禁用 `Fast` |
| 多层累加 | 求和顺序 | 固定顺序，不并行合并 |
| `Math.Pow` | 库实现差异 | 换成位移（仅校验用） |
| 全局 | Mono 与 Burst 逐位对比 | golden test，必要时设 `FloatMode.Deterministic` |
| 迁移后是否保持 `double` | 吞吐减半 | 先保持 `double` 保证与现有结果一致，稳定后再评估 `float` |

## 常见坑

- 以为开了 `Deterministic` 就万事大吉：它只管 Burst 编译的代码，托管侧的浮点输入、函数指针边界、intrinsics 都可能破坏它。
- 在编辑器里用 Burst、在玩家里用 IL2CPP 非 Burst 路径（比如回退路径），同一世界种子生成出不同地形。
- 用 `Fast` 提速后，区块边界出现肉眼可见的接缝：相邻区块的同一格点经不同的指令序列算出，差了一个 ULP，再经过阈值比较翻转了方块。
- 用 `==` 比较浮点结果做测试；应该比较位哈希或带容差。
- 对 `NaN` 做位级比较：`Deterministic` 也不保证 NaN 位模式一致。

## 小结

`FloatPrecision` 管数学函数的误差，`FloatMode` 管编译器能怎样改写算式。可复现的世界要靠整数哈希，把浮点限制在单次舍入的基本运算上，避免 `Fast`，并用 golden test 守住输出。本项目的 `ValueNoiseFunction` 与 `OctaveNoiseFunction` 基本符合这个模式，迁移时的关注点集中在 `FloorToInt` 边界、FMA 融合与累加顺序。

## 自测题

1. `FloatPrecision.Standard` 等同哪个取值，约多少 ULP？答：`Medium`，3.5 ULP。
2. `FloatMode.Fast` 为什么可能让求和结果改变？答：它允许重排，浮点加法不满足结合律，向量化后的累加顺序不同；还可能启用 FMA。
3. 为什么整数哈希适合做种子噪声的核心？答：整数运算与位运算在所有平台上语义一致，没有舍入问题。
4. `FloatMode.Deterministic` 是否保证 NaN 位模式一致？答：不保证，只保证结果是 NaN。
5. 写 golden test 时，逐位哈希与容差比较各适合什么场景？答：纯整数哈希加基本浮点运算的路径用逐位哈希；使用超越函数的路径用容差。
