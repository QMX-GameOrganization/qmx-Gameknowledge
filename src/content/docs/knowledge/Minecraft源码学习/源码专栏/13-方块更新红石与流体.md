## 要点

- 世界生成结束后，游戏转入**事件驱动**的运行时：方块变化 → 通知邻居 → 邻居自己决定要不要变 → 需要“过一会儿再变”就**调度一个计划刻**。几乎所有机制（红石、流体、植物生长、下落方块）都挂在这三样东西上。
- 通知有两种：**`neighborChanged`**（“邻居变了”，邻居自己决定后续）和 **`updateShape`**（“形状更新”，邻居返回自己的新状态，由调用方写回）。
- 通知的传播不是直接递归，而是**排进一个显式的栈**（`CollectingNeighborUpdater`，深度优先），防止深度递归爆栈，也给出了统一的数量上限。
- 红石导线用的是“**每格衰减 1 的信号强度**”加上“**临时关掉自己的信号再重新取邻居最大值**”的小技巧；准连接、更新顺序方向性这些著名现象，在源码里都能找到原因。
- 水与岩浆是同一套 `FlowingFluid` 代码，区别只在三个数字：**tickDelay、dropOff、slopeFindDistance**。
- 世界生成直接写区块、绕过了所有通知，所以对流体要**事后补一次更新**（`markPosForPostprocessing`）。

## setBlock：一次方块变化发生了什么

`Level.setBlock(pos, state, flags, depth)` 的 `flags` 是一组位标志：

| 值 | 名字 | 含义 |
| --- | --- | --- |
| 1 | `UPDATE_NEIGHBORS` | 通知 6 个邻居（`neighborChanged`） |
| 2 | `UPDATE_CLIENTS` | 把变化发给客户端 |
| 4 | `UPDATE_INVISIBLE` | 客户端不重绘 |
| 16 | `UPDATE_KNOWN_SHAPE` | 不做形状更新 |
| 32 | `UPDATE_SUPPRESS_DROPS` | 破坏时不掉落 |
| 64 | `UPDATE_MOVE_BY_PISTON` | 由活塞移动引起 |

常用组合：`3 = 1+2`（`UPDATE_ALL`）；`11 = 1+2+8`（`UPDATE_ALL_IMMEDIATE`，8 为 `UPDATE_IMMEDIATE`）；`20 = 16+4`（世界生成后处理用的，不通知邻居、不触发形状更新）。

执行顺序（简化）：

```java
// Level.setBlock
chunk.setBlockState(pos, newState)       // ① 旧状态 onRemove，新状态 onPlace（仅服务端）
if (flags & 2)  sendBlockUpdated(...)     // ② 同步给客户端
if (flags & 1)  blockUpdated(...)         // ③ 6 个邻居 neighborChanged；有模拟输出的再 updateNeighbourForOutputSignal
if (!(flags & 16) && depth > 0) {         // ④ 形状更新，flags 先清掉 1 和 32（& -34）
    old.updateIndirectNeighbourShapes(...); new.updateNeighbourShapes(...); new.updateIndirectNeighbourShapes(...);   // depth - 1
}
```

`depth` 默认来自 `Block.UPDATE_LIMIT = 512`：形状更新每传播一层减 1，到 0 停止。

### neighborChanged 与 updateShape

| | `neighborChanged` | `updateShape` |
| --- | --- | --- |
| 语义 | “我旁边的方块变了，你自己看着办” | “根据你旁边新的状态，你应该变成什么” |
| 返回值 | 无，方块自己 `setBlock` / `scheduleTick` | 返回自己的**新 BlockState**，调用方写回 |
| 邻居顺序 | `W, E, D, U, N, S` | `W, E, N, S, D, U` |
| 典型用途 | 红石导线、活塞、门的开关 | 栅栏 / 墙 / 楼梯的连接形状，**观察者的触发** |

两个顺序不同，这就是红石装置有“方向性”的根源之一：先通知谁、后通知谁，决定了同一个 tick 内的状态变化顺序。

### 通知不是递归的：CollectingNeighborUpdater

`Level` 创建的是 `CollectingNeighborUpdater`：更新请求先压进一个显式的栈，由最外层的调用统一循环执行。执行某个请求时产生的新请求先收集起来，**当前这一步返回后立刻压到栈顶**，先于同一次多邻居通知里尚未通知的方向执行。本质上是把递归改成了带显式栈的深度优先遍历。

```java
// 简化
stack.push(第一个请求)
while (stack 非空 && count < maxChainedNeighborUpdates) {      // 默认 1_000_000
    req = 取当前层下一个请求;  req.runNext(level);  count++
    // 这个请求里又调用了 setBlock → 新请求进入 addedThisLayer，这一步返回后压栈顶，先于被挂起的其余方向执行
}
超过上限：丢弃剩余请求并记录错误；整条最外层链结束后 count 清零（上限针对“一条连锁更新”，不是每个游戏刻）
```

对比 `InstantNeighborUpdater`（直接递归执行）：用显式栈的好处是**不会在极长的红石链上爆栈**，并且有统一的“一条连锁最多处理多少次”的熔断（服务器属性 `max-chained-neighbor-updates`，默认 1000000）。代价是新通知被**延后到当前这一次通知返回之后**才执行，而不是在调用点立刻递归发生，这会影响红石元件的更新顺序。

## 计划刻与随机刻

### 计划刻（scheduled tick）

“过 N 个游戏刻之后再检查一次这个位置”。方块和流体各有一个容器：`blockTicks`、`fluidTicks`。

| 概念 | 说明 |
| --- | --- |
| `ScheduledTick` | `(类型, 位置, 触发时刻, 优先级, 序号)`，按“触发时刻 → 优先级 → 序号”排序 |
| `TickPriority` | `EXTREMELY_HIGH(-3) … NORMAL(0) … EXTREMELY_LOW(3)`，同一刻内数值小的先执行 |
| `LevelChunkTicks` | 每个区块一份：`PriorityQueue` + 一个“同类型同位置”集合去重，所以重复调度同一个位置不会排两份 |
| `LevelTicks` | 汇总所有区块的容器，每个游戏刻 `tick(当前时刻, 65536, 执行器)`：收集到期的计划刻、执行、清理，**单刻最多处理 65536 个** |

“事件驱动”的好处在这里最明显：一个红石中继器不需要每刻检查自己，只在输入变化时调度一次 `tick`；水只在邻居变化时才调度下一次流动。**没有变化的地方不消耗任何计算。**

### 随机刻

每个游戏刻，对每个“正在随机刻的区块段”（`LevelChunkSection.isRandomlyTicking`，即段内含有会随机刻的方块），取 `randomTickSpeed` 次（默认 3）随机位置，对该位置的方块和流体各调用一次 `randomTick`。作物生长、树叶凋落、草蔓延、冰雪覆盖都靠它。随机刻的特点是**不精确的、统计意义上的速率**，所以生长速度表现为“平均每多少分钟”。

### ServerLevel 每刻的执行顺序

```text
世界边界、天气 → 睡眠与时间
→ 方块计划刻 (blockTicks) → 流体计划刻 (fluidTicks)       // 各最多 65536 个
→ 袭击
→ chunkSource.tick：区块加载 / 刷新生物 / 随机刻 (tickChunks)
→ runBlockEvents                                           // 活塞、音符盒等“方块事件”
→ 实体
→ 方块实体
```

这个顺序解释了很多红石现象：计划刻先于实体，方块事件（活塞推动）在计划刻之后、实体之前。

## 红石：几个元件的实现

红石没有专门的“电路引擎”，每个元件就是一个普通方块，靠 `neighborChanged` / `updateShape` / 计划刻互相驱动。

| 元件 | 机制 | 关键数字 |
| --- | --- | --- |
| 红石粉（`RedStoneWireBlock`） | 信号强度 `POWER` 0~15，每走一格减 1 | 16 档，衰减 1 |
| 中继器（`RepeaterBlock`） | 输入变化时调度一个计划刻，延迟后再改输出 | 延迟档位 × 2 个游戏刻 |
| 红石火把（`RedstoneTorchBlock`） | 输入变化时延迟 2 刻翻转；短时间翻转过多会烧毁 | 60 刻内 ≥ 8 次翻转即烧毁；160 刻后恢复 |
| 观察者（`ObserverBlock`） | 在 `updateShape`（而不是 `neighborChanged`）里检测前方方块变化，发出脉冲 | 调度 2 刻后通电，再 2 刻后断电 |
| 活塞（`PistonBaseBlock`） | `neighborChanged` → `checkIfExtend` → 计算能推哪些方块 → 发出**方块事件** → `triggerEvent` → `moveBlocks` | 最多推动 12 个方块 |

### 红石粉：信号强度的计算

```java
// RedStoneWireBlock.updatePowerStrength（简化）
target = calculateTargetStrength(pos);
if (target != 当前 power) {
    setBlock(pos, power = target, flags = 2);                 // 只通知客户端
    for (自己 + 6 个邻居位置) level.updateNeighborsAt(...);    // 通知邻居重新计算
}

calculateTargetStrength(pos):
    shouldSignal = false;                                      // 临时关掉：导线不去读自己和别的导线的信号
    best = getBestNeighborSignal(pos);                         // 红石块、火把、中继器等“真信号源”
    shouldSignal = true;
    for 每个水平方向: 取相邻的导线（包括上一格、下一格，规则取决于中间是不是实心块）
        best = max(best, 邻居 power - 1);                      // 每格衰减 1
    return best;
```

“**临时关掉 `shouldSignal`**”是一个很实用的小技巧：计算目标强度时，导线读取周围信号源，如果读到了自己（或别的导线）刚输出的值，会形成循环；先让导线对外“静音”，再统一用 `max(邻居) − 1` 的规则读取，保证结果与读取顺序无关。

### 准连接与更新顺序

两个著名现象在源码里都能找到直接原因：

- **准连接（quasi-connectivity）**：`PistonBaseBlock.getNeighborSignal` 除了检查自己 6 个面是否受电，还检查**自己上方一格**的 5 个方向。所以活塞可以被“斜上方”的信号推动，而且只有在发生 `neighborChanged`（或 `onPlace`）时才会重新检查，这就是“需要方块更新才生效”的原因。
- **更新顺序的方向性**：`neighborChanged` 的邻居顺序固定为 `W, E, D, U, N, S`，`updateShape` 为 `W, E, N, S, D, U`。同一个信号源变化时，哪个邻居先收到通知，决定了同刻内不同机器的先后，装置会表现出“方向敏感”。

### 为什么大型红石机器会卡

每次状态变化会通知 6 个邻居，邻居变化又继续通知；导线更新还会对自己加 6 个邻居全部再通知一遍。链越长、元件越多，**一个信号变化引发的更新数就线性甚至平方增长**。源码里的熔断（单条连锁更新最多 100 万次相邻更新、单刻计划刻 65536 个）是防止服务器被拖死的保险丝，而不是为了限速。

## 流体：水与岩浆

水和岩浆共用同一份算法 `FlowingFluid`，行为差异只来自三个数字：

| | tickDelay（每步间隔） | dropOff（每格减少的 amount） | slopeFindDistance（找落点的距离） |
| --- | --- | --- | --- |
| 水 | 5 刻 | 1 | 4 |
| 岩浆·下界 | 10 刻 | 1 | 4 |
| 岩浆·主世界 | 30 刻 | 2 | 2 |

流体用一个 `amount`（1~8）表示高度：源方块 `amount = 8`，流动方块 1~7，另有一个 `falling` 标志表示正在下落。

![流体在平地上的扩散](/qmx-Gameknowledge/assets/mc-source/22-fluid-spread.png)

平地上每向外一格 `amount` 减去 `dropOff`，减到 0 就停：水能流 7 格，下界岩浆也是 7 格，主世界岩浆只能流 3 格（8→6→4→2）。这就是“岩浆流得又慢又短”的全部原因。

### 一次流体 tick

```java
// FlowingFluid.tick（简化）
if (不是源方块) {
    new = getNewLiquid(pos);                 // 根据周围重新算自己应该是什么
    delay = getSpreadDelay(...);
    if (new 为空)       setBlock(pos, AIR, 3);
    else if (new != 当前) { setBlock(pos, new, 2); scheduleTick(pos, delay); updateNeighborsAt(pos); }
}
spread(pos);                                 // 无论是不是源，都尝试向外流
```

```java
spread(pos):
    below = pos.below()
    if (能流进下方)  { spreadTo(below, 下落流体);  if (周围源 >= 3) spreadToSides() }
    else if (自己是源 || 脚下不是“水洞”)  spreadToSides()
spreadToSides: amount = 当前 amount - dropOff; if (falling) amount = 7;
    只向 getSpread() 选出的方向流：在 slopeFindDistance 范围内找最近的落点，优先朝它流
```

关键点：

- **`getNewLiquid` 是“拉”而不是“推”**：每个流动方块的状态由它自己的邻居决定（取水平邻居最大 `amount − dropOff`，上方有同类流体则为满高的下落流体），不是由源“推”出去的。源被拿走后，下游会在后续 tick 里依次自己萎缩。
- **无限水源**：流动方块周围至少 2 个水源，且脚下是实心块或水源，就变成水源（`getNewLiquid` 里的 `j >= 2` 判断，受 `waterSourceConversion` 规则控制，默认开）。岩浆默认关。
- **遇水成石**：`LiquidBlock.shouldSpreadLiquid` 在岩浆邻接水时把岩浆源变成黑曜石、流动岩浆变成圆石；脚下是灵魂土且邻接蓝冰时变玄武岩。
- **调度**：`LiquidBlock.onPlace` / `neighborChanged` 里调用 `scheduleTick(pos, fluid, tickDelay)`，所以流体只在变化时才计算，稳定的湖面不消耗任何 tick。

## 与世界生成的衔接：后处理

世界生成往 `LevelChunkSection` 里直接写方块，**绕过了 `onPlace`、`neighborChanged` 和计划刻**。如果不处理，贴着空气或洞穴的水面会“冻结”，永远不会流。解决办法是后处理：

```java
// 生成时（NoiseBasedChunkGenerator.doFill / SurfaceSystem）
if (含水层说该位置需要更新 && 方块带流体)  chunk.markPosForPostprocessing(pos);

// 区块变成可玩区块前（LevelChunk.postProcessGeneration）
for (每个标记的位置) {
    fluidState = 方块.getFluidState();
    if (!fluidState.isEmpty())      fluidState.tick(level, pos);          // 直接跑一次流体更新，后面会自己调度
    if (!(方块 instanceof LiquidBlock)) {
        state = Block.updateFromNeighbourShapes(方块, level, pos);        // 非流体方块补一次形状更新（比如水生植物）
        level.setBlock(pos, state, 20);                                    // 20 = 16 + 4：不通知邻居、不触发形状更新
    }
}
```

- 标记的来源不止一处：噪声填充、地表规则、雕刻器（`WorldCarver`）、地物（`Feature`）、结构（`StructurePiece`）写入流体时都会标记；
- 噪声填充里 `Aquifer.shouldScheduleFluidUpdate` 在**远离水体边界的深处为 false**（最近两个中心距离差很大，`similarity` 低于一个阈值），在边界附近以及需要岩壁判定的位置多数为 true，所以湖心的水不标记，省掉了大部分后处理；
- 地表规则阶段 `SurfaceSystem` 只要写入的方块带流体（`BlockColumn.setBlock` 里的判断）就无条件标记；
- 标记用的是 `ShortList[]`，每个区块段一份，位置打包成 `x | y<<4 | z<<8`，很紧凑。

## 设计思想与优化

| 设计 | 解决的问题 |
| --- | --- |
| **事件驱动 + 计划刻** | 不轮询：没有变化的方块完全不耗时；“延迟”本身就是游戏机制（中继器、流体速度） |
| **显式栈（`CollectingNeighborUpdater`）** | 把深度递归改成带显式栈的循环，避免爆栈，并给出可统一熔断的计数 |
| **计划刻按区块存、同位置去重** | 区块卸载时它的计划刻一起卸载；反复调度同一位置不会膨胀 |
| **`flags` 位标志** | 一个函数覆盖“是否通知邻居 / 客户端 / 形状更新 / 掉落”的所有组合，调用方按需关掉不必要的传播（如世界生成用 20） |
| **形状更新与邻居通知分离** | 纯外观（连接形状）与有逻辑的响应（红石）各走各的通道，前者可被 `UPDATE_KNOWN_SHAPE` 整体跳过 |
| **随机刻按段、按次数抽样** | 作物和草的生长不需要逐方块计时 |
| **上限（单刻计划刻 65536、单条更新链 100 万）** | 防止恶意或意外的大型机器拖垮服务器 |

## 给 Unity 项目的取舍

世界生成做完以后，如果你要做“活”的世界（水流、植物、机关），建议按这个顺序：

1. **先只做计划刻队列**：`Schedule(pos, delay, kind)`，用最小堆或按到期时刻分桶的列表；同位置同类型去重。
2. **再做 `setBlock` + 邻居通知**：先只通知 6 个邻居，并用队列分层处理，**不要用递归**。
3. **流体用 `amount` 模型**：一个 `byte` 表示高度，`getNewLiquid`（从邻居拉取）+ `spread`（向下优先、再向侧面）。先做水，再用同一份代码加岩浆（三个参数不同）。
4. **红石晚点做**：先做“有信号 / 无信号”的二值元件，等更新队列稳定了再加 0~15 的强度。
5. **区块生成后补一次更新**：生成阶段不要触发更新，只把“需要更新的流体位置”记下来，等区块变成可玩时统一处理。

## 小结

- 方块变化 = `setBlock` → 邻居通知（队列化）+ 形状更新 + 计划刻；红石和流体都是在这三样之上写的普通方块逻辑。
- 计划刻按“时刻 → 优先级 → 序号”排序，每个区块一份并去重；随机刻按段抽样。
- 红石粉每格衰减 1，用“暂时静音自己”避免读到自己；中继器 / 火把 / 观察者 / 活塞各有明确的刻数。
- 水与岩浆共用 `FlowingFluid`，差别只有 tickDelay、dropOff、slopeFindDistance；世界生成写入的流体需要事后补更新。

参考答案：① 前者无返回值、邻居自己决定后续，后者返回邻居的新状态；邻居顺序也不同（`W,E,D,U,N,S` 与 `W,E,N,S,D,U`）。② 形状更新会递归地改变邻居并再触发形状更新，`depth` 从 512 递减作深度上限；邻居通知排进 `CollectingNeighborUpdater` 的显式栈，循环处理，并有总数上限。③ 岩浆在主世界 `dropOff = 2`，`amount` 从 8 每格减 2，到第 4 格变成 0。④ 生成时直接写区块，绕过 `onPlace` 和计划刻，流体不会自己开始流动；后处理补一次流体 tick。⑤ 同一个火把位置在 60 刻内被记录到翻转 8 次，就会烧毁，之后 160 刻恢复。
