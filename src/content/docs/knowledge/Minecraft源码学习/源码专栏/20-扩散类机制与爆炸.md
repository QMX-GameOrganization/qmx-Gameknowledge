> 对应源码（`world/level/` 下）：`Explosion`（及 `ExplosionDamageCalculator`）、`block/SculkSpreader`、`SculkBlock`、`SculkBehaviour`、`SculkCatalystBlockEntity`、`block/LeavesBlock`、`SpreadingSnowyDirtBlock`（草、菌丝）、`VineBlock`、`FireBlock`、`FallingBlock`、`SnowLayerBlock`。**没有读**：`SculkVeinBlock`、`MultifaceSpreader`、`VibrationSystem`、`EntityBasedExplosionDamageCalculator`，本页涉及它们的地方只说明接口，不展开。

## 要点

- 前面几页讲的是“一次生成完”的东西；这一页讲**运行时慢慢扩散**的东西：草、藤、火、幽匿、叶子衰减、重力方块。它们共同的问题是：**一个世界里有几十万个潜在的变化点，怎么保证每刻只做很少的工作？**
- 源码的回答有三类：**随机刻**（每个区块段每刻随机抽几个方块，见第 13 页）、**预约刻**（只有在条件变化时才排一个未来的 tick）、**游标**（用一个有限的、带预算的对象在世界里走，幽匿就是这样）。
- **爆炸**是反过来的：一次瞬间发射 1352 条射线，用“剩余强度”递减，累计出要破坏的方块集合。
- 看完这一页应该能回答：为什么叶子要几十秒才掉光？为什么火有时烧得很快有时自己熄灭？为什么幽匿最多只有 32 个游标？为什么 TNT 在石头里只能炸出很小的坑，在黑曜石里几乎什么也炸不掉？

## 三种驱动方式

| 方式 | 谁触发 | 例子 | 每刻成本 |
| --- | --- | --- | --- |
| 随机刻 | 区块段按 `randomTickSpeed`（默认 3）随机抽方块 | 草蔓延、藤蔓生长、叶子衰减、作物、雪融化 | 与方块数无关，只与“抽几次”有关 |
| 预约刻 | 方块变化时 `scheduleTick(pos, block, 延迟)` | 重力方块下落、火的下一次结算、叶子距离重算 | 只在有事发生时才有 |
| 游标 | 事件创建一个对象，每刻更新它 | 幽匿电荷 | 与游标数成正比，上限 32 |

第 13 页已经讲过随机刻和预约刻的底层；这一页看它们**被拿来做什么**。

## 爆炸：1352 条射线

### 射线从哪里发出

```java
// Explosion.explode（简化）
for j, k, l in 0..15:                       // 16×16×16 的格点
    if (j, k, l 中至少一个是 0 或 15):         // 只取立方体的表面：16³ − 14³ = 1352 个格点
        dir = normalize((j/15·2 − 1, k/15·2 − 1, l/15·2 − 1))
        h = radius · (0.7 + 0.6·nextFloat())  // 每条射线的初始强度：0.7 ~ 1.3 倍半径
        pos = 爆心
        while (h > 0):
            res = 方块爆炸抗性（空气没有）
            if res 存在:  h −= (res + 0.3) · 0.3
            if (h > 0 && 方块可炸):  set.add(pos 所在方块)
            pos += dir · 0.3
            h −= 0.225                       // 每步固定衰减
```

三个要点：

1. **射线方向来自立方体表面的网格，再归一化**，所以方向在球面上不是均匀分布的。我在移植里对比过 1352 条均匀球面方向：半径 4 的爆炸在泥土里平均炸掉约 244 格，均匀方向是约 235 格，差别不大，说明这个不均匀对结果影响很小（100 次平均）。
2. **每条射线独立的随机强度**（0.7~1.3 倍半径），所以同一次爆炸的坑边缘是毛糙的，不会是完美的球。
3. **步长 0.3 格**，每走一步固定扣 0.225，所以空气中的最大射程约是 `1.3 · radius / 0.225 · 0.3 ≈ 1.73 · radius` 格；加上方块阻力，实际范围更小。泥土（抗性 0.5）每步多扣 `(0.5 + 0.3) · 0.3 = 0.24`，约一半射程。

![爆炸的射线与破坏范围](/qmx-Gameknowledge/assets/mc-source/37-explosion-rays.png)

图是用同一份算法移植后的统计结果（颜色 = 150 次模拟中该格被炸掉的概率；爆心的空气格也算进集合，所以黑曜石里计数为 1）。可以看到：

- 泥土（抗性 0.5）里半径 4 的 TNT 炸出一个直径约 7 格的坑，边缘有概率渐变；
- 石头（抗性 6）每步多扣 `(6 + 0.3) · 0.3 = 1.89`，射线几乎在第一格就耗尽，只剩下爆心周围的 3×3×3 左右；
- 黑曜石（抗性 1200）一格就把射线吃光；
- 右图：同一种材料里，破坏量随半径增长得很快（泥土里半径 3 到 7 时约从 115 格增长到 830 格，对数坐标下斜率约 2.3），而石头几乎不随半径变化。**爆炸威力主要取决于周围方块的抗性，而不是半径**。

### 阻力与“能不能炸”是两件事

`ExplosionDamageCalculator` 把两件事拆开：`getBlockExplosionResistance`（返回抗性，空气和空流体返回“没有”，不扣阻力）和 `shouldBlockExplode`（默认总是 true）。子类可以改写这两个方法（有一个 `EntityBasedExplosionDamageCalculator`，让实体参与判断，本页没有读它）。这是**策略对象**的典型用法：爆炸算法本身不变，规则由传入的对象决定。

### 对实体的伤害

```java
// 在 explode 的第二半：取爆心 ±(2R+1) 的包围盒内的实体
q = radius · 2
w = 距离 / q                      // 归一化距离，> 1 的不受影响
seen = getSeenPercent(爆心, 实体)   // 沿实体包围盒内一个格点网格向爆心发射线，没被挡住的比例
ac = (1 − w) · seen
伤害 = (int)((ac² + ac) / 2 · 7 · q + 1)
击退 = 方向 · ac（生物按保护附魔缩减）
```

`getSeenPercent` 的网格步长是包围盒尺寸 `2 · size + 1` 的倒数，大实体的采样点更多。伤害公式是 `ac` 的二次函数，所以**离得近伤害增长很快**。

### 破坏、掉落与火

`explode()` 里射线先收集进一个局部 `HashSet` 去重，再灌入 `toBlow`（`ObjectArrayList`）。`finalizeExplosion` 做的事（客户端也会跑方块清除循环，只有战利品掉落被 `instanceof ServerLevel` 包住）：

1. 把 `toBlow` **随机洗牌**，保证掉落物的位置分布不偏；
2. 对每个非空气格：按战利品表算掉落（仅服务器；`DESTROY_WITH_DECAY` 模式带上 `EXPLOSION_RADIUS`，掉落有概率损失），`setBlock(AIR, 3)`，再调用 `wasExploded`（TNT 连锁、箱子清空等）；
3. 掉落**合并**：同类物品按每堆最多 16 个合并，最后一起 `popResource`，避免炸出几千个独立的掉落实体；
4. 如果是带火的爆炸（恶魂火球、床），对集合里每个格子，`1/3` 的概率在“已变成空气、且下面是实心”的位置放火。

`BlockInteraction` 有三种：`KEEP`（不破坏方块，如某些命令）、`DESTROY`（全部掉落）、`DESTROY_WITH_DECAY`（战利品上下文里带 `EXPLOSION_RADIUS`，掉落按半径有概率损失）。具体用哪种由 `Level.explode` 的调用方选，本页没有读。

## 幽匿：用“电荷游标”预算式地扩散

幽匿不用随机刻，它的扩散由 `SculkSpreader` 管理一个**游标列表**，每个游标是一个带电荷的小对象。

![幽匿游标的一次更新](/qmx-Gameknowledge/assets/mc-source/39-sculk-cursor.png)

### 数据

```java
// SculkSpreader
MAX_CURSORS = 32;  MAX_CHARGE = 1000;
createLevelSpreader()    = (isWorldGen=false, 可替换方块标签, growthSpawnCost=10, noGrowthRadius=4,  chargeDecayRate=10, additionalDecayRate=5)
createWorldGenSpreader() = (isWorldGen=true,  世界生成标签,   growthSpawnCost=50, noGrowthRadius=1,  chargeDecayRate=5,  additionalDecayRate=10)
ChargeCursor { pos, charge, updateDelay, decayDelay, facings }
```

幽匿催化体监听附近的实体死亡事件（半径 8），把死者的经验值作为电荷调用 `addCursors(pos, xp)`；电荷超过 1000 时拆成多个游标，列表满 32 个后新的直接丢弃。

### 一次更新

```java
// ChargeCursor.update（简化）
if (charge <= 0 || (非世界生成 && 催化体所在位置不在方块 tick 范围内)) return
if (updateDelay > 0) { updateDelay--; return }
behaviour = 当前格的 SculkBehaviour（幽匿块 / 幽匿脉 / 其它默认）
if (调用方允许扩散脉) behaviour.attemptSpreadVein(...)     // 在周围放幽匿脉（交给 MultifaceSpreader，没读）
charge = behaviour.attemptUseCharge(...)                      // 幽匿块：生长或衰减
if (charge > 0):
    newPos = getValidMovementPos(...)                         // 移动
    if newPos != null: pos = newPos                           // 世界生成模式下，移动后水平距离催化体 ≥ 15 格（不计 y）就清零
    updateDelay = behaviour.getSculkSpreadDelay() (=1)
```

### 幽匿块怎么用电荷（`SculkBlock.attemptUseCharge`）

```java
if (charge != 0 && nextInt(chargeDecayRate) == 0):          // 每次更新只有 1/10 的概率结算
    inside = 游标位置在 noGrowthRadius 之内
    if (!inside && canPlaceGrowth(pos)):                    // 上方是空气或水，且周围 9×3×9 内感测体 / 尖啸体 ≤ 2
        if (nextInt(growthSpawnCost) < charge):              // charge ≥ 10 时一定成立（普通模式）
            在 pos.above() 放 感测体（10/11）或 尖啸体（1/11）
        return max(0, charge − growthSpawnCost)
    else:
        if (nextInt(additionalDecayRate) != 0) return charge                  // 4/5 的概率什么都不发生
        return charge − (inside ? 1 : getDecayPenalty(...))
```

`getDecayPenalty = max(1, charge · min(1, (距离 − noGrowthRadius)² / (24 − noGrowthRadius)²) · 0.5)`：离催化体越远，每次衰减越多；距离超过 24 格（`MAX_GROWTH_RATE_RADIUS`）后系数封顶，每次衰减电荷的一半，游标很快耗尽。

### 移动与合并

- `getValidMovementPos` 把 **18 个非角邻居**（6 个面邻 + 12 个棱邻）随机洗牌，依次检查：是 `SculkBehaviour` 方块且没被阻挡（棱邻要求两个相邻面至少一个不是完整面）。遇到“有基质可附着”的就立刻停下，否则取最后一个合法的。所以游标会倾向于沿着幽匿块表面走。
- 一轮更新后，**同一位置的游标合并**（非世界生成、总电荷 ≤ 1000）；电荷为 0 的游标被丢弃。

幽匿设计要点：**用电荷当预算**。一个游标最多带 1000 电荷，每次生长扣 10，衰减随距离增加，最终自己消失；列表上限 32。无论玩家杀了多少只怪，每次更新一个 spreader 最多处理 32 个游标，成本有硬上限。

## 叶子衰减：距离 + 预约刻 + 随机刻

叶子有 `DISTANCE`（1~7，到最近原木的距离）和 `PERSISTENT`（玩家放的叶子不衰减）。第 18 页讲了生成时 `updateLeaves` 怎么把距离算对，运行时靠局部规则维护：

```java
// LeavesBlock（简化）
isRandomlyTicking(state) = state.DISTANCE == 7 && !state.PERSISTENT      // 只有“已经失联”的叶子才进随机刻
randomTick: if (DISTANCE == 7 && !PERSISTENT) { 掉落; 移除 }               // 衰减
updateShape(邻居变化): 除非 (变化的邻居是原木 && 自己的距离已经是 1)，否则 scheduleTick(自己, 1)
tick: DISTANCE = min(7, 6 个邻居的距离 + 1)；原木的距离是 0；不是叶子的方块视为 7
```

关键是**把“要不要处理”的判断前置**：绝大部分叶子距离 < 7，根本不进入随机刻；砍掉原木后，只有邻居变化的叶子才被预约刻重算距离，一圈一圈向外传播（每层一刻）；距离到 7 的叶子才可能被随机刻抽中，所以“砍树后叶子不是一下子掉光，而是陆续掉落”是**距离传播（每层 1 刻）+ 随机刻抽中概率**共同造成的。

## 草 / 菌丝：4 次随机尝试

```java
// SpreadingSnowyDirtBlock.randomTick
if (!canBeGrass(自己)) 变成泥土                         // 上方被遮光 / 被水淹没（满格流体）
else if (上方亮度 ≥ 9):
    repeat 4 次:  target = pos + (nextInt(3)−1, nextInt(5)−3, nextInt(3)−1)    // y 偏移 −3 ~ +1
        if (target 是泥土 && canPropagate(target)) 变成草（带 SNOWY 属性）
```

要点：**每次随机刻只尝试 4 个固定范围内的目标**，不需要“搜索附近有哪些泥土”；`canBeGrass` 用光照引擎的 `getLightBlockInto`（第 15 页的遮光量）判断，所以光照引擎的结果直接影响草的生死。

## 藤蔓：随机方向 + 数量上限

```java
// VineBlock.randomTick（大幅简化）
if (规则 doVinesSpread 开 && nextInt(4) == 0):
    dir = 随机方向
    if (dir 是水平 && 该面没有藤) && canSpread(pos):  尝试在 pos+dir 或绕角的位置放新藤
    else (方向不是水平，或该水平面已有藤):
        若方向为 上 且未到世界顶: 先尝试给自己加上顶面，或在上方空格放一块新藤，成功即返回
        其余情况落到“向下生长”分支: 下方为空气或藤蔓时，随机复制水平面（每面 50%），结果仍有水平连接才写入
    // 另外横向扩散里还有一支 5% 概率放“顶面藤”的分支
canSpread: 统计 pos 周围 9×3×9（x、z 各 ±4，y 各 ±1）里的藤蔓块，数到第 5 个就返回 false
```

这是一个很典型的**密度限制**：不用全局计数，直接数周围的同类数量，超过阈值就停止生长，防止藤蔓铺满整片林子。

## 火：每个火方块的小型细胞自动机

`FireBlock.tick` 是预约刻，每次结算后重新预约 `30 + nextInt(10)` 刻（约 1.7 秒）。

![火的蔓延与燃烧概率](/qmx-Gameknowledge/assets/mc-source/38-fire-spread.png)

```java
// FireBlock.tick（简化）
重新预约自己；若 canSurvive 为假（脚下不是实心顶面，且六个邻居都不可燃）→ 移除
非 infiniburn 的火：六个邻居都不可燃时，若 脚下不是实心顶面 或 AGE > 3 → 熄灭；无论是否熄灭，本次结算到此为止，不再蔓延
下雨且在雨中：有 0.2 + AGE·0.03 的概率直接熄灭
AGE = min(15, AGE + nextInt(3)/2)            // 每次结算有 1/3 的概率 AGE+1
若 脚下不可燃 && AGE == 15 && nextInt(4) == 0 → 熄灭
// 1) 烧掉 6 个直接邻居：
for 邻居 in 东西南北上下:   checkBurnOut(邻居, 分母 = 水平 300 / 垂直 250, AGE)
    if nextInt(分母) < burnOdds(邻居):               // burnOdds：木板 20、树叶 / 羊毛 60、草 / 藤 / TNT 100
        if nextInt(AGE + 10) < 5 && 没下雨: 该邻居变成新火 else 移除      // 替换完之后，若原方块是 TNT 再 explode
// 2) 向周围 53 个空格“点燃”：
for dx, dz in −1..1, dy in −1..4 (去掉自己):   // 3×3×6 − 1 = 53 格
    o = dy > 1 ? 100 + (dy − 1)·100 : 100        // 越往上越难：dy = 2、3、4 时分别是 200、300、400
// 修正项：在 INCREASED_FIRE_BURNOUT 标签的群系里，checkBurnOut 的分母各减 50，q 再整除 2；
//        “下雨”判定用 isNearRain（本格或东西南北四邻有雨），且熄灭判断只对非 infiniburn 生效；
//        AGE == 15 的熄灭判断用的是本次结算开始时的旧 AGE
    p = 该空格 6 个邻居中最大的 igniteOdds
    q = (p + 40 + 难度·7) / (AGE + 30)
    if q > 0 && nextInt(o) <= q && 没下雨: 变成新火（AGE' = min(15, AGE + nextInt(5)/4)）
```

读图：

- (a) 邻居越易燃（igniteOdds 60 的草 vs 5 的木板），点燃概率越高；随 AGE 增大而阶梯式下降（整数除法）。木板每次火刻只有约 2%，所以木屋烧得慢；草和树叶是 3%~4%。
- (b) 点燃上方的空格越来越难（分母 `o` 随高度增加到 400），所以火往上蔓延比水平慢；**往下一格（dy = −1）和同层（dy = 0）与上一格（dy = 1）概率相同**。
- (c) 相邻方块被烧掉的概率 `burnOdds / 300`（虚线）与“变成新火”的概率（实线，再乘 `5 / (AGE + 10)`）。年轻的火更容易把邻居变成火而不是单纯烧掉；这也是为什么新点燃的火比老火更有侵略性。

火的寿命：每次结算 AGE 有 1/3 概率 +1，平均 45 次结算到 15，每次间隔约 34.5 刻，所以长到 15 岁约需 `45 × 34.5 ≈ 1550` 刻（约 78 秒）；之后若脚下不可燃，每次结算还有 1/4 的概率熄灭。

## 重力方块与雪

- `FallingBlock`：`onPlace` 和 `updateShape` 都 `scheduleTick(2)`；`tick` 时如果脚下是“自由”的（空气、液体、火等），就生成一个 `FallingBlockEntity`。**用预约刻 + 把方块变成实体**把“下落”从方块更新里分出去，连锁下落时每层隔 2 刻。
- `SnowLayerBlock`：`randomTick` 里块光亮度 > 11 就掉落并移除。世界生成时的雪层是 `SnowAndFreezeFeature` 放的（第 9 页）。

## 共通的设计模式

| 模式 | 出现在哪里 | 好处 |
| --- | --- | --- |
| **随机采样代替遍历** | 草、藤、叶子衰减、雪融化（随机刻） | 成本与“抽几次”有关，与方块总数无关 |
| **先判定是否需要处理** | 叶子只有距离 7 才进随机刻；火只在有可燃物时蔓延 | 绝大多数方块零成本 |
| **事件触发 + 预约刻** | 叶子距离、重力方块、火 | 只在变化后才有后续工作 |
| **预算式对象** | 幽匿游标（电荷、衰减、最多 32 个） | 成本有硬上限，不会因为输入多而失控 |
| **局部规则的数量上限** | 藤蔓 `canSpread`、感测体 `canPlaceGrowth` | 不用全局计数 |
| **策略对象** | 爆炸的 `ExplosionDamageCalculator`、幽匿的 `SculkBehaviour` | 算法不变，规则由对象决定 |
| **概率用整数运算表达** | 火：`nextInt(o) <= (p + 40 + 难度·7) / (AGE + 30)` | 确定性强，参数可调，没有浮点误差 |
| **合并与去重** | 爆炸的 `HashSet` 和掉落合并；幽匿同位置游标合并 | 少生成实体，少触发方块更新 |

## 给 Unity 项目的取舍

1. **先做随机刻**：每个区块段每帧抽 N 个方块，调用 `block.RandomTick(...)`。这一个机制就能带出草蔓延、作物、叶子衰减、雪融化。N 做成配置。
2. **叶子和火都用“预约刻”**：做一个按到期帧排序的小根堆（或时间轮），键是 (到期时间, 位置)。
3. **幽匿这类“扩散”做成游标列表**：每个游标有电荷、延迟，设上限；比“全局随机刻 + 邻居检查”更容易控制性能，也更容易调参。
4. **爆炸先做射线版**：1352 条射线是固定的方向表，可以预算一次存成静态数组；射线逐步衰减的循环适合放进 Job，破坏集合用 `NativeHashSet`。
5. **火的参数用查表**：`igniteOdds / burnOdds` 做成 `ScriptableObject` 字典，调火势只需要改表。

## 小结

- 爆炸：1352 条来自立方体表面网格的射线，每条强度 0.7~1.3 倍半径，每步扣 0.225 和 `(抗性 + 0.3) · 0.3`；破坏集合去重，掉落合并；威力主要取决于周围方块的抗性。
- 幽匿：游标带电荷，每次结算 1/10 的概率生长（花 10 点电荷）或衰减，同位置合并，最多 32 个。
- 叶子衰减 = 距离传播（预约刻）+ 距离 7 的随机刻；草 = 4 次随机尝试；藤蔓 = 随机方向 + 数量上限；火 = 每个火方块一个小型细胞自动机。
- 共同思路：**把“要处理的东西”缩到最小，再用随机或预算限制每刻成本**。

参考答案：① 1352 条射线会反复经过同一个方块，集合保证每个方块只处理一次（也避免重复掉落）。② 每步扣除 `(抗性 + 0.3) · 0.3`：泥土（0.5）约扣 0.24，黑曜石（1200）扣 360，远大于射线的初始强度（半径 4 时约 2.8~5.2），一格就耗尽。③ 生长（扣 `growthSpawnCost`）、衰减（半径内扣 1，半径外按距离的惩罚）、与同位置游标合并。④ 距离小于 7 的叶子还和原木连通，不需要处理；只有失联的叶子才可能衰减，把它们挑出来可以让绝大多数叶子零成本。⑤ 点燃空格时分母 `o` 在 `dy > 1` 时按 `100 + (dy − 1) · 100` 增长（最高 400），越高越大，概率越低。
