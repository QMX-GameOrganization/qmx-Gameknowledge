> 对应源码：`ChunkStatus`、`ChunkGenerator`、`NoiseBasedChunkGenerator`、`RandomState`、`WorldgenRandom`、`PalettedContainer`。

## 要点

- 一个区块要经过 **12 个 `ChunkStatus` 台阶**才能“可玩”，每个台阶只做一件事，并明确声明自己需要**多大半径的邻居**。
- 邻居依赖形成一个“金字塔”：要让中心区块 `FULL`，第 1 圈要先跑完 features，第 2 圈要到 `CARVERS`，第 3 圈到 `BIOMES`，更外圈只要 `STRUCTURE_STARTS`。
- **地形主体（NOISE）不读邻居的方块**，只依赖确定性的噪声函数，所以可以放到后台线程并行。它会读邻居区块的“结构起点”（用于 `Beardifier` 让地形贴合结构）和旧世界的融合数据（`Blender`），这正是 NOISE 的 `range` 为 8 的原因。真正需要邻居方块的是后面的雕刻和特征。
- 整个世界只有一份不可变的“函数图”，但**每个区块都会得到一份私有的缓存副本**（`NoiseChunk`），这样多线程不需要加锁。
- 所有随机数都由 **种子 + 名字 / 坐标** 派生，和线程、加载顺序无关。

## 12 个台阶

![ChunkStatus 流水线与邻居依赖金字塔](/qmx-Gameknowledge/assets/mc-source/16-chunk-status-pyramid.png)

| 台阶 | 做什么 | 入口方法 | 邻居半径 `range` |
| --- | --- | --- | --- |
| `EMPTY` | 空容器 | — | — |
| `STRUCTURE_STARTS` | 决定附近有没有结构，起点在哪 | `ChunkGenerator.createStructures` | 0 |
| `STRUCTURE_REFERENCES` | 记录“哪些结构会覆盖到本区块” | `createReferences` | 8 |
| `BIOMES` | 填充群系（4×4×4 一个） | `NoiseBasedChunkGenerator.createBiomes` | 8 |
| `NOISE` | 填充固体、水、岩浆、矿脉 | `fillFromNoise` → `doFill` | 8 |
| `SURFACE` | 把表层石头换成草、沙、雪等 | `buildSurface` | 8 |
| `CARVERS` | 传统洞穴和峡谷 | `applyCarvers` | 8 |
| `FEATURES` | 矿石、树、花、湖；结构落地 | `applyBiomeDecoration` | 8 |
| `INITIALIZE_LIGHT`、`LIGHT` | 光照 | — | 0、1 |
| `SPAWN` | 生成初始生物 | `spawnOriginalMobs` | 0 |
| `FULL` | 从 `ProtoChunk` 变成 `LevelChunk`，可玩 | — | 0 |

这里的 `range` 是 `ChunkStatus` 注册时的第 3 个参数（`taskRange`）。读它时要小心：它**不是“这个台阶会写入多远”**，而是“调度器在启动这个台阶前，要求周围多大范围的区块**已经到达了哪个状态**”。到达什么状态，才由下面的金字塔表决定。

### 依赖金字塔：`STATUS_BY_RANGE`

```java
// ChunkStatus.java
STATUS_BY_RANGE = [ FULL, INITIALIZE_LIGHT, CARVERS, BIOMES,
                    STRUCTURE_STARTS × 8 ]
```

读法：加载系统要求，距离某个 `FULL` 区块 *d* 圈的区块，至少要到达下标为 *d* 的状态（`ChunkLevel` 用这张表给区块分配“加载等级”）。调度某个台阶 *S* 时用的是同一张表：环 *i* 上的邻居必须到达 `STATUS_BY_RANGE[getDistance(S) + i]`（*i* = 0 时是 *S* 的父状态，见 `ChunkMap.getDependencyStatus`）。于是得到这个金字塔：

- 第 1 圈至少到 `INITIALIZE_LIGHT`（意味着它们的 **features 已经跑完**，因为 features 的树和矿会越界写进相邻区块，中心区块必须等邻居写完才算定稿）；
- 第 2 圈至少到 `CARVERS`（第 1 圈在跑 features 时要读周围方块，所以再外一圈要先有地形和洞穴）；
- 第 3 圈至少到 `BIOMES`；
- 第 4 圈以外只要 `STRUCTURE_STARTS`。

## 为什么 NOISE 可以并行

`NoiseBasedChunkGenerator.fillFromNoise` 的骨架如下（省略了细节）：

```java
// 1. 先把这个区块用到的所有 LevelChunkSection 标记为“正在被使用”
for (section : sections) section.acquire();
// 2. 丢到后台线程池里去算
return CompletableFuture.supplyAsync(() -> doFill(...), Util.backgroundExecutor())
        // 3. 算完以后在原调度线程上解除标记
        .whenCompleteAsync((chunk, err) -> sections.forEach(s -> s.release()), executor);
```

`acquire / release` 背后是 `ThreadingDetector`：同一个 `PalettedContainer` 如果被两个线程同时访问就会抛异常，用来**尽早发现并发误用**，而不是真正的互斥锁。能这样做的前提是：`doFill` 只写**本区块自己的**段，读取的是**只依赖坐标的确定性函数**，不需要邻居的方块。

这给你的启示很直接：想让地形生成多线程，就保证“采样 = 纯函数 + 本区块私有缓存 + 只写自己的数组”。后面第 10 页会讲 Mojang 如何做到“共享函数图、私有缓存”。

## 确定性：种子怎么变成所有随机数

```text
世界种子 seed
  └─ RandomState.random = Xoroshiro(seed).forkPositional()
        ├─ fromHashOf("minecraft:continentalness")  → NormalNoise 的随机源
        ├─ fromHashOf("minecraft:erosion")          → 另一个独立的随机源
        ├─ fromHashOf("aquifer") / ("ore") / ("terrain") …
        └─ 每个噪声内部：forkPositional().fromHashOf("octave_-9") → 每个 octave 的排列表
```

关键点是 `fromHashOf(名字)`：**同一个名字永远得到同一个随机源，与创建顺序无关**。`RandomState.getOrCreateNoise` 用 `ConcurrentHashMap.computeIfAbsent` 按需创建，所以不管哪个线程先用到“侵蚀度噪声”，结果都一样。

区块级的随机数（特征、洞穴起点）则用 `WorldgenRandom` 里的几个公式，把“种子 + 区块坐标”揉成一个新种子：

| 方法 | 用途 | 思路 |
| --- | --- | --- |
| `setDecorationSeed(seed, x, z)` | 一个区块的“装饰”基础种子 | 用 seed 生成两个奇数 `m,n`，取 `x·m + z·n ^ seed` |
| `setFeatureSeed(decorationSeed, index, step)` | 区块里第 `index` 个特征、第 `step` 个阶段 | `decorationSeed + index + 10000·step` |
| `setLargeFeatureSeed(seed, x, z)` | 洞穴起点判定（按“源区块”） | `x·a ^ z·b ^ seed`，`a,b` 来自 seed |
| `setLargeFeatureWithSalt(seed, x, z, salt)` | 结构的 `random_spread` 位置 | 用大质数混合坐标，再加盐 |

“加盐（salt）”的作用是让不同结构、不同特征的随机序列互不相关。

## 数据怎么放：段、调色板与群系网格

方块不是放在一个 16×16×384 的大数组里，而是切成 24 个 **`LevelChunkSection`**（16×16×16，共 4096 个方块）。每个段里有两个 `PalettedContainer`：

| 容器 | 分辨率 | 策略 | 说明 |
| --- | --- | --- | --- |
| 方块状态 | 16³ = 4096 | `SECTION_STATES` | 按调色板位宽升级：0 位（只有 1 种）→ 单值；1~4 位 → 线性调色板（固定 4 位）；5~8 位 → 哈希调色板；更多 → 全局表 |
| 群系 | 4³ = 64 | `SECTION_BIOMES` | 每 4×4×4 一个群系值；1~8 种 → 线性调色板 |

“调色板”就是**用小整数下标代替重复出现的大对象**。一个全是石头的段只需要存 1 个值（`SingleValuePalette`），完全不占数组。群系也是同样的思路，而且分辨率只有方块的 1/4，下一页会看到这是有意为之。

高度图（`Heightmap`）也在这一层：`NOISE` 阶段更新的是 `OCEAN_FLOOR_WG`、`WORLD_SURFACE_WG`（带 `_WG` 的是“世界生成专用”），后面 `SURFACE` 要用它们找到每一列的最高点；`FEATURES` 开始前才会 `primeHeightmaps` 重算运行时用的高度图。

## 给 Unity 项目的取舍

| 内容 | 建议 |
| --- | --- |
| 阶段拆分（NOISE → SURFACE → FEATURES） | **做**。每个阶段写成独立函数，输入输出明确，后面才能并行 |
| 邻居依赖金字塔 | 先**简化**：地形主体不依赖邻居；做到特征/洞穴时再引入“需要几圈邻居” |
| “种子 + 名字 / 坐标”派生随机数 | **做**，越早越好。否则以后加多线程会出现“同一个种子两次结果不同” |
| `PalettedContainer` | 暂不做。先用 `byte[]`/`ushort[]`，内存成为瓶颈再说（你已经在流式区块里验证了这一点） |
| 群系 4×4×4 网格 | 做到群系时再做；先记住“存得粗、查得细” |
| `ThreadingDetector` 式的并发自检 | 调试期很有用，可以参考 |

## 小结

- 流水线有 12 个台阶，邻居依赖像金字塔：越晚的台阶需要的邻居越“成熟”。
- NOISE 阶段只依赖确定性函数，所以能放后台并行；写的只是本区块的段。
- 随机数一律由“种子 + 名字/坐标”派生。

## 自测

1. 为什么 `FEATURES` 之后第 1 圈邻居必须已经完成 features，中心区块才能算定稿？
2. `fromHashOf("minecraft:erosion")` 为什么能保证多线程下结果一致？
3. 一个全是石头的 16³ 段，在 `PalettedContainer` 里占多少存储？

参考答案：① 因为 features（树、矿）会越界写进邻居，邻居的写入必须先完成。② 同名永远得到同一随机源，与调用顺序和线程无关。③ 只存一个值（单值调色板），数据数组为空。
