## 要点

- 服务器用**一个整数“等级”**表示一个区块应该处于什么状态：数值越小越“重要”。等级既决定“要加载到哪个 `ChunkStatus`”，也决定“是否参与方块 / 实体 tick”。
- 等级由 **ticket** 产生。玩家附近的区块各有一张等级 31 的 `PLAYER` ticket；等级再沿 8 邻域**每走一圈 +1** 向外传播，传播是**增量**的，只重算变化的区块。
- 每个区块有一个 `ChunkHolder`，里面按 `ChunkStatus` 存着一排 `CompletableFuture`。等级变化 → 升级或降级 → 调度对应状态的 future。
- 所有生成任务进入**按区块队列等级分桶**的优先级队列，离玩家近的先执行；玩家移动时队列里的任务会**重新排序**。
- **视距**决定“哪些区块发给玩家 / 加载到 FULL”，**模拟距离**才决定“哪些区块真正 tick”，两者是两套追踪器。
- 卸载、保存、玩家 ticket 的放入都**限流**，避免一帧里做太多。

## 区块等级：一个整数的两种含义

```java
// ChunkLevel
FULL_CHUNK_LEVEL = 33;  BLOCK_TICKING_LEVEL = 32;  ENTITY_TICKING_LEVEL = 31;
MAX_LEVEL = 33 + ChunkStatus.maxDistance();             // = 33 + 12 = 45（按 STATUS_BY_RANGE 共 12 项算出）
byStatus(status)       = 33 + ChunkStatus.getDistance(status);
generationStatus(level) = level < 33 ? FULL : ChunkStatus.getStatusAroundFullChunk(level - 33);
fullStatus(level):  ≤31 → ENTITY_TICKING；32 → BLOCK_TICKING；33 → FULL；其余 → INACCESSIBLE
isLoaded(level) = level <= MAX_LEVEL
```

等级与状态的对应关系正是第 2 页讲过的 `STATUS_BY_RANGE`：

| 等级 | 区块需要到达的状态 |
| --- | --- |
| ≤ 33 | `FULL` |
| 34 | `INITIALIZE_LIGHT`（features 已完成） |
| 35 | `CARVERS` |
| 36 | `BIOMES` |
| 37 ~ 44 | `STRUCTURE_STARTS` |
| 45 | 刚刚加载（`EMPTY`） |
| > 45 | 不加载 |

也就是说，第 2 页的“依赖金字塔”不是在每次调度时才算出来的，而是**直接编码在等级里**：离玩家越远，要求的状态越低；一个等级数字就够了。

## Ticket：谁在“要求”这个区块

`Ticket` 是一条“请把区块 X 保持在等级 L”的声明，带类型、等级和创建时刻。`TicketType` 决定它会不会过期：

| 类型 | 过期时间（游戏刻） | 用途 |
| --- | --- | --- |
| `start` | 不过期 | 出生点区域 |
| `dragon` | 不过期 | 末影龙战场 |
| `player` | 不过期 | 玩家附近（随玩家移动增删） |
| `forced` | 不过期 | `/forceload` 强制加载 |
| `light` | 不过期 | 光照计算期间临时持有 |
| `portal` | 300 | 传送门传送 |
| `post_teleport` | 5 | 传送后短暂保持 |
| `unknown` | 1 | 其它 |

`DistanceManager.purgeStaleTickets` 每刻把计数器加 1，把 `timeout != 0 && 现在 − 创建时刻 > timeout` 的 ticket 清掉。一个区块上可以有多张 ticket，**取等级最小的那张**（`getTicketLevelAt`）。

### 等级的传播：每圈 +1，增量更新

![ticket 等级的传播](/qmx-Gameknowledge/assets/mc-source/28-ticket-levels.png)

一个区块上的 ticket 等级会沿 8 邻域向外扩散，每走一圈 +1（切比雪夫距离）：

```java
// DistanceManager.ChunkTracker（继承自增量图算法 DynamicGraphMinFixedPoint）
computeLevelFromNeighbor(源等级 l, 到邻居) = l + 1
一个区块的最终等级 = min(自己的 ticket 等级, 所有 8 个邻居的等级 + 1)
```

图左：视距 6 的玩家，白虚线内每个区块都有一张等级 31 的 `PLAYER` ticket，再往外每圈 +1，一直到 45。图右：同样的数据翻译成“必须到达的 `ChunkStatus`”：视距内加上外圈的两圈是 `FULL`，再外面依次是 `INITIALIZE_LIGHT`、`CARVERS`、`BIOMES`、八圈 `STRUCTURE_STARTS`，最后一圈是刚加载的空区块。所以**服务器实际加载的区块比视距大得多，但越外面的区块越“半成品”**。

传播是**增量**的（`ChunkTracker.update` 只处理等级变化的区块，用一个按等级分桶的队列，见 `DynamicGraphMinFixedPoint`）。玩家走一步，只有新进入和离开范围的那一圈区块需要重算，不会每刻全量扫描。

### 视距与模拟距离是两套追踪器

| 追踪器 | 距离 | 产生什么 |
| --- | --- | --- |
| `PlayerTicketTracker` | 视距（`ChunkMap.setViewDistance` 夹在 2~32） | 距玩家切比雪夫距离 ≤ 视距的区块各加一张等级 31 的 `PLAYER` ticket |
| `TickingTracker` | 模拟距离（默认 10） | 玩家所在区块等级 = `max(0, 31 − 模拟距离)`，向外每圈 +1；**这里等级 ≤ 31 的区块 tick 实体，≤ 32 的区块 tick 方块**（所以方块 tick 的范围比实体大一圈） |
| `FixedPlayerDistanceChunkTracker(8)` | 固定 8 | 自然刷新的可刷新区块数（第 14 页的 `289`） |

于是服务器上有三个互相独立的范围：**加载 / 发包范围**（视距）、**tick 范围**（模拟距离）、**刷新范围**（8）。`ServerLevel` 在决定“这个实体 / 这个位置要不要 tick”时问的是 `inEntityTickingRange` / `inBlockTickingRange`（用的是 `TickingTracker`），而不是区块是否已加载。

玩家 ticket 的放入还有**节流**：`PlayerTicketTracker` 把“加 ticket”的请求交给 `ticketThrottler`（一个单队列的 `ChunkTaskPriorityQueueSorter`，`maxTasks = 4`），按到玩家的距离排序，由近及远，**同一时刻最多处理 4 个区块的 ticket**，等对应区块变成 `ENTITY_TICKING` 后才释放下一个。这样玩家传送到新地方时，不会一下子把几百个区块全部排进生成队列，而是由近到远逐步展开。

## ChunkHolder：一排 future

每个被追踪的区块有一个 `ChunkHolder`，核心字段是按 `ChunkStatus` 下标存放的 `AtomicReferenceArray<CompletableFuture<...>>`：第 *i* 格是“这个区块到达第 *i* 个状态”的 future。

```java
// ChunkHolder.getOrScheduleFuture(status)（简化）
future = futures[status.index];
if (future 存在且（未完成 或 已成功完成）) return future;                  // 已有 future 就直接复用，不再检查等级
if (ChunkLevel.generationStatus(ticketLevel).isOrAfter(status)) {        // 槽为空或已失败，才看等级是否允许
    future = chunkMap.schedule(this, status); futures[status.index] = future; return future;
}
return 旧的失败 future，槽为空则返回 UNLOADED_CHUNK_FUTURE;               // “Unloaded ticket level”
```

`updateFutures`（等级变化时由 `DistanceManager.runAllUpdates` 调用）做三件事：

1. **降级**：把新状态以上的空槽填上“失败”的 future；
2. **升级**：按等级跨过 `FULL / BLOCK_TICKING / ENTITY_TICKING` 的边界，依次触发 `prepareAccessibleChunk`、`prepareTickingChunk`、`prepareEntityTickingChunk`（等待周围范围内的邻居区块到达所需状态，再取出中心的 `LevelChunk`；ticking 阶段还会做生成后处理并启动区块 tick。`ProtoChunk` 到 `LevelChunk` 的转换发生在 `FULL` 状态的生成任务里）；
3. 通知队列排序器 `onLevelChange`，让已排队的任务按新等级重新排序（见下）。

### ChunkMap：真正安排一个状态

`ChunkMap.schedule(holder, status)` 按状态选路径：`EMPTY` 走 `scheduleChunkLoad`（从磁盘读）；`LIGHT` 先加一张 `light` ticket；能直接读盘的先试 `load`，否则走 `scheduleChunkGeneration`：

```java
// scheduleChunkGeneration（简化）
邻居们 = getChunkRangeFuture(holder, status.getRange(), i -> getDependencyStatus(status, i));   // (2r+1)² 个 future 合并
return 邻居们.thenComposeAsync(list -> status.generate(...), runnable -> worldgenMailbox.tell(message(holder, runnable)));
```

`getChunkRangeFuture` 取周围 (2r+1)² 个 `ChunkHolder`，按切比雪夫环号 *i* 向每个邻居要求 `getDependencyStatus(status, i)` 状态的 future（第 2 页的公式），任何一个区块不存在就直接失败，其余用 `Util.sequence` 合并成一个 future。**依赖关系就是 future 的组合**：邻居的 future 完成，后续步骤才会被投递到队列。

## 任务队列：按区块等级分桶

![区块任务的线程与队列架构](/qmx-Gameknowledge/assets/mc-source/29-chunk-task-architecture.png)

`ChunkMap` 创建三个 mailbox：`worldgen`、`light`，以及包装主线程的 `main`，交给一个 `ChunkTaskPriorityQueueSorter`（没有任务数上限）。

```java
// ChunkTaskPriorityQueue
PRIORITY_LEVEL_COUNT = MAX_LEVEL + 2 = 47;
taskQueue = 47 个桶，下标 = 区块的队列等级；每个桶按区块坐标存一批任务（Long2ObjectLinkedOpenHashMap）
firstQueue = 当前最小的非空桶
pop(): 取 firstQueue 桶里的第一个区块，把这个区块积压的任务整批弹出
resortChunkTasks(区块, 旧等级, 新等级): 把任务从旧桶搬到新桶，更新 firstQueue
```

- **等级小的先执行**：靠近玩家（等级小）的区块的任务总是排在远处前面；
- **玩家移动时重排**：`ChunkHolder.updateFutures` → `onLevelChange` → `resortChunkTasks`，已经排队的任务会跟着区块的新等级换桶；
- **释放 / 占用**：队列里可以放“占位”条目，表示“某个区块正在处理，后面的任务要等它释放”，用来保证同一区块的任务按顺序执行；
- 排序器自己的内部消息也有 4 档优先级（改等级 0、释放 1、提交 2、取任务 3），改等级永远先于取任务。

### 线程

```java
// MinecraftServer
this.executor = Util.backgroundExecutor();          // 传给每个 ServerLevel → ServerChunkCache → ChunkMap

// Util.makeExecutor
线程数 = Mth.clamp(Runtime.getRuntime().availableProcessors() - 1, 1, getMaxThreads());   // getMaxThreads 默认 255
ForkJoinPool(asyncMode = true)，线程名 Worker-Main-N
```

- 所有 mailbox（`worldgen`、`light`）都建立在这个同一个线程池上；`ProcessorMailbox` 用一个原子状态位（CAS）保证**同一个 mailbox 同一时刻只被一个线程消费**，不需要锁；
- 主线程 mailbox 的任务由 `ServerChunkCache` 的主线程执行器处理；它每次取任务之前先 `runDistanceManagerUpdates`，并让光照引擎尝试调度（`tryScheduleUpdate`）。

## 卸载与保存：限流

区块等级超过 `MAX_LEVEL` 就不再加载。卸载不是立即发生的，而是排队、限量处理：

| 动作 | 限制 |
| --- | --- |
| `processUnloads` | 本刻还有时间预算时不限量；预算用完后每刻仍至少处理 **200** 个待卸载区块；`toDrop` 积压超过 **2000** 时不再受预算限制，另外 `unloadQueue` 超出 2000 的部分会被强制执行 |
| 保存 | 时间预算未耗尽时，每刻最多成功保存 **20** 个区块（`saveChunkIfNeeded`）；保存成功的区块有 **10 秒**（10000 ms）冷却 |
| `scheduleUnload` | 等区块的“待保存”future 完成，保存，再从世界里移除、更新光照 |
| `pendingUnloads` | 卸载队列中的区块如果又回到加载范围（等级 ≤ 45），直接复用原来的 `ChunkHolder`，不用重新创建 |

这几个数字的作用都是**把磁盘 IO 和对象销毁摊平到多个刻里**，避免玩家快速移动时一帧卡住。

## 视距与发包

- `setViewDistance` 把视距夹在 2~32，更新玩家 ticket 追踪器，并对新旧范围的差集调用 `updateChunkTracking`：进入范围且区块已经 ticking 就发给玩家（`playerLoadedChunk`），离开范围就取消追踪。
- `isChunkInRange` 用 `max(0, |dx| − 1)` 一类的修正做**近似圆形**判断，而不是正方形。
- 发区块包时用一个 `MutableObject` 缓存同一个区块的包，**多个玩家共用同一份序列化结果**。
- 在 1.20.1 里没有找到逐刻发送区块数量的节流器：节流主要靠上面的 ticket 节流器和任务队列。

## 主线程怎么“等”一个区块

`ServerChunkCache.getChunk(x, z, status, load)` 在主线程调用时，如果区块还没准备好，会先查一个 4 项的小缓存，再取 future，最后用 `managedBlock(future::isDone)` 等待：

```java
// BlockableEventLoop.managedBlock（简化）
while (!条件满足) {
    if (!pollTask()) waitForTasks();       // 没有任务可跑就让出一会儿（yield + parkNanos(100 微秒)）
}
```

关键点是：**等待期间主线程仍在执行排队的主线程任务**（比如区块完成后的回调），所以不会死锁；在非主线程调用则先转交到主线程再等待。

## 设计观察

1. **一个整数表示全部状态**（`ChunkLevel`）：加载到哪、是否 tick 都由它推出，不需要多套状态机。
2. **等级是增量传播的**（`DynamicGraphMinFixedPoint`）：玩家移动只重算边缘一圈。
3. **优先级 = 区块等级**：靠近玩家的先做，且等级变化时队列里的任务跟着重排。
4. **依赖 = future 的组合**：邻居的 future 完成了，后续步骤才被投递；调度器不用自己写依赖图。
5. **限流到处都有**：玩家 ticket 4 个、卸载保底 200 个、保存 20 个、冷却 10 秒（卸载和保存都与本刻的时间预算挂钩）。
6. **一个 mailbox 一个消费者**：靠原子状态位保证，不用锁。
7. **共享序列化结果**：多个玩家同时进入同一区块，只序列化一次。
8. **视距、模拟距离、刷新范围三套追踪器**：各管各的，互不干扰。

## 给 Unity 项目的取舍

1. **先用“距离 → 等级”的纯函数**：`level = base + 切比雪夫距离`，等级决定目标状态（第 2 页的金字塔）。不必一开始就写增量传播，直接按玩家位置重算一圈也行。
2. **优先级队列按等级分桶**：数组 + 链表即可，`pop` 取最小非空桶。玩家移动时只在变化的区块上换桶。
3. **用 `Task`/Job 句柄表示依赖**：每个状态一个句柄，邻居句柄全部完成后再调度下一步。
4. **限流**：每帧最多启动 N 个新任务、最多卸载 M 个区块，N、M 做成可调参数。
5. **把“视距”和“模拟距离”分开**：远处只渲染不 tick，能省下一大块 CPU。

## 小结

- 区块等级 = 33 + 到“完整区块”的距离；等级同时决定加载状态和 tick 资格。
- ticket 产生等级，等级沿 8 邻域每圈 +1 增量传播；视距、模拟距离、刷新范围各有一套追踪器。
- `ChunkHolder` 保存一排按状态下标的 future；依赖由邻居 future 的组合表达。
- 任务进按等级分桶的队列，近的先执行，等级变化时重排；线程池 = CPU−1，mailbox 用 CAS 保证单消费者。
- 卸载、保存、玩家 ticket 都限流。

## 自测

1. 玩家站在原地不动，视距 10，服务器会把哪些范围的区块加载到 `FULL`？
2. 为什么玩家 ticket 要经过节流器，一次最多 4 个？
3. 区块等级 36 对应什么状态？为什么要加载这么多“半成品”区块？
4. 模拟距离小于视距时，视距外圈的区块处于什么状态？
5. `resortChunkTasks` 解决了什么问题？

参考答案：① 视距内加上外面两圈（等级 31、32、33）都是 `FULL`，即 12 圈。② 避免瞬移或进入新地图时一次性排进大量任务，而是由近及远逐步展开，并且在区块真正变成实体 tick 前不再放入新的。③ `BIOMES`；因为玩家视野内的区块要走完全部阶段，而每个阶段都要求周围一定半径的邻居处于较低一级的状态（第 2 页金字塔）。④ 它们已经加载并发给玩家，但不 tick 方块和实体（它们在 `TickingTracker` 的范围之外）。⑤ 玩家移动后，区块的等级变了，已经在队列里排好的任务要跟着换到新的桶，保证优先级总是反映当前位置。
