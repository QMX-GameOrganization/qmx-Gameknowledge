## 要点

- 第 9 页讲的是“地物放在哪”（`PlacedFeature` 的位置管线）；这一页讲“地物本身长什么样”（`ConfiguredFeature` 的造型算法）。
- 这些造型算法有很强的共性：**用几个简单的几何基元（球、线段、距离和）叠出复杂形状**，用阈值把连续量切成层，用 `BitSet`/`HashSet` 去重，先判定再写入。
- 每个算法都只有几十到两百行，**几乎独立、参数全部来自 JSON**，是最容易搬进自己项目的一批代码。
- 这一页的配图里，矿脉、叶片、晶洞、滴水石的形状是用源码算法的 Python 移植算出来的（晶洞的噪声种子是示意的）。

## 矿脉：一串大小渐变的球

`OreFeature` 没有用椭球（三个轴除以的是同一个半径），而是在一条**水平线段**上放 `size` 个球：

```java
// OreFeature.place / doPlace（简化）
f = nextFloat() * PI                          // 线段在水平面上的方向角
g = size / 8.0                                // 线段半长
A = (x + sin f · g,  y + nextInt(3) − 2,  z + cos f · g)      // 两个端点；y 各自独立随机
B = (x − sin f · g,  y + nextInt(3) − 2,  z − cos f · g)
for q in 0..size-1:
    t = q / size;   center = lerp(t, A, B)
    v = nextFloat() * size / 16
    r = ((sin(PI · t) + 1) · v + 1) / 2        // 中间粗、两端细；r 约 0.5 ~ size/16+0.5
for 每一对球 (q, x):
    if (r_q − r_x)² > |c_q − c_x|²:  较小的球 r = −1   // 一个球完全包含另一个 → 丢掉小的
for 每个 r ≥ 0 的球, 遍历它的包围盒:
    if (dx² + dy² + dz² < 1)   // 以球半径归一化后的距离
        idx = (x − x0) + (y − y0)·W + (z − z0)·W·H
        if (!bitSet[idx]) { bitSet[idx] = true;  对 targets 里第一个匹配的 → 放矿 }
```

![矿脉的形状和方块数分布](/qmx-Gameknowledge/assets/mc-source/30-ore-vein-shape.png)

上图用同一份算法算了 4 种 `size`：上排是一次采样的俯视图，下排是 120 次的方块数分布。可以看到**矿脉的方块数并不等于 `size`**：`size = 17` 的煤矿脉大约 14~29 格（中位数约 23），`size = 4` 的小钻石脉可能只有 0~5 格，`size = 64` 能到 500~800 格。`size` 是“球串的长度”，不是方块数。

几个细节：

1. **`BitSet` 去重**：相邻的球会重叠，同一个格子可能被多个球覆盖，`BitSet` 保证每个格子最多判定一次，因此随机数最多消耗一次（只有目标规则带随机测试，或 `0 < discardChance < 1` 时才真的取随机数），这对确定性很重要。
2. **提前剔除**：只有当包围盒内某个 (x, z) 的 `OCEAN_FLOOR_WG` 高度不低于盒底时，才进入 `doPlace`，整个脉在地面上方时直接放弃。
3. **暴露在空气中的概率**：`discardChanceOnAirExposure`（0~1）在判定每个格子时检查它是否紧邻空气：为 0 总是放；为 1 紧邻空气就不放；中间值按概率。煤矿 0.0（露天可见），埋藏煤 0.5，大钻石 0.7，埋藏钻石 1.0。**这就是“钻石几乎不会露在洞壁上”的来源**。
4. **`ScatteredOreFeature`**（散点式）则完全不同：数量取 `nextInt(size + 1)`，每个位置相对原点的偏移用 `round((nextFloat() − nextFloat()) · min(j, 7))`，序号越大偏移越大，三角分布，直接 `setBlock`。

## 树：树干 + 叶片 + 装饰 + 距离更新

`TreeFeature` 本身只是流水线，具体形状由配置里的三个“零件”决定，再加一组装饰器：

| 零件 | 作用 | 例子 |
| --- | --- | --- |
| `trunk_placer` | 决定树高，放树干，返回“叶片附着点”列表 | `straight`（笔直）、`forking`（分叉）、`fancy`（大橡树）、`bending`、`dark_oak`（2×2）、`cherry` |
| `foliage_placer` | 在每个附着点周围逐层放叶子 | `blob`、`spruce`、`pine`、`fancy`、`acacia`…… |
| `minimum_size` | 判断这里的空间够不够 | `two_layers_feature_size`、`three_layers_feature_size` |
| `decorators` | 放完之后的小装饰 | 蜂巢、可可豆、树干 / 树叶藤蔓、改变地面（灰化土）、附着于树叶的方块 |

```java
// TreeFeature.doPlace（简化）
H = trunkPlacer.getTreeHeight(random)           // base + nextInt(a+1) + nextInt(b+1)
foliageH = foliagePlacer.foliageHeight(random, H, cfg);  foliageR = foliagePlacer.foliageRadius(random, H - foliageH)
// （先检查建造高度范围；有 rootPlacer 时还会先放根）
free = getMaxFreeTreeHeight(...)                // 沿高度逐层用 minimum_size 给的半径检查有没有被挡住
if (!(free >= H || (minClippedHeight 存在 && free >= minClippedHeight))) return false    // minClippedHeight 为空时，free < H 就失败
attachments = trunkPlacer.placeTrunk(..., free, ...)    // 传入的是 free（树可能被削矮），不是 H
for (a : attachments) foliagePlacer.createFoliage(..., a, foliageH, foliageR)   // 叶高和叶半径仍按 H 算
```

写入一律使用 flag 19，并把根、树干、叶、装饰器位置分别记在四个 `HashSet` 里。成功之后依次运行装饰器和 `updateLeaves`。

### 树干放置器

`StraightTrunkPlacer`（橡树、云杉、松树）整个核心只有三行：

```java
setDirtAt(level, below);                                   // 脚下变泥土
for (j = 0; j < H; j++) placeLog(level, pos.above(j));      // 竖直放 H 根原木
return [ FoliageAttachment(pos.above(H), 0, false) ];       // 叶子附着在树顶
```

其它放置器都在这个基础上加变化：`forking`（主干在顶部朝随机水平方向倾斜，另有约 3/4 的概率再长一根斜枝，金合欢）、`bending`（先竖直再沿随机方向折弯，从 `minHeightForLeaves` 起的每一格和折弯段的每一格都产生一个叶片附着点）、`dark_oak`（2×2 树干，外圈约 1/3 的概率长出短枝）、`cherry`（`branch_count` 为 1~3：侧枝最多 2 条，值为 3 时额外在树顶产生一个叶片附着点）。

**大橡树**（`FancyTrunkPlacer`）最复杂：按树高 `k = H + 2` 取主干高 `floor(k · 0.618)`（黄金分割），自上而下每层决定一条分枝：半径取一个圆弧形的轮廓（`treeShape`），分枝端点沿随机角度偏移，先用 `makeLimb(…, false)` **只检查不写入**确认路径畅通，通过后才登记；分枝点高度由 `0.381 × 水平距离` 压低；`trimBranches` 去掉太靠近树干基部的分枝（`(branchBase − y) ≥ k · 0.2` 才保留）。每条分枝末端有一团叶子。`treeShape` 在高度低于 `k · 0.3` 的层返回 −1（该层不长分枝），其余层每层最多一条。

### 叶片放置器：每层一个半径

![不同叶片放置器的每层半径](/qmx-Gameknowledge/assets/mc-source/31-foliage-layers.png)

`FoliagePlacer.placeLeavesRow` 的逻辑很简单：在某一层 y 上，遍历 `[−r, r]²` 的方形，凡是 `shouldSkipLocation` 不跳过的格子就放叶子。**各树种的差别只有两处：每一层的半径序列，和 `shouldSkipLocation`（要不要把角落去掉）**：

| 放置器 | 每层半径 | 角落的处理 |
| --- | --- | --- |
| `blob`（橡树、桦树） | 设 `m` 为相对附着点的 y 偏移（0, −1, −2, …），半径 `max(R + radiusOffset − 1 − m/2, 0)`（Java 整数除法向 0 取整）；橡树 4 层：1, 1, 2, 2（自上而下） | 最外圈的四个角：附着点那一层一定去掉，其它层 50% 去掉 |
| `spruce`（云杉） | 一个小状态机：半径在 `m → m+1 …` 与回到 0/1 之间交替，形成一圈宽一圈窄的锥形 | 角落一律去掉（半径 > 0 时） |
| `pine`（松树） | 从 0 起每层 +1，上限 R（R 含配置里的随机项）；最后一层比倒数第二层小 1（当其 ≥ 1） | 角落一律去掉 |
| `fancy`（大橡树的一团叶） | 两端层取 R，中间层取 R+1 | 去掉距离 `(x+0.5)² + (z+0.5)² > r²` 的格子，得到圆盘 |

云杉的叶高是 `max(4, H − trunk_height)`，松树的叶高是配置里的 3~4。这几个形状都是**同一个函数、不同的几行**。

### 叶子的“距离”：updateLeaves

叶子方块有一个 `DISTANCE` 属性（到最近原木的距离，1~7）。放完所有叶子后，`updateLeaves` 用一个**按距离分 7 个桶的最短路**（类似 Dijkstra）把每片叶子的距离算对：

```java
buckets[0] = 所有原木;            // 距离 0
for d in 0..6: 对 buckets[d] 里每个位置, 对 6 个邻居:
    若邻居不在“已处理”体素里，且带 DISTANCE 属性: 新距离 = min(邻居当前距离, d+1)；新距离 < 7 才放进 buckets[d+1]
出队时 (d != 0): 叶子方块.setValue(DISTANCE, d)，flag 19 写入
```

用 `BitSetDiscreteVoxelShape` 记录处理过的体素（根和装饰器位置也只是在体素里标记为已处理），最后一次性刷新邻接形状。这个距离同时是第 20 页叶子衰减机制的初始状态：**生成时算对，运行时才能靠局部规则维护**。

## 晶洞：距离和 + 阈值分层

![晶洞的分层（水平切片）](/qmx-Gameknowledge/assets/mc-source/32-geode-layers.png)

晶洞（紫水晶晶洞）是“用一个标量场的几个等值面切出同心壳”的典型。

```java
// GeodeFeature.place（简化）
points = k 个中心点: origin + (outerWallDistance 采样 ×3)，每个带一个 pointOffset      // k = distribution_points（3~4）
若采样点所在是空气 / 无效方块，累计超过 invalidBlocksThreshold → 放弃

d = k / outerWallDistance.max
阈值: filling = 1/√1.7,  inner = 1/√(2.2 + d),  middle = 1/√(3.2 + d),  outer = 1/√(4.2 + d)    // 递减

for pos in [origin + min_gen_offset, origin + max_gen_offset]³:    // 默认 −16 ~ +16，可配置
    n = NormalNoise(pos) · noise_multiplier                         // 0.05，让壳的边缘不规则
    s = Σ_{p ∈ points} ( 1/√( |pos − p|² + p.offset ) + n )          // 越靠近中心点 s 越大；噪声项在每个点的贡献里各加一次
    if s < outer:                       跳过            // 在晶洞之外
    elif 裂缝启用 && t ≥ crack阈值 && s < filling:  置空气            // t 是到“裂缝中心”的同类距离和
    elif s ≥ filling: 填充层（空腔，含水晶芽的位置）
    elif s ≥ inner:   内层（紫水晶块；有概率用备用方块；有概率记为“可长水晶芽”的候选）
    elif s ≥ middle:  中层（方解石）
    else:             外层（平滑玄武岩）
```

设计点：

1. **用 `1/√(d² + offset)` 做“势场”**：点离得越近越大，几个点的势场相加就得到一个自然的、有凹凸的团块；`pointOffset` 控制每个点的“软化”程度，避免中心发散。
2. **阈值 = 壳的厚度**：四个阈值递减，层与层的“厚度”由阈值间隔和势场梯度共同决定；改配置里的 `filling / inner / middle / outer` 数值（默认 1.7 / 2.2 / 3.2 / 4.2）就能改各层厚度。
3. **噪声扰动 s 而不是扰动位置**：同一个格子的噪声值 `n` 在每个中心点的贡献里各加一次（共加了 `k` 次，相当于噪声被放大 `k` 倍），壳的边缘就会起伏，而内部各层保持同心。
4. **裂缝**是另外一组“点”的势场：三个点的 y 固定为 +7、+5、+1，水平位置在 4 种方案里随机选（沿 x、沿 z、对角、原点；水平偏移是 `2k + 1`），阈值 `1/√(baseCrackSize + nextDouble()/2 + (k>3 ? d : 0))`。`t` 大的地方挖成空气，并对相邻流体 `scheduleTick`，让水从裂缝里渗进去。
5. 最后在“可长水晶芽”的候选位置，向六个方向找第一个能长芽的格子放下水晶簇。

## 湖与冰山：椭球叠加

**湖**（`LakeFeature`）：在 16×16×8 的 `boolean[]` 里叠加 4~7 个随机椭球（x、z 轴长 3~9，y 轴长 2~6），标记为“湖体”；然后检查边缘：水面及以上（`u ≥ 4`）的邻居不能是液体；水面以下（`u < 4`）的邻居必须是实心方块或要填的流体，否则放弃整个湖。通过后水平面以下填水、以上填空气；边缘一圈在水面以下必换成实心方块，水面及以上只有 50% 的概率换，再视群系冻结。整体向下平移 4 格。

**冰山**（`IcebergFeature`）：先随机决定形态（约 70% 圆形，约 30% 椭圆形），再分别用三个函数决定水面以上、水面以下的各层半径（`heightDependentRadiusRound / Ellipse / Steep`），最后 `smooth` 去掉悬空的点和孤立的点，`carve` 用一个有符号距离函数在冰山上挖一个切口（只有概率触发：椭圆 90%，圆形 30%）。冰山直接读写世界，没有本地缓冲。

**湖**的做法是：先在一个本地的小数组里把形状算好，再整体检查，通过才写入世界。

## 滴水石：一个高度曲线

![滴水石的高度曲线](/qmx-Gameknowledge/assets/mc-source/33-dripstone-profile.png)

大型滴水石柱的轮廓由 `DripstoneUtils.getDripstoneHeight` 决定：

```java
// d = 到柱中心的水平距离, e = 柱半径, f = 高度缩放, g = 钝度（bluntness）
if (d < g) d = g;                                  // 靠近中心的一小段取平，形成“钝头”
i = d / e * 0.384;
h = f * (0.75 · i^(4/3) − i^(2/3) − (1/3) · ln(i));
return max(h, 0) / 0.384 * e;
```

- 距离越近，柱越高，在 `d = e`（柱边缘）处刚好降为 0，所以柱子的底部总是与洞壁严丝合缝；
- `bluntness` 越大，中心被削得越平（图左：0.3 的柱子尖，0.9 的像平台）；
- `height_scale` 直接按比例拉高（图右）。

`LargeDripstoneFeature` 在洞穴的上下洞壁各建一根（钟乳石和石笋），半径是 `[min, clamp(洞高 × max比例, min, max)]` 中的随机整数；高度曲线沿柱子逐格堆叠 `DRIPSTONE_BLOCK`；风偏移 `windSpeed` 让每一层水平错开 `floor(wind × (originY − y))`，做出倾斜的柱子（只对半径和钝度足够大的柱子启用）。`DripstoneClusterFeature` 则是在一片范围内，按“离中心越远越稀疏”的概率放很多小柱子，并让上下柱子的高度重新分配，使它们在中间相接。

## 共通的模式

| 模式 | 出现在哪里 | 好处 |
| --- | --- | --- |
| **几何基元叠加**（球、线段、椭球、距离和） | 矿脉、湖、晶洞、冰山 | 用少量参数得到自然的团块 |
| **阈值分层** | 晶洞的四个阈值、叶片的半径表 | 一个连续量切出同心壳 / 分层 |
| **本地缓冲 / 预检查，再写入** | 湖（`boolean[]` 整体检查）、树（`getMaxFreeTreeHeight`、`makeLimb(false)` 预检查）；矿脉和冰山则直接写世界 | 失败时不需要回滚 |
| **去重容器** | 矿脉的 `BitSet`、树的 `HashSet` | 每个格子只处理一次，也就只消耗一次随机数 |
| **随机游走 / 随机方向** | 分叉树、弯曲树、洞穴、矿脉的线段方向 | 方向由配置里的范围控制 |
| **配置驱动** | 全部 | 新增一种矿或一种树，只是新增 JSON |
| **写入窗口** | `WorldGenLevel` 的写入限制、`BulkSectionAccess` | 不会写出允许的区域，保证跨区块一致 |
| **距离场作为状态** | 叶子的 `DISTANCE`、晶洞的 `s` | 把“形状”变成一个标量，便于阈值与局部更新 |

## 给 Unity 项目的取舍

1. **先做矿脉**。`OreFeature` 的 40 行核心几乎可以原样搬走，是理解“球串 + BitSet”的最好入口。保留 `discard_chance_on_air_exposure`，矿石的外观立刻接近原版。
2. **树用“树干放置器 + 叶片放置器”两个接口**。先写 `Straight` + `Blob`，再加 `Spruce` 的小状态机，最后才考虑大橡树。`updateLeaves` 的距离更新可以和叶子衰减（第 20 页）一起做。
3. **晶洞 / 湖 / 滴水石都可以放进“形状函数 + 阈值”框架**：写一个 `Shape(pos) → 标量`，再有一张阈值表。
4. **所有造型算法都先写进本地缓冲，再整体提交到区块**。这样容易单元测试，也容易放进 Job。
5. **随机数的消耗顺序要稳定**：`BitSet` 去重让重叠格子只判一次，就是为了确定性。

## 小结

- 矿脉是“水平线段上一串大小渐变的球”，方块数不等于 `size`；`discard_chance_on_air_exposure` 控制暴露概率。
- 树由 `trunk_placer`、`foliage_placer`、`minimum_size`、`decorators` 组合；叶片放置器的差别只是每层半径序列和跳过角落的规则；`updateLeaves` 用按距离分桶的最短路写入 `DISTANCE`。
- 晶洞用“势场 + 递减阈值”分层，噪声扰动势场；湖是椭球叠加；滴水石有一个封闭形式的高度曲线。
- 共同点：几何基元、阈值分层、先判定后写入、去重、配置驱动。

## 自测

1. `OreFeature` 里 `size = 17` 为什么放出来的方块不是 17 个？
2. `discard_chance_on_air_exposure = 1.0` 的矿脉会怎样？
3. 云杉和橡树的叶片放置器，差别在哪两处？
4. 晶洞里，哪个量决定“某个格子属于哪一层”？噪声加在哪里？
5. 为什么湖要先在一个 `boolean[]` 里算好，再检查边缘，最后才写入？

参考答案：① 17 是球串的长度，每个球只占自己半径范围内的格子，重叠格子只算一次，实际数量约 14~29 格。② 紧邻空气（6 邻接）的格子就不放矿，所以矿脉不会暴露在空气里（相邻的水、岩浆等不受这条限制）。③ 每层半径序列，以及 `shouldSkipLocation`（是否去掉角落）。④ 势场和 `s`（到各中心点距离的 `1/√(d²+offset)` 之和）与四个递减阈值比较；噪声被加到每个格子的 `s` 上。⑤ 先判定后写入，失败时不需要撤销已写入的方块，也避免写到不能替换的位置。
