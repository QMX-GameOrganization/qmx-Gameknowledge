## 要点

- 客户端渲染的单位是 **16³ 的段（section）**：每个段有自己的网格，变脏就重新编译。
- 编译在**后台线程**做，输入是一份**带 1 格边界的快照**（不读正在变化的区块），输出是顶点数据、可见性集合和半透明排序状态。OpenGL 上传只在渲染线程。
- 远处的段不画，靠三层剔除：**视锥剔除**（相机看不到）、**遮挡剔除**（`VisGraph`：被别的段挡住）、**面剔除**（两个实心方块之间的面不生成）。
- 光照在**建网格时一次性烘进顶点**（平滑光照 / AO），所以光值变了就要重建网格，而不是每帧计算。
- 调度偏向玩家：选项 `prioritizeChunkUpdates` 为 `NEARBY` 时，玩家改动的和近处的段**同步编译**（默认值 `NONE` 时全部走后台）；其余按距离分高 / 低两个优先级队列，用 **2:1** 的配额交替，保证近处先出结果、远处不饿死。

## 一个段的网格是怎么生成的

![区块网格编译的流水线](/qmx-Gameknowledge/assets/mc-source/27-chunk-compile-pipeline.png)

### 脏标记与同步 / 异步

方块变化、光照变化、区块包到达都会调用 `setSectionDirty` 一类方法，只是在对应的 `RenderChunk` 上记一个脏标记。真正的编译在每帧的 `LevelRenderer.compileChunks` 里决定：

```java
// compileChunks（简化）：只处理“视锥内、且光照已就绪”的脏段
for (renderChunk : 视锥内的脏段) {
    boolean 同步 = (选项 == NEARBY)          ? (到相机的距离平方 < 768.0 || renderChunk.isDirtyFromPlayer())
                 : (选项 == PLAYER_AFFECTED) ?  renderChunk.isDirtyFromPlayer()
                 : false;                                                          // 默认 NONE：全部异步
    if (同步) renderChunk.rebuildChunkSync(...);                                    // 主线程立即编译，用固定的一份缓冲
    else      待异步列表.add(renderChunk);
}
uploadAllPendingUploads();                                                          // 先把已完成的结果上传
for (renderChunk : 待异步列表) renderChunk.rebuildChunkAsync(dispatcher, ...);
```

`isDirtyFromPlayer` 是“脏，并且是玩家自己改的”。选项为 `NEARBY` 时近处的段和玩家改动的段同步编译；为 `PLAYER_AFFECTED` 时只有玩家改动的同步；**默认的 `NONE` 下所有脏段都走后台线程**。同步编译让放置 / 破坏方块的反馈当帧就能看到，而不是等后台线程排队。距离平方 768 约等于 28 格。

### 两个优先级队列

```java
// ChunkRenderDispatcher.pollTask（简化）
// 每连续取 2 个高优先级任务（MAX_HIGH_PRIORITY_QUOTA = 2），就放 1 个低优先级任务
```

- 高优先级队列是 `PriorityBlockingQueue`，按**任务创建时到玩家的距离**排序；低优先级是先进先出。
- 已经编译过的段，重建都是高优先级；首次编译被取消超过 2 次的段也会升级。
- 任务通过 `ProcessorMailbox` 串行派发到 `Util.backgroundExecutor()`（第 17 页会讲这个线程池），同时运行的编译数受缓冲数量限制：每个槽位对应一份 `ChunkBufferBuilderPack`（所有渲染层的缓冲加在一起），槽位数取 `min(处理器数, 按最大内存 30% 推出的数量)`，至少 1 个。

### 快照：后台线程不读活数据

`RenderRegionCache.createRegion(level, origin − 1, origin + 16, 1)` 在主线程上复制编译需要的数据。逻辑上要读的是**这个段及向外 1 格**（18³ 个方块的范围），但**复制的粒度是整根区块柱**（通常 3×3 根），同一帧内多个段共用同一份缓存：

- 方块：复制各 section 的 `PalettedContainer`（`getStates().copy()`），全空气的 section 存 `null`，读取时直接返回空气；
- 方块实体：整根柱的 `ImmutableMap.copyOf`；
- 流体：不单独存，由方块状态推出；
- **光照没有复制**：`getLightEngine()` 直接指向世界的光照引擎。光照引擎自己用双缓冲发布结果（第 15 页），后台线程读到的是一份一致的快照，不需要再复制一遍；
- 如果 18³ 对应的 Y 区间内完全是空的，`createRegion` 返回 `null`，整个段不用编译。

复制 1 格边界的原因与你笔记里的“跨区块边界剔除”一样：段边缘的面要不要生成，取决于隔壁那个方块。

## 面剔除：`shouldRenderFace`

对每个方块的每个面，先问“要不要生成”：

```java
// Block.shouldRenderFace（简化）
if (state.skipRendering(邻居, direction)) return false;     // 同种方块（如玻璃）之间不画
if (!邻居.canOcclude())                   return true;      // 邻居不挡光（空气、树叶…）→ 要画
key = (自己, 邻居, direction);
if (OCCLUSION_CACHE 命中) return 缓存值;                       // 缓存里存的就是“应渲染”
if (自己这个面的遮挡形状为空) return true;                     // 不入缓存
应渲染 = Shapes.joinIsNotEmpty(自己面形状, 邻居面形状, ONLY_FIRST);   // 自己的面有部分没被邻居盖住
缓存[key] = 应渲染;  return 应渲染;
```

- 缓存是 `ThreadLocal<Object2ByteLinkedOpenHashMap<BlockStatePairKey>>`，**容量 2048，最近最少使用淘汰**；每个编译线程一份，无锁。
- 绝大多数方块是完整立方体，判断“邻居面盖住自己面”的结果只取决于 `(自己状态, 邻居状态, 方向)` 这个三元组，所以命中率很高。
- 这是你笔记里“相邻面剔除”的通用版本：不只是“邻居是实心就不画”，而是用面的遮挡形状（楼梯、台阶也能正确处理）。

## 生成网格：渲染层、顶点与排序

每个方块的网格由 `BlockRenderDispatcher.renderBatched` → `ModelBlockRenderer.tesselateBlock` 写入对应渲染层的缓冲。区块用到的渲染层（`RenderType.chunkBufferLayers()`）有五种，绘制顺序固定：

| 渲染层 | 用途 | 每层缓冲大小 |
| --- | --- | --- |
| `solid` | 不透明方块 | 2 MB（2097152） |
| `cutout_mipped` | 镂空（树叶），使用 mipmap | 128 KB |
| `cutout` | 镂空（玻璃板、栅栏），不使用 mipmap | 128 KB |
| `translucent` | 半透明（水、有色玻璃） | 2 MB |
| `tripwire` | 绊线等 | 256 KB |

先画 solid、cutout_mipped、cutout，再画 translucent、tripwire（半透明的列表从远到近倒序遍历）。

块顶点格式 `DefaultVertexFormat.BLOCK`：位置（3 个 float）+ 颜色（4 个 ubyte）+ 纹理坐标（2 个 float）+ lightmap 坐标（2 个 short）+ 法线（3 个 byte）+ 1 字节填充，**合计 32 字节**（这是按各元素类型相加得到的）。一个面 4 个顶点就是 128 字节。

半透明需要按距离排序才能正确混合。编译时把**排序状态**（`SortState`）一起保存；之后相机移动，只需要 `ResortTransparencyTask`（始终是高优先级任务）取回状态、重排索引、重新上传，**不必重建整个网格**。相机相对上次重排位置移动超过 1 格后，绘制半透明层时每次最多提交 15 个段的重排（相机跨段时检查所有视锥内的段，否则只检查轴对齐的段）。

## 遮挡剔除：VisGraph

视锥剔除只能去掉“相机背后和视野外”的段，但山洞里、山背后的大量段虽然在视野内，却完全看不到。`VisGraph` 用一个很小的预计算解决：**对每个段，算出“从哪个面进来，能从哪个面出去”**。

### 编译时：段内泛洪

```java
// 编译一个段时，每遇到不透明（isSolidRender）的方块就 visGraph.setOpaque(pos)
// 编译结束：compileResults.visibilitySet = visGraph.resolve()

resolve():
    if (不透明格子 < 256)  → 全部面互相可见          // 太空了，不值得算
    if (不透明格子 == 4096) → 全部面互相不可见        // 整段是实心
    else 对段表面的 1352 个格子（16³ − 14³）：
        若该格子是空的且没被访问过 → 6 邻域广度优先泛洪，收集它碰到的所有面（EnumSet<Direction>）
        VisibilitySet.add(这些面)   // 集合里的面两两置位
```

结果存成一个 6×6 = 36 位的位集（`VisibilitySet`）：第 (a, b) 位为 1 表示“从面 a 进来，能走到面 b”。每个段只多保存 36 位。

### 渲染时：沿连通的面做广度优先遍历

![VisGraph 遮挡剔除（2D 玩具）](/qmx-Gameknowledge/assets/mc-source/25-visgraph-culling.png)

上图是 2D 玩具：9×9 个段，每段 12×12 个格子，白色为空气，深色为实心。三幅图是相机位于不同段（红框）时，遍历送去绘制的段（绿）和被剔除的段（灰斜线）。真实的遍历（`LevelRenderer.updateRenderChunks`）：

```java
// 从相机所在的段出发，广度优先
queue.add(相机所在段)
while (queue 非空):
    info = queue.poll()
    for (direction in 6 个方向):
        if (info 的“已走过方向”含 direction.opposite) continue           // 不回头
        if (info 有来源方向 && 没有任何来源 j 满足
              compiled.facesCanSeeEachother(j.opposite, direction)) continue   // 入口面到出口面不连通 → 剪枝
        邻居 = 该方向的相邻段;  超出渲染距离或世界高度 → 跳过
        邻居没有加载齐周围区块（hasAllNeighbors 为 false）→ 不入队；不在渲染边界附近时 500ms 后触发一次全量重算
        邻居入队        // 这里没有视锥判断，视锥剔除在遍历结束后单独做
```

要点：

1. **来源方向**：到达某个段时记下“是从哪个方向走进来的”，只允许从入口面走向与它连通的出口面。
2. **不回头**：沿路径已走过的方向的反方向不再走，避免来回。
3. **旁观者进入实心方块时关闭**：`smartCull` 默认开；只有旁观者模式下相机位于实心方块里时才关掉（`setupRender` 的 `isSpectator` 参数），否则从方块内部出发的遍历会把外面剔光。非旁观者没有这个特判。
4. **距离超过 60 格时额外做射线检查**：沿射线看中间的段是否已被访问，进一步减少误绘。
5. **相机量化**：位置按 8 格、旋转按 2° 的粒度变化才触发重新遍历，不是每帧都做；全量遍历在后台线程做，局部更新用 `recentlyCompiledChunks`。
6. 遍历完后再做**视锥剔除**（`frustum.isVisible(chunk 的包围盒)`），得到最终要绘制的段。

注意它是**保守的**：只要存在一条连通的面路径就认为可能可见。它并不精确（它不知道视线角度），但代价极小，而且不会漏画。

## 平滑光照与 AO：光在建网格时烘进顶点

![平滑光照 / AO](/qmx-Gameknowledge/assets/mc-source/26-smooth-lighting-ao.png)

`ModelBlockRenderer.tesselateBlock` 有两条路径：

- **平滑光照（AO）**：条件是选项开启、方块自身不发光（`getLightEmission() == 0`）、模型允许 AO。
- **平面光照**：每个面只取面前那一格的光，整面一个亮度。

AO 路径对每个面的每个顶点，取四个格子的平均（`AmbientOcclusionFace.calculate`）：

```java
// 一个顶点：中心格 w、两条边邻 (f, h 之类)、一个角邻
亮度 = (边邻1 + 边邻2 + 角邻 + 中心) * 0.25;
// 每一项是该格的 shade brightness：完整碰撞方块 0.2，否则 1.0（BlockBehaviour.getShadeBrightness）
// 每个角邻对应两条相关边邻：若这两条边邻沿面法线外侧的方块都既挡视线又挡光，
// 就不读角邻，直接复用其中一条边邻（源码里的 corners[0]）的 shade 和光值
最后整个面乘以方向系数 getShade(direction, shaded)    // 顶面最亮，侧面稍暗，底面最暗
```

光照（lightmap）同理：四项各自取 `LevelRenderer.getLightColor`，再用 `blend` 平均，其中光值为 0 的项用中心值代替。

`getLightColor` 把天空光与方块光打包成一个 int：`sky << 20 | max(block, 方块自身发光) << 4`；发光渲染的方块直接返回常量 `15728880`（= `0xF000F0`，两个 15）。这个值作为顶点里的 lightmap 坐标，片元着色器再去采样一张 16×16 的 lightmap 贴图（昼夜、天气变化都靠这张贴图，不用重建网格）。

两个性能点：

1. **线程私有缓存**：`ModelBlockRenderer.Cache` 是 `ThreadLocal`，容量 100，只在一次编译期间生效（`enableCaching()` 到 `clearCache()` 之间），避免同一个格子的光照和 shade 值被反复读取。
2. **AO 只用邻居的 `shade` 与光值**，没有任何射线或遮挡计算，成本是“每个顶点读 4 个格子”。

### 光变化如何触发重建

- 方块变化：`blockChanged` 标记包含“方块坐标 ±1”范围内方块的所有段，方块在段中间时只涉及 1 个段，靠近边界才会涉及邻居，**最多 3×3×3 个**（周围的段也受影响，因为 AO 读取了它们的数据）；
- 光照引擎回调“这个段的光变了”：`ClientChunkCache.onLightUpdate` 只标记**这一个段**，不带邻居；
- 区块包、光照数据包到达：`setSectionDirtyWithNeighbors`，标记 3×3×3。

## 与你的网格优化清单对照

| 你的条目 | 客户端的做法 | 备注 |
| --- | --- | --- |
| #1 相邻面剔除 | `shouldRenderFace` + 面形状遮挡 + `OCCLUSION_CACHE`（LRU 2048） | 你的位掩码版本是它的简化；形状遮挡能处理台阶、楼梯 |
| #3 / #4 按 16×16 切分与边界剔除 | 16³ 段 + 1 格边界快照 | 一致；MC 用的是 16³ 而不是整根柱子，改一个方块只重建一个段（及其邻居） |
| #5 分帧 | 选项为 `NEARBY` 时玩家改动的和近处的段同步编译，其余（默认全部）交给后台线程；结果在渲染线程集中上传（上传没有逐帧预算） | 和你“按依赖顺序分帧”都是把重活挪出主线程 |
| #7 缓冲复用 | `ChunkBufferBuilderPack` 池 + `ThreadLocal` 缓存 | 缓冲是按槽位预分配的，用完回收 |
| 规划 #5 工作线程构建顶点 | `RebuildTask` 在后台线程；快照保证线程安全 | 一致，Mesh 上传在主线程 |
| 规划 #7 按 16³ 切分网格 | `RenderChunk` | 一致 |
| 你还没有的 | 遮挡剔除（`VisGraph`）、半透明排序、AO | 如果你的世界有大量洞穴和山体，遮挡剔除收益明显；AO 是纯 CPU 的一次性开销 |

## 给 Unity 项目的取舍

1. **先做快照 + 后台线程**：把 18³ 的数据拷到 `NativeArray`（MC 复制的是整根区块柱，你只需要拷用得到的部分），在 Job 里生成顶点，主线程只上传 `Mesh`（`Mesh.AllocateWritableMeshData` / `ApplyAndDisposeWritableMeshData`）。
2. **同步 / 异步分档**：玩家改动的段当帧同步（或下一帧），其余进队列，高 / 低优先级 2:1。
3. **AO 放进顶点颜色**：4 个格子的平均，写入顶点色即可，不需要额外贴图；光变化标记单段，方块变化标记 3×3×3。
4. **遮挡剔除可以后做**：先用视锥剔除；等地下和山地的段数很多时，再做 `VisGraph`（36 位 / 段，泛洪一次，遍历时用位运算）。
5. **半透明单独一层**：保存排序状态，相机移动只重排索引，不重建顶点。

## 小结

- 编译在后台线程，输入是带 1 格边界的快照；选项为 `NEARBY` 时近处和玩家改动的段同步编译，其余按距离分两队列 2:1 派发。
- 三层剔除：视锥、`VisGraph`（面到面的可见性 + 广度优先）、面剔除（带 LRU 缓存）。
- 光照与 AO 在建网格时烘进顶点；方块变化标记 3×3×3，光变化只标记一个段。
- 半透明保存 `SortState`，重排只重新上传索引。

## 自测

1. 在 `prioritizeChunkUpdates` 设为 `NEARBY` 或 `PLAYER_AFFECTED` 时，为什么玩家放置方块后，那个段会在当帧同步编译，而不是排进后台队列？
2. `VisGraph` 里“不透明格子少于 256 个，就认为所有面互相可见”，为什么这样做？
3. `OCCLUSION_CACHE` 的键为什么包含方向？
4. 一个顶点的 AO 亮度是怎么得到的？两条边邻都被挡住时角邻怎么处理？
5. 光照引擎通知一个段的光变了，为什么只重建这一个段，而方块变化要标记 3×3×3？

参考答案：① 为了让操作反馈立刻可见；后台队列有排队延迟。② 空旷的段几乎不可能挡住视线，跳过泛洪省掉开销，代价只是遮挡剔除对它不起作用。③ 同一对方块，从不同方向看，面的遮挡关系不同。④ 中心、两条边邻、一个角邻的 shade 值取平均；对应的两条边邻外侧都既挡视线又挡光时，不读角邻，直接复用一条边邻的值。⑤ 方块变化会影响邻居段的 AO（AO 读取了邻居的数据），光值变化本身只是这个段内的数据，而光值跨段传播时，光照引擎会对每个受影响的段分别通知。
