> 对应源码：`world/level/lighting/*`（`LightEngine`、`BlockLightEngine`、`SkyLightEngine`、`ChunkSkyLightSources`、`LayerLightSectionStorage`、`LevelLightEngine`）、`server/level/ThreadedLevelLightEngine`、`DataLayer`、`ChunkStatus`（`INITIALIZE_LIGHT`、`LIGHT`）、`LevelChunk.setBlockState`。

## 要点

- 光有两种：**方块光**（火把、岩浆等光源，0~15）和**天空光**（天空可见处为 15）。游戏里用到的“亮度”是 `max(天空光 − 天空变暗量, 方块光)`。
- 每个方块的光值只占 **4 位**，一个 16³ 的段用 `DataLayer`（2048 字节）保存。
- 传播是**洪水填充**：每走一格衰减 `max(1, 方块不透明度)`。更新靠两条队列——“**减少**”队列把过期的光抹掉，“**增加**”队列再把光重新灌回来。
- 光照变化是**批量**的：`setBlock` 只是把位置记进一个集合，等光照线程一次性处理，大量改动被合并。
- 天空光用一个**每列“最低光源高度”的高度图**（`ChunkSkyLightSources`）代替逐格传播：光源之上整列直接是 15，只在柱子的边缘向侧面传播。
- 光照在**单独的线程**运行，用**双缓冲**把结果发布给其他线程；区块生成里有两个专门的阶段 `INITIALIZE_LIGHT` 和 `LIGHT`。

## 数据：4 位的光值

| 概念 | 内容 |
| --- | --- |
| 光值 | 0~15，`LightEngine.MAX_LEVEL = 15` |
| 存储 | `DataLayer`：`byte[2048]`，每字节存两个方块（nibble）；下标 `y<<8 \| z<<4 \| x` |
| 光照段 | 对应每个 16³ 段，但上下各多 1 段（`LIGHT_SECTION_PADDING = 1`），所以光照段数 = 方块段数 + 2 |
| 段类型 | `EMPTY`（没有光照数据）、`LIGHT_ONLY`（本段全是空气，但 3×3×3 邻域内有含方块的段，所以需要存光）、`LIGHT_AND_DATA`（本段含有方块） |
| 惰性 | `DataLayer` 的数组是惰性分配的：新建或被 `fill()` 之后 `data == null`，读取直接返回 `defaultValue`，不占数组；一旦 `set()` 写入就会分配 2048 字节 |

每个方块 4 位，意味着一个 16×16×384 的区块的方块光和天空光各最多约 **52 KB**（24 个方块段 + 上下各 1 个填充段 = 26 段，每段 2048 字节），而且大量未写入的天空段没有数组，实际远小于此。

## 传播算法：两条队列

![方块光的增量更新](/qmx-Gameknowledge/assets/mc-source/24-block-light-incremental.png)

上图是用 2D 玩具重写的同一套规则（衰减 1、不透明方块挡光）。三步操作：放两个火把、砌一道墙、拿走左边的火把。注意第二、三幅的标题：**每次只处理变化涉及到的那部分，而不是重算全部 135 格**。

### 队列里放什么

每个队列元素是两个 `long`：位置，加一个 `QueueEntry`——把几项信息压进一个 `long`：

| 位 | 内容 |
| --- | --- |
| 低 4 位 | 光的“来源等级” `fromLevel` |
| 接着 6 位 | 六个方向的掩码：要不要向这个方向传播（`shouldPropagateInDirection`） |
| 标志位 | `FLAG_FROM_EMPTY_SHAPE`（来源方块形状为空）、`FLAG_INCREASE_FROM_EMISSION`（这次增加来自光源本身） |

队列用 `LongArrayFIFOQueue`（原始类型队列，没有装箱）。方向掩码让每次入队时可以**跳过“来的那个方向”**（`decreaseSkipOneDirection` / `increaseSkipOneDirection`），不做无意义的回头检查。

### 三个函数：检查、增加、减少

```java
// BlockLightEngine.checkNode(pos) —— 一个位置的方块或光源变了
emission = 该方块的发光等级（该区块列没启用光照时为 0）;  stored = 现在存的光值;
// 前提：这个位置所在的段正在存光（storingLightForSection）
if (emission < stored) {                      // 原来的光比现在能提供的亮：这里的光是“过期”的
    stored = 0;  enqueueDecrease(pos, 来源等级 = 原 stored);        // 先抹掉，再让邻居重新补
} else {
    enqueueDecrease(pos, PULL_LIGHT_IN_ENTRY)                       // 来源等级 1：让亮的邻居把光“灌”过来
}
if (emission > 0) enqueueIncrease(pos, 来源 = 光源, 等级 = emission);
```

```java
// propagateDecrease(pos, 来源等级 i)：对每个允许的方向 n
j = stored(n);
if (j == 0) continue;
if (j <= i - 1) {                              // n 的光是从 pos 传来的 → 一起抹掉
    stored(n) = 0;
    if (emission(n) < j) enqueueDecrease(n, j, 跳过回头方向);
    if (emission(n) > 0) enqueueIncrease(n, emission(n));           // n 自己是光源，要重新灌回去
} else {
    enqueueIncrease(n, j, 只朝 pos 方向);        // n 的光不低于来源等级，说明不是从 pos 来的（有别的光源）→ 让它回灌；PULL 条目（等级 1）时，所有有光的邻居都会回灌
}
```

```java
// propagateIncrease(pos, 等级 i)：对每个允许的方向 n
k = i - 1;                                     // 至少衰减 1
if (k > stored(n)) {
    o = i - max(1, 不透明度(n));
    if (o > stored(n) && !形状遮挡(pos → n)) {
        stored(n) = o;
        if (o > 1) enqueueIncrease(n, o, 跳过回头方向);
    }
}
```

这就是经典的“**先移除，再重新填充**”。设计上的几个点：

1. **减少队列先跑完，增加队列再跑**（`runLightUpdates` 里 `propagateDecreases()` 然后 `propagateIncreases()`）。先把所有受影响的旧光清零，再从仍然成立的光源重新铺开，避免两个过程互相干扰。
2. **只处理受影响的区域**。拿走左边的火把（图中第三幅）只需要处理被这个火把照亮的那片，重新灌回来的光来自右边仍然存在的火把。
3. **不透明度用 `max(1, getLightBlock)`**：空气也要衰减 1，不透明方块的 `lightBlock` 通常是 15，光到那里减为 0 或负数，传不过去。
4. **形状遮挡**：楼梯、台阶等形状特殊的方块，两个相邻面是否真的相接决定能不能透光（`shapeOccludes` 比较两个面的形状）。只有 `useShapeForLightOcclusion` 的方块才走这条较慢的路径，普通方块只看不透明度。

## 批量：先记录，再统一处理

方块变化时并不会立刻传播光，只是把位置放进一个集合：

```java
// LightEngine
checkBlock(pos) { blockNodesToCheck.add(pos.asLong()); }          // LongOpenHashSet：同一个位置反复变化只记一次

runLightUpdates() {
    for (pos : blockNodesToCheck) checkNode(pos);                  // ① 把所有变化展开成队列元素
    blockNodesToCheck.clear();
    propagateDecreases();                                          // ② 先减少
    propagateIncreases();                                          // ③ 再增加
    storage.markNewInconsistencies(this);                          // ④ 装入排队的光照数据（来自存档），移除失效的段
    storage.swapSectionMap();                                      // ⑤ 发布结果（双缓冲，见下）
}
```

图 24 的第二幅就是这个效果：砌 8 格墙，如果一格一格各跑一遍要 255 次队列处理；放进集合一起处理只要 **66 次**，因为同一片区域不会被反复抹掉又重新灌回来。

另外 `LightEngine.getChunk` 里还有一个**两项的最近区块缓存**（`lastChunk[2]`），传播时相邻方块几乎都在同一个区块，免得每次都去查区块表。

## 天空光：用高度图代替逐格传播

天空光和方块光的传播规则相同，但有一个特殊情形：**一整列从天空直射下来的光**。如果按方块光那样从世界顶部逐格往下传，每个区块要处理 16×16×约 300 个方块。`ChunkSkyLightSources` 用一张高度图解决：

```java
// 每个区块一份：256 个值（每列一个），表示这一列“最低的天空光源”的 y
// 存储用 BitStorage，位宽 = ceilLog2(世界高度 + 2)
getLowestSourceY(x, z)
```

“天空光源”的定义：从上往下走，直到遇到第一个**挡光的边缘**（`isEdgeOccluded`：下面那格 `lightBlock != 0`，或者两个相邻面的形状互相遮挡）。这个高度**以上**整列都是天空光 15，不需要传播；只在以下几处补充：

- 列与列之间高度不同的位置：光源更低（照得更深）的一列，对低于相邻列光源高度的那些格子入队，向相邻列传播，照亮悬崖下面、洞口里面；
- 光源高度变化时（挖开或封上洞口）：`removeSourcesBelow` 抹掉原来在光源之下的 15，`addSourcesAbove` 把新露出的列填成 15。

初始化时（`SkyLightEngine.propagateLightSources`）也是这样：对每一列，从高到低把 `DataLayer` 中光源以上的格子直接写成 15，**只对“边界上”的格子入队**（`z == 光源高度` 或者 `z < 相邻列的光源高度`）。大片开阔的天空完全不进队列。

方块变化时维护这张图的代价也很小：`ChunkSkyLightSources.update(x, y, z)` 先检查改动位置上下两条边，决定光源高度要不要升降；只有在打开当前最低光源处的遮挡时，才需要沿这一列向下扫描找到下一个遮挡边。

## 运行时：什么时候触发光照更新

触发点在 `LevelChunk.setBlockState`：

```java
if (段是否全空气 发生了变化)  lightEngine.updateSectionStatus(pos, 现在是否全空气);
if (LightEngine.hasDifferentLightProperties(旧状态, 新状态)) {     // 只有“影响光”的变化才触发
    skyLightSources.update(...);                                    // 维护天空光源高度图
    lightEngine.checkBlock(pos);                                    // 记进待检查集合
}
```

`hasDifferentLightProperties` 判断四件事：`getLightBlock`（不透明度）变了、`getLightEmission`（发光等级）变了、旧或新状态使用形状遮挡。**把泥土换成石头不会引起任何光照计算**，因为两者的光学属性相同。

## 后台线程与双缓冲

光照有自己的线程（`ThreadedLevelLightEngine`，一个 `ProcessorMailbox`）。其他线程只负责投递任务：

```java
// ThreadedLevelLightEngine
checkBlock(pos) → addTask(chunkX, chunkZ, PRE_UPDATE, () -> super.checkBlock(pos))   // 经 ChunkTaskPriorityQueueSorter 按区块等级投递
// 光照线程每次醒来：
runUpdate() {
    取最多 1000 个任务;
    先执行其中的 PRE_UPDATE 任务;     // 记录变化、启用光照、传入数据
    super.runLightUpdates();           // 整批一次性传播（上面那套两条队列）
    再执行 POST_UPDATE 任务;           // 回调：例如“这个区块光照完成”
}
```

- **批量上限 1000**：一次最多合并 1000 个任务，再多就下一轮。
- **PRE → 传播 → POST** 的三段结构：所有输入先就位，传播只发生一次，之后才通知完成。
- **双缓冲**：存储里有 `updatingSectionData`（光照线程写）和 `visibleSectionData`（其他线程读）。`runLightUpdates` 结束时 `swapSectionMap()` 把结果发布出去。主线程和渲染线程读到的永远是一份**一致的快照**，不会读到传播做了一半的光值，也不需要加锁。代价是读到的光可能比最新状态晚一个批次。

## 区块生成里的两个阶段

回到第 2 页的 12 个 `ChunkStatus`，光照占了其中两个：

| 阶段 | `range` | 做什么 |
| --- | --- | --- |
| `INITIALIZE_LIGHT` | 0 | `chunk.initializeLightSources()`：根据当前方块算出天空光源高度图；`ThreadedLevelLightEngine.initializeLight`：把非全空气的段登记为“有数据”；只有已经光照正确的区块才在这里启用光照，新生成的区块在 `LIGHT` 阶段才启用 |
| `LIGHT` | 1 | `lightChunk`：`setLightCorrect(false)`，对尚未光照的区块调用 `propagateLightSources`（方块光源入队、天空光按高度图铺开）；在 `POST_UPDATE` 里 `setLightCorrect(true)` 并释放光照票据 |

两点值得注意：

1. `LIGHT` 要求邻居半径 1：区块边缘的光需要邻居的方块（光源和遮挡）才能算对，所以光照放在 `FEATURES` 之后——树、矿、结构都放好以后再算光。
2. `isLighted(chunk) = 状态 ≥ LIGHT && lightCorrect`。**从存档读出的区块如果光照标记正确，就不会重新算**，只有新生成的区块才需要完整的 `propagateLightSources`。

## 光的用途

`LevelLightEngine.getRawBrightness(pos, skyDarken)` 返回 `max(天空光 − 天空变暗量, 方块光)`。天空变暗量（`skyDarken`）随昼夜与天气变化，所以**天空光的存储值不随时间变，夜晚只是在读取时减去一个数**。这样昼夜交替不需要重新传播任何东西。

光值被许多系统读取：怪物刷新（第 14 页：天空光、方块光、雷暴时的亮度）、植物生长、渲染（顶点亮度）、各种方块的条件。

## 设计思想与优化汇总

| 设计 | 解决的问题 |
| --- | --- |
| **只在光学属性变化时触发**（`hasDifferentLightProperties`） | 绝大多数方块变化不影响光，不产生任何计算 |
| **批量集合 + 一次传播** | 合并重复变化（图 24：255 次 → 66 次） |
| **先减少、后增加** | 清除过期的光，再从仍然成立的光源重新铺开，保证结果正确 |
| **`long` 打包的队列元素 + 方向掩码** | 无装箱、无对象分配；跳过回头方向 |
| **天空光源高度图** | 整列直射光不用传播，开阔天空不进队列 |
| **`DataLayer` 惰性数组、按邻域决定哪些段需要存光** | 未写入的段不占内存 |
| **独立线程 + 任务按区块等级排序 + 批量 1000** | 主线程不被光照阻塞；离玩家近的区块先算 |
| **双缓冲（updating / visible）** | 读写分离，无锁，读者拿到一致的快照 |
| **最近区块缓存 `lastChunk[2]`** | 传播时反复查邻居区块的开销 |
| **已光照的存档区块不重算** | 加载速度 |

## 给 Unity 项目的取舍

| 阶段 | 做什么 | 要点 |
| --- | --- | --- |
| 1 | 只做**方块光**：光源 + 洪水填充 | 每个区块一个 `NativeArray<byte>`（或 nibble）；增加队列即可，先不处理移除 |
| 2 | 加**移除**（减少队列） | 严格“先减少、后增加”；用 `int` 打包位置，用 `NativeQueue<int>`；放置 / 破坏方块只记录位置，等帧末统一处理 |
| 3 | **天空光**：每列最低光源高度 | 开阔区域直接填 15；只对边界入队 |
| 4 | **跨区块** | 区块边缘的光要读邻居；改动落在边缘时标记邻居也要重新网格化 |
| 5 | **线程与双缓冲** | 光照放进 Job 或工作线程；两份数组，写一份、读一份，批次结束交换 |
| 6 | **网格** | 光值作为顶点属性（或贴图），光变化的区块要重建网格（包括被边缘光影响的邻居） |

一个小提醒：如果你的世界是一次性生成大地图，先用“生成完再算一遍光”的批量版，不要在生成过程中走增量路径；增量更新用在玩家改动世界时。

## 小结

- 光值 4 位，方块光和天空光分开存；亮度 = `max(天空光 − 天空变暗量, 方块光)`。
- 传播是洪水填充；增量更新靠“先减少、后增加”两条队列，位置变化先记进集合再批量处理。
- 天空光用每列最低光源高度的高度图代替逐格传播。
- 光照在独立线程，批量 1000，结果用双缓冲发布；生成阶段有 `INITIALIZE_LIGHT` 与 `LIGHT` 两步。

## 自测

1. 为什么先跑“减少”队列再跑“增加”队列？
2. 把泥土换成石头为什么不触发光照？
3. 一个完全开阔的平原，天空光是怎么算出来的？为什么不需要把光从 y=320 逐格传到地面？
4. 双缓冲解决了什么问题？代价是什么？
5. 夜晚到来时，为什么不需要重新传播天空光？

参考答案：① 先把所有受影响的旧光抹掉，再从仍然成立的光源重新铺开，两个过程不会互相覆盖。② 两种方块的不透明度、发光等级和形状遮挡属性都一样，`hasDifferentLightProperties` 为 false。③ 由 `ChunkSkyLightSources` 记录每列最低光源高度，光源以上整列直接写成 15，只在边界入队。④ 保证读线程拿到一致快照、无锁；代价是读到的光值可能晚一个批次。⑤ 存储的天空光不变，读取时用 `sky − skyDarken`，昼夜变化只改变 `skyDarken`。
