> 适用版本：Addressables 1.2x 到 2.x。API 示例基于 `AsyncOperationHandle`；2.x 对部分 API 有调整，具体签名以所装版本为准（待核实）。

## 要点

- 运行时更新的三步：**检查目录更新**（`CheckForCatalogUpdates`）→ **更新目录**（`UpdateCatalogs`）→ **下载新内容**（`GetDownloadSizeAsync` + `DownloadDependenciesAsync`）。
- 发版构建与更新构建不同：首次发版用 *New Build*；之后的热更用 *Update a Previous Build*，依赖保存好的 `addressables_content_state.bin`。
- 静态组（Cannot Change Post Release）里的资源如果有变化，更新构建会把变化的资源**放进新的远程组**，原包不动，这样旧客户端缓存的包仍然有效，只下载新增部分。
- 下载后的包进入 Unity 的 AssetBundle 缓存，之后加载直接读缓存。缓存可手动清理。

## 运行时流程

```csharp
IEnumerator Boot()
{
    // 1. 初始化(拿到本地 catalog)
    yield return Addressables.InitializeAsync();

    // 2. 检查远程 catalog 是否更新
    var check = Addressables.CheckForCatalogUpdates(false);
    yield return check;
    if (check.Status == AsyncOperationStatus.Succeeded && check.Result.Count > 0)
    {
        // 3. 更新 catalog
        var update = Addressables.UpdateCatalogs(check.Result, false);
        yield return update;
        Addressables.Release(update);
    }
    Addressables.Release(check);

    // 4. 计算需要下载的体积(按 key 或 label)
    var sizeOp = Addressables.GetDownloadSizeAsync("preload");
    yield return sizeOp;
    long bytes = sizeOp.Result;
    Addressables.Release(sizeOp);

    // 5. 下载
    if (bytes > 0)
    {
        var dl = Addressables.DownloadDependenciesAsync("preload", true);
        while (!dl.IsDone) { UpdateProgress(dl.PercentComplete); yield return null; }
    }
}
```

要点：

- `autoReleaseHandle` 参数设为 `false` 时，必须自己 `Release` 句柄，否则泄漏；设为 `true` 则完成后自动释放。
- `GetDownloadSizeAsync` 返回 0 表示依赖已全部在本地缓存。
- 默认的 `Addressables.InitializeAsync` 在第一次加载时会自动调用，但显式调用便于控制时机与错误处理。
- 也可以配置 catalog 自动检查（Addressable Asset Settings 中的 *Check for Content Update Restrictions* 与 Catalog 相关选项，行为随版本，待核实），一般项目选择手动控制以便显示进度。

## 发版与更新构建

**首次发版**

1. 设置各组的 Build/Load Path（本地或远程）与更新限制。
2. 在 Addressables Groups 窗口 *Build → New Build → Default Build Script*。
3. 保存构建产物，**把 `addressables_content_state.bin` 提交到版本管理**。
4. 把远程产物上传到 CDN，客户端包内带本地部分与远程 catalog 地址。

**之后更新内容**

1. 拉取上次发版对应的 `addressables_content_state.bin`。
2. 先运行 *Tools → Check for Content Update Restrictions*：检查静态组里有哪些资源在发版后被修改，工具会把这些资源移到新的远程组。
3. *Build → Update a Previous Build*，选择那份 `.bin`。
4. 上传新的 catalog、hash 与新增或改变的 bundle 到 CDN。保持旧文件不删（旧版本客户端可能还在用）。

核心思想：**静态组的包一旦发布就不再变化**，变化内容以新包形式追加。可变组（Can Change Post Release）的包会被重新构建，同名但内容哈希不同，客户端会重新下载整个包。

## 缓存

- 下载的 bundle 存放在 Unity 的 AssetBundle 缓存目录，按 bundle 名与哈希管理，不同哈希视为不同版本。
- 旧版本的包不会自动立即清理，可用 `Addressables.CleanBundleCache()` 清理不再被当前 catalog 引用的缓存（具体行为随版本，待核实）。
- 缓存大小上限可通过 `Caching` 相关设置控制，超限时按最近未使用淘汰（细节待核实）。
- 如果自己需要加密、断点续传或自定义缓存目录，可以实现自定义的 `ResourceProvider`/`AssetBundleResource` 相关扩展，或者使用 `WebRequestOverride` 修改请求。

## 失败处理

- 每个 `AsyncOperationHandle` 检查 `Status` 与 `OperationException`。
- 网络失败：`DownloadDependenciesAsync` 失败时，已下载的包保留，重试只会补缺。
- 目录更新失败：回退使用本地已有目录，允许离线进入游戏（若业务允许）。
- 远程不可用时 `InitializeAsync` 仍可成功（用本地目录），要在更新阶段单独处理远程失败。
- 设置合理的超时与重试次数：`AddressableAssetSettings` 中的 *Catalog/Bundle Request* 相关选项。

## 常见坑

1. **忘记保存或使用了错误的 `content_state.bin`**：更新构建出的内容与线上不一致，客户端出现资源缺失或重复下载。每次发版都归档。
2. **用 New Build 替代 Update a Previous Build 做热更**：所有包哈希重算，旧客户端缓存全部失效，需要全量重下。
3. **CDN 缓存旧 catalog**：catalog 的 hash 文件要禁缓存或带版本，否则客户端检查不到更新。
4. **未释放句柄**：`CheckForCatalogUpdates`、`GetDownloadSizeAsync` 等返回的句柄必须释放。
5. **更新后立即加载时仍用旧资源**：已加载的旧资源不会自动替换，需要重新加载或重启场景。
6. **删除 CDN 上的旧文件**：仍在使用旧 catalog 的客户端会加载失败。

## 面试追问

**Q：Addressables 热更新的完整流程？**
初始化，检查并更新 catalog，用 `GetDownloadSizeAsync` 计算体积，`DownloadDependenciesAsync` 预下载，之后的加载从缓存读取。发版端用 Update a Previous Build 配合 content state 文件。

**Q：为什么要有静态组？**
让已发布的包保持不变，更新时只追加新包，客户端已有的缓存继续有效，减少重复下载。

**Q：如何避免热更后用户全量重下？**
用 Update a Previous Build 而不是重新 New Build；保留旧 bundle 文件名与哈希；不要随意调整分组。
