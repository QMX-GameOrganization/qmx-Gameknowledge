> 适用版本：Addressables 1.2x 到 2.x。引用计数的核心语义稳定；Event Viewer 与 Profiler 的界面细节随版本变化（待核实）。

## 要点

- Addressables 对**每次加载操作**记录引用：每一次 `LoadAssetAsync`/`InstantiateAsync` 增加一次引用，每一次 `Release`/`ReleaseInstance` 减少一次。**Load 与 Release 必须成对**。
- 资源的引用降到 0 时，系统卸载该资源；当一个 bundle 里所有资源引用都为 0，且没有依赖它的 bundle 在用，bundle 才会被卸载。
- 释放对象是 **handle（或结果对象）**：`Addressables.Release(handle)` 或 `Addressables.Release(result)`。用同一个句柄多次 `Release` 会报错。
- `Addressables.InstantiateAsync` 返回的实例要用 `Addressables.ReleaseInstance(go)` 释放（它会 Destroy 实例并减引用）；对这种实例用 `Object.Destroy` 只销毁对象，**引用计数不减**，会泄漏（除非开启自动跟踪，见下）。
- 与 Unity 本身的 `Resources.UnloadUnusedAssets` 无关：Addressables 靠自己的计数卸载，而不是引擎判断可达性。

## 加载与释放的语义

```csharp
// 加载资源(不实例化)
AsyncOperationHandle<Sprite> h = Addressables.LoadAssetAsync<Sprite>("icon_sword");
yield return h;
image.sprite = h.Result;
// ...不再使用时
Addressables.Release(h);          // 计数 -1

// 实例化
AsyncOperationHandle<GameObject> ih = Addressables.InstantiateAsync("Hero");
yield return ih;
GameObject hero = ih.Result;
// ...销毁时
Addressables.ReleaseInstance(hero);   // 销毁并计数 -1
```

要点：

- 同一个 key 加载 N 次，计数为 N，需要释放 N 次，bundle 在最后一次释放后才可能卸载。
- 资源是共享的：两个界面都加载同一个图标，各持有一个句柄，各自释放。
- `LoadAssetAsync` 返回的是资产本身，不创建实例；`InstantiateAsync` 同时创建实例，且实例与其来源引用绑定。

## 句柄生命周期

- 句柄 `AsyncOperationHandle` 是值类型包装，持有内部操作对象。操作完成后结果一直有效，直到 `Release`。
- 不 `Release` 的句柄会让结果与依赖一直留在内存，是最常见泄漏。
- 对短命的操作（`CheckForCatalogUpdates` 等）传 `autoReleaseHandle: true` 或手动释放。
- 失败的操作也要 `Release`，否则内部状态留存。
- 句柄可以保存在你的管理类中，与持有它的对象生命周期绑定，例如 UI 面板打开时加载，关闭时释放。

## 自动释放实例

`InstantiateAsync` 有一个 `trackHandle` 参数（默认 true）：系统会跟踪该实例，在特定情况下可以通过 `Addressables.ReleaseInstance` 一并处理。另外，若实例被 `Destroy`，可以借助一个组件在 `OnDestroy` 中调用 `ReleaseInstance`，把释放与对象生命周期绑定：

```csharp
public class AutoRelease : MonoBehaviour
{
    void OnDestroy() => Addressables.ReleaseInstance(gameObject);
}
```

这是常见的封装手法，但要避免重复释放；是否需要此组件取决于你的版本与设置（待核实）。

## 封装建议

直接使用 Addressables 的 API 容易遗漏释放。常见封装：

1. **按“拥有者”集合管理句柄**：每个 UI 面板、关卡维护一个 `List<AsyncOperationHandle>`，销毁时统一 `Release`。
2. **加载作用域（Scope）对象**：`using var scope = new LoadScope(); scope.Load<T>(key)`，作用域结束自动全部释放。
3. **缓存与延迟释放**：释放后不立即卸载，进入 LRU 缓存，避免短时间重复加载同一资源。
4. **统一入口**：业务代码只通过封装层加载，封装层统计计数、记录调用栈，便于排查泄漏。

## 泄漏排查

- **Event Viewer**（Addressables 提供的 Profiler 视图，需要在设置里启用 *Send Profiler Events*）：显示每个资源与 bundle 的引用计数随时间变化，应在离开场景后回落。
- **Memory Profiler**：快照对比看资源与 bundle 是否残留。
- **自检日志**：在封装层记录每次 Load/Release 的 key，离场景时检查未配对的项。
- **Analyze 规则**：检查重复依赖，避免因冗余造成多份内存。

## 内存释放的时机

- 引用降为 0 时，资源的卸载是**即时或帧末**进行，随版本可能有延迟（待核实）。
- 如果 bundle 里的某个资源仍被其他持有者引用，bundle 不会卸载；这会让“明明释放了但内存没降”。检查是否有其他句柄或实例仍引用同一 bundle 中的资源。
- 场景加载：`Addressables.LoadSceneAsync` 返回的句柄要用 `UnloadSceneAsync` 释放。

## 常见坑

1. **只 `Destroy` 不 `ReleaseInstance`**：计数不减，bundle 不卸载。
2. **重复 `Release` 同一句柄**：报错或误释放，需要置空句柄。
3. **加载后立刻释放，但仍在使用结果**：对于 `LoadAssetAsync` 的资产，释放后资源可能被卸载，场景里的引用变成丢失。
4. **在异步未完成时释放**：应等待完成后释放，或使用取消机制；直接释放未完成的句柄行为依版本而定（待核实）。
5. **在每帧里 `LoadAssetAsync` 同一 key**：计数不断增加却不释放。
6. **混用 Addressables 与手写 AB**：两套计数互相不知道，容易重复加载同一个 bundle 报错。

## 面试追问

**Q：Addressables 的引用计数怎么工作？**
每次 Load/Instantiate 计数加一，Release/ReleaseInstance 减一；资源计数为 0 才可卸载，bundle 内所有资源都为 0 且无依赖者才卸载 bundle。

**Q：为什么 `Destroy` 一个 Addressables 实例会泄漏？**
`Destroy` 只销毁对象，Addressables 的引用计数没有减，bundle 与资源保留。应使用 `ReleaseInstance`，或在 `OnDestroy` 里调用它。

**Q：怎样降低漏释放的概率？**
封装加载作用域，让句柄与拥有者生命周期绑定，统一入口并统计未配对的加载。
