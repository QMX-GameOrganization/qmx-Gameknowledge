> 适用版本：Addressables 1.2x 到 2.x（Unity 2021 LTS 至 Unity 6000.x）。包的 API 与界面随版本有变动，文中类名以 `UnityEngine.AddressableAssets` 为准，细节以所装版本的官方文档为准，个别项标"待核实"。

## 要点

- Addressables 是建立在 AssetBundle 之上的资源管理系统，解决了手写 AB 的三件事：**依赖加载、引用计数与卸载、本地与远程路径的统一寻址**。
- 核心抽象：**Address**（资源的逻辑名）、**Group**（打包与加载规则的容器）、**Label**（分类标签）、**Catalog**（运行时的寻址目录）。
- 你不再关心 AB 文件名与依赖，通过 `Addressables.LoadAssetAsync<T>(key)` 加载，系统自动加载依赖并计数。
- 打包规则由 Group 的 **Schema** 决定：打包模式（一组一个包、每个资源一个包、按标签合并）、压缩、是否可更新、本地或远程。
- 它不是银弹：仍需要设计分组、管理释放、处理冗余，只是把底层样板代码替你写了。

## 与手写 AB 的关系

```
手写 AB:   业务 → 你的 AB 管理器(依赖/计数/路径/版本) → AssetBundle API
Addressables: 业务 → Addressables API(依赖/计数/Catalog/下载) → AssetBundle API
```

好处：少写、少错、有官方工具链（Groups 窗口、Build Layout 报告、Analyze 规则）。代价：黑盒感强，出问题要读懂它的内部流程；与自有的加密、特殊缓存策略集成需要通过自定义 Provider 或 Resource Locator。

## 核心概念

- **Address**：资源在系统里的主键，默认是资源路径，可改成短名。同一个 Address 在所有 Group 中必须唯一。
- **Label**：可多选的标签，用于批量加载（例如加载所有 `level1` 标签的资源）或批量下载预热。
- **Group**：一个或多个资源的集合，附带若干 Schema，决定怎么打包、放在哪、是否可更新。
- **Catalog**：构建产物之一，记录 Address 到实际 AB 位置与依赖的映射。本地有一份，远程可有更新的一份。
- **Resource Locator**：运行时用 Catalog 解析 key 的组件，可以有多个（包括自定义）。

## Group 与 Schema

最重要的两个 Schema：

**Content Packing & Loading**

- *Build Path / Load Path*：用 Profile 变量表示，如 `LocalBuildPath`/`LocalLoadPath`、`RemoteBuildPath`/`RemoteLoadPath`。
- *Bundle Mode*：
  - `Pack Together`：整组打成一个包。
  - `Pack Separately`：组内每个资源（或每个文件夹，随版本，待核实）一个包。
  - `Pack Together By Label`：同标签的打一个包。
- *Compression*：LZ4 / LZMA / Uncompressed，与 2.1 节同理。
- *Include in Build*、*Use Asset Bundle Cache*、*Asset Bundle CRC*：影响缓存与校验。

**Content Update Restriction**

- `Can Change Post Release`：可变组，更新后会出新的包，旧包若内容变化会被新包替代。
- `Cannot Change Post Release`（静态组）：发版后内容视为固定；更新时若里面资源变了，会被**移到一个新的远程组**而不是修改原包（见 3.2）。

## Profile 与路径

Profile 是一组变量（路径、服务器地址等）的集合，用于区分开发、测试、线上环境：

```
RemoteBuildPath = ServerData/[BuildTarget]
RemoteLoadPath  = https://cdn.example.com/game/[BuildTarget]
```

构建时输出到 `RemoteBuildPath`，运行时从 `RemoteLoadPath` 下载，你把产物上传到 CDN 对应目录即可。多环境切换通过切换 Profile。

## 构建产物

默认构建后得到：

- 一批 `.bundle` 文件，文件名可带哈希。
- `catalog_*.json`（或二进制）与 `catalog_*.hash`：目录及其哈希，哈希用来判断目录是否更新。
- `addressables_content_state.bin`：记录上次发版时静态组的内容状态，用于“基于上次构建更新”（3.2 节）。**必须保存好并纳入版本管理**，丢了就无法做内容更新。
- `settings_*.json` 等运行时设置与链接信息。

## 分组策略

与 2.1 节思路一致，Addressables 里的落点：

1. **按功能与生命周期**：UI 一组、角色一组、关卡一组。
2. **静态与动态分离**：几乎不变的（基础 UI、Shader、通用字体）放静态组，常变的放可变组，避免动态内容的小改动触发大包重传。
3. **本地与远程**：首包必要内容放本地组，大体量或可选内容放远程组。
4. **避免组内资源被多个组隐式依赖**：Addressables 会将依赖自动一并打包，被多个可寻址资源依赖但自身未设为可寻址的资源，同样会被复制到每个引用它的包里，导致冗余。把公共依赖也标记为可寻址并放入公共组。
5. **控制包数量**：`Pack Separately` 会产生很多小包，文件数与请求数增加。

## 分析工具

- **Analyze 窗口**：检查重复依赖（Check Duplicate Bundle Dependencies）、系统共享资源等，可一键修复部分问题。
- **Build Layout Report**：构建后输出每个包的内容和大小，便于找出大包与冗余。
- **Event Viewer / Profiler**：运行时查看加载与引用计数。

## 常见坑

1. **改了资源又改了分组，内容更新出现重复资源**：静态组与动态组切换需遵循更新流程，不要随意移动资源。
2. **丢失 `addressables_content_state.bin`**：无法基于上次构建出增量更新，只能全量，且旧客户端可能出现不一致。
3. **Address 重名**：同一 Address 对应多个资源，行为取决于顺序，难以排查。
4. **把所有资源放一个 Pack Together 的大组**：改一个资源整包重下。
5. **忽视公共依赖冗余**：用 Analyze 的重复依赖规则定期检查。

## 面试追问

**Q：Addressables 相比直接用 AssetBundle 的优势？**
自动处理依赖加载、引用计数、本地与远程寻址、目录更新与下载，提供分组与分析工具，减少自写管理器的出错面。

**Q：Group 里的 Bundle Mode 怎么选？**
内容整体加载、整体更新选 Pack Together；需要细粒度更新与按需加载选 Pack Separately，但包数量会增多；按标签合并适合按场景或语言分类。

**Q：`addressables_content_state.bin` 的作用？**
记录静态组在上次发版时的内容状态，用于增量更新时判断哪些静态资源已变化，需要被移到新组，避免动到旧包。
