> 适用版本：Unity 2021 LTS 到 Unity 6000.x。三个方案的活跃度、功能与限制随时间变化，**表中涉及版本支持和性能的描述为定性判断，上线前以各项目官方文档和自测结果为准（待核实）**。

## 要点

- 三类方案的差别主要在**执行模型**与**类型系统是否统一**：HybridCLR 是运行时内建解释器，类型统一；ILRuntime 是独立解释器，类型隔离；Lua 是另一门语言，通过绑定桥接。
- 工程成本主要集中在：**适配代码量、构建流程复杂度、调试体验、团队技能匹配**。性能差异多数时候不是首要因素，除非热更层承载大量计算。
- 迁移的核心是**边界重新划分**：哪些逻辑留在 AOT，哪些进热更层，以及稳定的接口层。

## 详细对比

| 维度 | HybridCLR | Lua（xLua/ToLua） | ILRuntime |
|---|---|---|---|
| 开发语言 | C# | Lua | C# |
| 热更代码与主工程互操作 | 同一运行时，直接互调，经桥接 | 通过 Wrap/反射，边界清晰但成本高 | 跨域，需适配器、委托转换、CLR 绑定 |
| 类型系统 | 统一 | 两套（Lua 动态类型） | 隔离（热更类型非 CLR 类型） |
| 泛型支持 | 好，AOT 泛型需补充元数据 | 不涉及 C# 泛型实例化问题（Lua 动态） | 较复杂 |
| 反射与序列化 | 基本可用 | Lua 侧自行处理 | 对热更类型有限制 |
| 构建要求 | 需要集成修改版 IL2CPP | 需要生成 Wrap；Hotfix 需要 IL 注入 | 纯 C# 库，无特殊构建 |
| 运行时性能 | 解释部分较慢，AOT 部分原生 | Lua 解释执行，边界开销明显 | 解释执行，跨域调用开销 |
| 调试体验 | 编辑器接近原生 C# | 需要 Lua 调试器 | 需要专用调试支持 |
| 团队技能 | 会 C# 即可 | 需要 Lua 与绑定机制知识 | C# + 跨域机制 |
| 灵活性（即写即改） | 需要编译 | 脚本可直接改 | 需要编译 |
| 平台审核认知 | 视为执行下载的代码，需关注条款 | 同样需关注，业界使用历史长 | 同上 |
| 维护风险 | 依赖对 Unity 版本的跟进 | 取决于库的维护状况 | 取决于项目维护状况（待核实） |

## 决策思路

1. **起点是团队与代码资产**
   - 以 C# 为主且逻辑要在热更与非热更间自由移动：HybridCLR。
   - 已有大型 Lua 框架与团队积累：保持 Lua，避免为了换方案重写。
   - 已用 ILRuntime 且运行稳定：评估迁移收益，不要仅为追新而迁移。
2. **看热更层的职责**
   - 以 UI、流程、活动为主：三者均可，性能差异不显著。
   - 含大量战斗/AI/寻路等计算：把计算部分放 AOT，不论哪种方案。
3. **看 Unity 版本规划**
   - 计划升级到较新的 Unity 版本（含 Unity 6 系列）：先确认方案对目标版本的支持。
   - 关注 Unity 6.8 起 CoreCLR 取代 Mono 的计划（见 C# 底层专栏 4.1），IL2CPP 保留；依赖 IL2CPP 运行时修改的方案需要关注版本跟进。
4. **看审核与合规**
   - 与发行渠道确认对热更新技术的态度，规划“审核期关闭热更”的开关。
5. **看团队人员稳定性**
   - Lua 方案对新成员有学习曲线；C# 方案对应聘者门槛更低。

## 示例：三种方案的"入口调用"

```csharp
// HybridCLR: 反射进入入口即可,之后写普通 C#
Assembly.Load(bytes).GetType("Hotfix.Entry").GetMethod("Run").Invoke(null, null);

// Lua: 创建环境, require 入口脚本
luaEnv.DoString("require 'Main'");

// ILRuntime: 在其域内调用静态方法
appdomain.Invoke("Hotfix.Entry", "Run", null, null);
```

差异体现在：入口之后的代码里，HybridCLR 与原生 C# 几乎一致；Lua 是另一门语言；ILRuntime 里每当触及主域类型继承或委托，都会遇到额外适配。

## 迁移思路

### 从 ILRuntime 迁移到 HybridCLR

1. 确认目标 Unity 版本与 HybridCLR 的支持范围。
2. 先把"适配器、委托转换、CLR 绑定"相关代码列出来，它们在新方案里大多可以删除，因为类型统一。
3. 整理程序集：热更程序集不被主包引用，改为 Assembly Definition 管理。
4. 补充元数据与 AOT 泛型问题要重新验证，之前 ILRuntime 里能工作的泛型代码可能需要新的处理。
5. 用同一套测试在真机对比功能与性能，分模块逐步切换，而不是一次性替换。

### 从 Lua 迁移到 C# 热更

1. 先按模块迁移：新模块用 C# 热更，旧模块暂留 Lua。
2. 建立统一的服务接口，使 Lua 与 C# 热更层通过同一组接口访问系统功能。
3. 迁移期间保证两条热更链路可同时运行并共享资源系统。
4. 逐步移除 Wrap 范围，减少包体与生成时间。

### 通用原则

- 定义稳定的 **AOT 接口层**（系统服务、数据结构），热更层只依赖它。
- 版本清单中记录热更代码与 AOT 主包的兼容范围。
- 迁移前先建立自动化冒烟测试（启动、关键玩法、内存），否则无法量化迁移是否倒退。

## 常见坑

1. **一次性全部重写**：风险高，应分模块迁移，保持可回滚。
2. **只测编辑器**：所有方案在编辑器里的行为都与真机不同。
3. **忽视人员技能**：选了团队不熟悉的方案，后续排错成本高。
4. **没有划分好边界**：热更层直接依赖大量 AOT 内部实现，AOT 一改动热更就坏。

## 面试追问

**Q：三类方案各自适合什么场景？**
HybridCLR 适合以 C# 为主、希望统一类型系统的项目；Lua 适合已有 Lua 框架、需要最大灵活性的项目；ILRuntime 适合存量项目或无法修改 IL2CPP 的场景。

**Q：选型时性能是不是第一考虑？**
通常不是。多数热更层承载 UI 与流程，性能差异小；更重要的是团队技能、工程成本、调试体验和长期维护。

**Q：热更层与 AOT 层的边界怎么划？**
稳定的、性能敏感的、与平台强相关的放 AOT；易变的玩法与 UI 放热更层；两者之间用稳定接口，避免热更层依赖 AOT 的内部细节。
