> 适用版本：HybridCLR 各版本。与 AOT 泛型相关的机制（补充元数据、泛型实例生成）在不同版本里的命令和行为有差异，**本页具体名称与数字均需以官方文档为准（待核实）**；性能结论没有统一基准，应以项目实测为准。

## 要点

- 核心矛盾仍是 C# 底层专栏 4.2 讲的 **AOT 泛型实例缺失**：热更代码里新出现的泛型实例（如 `List<HotStruct>`、`Dictionary<int, MyStruct>`），主包的 IL2CPP 没有生成对应原生代码。
- HybridCLR 的解决办法分两层：**热更类型作为泛型实参时**，解释器能处理（泛型代码由解释器按元数据执行）；**AOT 泛型类型的值类型实例化**，需要通过**补充元数据**让解释器取得 AOT 泛型方法的 IL 并解释执行，或者在 AOT 侧生成并保留该实例。
- 解释执行比原生慢，慢多少取决于代码形态。把计算密集的热点放在 AOT，把胶水和业务逻辑放在热更层。
- 多数线上问题来自：缺元数据、缺桥接、裁剪过度、编辑器与真机差异、主包与热更版本不匹配。

## AOT 泛型缺失的分类

| 场景 | 例子 | 处理 |
|---|---|---|
| 泛型实参是热更类型（引用类型） | `List<HotClass>` | 引用类型共享泛型代码，通常无需额外处理 |
| 泛型实参是热更值类型 | `List<HotStruct>` | 需要泛型代码的 IL，依赖补充元数据 |
| AOT 泛型 + AOT 值类型，但主包没引用到该组合 | `Dictionary<int, Vector3>` 若主包没用过 | 补充元数据，或在 AOT 侧加“实例引用”代码 |
| 泛型虚方法/泛型接口方法的值类型实例 | 接口含 `T Get<T>()` | 补充元数据，或改设计（避免泛型虚方法） |

## 补充元数据

做法回顾（4.2 的加载流程）：生成阶段导出 AOT 程序集（如 `mscorlib`、`System.Core`、`UnityEngine.CoreModule`）的元数据 dll，运行时在加载热更程序集之前调用 `RuntimeApi.LoadMetadataForAOTAssembly(bytes, mode)`。

注意点：

- 补充元数据**只补“元数据”，不补“原生代码”**；缺失的泛型实例由解释器执行，所以更慢。
- 只需要补充热更代码实际用到的 AOT 程序集，列表可由生成工具给出，也可以手动维护。
- 元数据 dll 需要与主包里该 AOT 程序集（裁剪后）完全对应，使用生成命令从当前构建导出的“裁剪后的 dll”，而不是 Unity 安装目录里的原始 dll（待核实）。
- 补充元数据文件有额外下载与内存开销，按需精简。

## 主动在 AOT 侧保留泛型实例

对热点泛型（例如大量使用的 `List<int>`、`Dictionary<int, Item>`），更好的做法是让它在 AOT 里有原生版本：

```csharp
// AOT 程序集里
[Preserve]
static class AotGenericHints
{
    [Preserve]
    static void Use()
    {
        new List<int>();
        new Dictionary<int, long>();
    }
}
```

HybridCLR 的生成流程也会根据热更代码自动生成这类引用代码（待核实），确保常见泛型实例走原生。

## 性能特点与建议

解释执行额外开销的来源：指令分发、栈操作、缺少内联和寄存器分配优化、与 AOT 之间的桥接。实际表现：

- **纯计算循环**：解释部分相对原生可差一个数量级（范围因代码而异，待实测）。
- **调用引擎 API 为主的代码**：大部分时间花在 Unity 原生函数里，解释器开销占比小，通常可接受。
- **热点与高频回调**：`Update` 里的大量逻辑、寻路、战斗帧同步、物理回调应放 AOT，或减少调用频率。

优化原则：

1. **分层**：热点算法、数据结构、数学库放 AOT；UI、流程、活动逻辑放热更。
2. **减少跨界调用次数**：热更与 AOT 之间每次调用都经桥接，粗粒度接口优于细粒度大量调用。
3. **避免泛型值类型在热更层走“补充元数据”路径**：把关键容器的实例固化到 AOT。
4. **缓存反射结果**：反射在解释器里更慢。
5. **实测**：在目标低端机上用真实场景 Profile，而不是依赖微基准。

DHE（差分混合执行）等进阶特性可以把未修改的热更函数继续走原生，降低解释开销，但属于商业版能力，使用前向官方确认（待核实）。

## 反射、委托、多线程

- **反射**：在热更程序集上反射可用；对 AOT 程序集的泛型方法 `MakeGenericMethod` 若实例缺失同样会失败。
- **委托与回调**：热更方法转为委托传给 AOT 代码（`Action`、事件）需要桥接，生成工具会覆盖大部分，特殊签名可能缺失。
- **原生回调**：P/Invoke 的反向回调（`MonoPInvokeCallback`）要求静态方法，热更层使用有额外限制，必要时放在 AOT 层（见 C# 底层专栏 2.2）。
- **多线程**：解释器支持多线程，但需注意线程静态状态与同步，遇到问题优先查官方 Issue。
- **协程与 async**：基本可用；`async` 的状态机生成的泛型实例同样可能涉及 AOT 泛型（`AsyncTaskMethodBuilder<T>` 等），必要时补充元数据。

## 调试

- 编辑器里热更程序集就是普通 Mono 程序集，可以用 IDE 断点调试。
- 真机上的解释执行调试支持有限，主要靠日志与堆栈；异常堆栈里的方法名通常可读，但行号信息取决于符号处理（待核实）。
- 建立真机冒烟流程：每次构建后在真机或 IL2CPP 桌面 Player 运行关键路径。

## 常见错误速查

| 现象 | 常见原因 | 方向 |
|---|---|---|
| "no ahead of time (AOT) code was generated" | AOT 泛型实例缺失 | 补充元数据或在 AOT 侧引用实例 |
| 找不到桥接函数 / 签名不匹配 | 桥接函数没生成或过期 | 重新执行生成命令，重新打主包 |
| `MissingMethodException` / 类型找不到 | 裁剪删除了 AOT 类型 | 生成保留文件，补 `link.xml` |
| 热更脚本 Missing Script | 预制体先于热更程序集加载 | 调整加载顺序，或运行时 `AddComponent` |
| 编辑器正常，真机崩溃 | 编辑器用 Mono 跑，掩盖了 AOT 问题 | 真机/IL2CPP Player 测试 |
| 更新后崩溃 | 主包 AOT 与热更 dll 版本不匹配 | 版本清单约束，保留旧版回滚 |

## 面试追问

**Q：HybridCLR 里为什么还需要补充元数据？**
热更代码会引用主包里没有原生实现的 AOT 泛型实例，解释器需要这些泛型的完整 IL 才能执行，补充元数据就是把 AOT 程序集的元数据提供给运行时。

**Q：热更逻辑性能不够怎么办？**
把热点下沉到 AOT 程序集，减少跨界调用，固化关键泛型实例，缓存反射；再不够再看进阶的混合执行方案。

**Q：为什么编辑器里不出问题？**
编辑器是 Mono JIT 运行，没有 AOT 限制，也不走 HybridCLR 的解释器路径。
