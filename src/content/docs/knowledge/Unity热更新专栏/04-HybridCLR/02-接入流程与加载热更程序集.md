> 适用版本：HybridCLR 的安装方式、菜单命令名、API 名称在不同版本之间有变化。**下文步骤是通用流程，具体菜单与命令以所用版本的官方文档为准，文中标"待核实"的是尤其容易变化的名称。**

## 要点

- 接入分四个阶段：**安装与配置**、**划分程序集**、**构建主包并生成辅助代码**、**构建热更 dll 并在运行时加载**。
- 热更代码必须放在独立的 Assembly Definition 中，并且**不被主包引用**，通过 HybridCLR 的配置标记为热更程序集。
- 运行时需要：下载热更 dll → （必要时）为 AOT 程序集补充元数据 → `Assembly.Load` → 通过反射拿到入口方法并调用。
- 编辑器下通常直接加载 Assembly，不走真实的下载流程，真机行为需要用真正的打包流程验证。

## 步骤一：安装与配置

1. 通过 Package Manager 安装 HybridCLR 包（常见方式是 Git URL 或包名，待核实）。
2. 在编辑器的 HybridCLR 菜单下执行 **Installer**：它会下载与你的 Unity 版本匹配的 IL2CPP 源码，并把 HybridCLR 的运行时代码合并进去（命令名待核实）。
3. 配置 **HybridCLR Settings**：
   - 热更程序集列表（`hotUpdateAssemblies`，按 Assembly Definition 名称）。
   - 预留（补充元数据所需的）AOT 程序集列表（可由工具生成）。
4. Player Settings：**Scripting Backend 设为 IL2CPP**，API Compatibility Level 与工程一致，`Managed Stripping Level` 注意裁剪问题（见下）。

## 步骤二：划分程序集

典型结构：

```
Assets/
  Scripts/
    Boot/          Assembly: Game.Boot        (AOT, 启动与热更流程、资源下载)
    Core/          Assembly: Game.Core        (AOT, 稳定的公共库)
    Hotfix/        Assembly: Game.Hotfix      (热更, 游戏逻辑与 UI)
```

规则：

- `Game.Hotfix` 可以引用 `Game.Core`、`Game.Boot`，反向不能引用。
- `Game.Hotfix` 的 Assembly Definition 勾选 *Auto Referenced = false*，防止被 `Assembly-CSharp` 自动引用。
- 启动流程（下载、加载热更）必须在 AOT 程序集里，因为这时热更代码还没加载。
- 稳定的、不常改的底层库放 AOT，利用原生性能。

## 步骤三：生成与构建

构建主包前执行生成命令（常称为 **Generate All** 或同类命令，待核实）。它会完成：

1. 生成裁剪保留文件，避免 AOT 里被热更代码用到的类型被 stripping 删除。
2. 生成桥接函数 C++ 代码（4.1 提到的签名桥接）。
3. 生成 AOT 泛型实例引用的 C# 代码（用于解决 AOT 泛型实例缺失，见 4.3）。
4. 复制 AOT 程序集的元数据 dll，供运行时补充元数据使用。

然后：

- **构建主包**：File → Build，使用 IL2CPP。
- **构建热更 dll**：用 HybridCLR 提供的编译命令（例如 *CompileDll*，待核实）生成热更程序集，并把输出拷贝为 `.bytes` 后纳入资源系统（AB 或 Addressables），因为 Unity 对 `.dll` 的资源导入有特殊处理，放 `.bytes` 更稳妥。

注意：**主包用的 AOT 程序集与生成命令里用的版本必须一致**。更换了 AOT 代码或第三方库，需要重新生成并重新发主包。

## 步骤四：运行时加载

```csharp
public class Bootstrap : MonoBehaviour
{
    IEnumerator Start()
    {
        // 1. 下载热更 dll 与资源(省略,见第 1 章)
        byte[] hotDll = LoadBytes("Game.Hotfix.dll.bytes");

#if !UNITY_EDITOR
        // 2. 补充元数据: 让 AOT 程序集的泛型能被热更代码使用
        foreach (var name in aotMetaNames)
        {
            byte[] meta = LoadBytes(name + ".bytes");
            var err = HybridCLR.RuntimeApi.LoadMetadataForAOTAssembly(meta, HomologousImageMode.SuperSet);
            Debug.Log($"LoadMetadataForAOTAssembly {name}: {err}");
        }
        // 3. 加载热更程序集
        Assembly hotAsm = Assembly.Load(hotDll);
#else
        Assembly hotAsm = AppDomain.CurrentDomain.GetAssemblies()
            .First(a => a.GetName().Name == "Game.Hotfix");
#endif
        // 4. 通过反射进入热更入口
        var entry = hotAsm.GetType("Game.Hotfix.Entry");
        entry.GetMethod("Run").Invoke(null, null);
        yield break;
    }
}
```

要点：

- `LoadMetadataForAOTAssembly` 的第二个参数（一致性模式）与具体含义（待核实）：它用于让运行时知道 AOT 程序集的完整元数据，以便为热更代码里新出现的泛型实例提供解释执行的实现。
- 补充元数据必须在**第一次执行用到相关泛型的热更代码之前**完成。
- 热更程序集如果有多个，按依赖顺序先加载被依赖者。
- 编辑器里热更程序集已经被 Unity 编译并加载，不需要重复 `Assembly.Load`；这也是编辑器和真机行为可能不同的来源。

## 热更代码里的 MonoBehaviour 与资源

- 热更程序集里的 `MonoBehaviour` 如果要挂在预制体上，必须在预制体实例化之前，热更程序集已被加载。运行时可以通过 `AddComponent(Type)` 动态挂载，这是最稳妥的方式。
- 预制体上序列化引用热更脚本，需要 Unity 能解析该脚本类型。具体支持方式与限制（例如脚本 GUID 的处理）随 HybridCLR 版本而异，**待核实**；遇到“Missing Script”时先确认加载顺序与 AB 打包设置。
- `ScriptableObject`、序列化数据同理，要在热更程序集加载后再加载这些资源。

## 常见坑

1. **启动流程放进热更程序集**：下载和加载逻辑本身必须在 AOT。
2. **忘记补充元数据**：热更代码使用 `List<MyStruct>`、`Dictionary<int, MyStruct>` 之类 AOT 泛型时报“找不到方法/没有 AOT 代码”。
3. **dll 被当成普通资源 Import**：以 `.dll` 放进 `Assets` 会被 Unity 当插件处理，改为 `.bytes`。
4. **编辑器与真机行为不同**：编辑器直接用 Mono，漏掉的 AOT 泛型、桥接问题只在真机暴露。务必做真机构建冒烟。
5. **主包与热更不匹配**：AOT 代码改过之后，仍用旧的热更 dll，会出现类型或方法找不到。版本清单里用 `appVersionMin` 约束兼容范围。
6. **裁剪删掉热更用到的 AOT 类型**：重新跑生成命令并检查保留文件，或在 `link.xml` 补充。

## 面试追问

**Q：热更程序集为什么不能被主包引用？**
被主包引用就会被 IL2CPP 提前编译进原生代码，失去热更意义，且主包发布后无法替换。

**Q：`LoadMetadataForAOTAssembly` 解决什么问题？**
热更代码出现了主包里没有 AOT 实现的泛型实例，补充 AOT 程序集的完整元数据后，解释器可以为它们提供解释执行的实现，避免缺失原生代码的报错。

**Q：怎么进入热更代码？**
在 AOT 的启动脚本里 `Assembly.Load` 后，通过反射获取入口类型与方法调用，或用接口 + 工厂在热更层注册自己。
