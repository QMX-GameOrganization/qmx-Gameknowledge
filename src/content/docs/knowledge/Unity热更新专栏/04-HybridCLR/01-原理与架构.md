> 适用版本：HybridCLR 的具体版本、支持的 Unity 版本、社区版与商业版的功能划分（例如差分混合执行 DHE）随项目更新而变化，**以官方文档为准，本页相关细节均标"待核实"**。Unity 6.8 起 CoreCLR 取代 Mono，IL2CPP 保留（见 C# 底层专栏 4.1），HybridCLR 针对 IL2CPP，是否继续适用于新版本需查官方公告。

## 要点

- HybridCLR 是一个面向 Unity IL2CPP 的 C# 代码热更新方案。思路是：**扩展 IL2CPP 运行时，使其在原有 AOT 执行之外，还能解释执行动态加载的 IL**，即"AOT + Interpreter 混合执行"，因此得名 Hybrid CLR。
- 热更代码是普通 C# 程序集（dll），通过 `Assembly.Load(byte[])` 加载。热更程序集里的代码走解释器，主包原有程序集仍是原生 AOT 代码，两者共享同一套运行时类型系统，互相调用基本无需适配。
- 因为热更程序集没有预先编译成原生代码，其中用到的 **AOT 泛型实例**（例如 `List<MyHotStruct>`）在包里可能没有对应原生代码，需要通过"补充元数据"或"泛型实例生成"来解决（见 4.2、4.3）。
- 它实现的是 IL 级别的解释，因此语言特性、泛型、反射、协程、async 等大多可以直接使用，学习成本低于换语言的方案。

## 背景：IL2CPP 缺什么

回顾 4.2（C# 底层专栏）：IL2CPP 的流程是 IL → C++ → 原生代码，包里没有 IL 执行引擎。对一个新的 dll：

1. 没有现成的原生实现，也无法 JIT。
2. 运行时存储的类型元数据是为 AOT 代码服务的，缺少加载新程序集所需的机制。

HybridCLR 的做法是在 `libil2cpp`（IL2CPP 的运行时库）里加入：

- **元数据解析**：能读取新 dll 的元数据，创建对应的运行时类型、方法描述。
- **IL 解释器**：把 IL 转成内部的指令形式（HiOpCode），按解释方式执行。
- **互操作桥接**：解释器代码调用 AOT 方法，AOT 代码回调解释器代码（例如虚函数、委托、接口）时，通过**桥接函数（Bridge）**进行参数与调用约定转换。

## 程序集划分

```
主包(随安装包发布)
  ├─ Unity 引擎程序集、第三方库、你的 AOT 代码 → 编译成原生
  └─ 不含热更程序集
热更包(从 CDN 下载)
  └─ Assembly-CSharp-Hotfix.dll(.bytes)、依赖的热更程序集
```

划分原则：

- **热更程序集不参与 Player 的 IL2CPP 编译**（通过 Assembly Definition 单独构建，不放入主包）。
- 热更代码可以引用 AOT 程序集的类型和方法，反之 AOT 代码不能静态引用热更程序集（编译期看不见），需要通过接口、委托、反射或入口约定调用。
- 热更程序集本身可以包含多个 dll，按依赖顺序加载。

## 工作流程（概述）

1. **构建主包前**：执行 HybridCLR 的生成流程，包括：为 AOT 桥接函数生成 C++ 代码、生成裁剪保留信息、生成 AOT 泛型实例引用（见 4.3）。
2. **构建主包**：Unity 用修改版 `libil2cpp` 构建 Player。
3. **构建热更 dll**：用 HybridCLR 提供的工具编译热更程序集，导出为 `.bytes` 放入资源系统。
4. **运行时**：下载热更 dll → 补充元数据（若需要）→ `Assembly.Load` → 通过反射或约定入口调用热更代码。

## 桥接函数与调用约定

AOT 代码是 C++ 编译出的，调用约定固定；解释器的函数使用自己的调用方式。当 AOT 调用一个由解释器实现的方法（例如热更类重写了 AOT 基类的虚方法），需要一个**桥接函数**：它的签名与原生调用匹配，内部把参数转换后调用解释器。桥接函数是按"签名"生成的（参数与返回值的类型组合），因此需要覆盖热更代码会用到的签名，生成工具会遍历热更程序集收集，也可能漏掉某些反射或泛型场景，导致运行时报找不到桥接函数的错误（待核实报错措辞）。

## 与 ILRuntime 的区别

| 项 | HybridCLR | ILRuntime |
|---|---|---|
| 位置 | 改造 IL2CPP 运行时，解释器是运行时一部分 | 独立的解释器，运行在托管层 |
| 类型系统 | 热更类型是运行时原生的类型 | 热更类型在 ILRuntime 域内，对外是"异域对象" |
| 继承 AOT 类/接口 | 直接继承，无需适配器 | 需要 CrossBindingAdaptor |
| 调用 AOT | 直接调用，经桥接 | 通过反射或 CLR 绑定生成的直调 |
| 构建要求 | 需要替换/扩展 IL2CPP 源码（通过安装工具完成） | 纯 C# 库，导入即用 |
| 反射、泛型 | 基本与原生一致，AOT 泛型需补充 | 有若干限制 |

## 优势与代价

优势：

- 近乎原生的 C# 开发体验，热更与非热更代码可共享类型、工具链、调试方式。
- 减少适配代码（适配器、绑定、Wrap 生成）。
- 热更代码可以用 MonoBehaviour 等 Unity 的机制（具体使用前提见 4.2）。

代价：

- 需要修改并维护 IL2CPP 运行时，升级 Unity 版本要等对应版本的支持或自己合并。
- 解释执行比 AOT 原生慢，热点逻辑应留在 AOT 或谨慎评估（4.3）。
- 构建流程变复杂：生成步骤顺序、裁剪、AOT 泛型都需要纳入流水线。
- 对 Unity 版本和平台有要求，需要按官方矩阵选择。

## 常见坑

1. **把热更程序集也编进主包**：会导致它被 AOT 编译，热更时反而冲突或不生效。
2. **升级 Unity 版本不更新 HybridCLR 的 il2cpp 补丁**：运行时版本与 Unity 不匹配会崩溃或构建失败。
3. **忘记在每次主包构建前重新生成桥接**：新增的 AOT 调用签名缺桥接。
4. **以为 HybridCLR 让 IL2CPP 有了 JIT**：它是解释器，没有生成原生代码，性能特征要按解释器看待。

## 面试追问

**Q：HybridCLR 如何让 IL2CPP 支持加载新的 dll？**
扩展 `libil2cpp`，加入元数据加载和 IL 解释器，使新程序集的类型能注册到运行时，并解释执行其方法，AOT 与解释器之间通过桥接函数互调。

**Q：为什么它与主工程互操作比 ILRuntime 好？**
热更类型是运行时原生类型，继承、虚调用、泛型、反射都走统一机制，不需要像 ILRuntime 那样在独立域内转换。

**Q：热更代码的性能为什么比 AOT 差？**
解释执行每条指令要额外分发，没有编译期优化与内联；热点逻辑应放在 AOT 层。
