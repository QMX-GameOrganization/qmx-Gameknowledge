> 适用版本：Unity 2021 LTS 到 Unity 6000.x。构建 API 以 `BuildPipeline.BuildAssetBundles` 为基准，Scriptable Build Pipeline（SBP）以 `com.unity.scriptablebuildpipeline` 包为准。选项枚举的细节以官方手册为准，个别行为标"待核实"。

## 要点

- AssetBundle（下称 AB）是 Unity 的资源归档格式，里面是序列化后的对象和它们的引用信息，由 `AssetBundle` 类在运行时加载。
- 一个资源被某个 AB 包含，要么**显式**（被你分配到这个 AB），要么**隐式**（被显式资源依赖，且自己没被分配到任何 AB）。**隐式依赖会被复制进每一个依赖它的 AB**，这是冗余的主要来源。
- 解决冗余的办法：把共享资源显式分配到独立的"公共 AB"，让其他 AB 依赖它，加载时必须先加载依赖。
- 压缩格式三选一：不压缩、LZMA（整体压缩，包最小，加载需整包解压）、LZ4/ChunkBased（分块压缩，支持随机读取，运行时首选）。
- 打包粒度是权衡：粒度太粗，改一个资源要更新整个包；粒度太细，文件数、依赖数、请求数都爆炸。

## AB 的内容与结构

AB 文件由头部、目录、序列化文件（SerializedFile）和资源文件（`.resS` 之类的流数据）组成（细节随版本，待核实）。运行时：

- 序列化对象依赖的**类型信息**可以存在文件里（TypeTree）。包含 TypeTree 使得不同 Unity 版本构建的 AB 之间有一定兼容容错，代价是包体和加载时间略增。
- 构建选项 `DisableWriteTypeTree` 可去掉 TypeTree，包更小、加载更快，但要求构建 AB 的 Unity 版本与运行时一致。

## 构建选项

```csharp
BuildPipeline.BuildAssetBundles(
    outputPath,
    BuildAssetBundleOptions.ChunkBasedCompression      // LZ4
    | BuildAssetBundleOptions.DeterministicAssetBundle // 构建确定性(新版本默认行为，待核实)
    | BuildAssetBundleOptions.StrictMode,              // 有错误则失败
    BuildTarget.Android);
```

压缩选项对比：

| 选项 | 包体 | 加载方式 | 适用 |
|---|---|---|---|
| `None`（`UncompressedAssetBundle`） | 最大 | 可直接 mmap，最快 | 本地大包、对包体不敏感 |
| LZMA（默认，不传 ChunkBased） | 最小 | 加载时整体解压，内存与时间开销大 | 通常用于下载传输，本地落盘后更适合转 LZ4 |
| LZ4（`ChunkBasedCompression`） | 中等 | 按块解压，只解压用到的块 | 运行时首选 |

其他常用选项：`AppendHashToAssetBundleName`（文件名带哈希，便于缓存与不覆盖）、`DryRunBuild`（预演，不生成文件，可用于分析依赖）。

## 依赖与冗余

示例：材质 `M` 被预制体 `A`、`B` 引用，`A` 在 `ab_a`，`B` 在 `ab_b`，而 `M` 没有被分配给任何包：

```
ab_a: A, M(副本)
ab_b: B, M(副本)
```

运行时 `A` 和 `B` 各用一份独立的 `M`，内存里出现两个材质实例，并且包体变大。正确做法：

```
ab_a:      A   (依赖 ab_common)
ab_b:      B   (依赖 ab_common)
ab_common: M
```

排查工具：Unity 的 Build Report、`Bundle Browser`（旧）、Addressables 的 Build Layout 报告、或自己用 `AssetDatabase.GetDependencies` 做静态检查，找出被多个 AB 隐式包含的资源。

## 打包粒度策略

常见策略按"更新频率 + 加载时机 + 依赖关系"划分：

1. **按功能模块**：一个 UI 面板或一个玩法一个包，加载单元与业务单元一致。
2. **按资源类型**：Shader、字体、通用贴图单独成包（常驻或首包）。
3. **按更新频率**：经常变的和几乎不变的分开，避免小改动导致大包重下。
4. **按加载时机**：启动必需、进入场景必需、按需。

经验：

- Shader 单独一个包，并预热（`ShaderVariantCollection.WarmUp`），避免首次使用时卡顿。
- 小文件（图标）合包，大文件（场景、大音频）独立，便于差异下载。
- 一个 AB 控制在几百 KB 到几十 MB 之间，具体取决于更新模式（数字为经验值，非官方建议，待核实）。

## 清单（AssetBundleManifest）

构建后会生成一个与输出目录同名的 manifest AB 和各自的 `.manifest` 文本文件：

```csharp
var mainAB = AssetBundle.LoadFromFile(Path.Combine(dir, "Android")); // 名字等于输出目录名
var manifest = mainAB.LoadAsset<AssetBundleManifest>("AssetBundleManifest");
string[] deps = manifest.GetAllDependencies("ui_main");
Hash128 h = manifest.GetAssetBundleHash("ui_main");
```

它记录依赖列表和哈希，可作为 1.3 节清单的基础。

## Scriptable Build Pipeline（SBP）

SBP 把构建拆成可定制的任务，Addressables 的底层就用它。相比旧的 `BuildAssetBundles`：

- 构建更快，支持增量缓存。
- 可自定义依赖处理、命名、打包规则。
- 构建结果带更丰富的报告信息。

自研打包流程在新项目里常基于 SBP；使用 Addressables 则不用直接操作。

## 常见坑

1. **隐式依赖冗余**：同一材质、贴图、Shader 在多个包里重复。每次发版前跑冗余检查。
2. **TypeTree 版本不一致**：禁用 TypeTree 后，用不同 Unity 补丁版本构建的包在运行时可能加载失败。固定打包用的 Unity 版本。
3. **LZMA 当运行时压缩**：每次加载都要整包解压，内存与卡顿。下载后改用 LZ4 重新落盘，或直接构建 LZ4。
4. **Shader 变体被裁剪**：AB 里的 Shader 与包内变体收集不一致，真机出现粉红。使用 ShaderVariantCollection 并随 AB 一起打包。
5. **一个资源分配到多个 AB**：Unity 不允许，构建会报错或只取一个，需检查分配规则。

## 面试追问

**Q：显式和隐式依赖的区别？**
显式资源是你分配到 AB 的资源；隐式依赖是被显式资源引用但没有分配给任何 AB 的资源，会被复制进每个引用它的 AB，造成冗余。

**Q：LZMA 与 LZ4 如何选？**
LZMA 压缩率高但要整体解压，适合传输；LZ4 分块压缩，随机访问，运行时加载快，占用内存小，运行时首选。

**Q：如何减少 AB 冗余？**
把共享资源显式放入公共包，其余包依赖它；构建后用报告工具检查被重复包含的资源。
