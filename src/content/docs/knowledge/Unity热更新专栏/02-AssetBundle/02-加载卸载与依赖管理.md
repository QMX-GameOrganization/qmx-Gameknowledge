> 适用版本：Unity 2021 LTS 到 Unity 6000.x。API 名称以官方脚本参考为准。内存行为的细节（解压缓冲、mmap）随平台与版本变化，标"待核实"的地方需实测。

## 要点

- 四条加载路径：`LoadFromFile`（本地，LZ4/未压缩时近似 mmap，最省内存最快）、`LoadFromMemory`（整包字节已在内存，会多一份拷贝）、`LoadFromStream`、`UnityWebRequestAssetBundle`（网络或本地 URL，可带缓存）。
- 从 AB 里取资源用 `LoadAsset` 家族；**AB 对象本身与它加载出的资源是两层生命周期**，要分别管理。
- 加载前必须先加载依赖的 AB，否则资源引用丢失（常表现为粉红材质、缺贴图）。
- `Unload(false)`：卸载 AB 本体，保留已加载的资源对象（之后无法再从该 AB 取资源，并可能造成重复加载）。`Unload(true)`：连同已加载的资源一起销毁，仍被引用的对象会变成"丢失引用"。
- 项目里必须自己做**引用计数**或使用 Addressables，手动管理极易泄漏或误卸载。

## 加载 API 对比

| API | 数据来源 | 内存 | 注意 |
|---|---|---|---|
| `AssetBundle.LoadFromFile(Async)` | 本地文件路径 | LZ4 或未压缩：按需读取，开销小 | LZMA 会整体解压到内存 |
| `AssetBundle.LoadFromMemory(Async)` | `byte[]` | 字节数组加解压后一份，共两份 | 用于解密后加载，注意峰值内存 |
| `AssetBundle.LoadFromStream(Async)` | `Stream` | 取决于流实现 | 自定义流可实现边读边解密 |
| `UnityWebRequestAssetBundle.GetAssetBundle` | URL | 由 Unity 缓存管理 | 带 `Hash128`/`crc` 时使用内置缓存，缓存目录不好精细控制 |

加密场景：把 AB 加密存储，加载前解密。可选 `LoadFromMemory`（简单，内存峰值高）或 `LoadFromStream` 配合解密流（省内存，实现复杂）。

## 同步与异步

```csharp
// 异步加载 AB 本体
var req = AssetBundle.LoadFromFileAsync(path);
yield return req;
AssetBundle ab = req.assetBundle;

// 异步取资源
var assetReq = ab.LoadAssetAsync<GameObject>("Assets/Prefabs/Hero.prefab");
yield return assetReq;
var prefab = (GameObject)assetReq.asset;
```

- 同步 `LoadAsset` 在资源未就绪时会阻塞主线程。
- 异步加载数量受 Unity 的后台加载线程与 `Application.backgroundLoadingPriority` 影响，同时发起过多会让主线程集成（integration）耗时变长而掉帧，需要分帧或限流。

## 依赖加载

```csharp
IEnumerator LoadWithDeps(string name)
{
    foreach (var dep in manifest.GetAllDependencies(name))
        yield return LoadBundle(dep);   // 递归或平铺，注意去重与引用计数
    yield return LoadBundle(name);
}
```

要点：

- `GetAllDependencies` 返回传递依赖（含间接）；`GetDirectDependencies` 只返回直接依赖。
- 同一个 AB 重复加载会报错："The AssetBundle 'xxx' can't be loaded because another AssetBundle with the same files is already loaded"。需要维护"已加载表"，并处理"加载中"的并发请求（多个请求等同一个异步操作）。
- 依赖加载完成之前不要从主包取资源。

## 卸载语义

```
ab.Unload(false)  → 卸载 AB 容器及其压缩/原始数据缓冲;已取出的资源对象仍留在内存
ab.Unload(true)   → 同时销毁从它加载出的资源对象;场景里仍引用它们的对象会出现丢失引用
Resources.UnloadUnusedAssets() → 扫描并卸载没有任何引用的资源(开销大，通常配合场景切换)
```

两种常见错误：

1. `Unload(false)` 后又重新加载同一个 AB 并取同一资源：内存里出现两份（旧的泄漏）。
2. `Unload(true)` 时仍有 UI 在用其中的贴图：UI 变空白或粉红。

可用策略：

- **基于引用计数的 Unload(true)**：只有引用降到 0 时才真正卸载，这是最干净的做法，需要每个加载者在用完后显式释放。
- **基于场景生命周期的统一释放**：切场景时 `Unload(true)` 所有该场景的资源，避免细粒度计数（简单粗暴，适合关卡制游戏）。
- **`Unload(false)` + `UnloadUnusedAssets`**：由引擎判断可达性，开销大，会卡一帧，需在加载界面使用。

## 引用计数设计

```csharp
class BundleRef { public AssetBundle ab; public int refCount; public string[] deps; }

void Retain(string name) {
    var b = Get(name);
    b.refCount++;
    foreach (var d in b.deps) Retain(d);      // 依赖也被持有
}
void Release(string name) {
    var b = Get(name);
    if (--b.refCount == 0) { b.ab.Unload(true); Remove(name); }
    foreach (var d in b.deps) Release(d);
}
```

要点：

- 持有一个包就持有它的依赖，释放同理，避免被依赖的包被提前卸载。
- 对象级别（`GameObject` 实例）的引用计数通常不在 AB 层管理，而由业务层（UI 管理器、对象池）决定何时 `Release`。
- 加载失败路径也要保证计数配平（异常、取消加载）。
- 缓存策略：计数为 0 后可延迟卸载（LRU 缓存），避免短时间内反复打开同一面板反复加载。

## 常见坑

1. **忘记加载依赖**：材质或贴图丢失，只在真机出现，因为编辑器模式下直接用 AssetDatabase。开发时使用 AB 模式（Editor 下也走 AB）测试。
2. **重复加载同一 AB 报错**：必须去重，并处理异步并发。
3. **`Unload(true)` 误伤正在使用的资源**：先确认没有实例在用。
4. **`LoadFromMemory` 内存翻倍**：大包不要用，改 `LoadFromFile` 或流式解密。
5. **异步加载一次性发太多**：主线程集成耗时过长，需限流。
6. **资源路径写错大小写**：Android/iOS 文件系统大小写敏感，`LoadAsset` 的名称匹配规则按构建时的路径（小写化与否随设置，待核实）。

## 面试追问

**Q：`Unload(true)` 与 `Unload(false)` 的区别？**
`true` 连同已加载的资源对象一起销毁，`false` 只卸载 AB 容器，已加载的资源留在内存且之后无法回收，除非 `UnloadUnusedAssets`；二者误用分别导致丢失引用和内存泄漏。

**Q：怎么保证依赖包不被提前卸载？**
引用计数：加载包时对其所有依赖加计数，释放时同步减，计数为 0 才真正卸载。

**Q：为什么编辑器里正常，真机资源丢失？**
编辑器常使用 `AssetDatabase` 直接加载，不经过 AB，依赖缺失被掩盖。真机走 AB，缺依赖就丢失。
