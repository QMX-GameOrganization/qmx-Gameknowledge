> 适用版本：Unity 2021 LTS 到 Unity 6000.x。Memory Profiler 包版本与界面随版本变化，下文以思路为主，具体界面位置待核实。

## 要点

- 一个已加载 AB 的内存由几部分组成：AB 容器本身（含目录与可能的压缩缓冲）、已加载的资源对象（Texture、Mesh、AudioClip 等）、被引用的托管对象。大头通常是资源对象，不是容器。
- 内存问题分三类：**泄漏**（该释放没释放）、**冗余**（同一资源多份）、**峰值**（瞬时占用过高导致被系统杀）。
- 先用工具量，再改。Memory Profiler 的快照对比能直接看到哪些对象在两次快照之间新增且没有被释放。
- 多数泄漏的根因是引用链：静态变量、事件订阅、缓存字典持有了资源，导致 `UnloadUnusedAssets` 也回收不了。

## 内存构成

加载一个 LZ4 的 AB 并取出一张贴图：

```
AB 容器: 目录元数据 + 按块解压缓存(很小)
Texture2D 对象: 原生内存(CPU 侧像素数据可能被释放，若关闭 Read/Write)+ GPU 显存
托管包装对象: 少量 GC 堆
```

注意：

- 贴图开启 Read/Write 会在 CPU 内存里额外保留一份，内存翻倍。非必要关闭。
- 网格开启 Read/Write 同理。
- AudioClip 的加载类型（Decompress On Load / Compressed In Memory / Streaming）决定内存与 CPU 开销。
- 原生内存不在 GC 堆里，托管 GC 的指标看不到，必须用 Memory Profiler 或平台工具查看。

## 常见问题清单

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 切场景后内存不降 | 缓存字典/静态引用仍持有资源；`Unload(false)` 遗留资源 | 清理引用后再 `UnloadUnusedAssets` |
| 同一贴图内存里出现多份 | 隐式依赖冗余；`Unload(false)` 后重复加载 | 公共包；改引用计数 |
| 峰值内存高 | 同时加载大量 AB；`LoadFromMemory`；LZMA 整包解压 | 限流、改 LZ4、改 `LoadFromFile` |
| 加载卡顿 | 同步加载；同时发起过多异步；资源 Integration 耗时 | 异步分帧，限制并发 |
| Shader 首次出现卡顿 | 变体首次编译 | 预热 `ShaderVariantCollection` |
| 低端机被杀 | 总内存超限 | 降分辨率、压缩格式、按需释放 |

## 用 Memory Profiler 排查

流程（思路层面）：

1. 进入场景前拍快照 A，进入并操作后拍快照 B，退出回到起点拍快照 C。
2. 对比 A 与 C：本应回到基线的对象仍存在，就是泄漏候选。
3. 在快照中选中对象，查看**引用路径（References / Referenced By）**，沿着路径找到持有者（静态字段、单例、事件）。
4. 对比同类型对象数量：同一路径的 Texture 出现多个实例，就是冗余。

补充手段：

- 日志统计：在你自己的 AB 管理器里维护"已加载 AB 列表 + 引用计数"，切场景时打印，发现计数不为 0 的包。
- 编辑器模拟：开发期使用 AB 模式运行编辑器，避免 `AssetDatabase` 掩盖问题。
- 真机采样：Android 用 Android Studio Profiler 或 `dumpsys meminfo`，iOS 用 Xcode Instruments，两端看到的是整体进程内存，包含引擎、原生插件与图形驱动占用。

## 冗余检查（构建期）

在构建流程里加检查：

1. 遍历所有 AB 的资源列表（构建报告或 `.manifest` 文本）。
2. 统计每个资源 GUID 出现在几个包里，大于 1 的列为冗余。
3. 超过阈值则让构建失败或警告，推动把它提取到公共包。

## 常见泄漏模式

```csharp
// 1. 静态缓存持有资源
static Dictionary<string, Sprite> cache = new();   // 永远不清理

// 2. 事件订阅未取消
void OnEnable()  { Manager.OnChanged += Handle; }
// 缺少 OnDisable 取消订阅,对象和它引用的资源无法释放

// 3. 加载了却没有 Release
var go = Instantiate(bundle.LoadAsset<GameObject>("Hero"));
// 实例销毁了，但 AB 引用计数没减
```

补充：销毁实例（`Destroy`）不等于释放资源。实例引用的 Mesh、Material、Texture 是共享资源，要靠 AB 卸载或 `UnloadUnusedAssets` 回收。

## 峰值内存控制

- 限制同时存在的异步加载数量。
- 大场景分批加载，加载一批释放一批。
- 解密流程避免整包 `byte[]` 常驻，用流式解密。
- 降低贴图 mip 与分辨率（设备分级），或使用 Mipmap Streaming（Unity 的纹理流送功能，使用条件见官方手册，待核实）。

## 常见坑

1. **只看托管内存**：AB 资源在原生内存，GC 面板里看不到。
2. **只在编辑器测内存**：编辑器内存数字与真机无可比性。
3. **每次切场景都 `UnloadUnusedAssets`**：开销大，会卡顿，应放在加载界面。
4. **以为 `Destroy` 释放了资源**：只销毁实例，共享资源仍占内存。
5. **开发期没有检查冗余**：到了后期包体与内存都膨胀，补救代价高。

## 面试追问

**Q：内存里同一张贴图有多份，原因有哪些？**
被多个 AB 隐式包含造成冗余；`Unload(false)` 之后再次加载同一包，旧对象仍在；多个独立加载路径各取一份。

**Q：怎么定位 AB 相关的内存泄漏？**
Memory Profiler 做快照对比，找出应该被释放却仍存在的对象，沿"被谁引用"的路径找到持有者；同时在 AB 管理器里打印引用计数。

**Q：`Resources.UnloadUnusedAssets` 做了什么，代价是什么？**
遍历所有对象，找出没有任何引用的资源并卸载，需要扫描整个对象图，耗时随对象数增长，会造成卡顿。
