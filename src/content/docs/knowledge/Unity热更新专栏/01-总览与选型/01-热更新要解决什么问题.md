> 适用版本：以 Unity 2022 LTS 到 Unity 6000.x、IL2CPP 后端为主线。平台政策（Apple、Google Play）随时间变化，文中涉及处标"待核实"，以官方最新条款为准。

## 要点

- 热更新的本质：**不重新走应用商店发版，让已安装的客户端获得新的内容或逻辑**。拆成两条互相独立的线：资源热更（美术、配置、预制体、场景）和代码热更（C# 或脚本逻辑）。
- 资源热更是成熟、风险低的一条线，主要靠 AssetBundle 或 Addressables。代码热更受平台限制，要在 IL2CPP/AOT 环境下想办法，方案包括 HybridCLR、Lua（xLua/ToLua）、ILRuntime 等。
- 能走资源热更解决的需求，不要走代码热更。数据驱动（配置表、状态机配置、Timeline）能覆盖很大一部分"逻辑变更"。
- 热更新不是单一技术，是一条链路：构建产物、版本清单、CDN 分发、客户端比对与下载、校验、加载、失败回滚。

## 为什么需要热更新

1. **发版周期**：iOS 审核、Android 各渠道上架，周期以天计，线上 bug 或活动配置等不起。
2. **包体与首包**：首包只带核心内容，其余按需下载，降低下载门槛。
3. **运营活动**：活动资源、限时玩法需要在固定时间点生效。
4. **灰度与回滚**：按用户分组下发不同版本，出问题可回退到上一个资源版本。

## 两条线的对比

| 维度 | 资源热更 | 代码热更 |
|---|---|---|
| 内容 | 预制体、贴图、音频、场景、配置、Shader | 游戏逻辑、UI 逻辑、玩法 |
| 主要技术 | AssetBundle、Addressables | HybridCLR、xLua/ToLua、ILRuntime |
| 平台政策风险 | 低 | 较高，iOS 需关注审核条款 |
| 技术难点 | 依赖管理、内存释放、版本管理 | AOT 限制、泛型、性能、调试 |
| 失败后果 | 资源缺失、表现异常 | 逻辑崩溃、闪退 |

## 整体链路

```
构建机:  打 AB / Addressables 内容 ──┐
         编译热更程序集 / 打包 Lua ──┤→ 生成版本清单(文件名、哈希、大小、版本号)
                                    ↓
                                   CDN
                                    ↓
客户端:  启动 → 拉取版本清单 → 与本地比对 → 下载差异文件 → 校验哈希 → 落盘
         → 加载热更程序集 / 脚本 → 进入游戏 → 按需加载资源
```

各环节的对应章节：清单与版本见 1.3，AB 见第 2 章，Addressables 见第 3 章，代码热更见第 4 到 6 章，回滚与校验见第 7 章。

## 什么该热更，什么不该

适合热更：

- 数值配置、关卡数据、文本与多语言。
- UI 预制体、特效、角色与场景美术。
- 活动玩法的脚本逻辑。

不适合热更，或必须随包更新：

- 引擎本身、原生插件（SDK、Native 库）的变更。
- 需要改动 Player 设置、权限、manifest/Info.plist 的内容。
- 依赖底层 C# 类型布局变化的改动（例如修改 AOT 程序集里的类型，见 4.3）。

## 常见坑

1. **把热更当成万能**：原生插件、引擎升级、权限变更必须发整包。
2. **没有强制更新兜底**：客户端和热更内容的兼容范围要有版本号约束，旧客户端拿到不兼容的资源会崩溃。
3. **只设计下载，不设计失败**：断网、磁盘满、下载一半被杀，必须能续传或回退。
4. **热更内容和包内内容出现重复**：同一资源在包内和热更包里各有一份，造成包体和内存浪费。

## 面试追问

**Q：资源热更和代码热更的区别？**
资源热更换的是数据，运行时加载即可，平台限制少。代码热更换的是可执行逻辑，在 IL2CPP/AOT 的平台上无法直接加载新的原生代码，需要借助解释执行（解释器或脚本语言）。

**Q：为什么说能数据驱动就别代码热更？**
数据变更不触发代码执行路径变化，风险小、审核压力小、测试面小；代码热更引入解释执行性能、AOT 兼容、调试难度三类成本。

**Q：一次完整的热更新流程包含哪些步骤？**
构建产物、生成清单、上传 CDN、客户端拉清单并比对、下载差异、校验、落盘、加载、失败回滚。
