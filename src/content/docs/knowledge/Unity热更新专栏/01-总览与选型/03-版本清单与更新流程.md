> 适用版本：与引擎版本无关的通用设计。示例使用 `UnityWebRequest`（Unity 2019+），哈希算法示例用 MD5/SHA256，具体选型取决于安全要求。

## 要点

- 更新流程的核心是**清单（manifest）**：一份描述所有可下载文件名、哈希、大小、依赖的文本或二进制文件，客户端靠它判断"缺什么、变了什么"。
- 推荐**按内容哈希比对**，而不是按版本号整体覆盖。版本号用于判断客户端是否兼容，哈希用于判断单个文件是否需要下载。
- 清单本身要小、可被 CDN 缓存且不会被中间缓存"卡旧版本"：清单文件名带版本或哈希，或者通过一个极小的入口文件（`version.json`）指向最新清单。
- 下载必须支持失败重试、断点续传、校验失败重下，并且**先写临时文件，校验通过后再原子替换**。
- 启动更新阶段应是一个明确的状态机，每个状态失败都有对应处理。

## 清单设计

一个够用的清单结构：

```json
{
  "appVersionMin": "1.2.0",
  "resVersion": 135,
  "files": [
    { "name": "ui_main.bundle", "hash": "9f2c...", "size": 182340, "group": "core" },
    { "name": "hotfix_game.dll.bytes", "hash": "a71b...", "size": 954112, "group": "code" }
  ]
}
```

字段说明：

- `appVersionMin`：能使用这批热更内容的最低客户端版本，低于它的客户端提示强更。
- `resVersion`：资源版本号，单调递增，便于日志和回滚。
- `hash`：文件内容哈希，同名文件内容一致则不下载。
- `group`：分组（首包必需、按需下载、语言包），便于分阶段下载。

AssetBundle 的构建自带 `AssetBundleManifest`（见 2.1），它包含依赖信息和每个 bundle 的哈希；Addressables 有自己的 catalog（见 3.2）。自研方案常在这些之上再加一层自己的文件清单。

## 入口文件与缓存问题

CDN 与浏览器类缓存可能让客户端拿到过期的清单。常见做法：

1. 入口文件 `version.json` 体积很小，请求时带随机查询参数或设置 `Cache-Control: no-cache`。
2. 入口文件里写明当前清单文件名（如 `manifest_135.json`），清单文件本身带版本号，可被长期缓存。
3. 大文件（bundle）文件名带内容哈希，永不覆盖，只新增。这样回滚就是把入口指回旧清单，不需要重新上传。

## 比对与差异下载

```csharp
// 示意：计算需要下载的文件列表
List<FileEntry> BuildDownloadList(Manifest remote, LocalState local)
{
    var list = new List<FileEntry>();
    foreach (var f in remote.files)
    {
        if (!local.TryGet(f.name, out var cur) || cur.hash != f.hash)
            list.Add(f);
    }
    return list;
}
```

要点：

- 本地记录“已下载并校验通过”的文件及哈希，不要每次启动都重算所有文件的哈希（大量文件会拖慢启动）。校验只在下载后与怀疑损坏时做。
- 用 `size` 汇总估算下载量，在移动网络下弹窗确认。
- 同一文件被多个分组引用时，只下载一次。

## 下载实现

- 使用 `UnityWebRequest`，设置 `DownloadHandlerFile` 把数据直接写到磁盘，避免大文件占满内存。
- 并发数控制在几个到十几个之间，视服务器与网络而定。
- 下载写到 `xxx.tmp`，完成后校验大小与哈希，通过后再重命名为正式文件名。这样被杀进程不会留下"看起来完整"的坏文件。
- 断点续传：用 HTTP `Range` 请求头从已下载字节处续传（服务器需支持），或者把大文件切成固定大小的块各自校验。
- 失败重试用指数退避，并设置最大重试次数，最终失败给用户明确提示。

## 启动更新状态机

```
检查网络 → 拉入口文件 → 版本兼容检查(appVersionMin) → 拉清单
→ 比对 → 计算下载量并确认 → 下载 → 校验 → 落盘并更新本地状态
→ 加载热更代码 → 初始化资源系统 → 进入游戏
```

每一步的失败处理：

| 状态 | 失败处理 |
|---|---|
| 拉入口/清单 | 重试若干次；允许使用本地已有版本离线进入（若策略允许） |
| 版本不兼容 | 提示强更并跳转商店 |
| 下载 | 续传、重试，最终失败提示重试或退出 |
| 校验失败 | 删除坏文件，重新下载 |
| 加载热更代码失败 | 回滚到上一个可用版本（见 7.1） |

## 本地目录管理

- 热更文件放 `Application.persistentDataPath`（可写、不随应用升级清空，但卸载会清除）；首包内的文件放 `StreamingAssets`（只读）。
- 本地需要保存当前资源版本、各文件哈希、上一个稳定版本的信息，以便回滚。
- 整包升级后，旧的热更目录是否保留要有策略：通常用新包自带的 `resVersion` 与本地对比，包内版本更新则清理旧缓存。
- 清理旧版本文件时要小心还在被加载中的 bundle，不要在运行时删除打开着的文件。

## 常见坑

1. **清单被 CDN 缓存**：客户端一直拿到旧清单，更新"不生效"。入口文件要关缓存或用版本化文件名。
2. **下载未校验完整性**：网络中断留下半截文件，之后加载崩溃。必须先写临时文件并校验。
3. **整包升级后沿用旧热更目录**：旧的热更内容与新包 AOT 部分不匹配。用 `appVersionMin` 与包内资源版本判断是否作废。
4. **一次性计算所有文件哈希**：启动卡很久，改成下载时校验，运行时按需抽检。
5. **覆盖同名文件**：回滚困难，也容易被 CDN 缓存。文件名带哈希，只增不改。

## 面试追问

**Q：怎么判断哪些文件需要重新下载？**
比对远端清单与本地记录的内容哈希，不同或缺失的才下载。版本号只用来判断兼容性。

**Q：如何做到更新过程中被杀进程也不会损坏？**
下载到临时文件，校验大小与哈希通过后再原子重命名；本地状态记录在写入完成之后才更新。

**Q：CDN 缓存导致更新不生效怎么处理？**
入口文件禁缓存，清单与大文件使用带版本或哈希的文件名，旧文件保留不覆盖。
