> 适用版本：Unity 2022 LTS 到 Unity 6000.x。Apple App Store 审核指南 2.5.2 与 Google Play 政策中关于"下载可执行代码"的条款会更新，文中措辞为概述，**以官方最新条款为准（待核实）**。Unity 6.8 起 CoreCLR 取代 Mono 的计划见 C# 底层专栏 4.1，IL2CPP 保留。

## 要点

- Mono 后端有 JIT，可以 `Assembly.Load(bytes)` 直接加载新 dll；IL2CPP 把 C# 提前编译成 C++ 再编译成原生代码，**运行时没有 JIT，不能执行新生成的 IL**。iOS 又禁止在运行时生成可执行内存，所以 iOS 必走 AOT。
- 因此代码热更的方案分三类：**换语言**（Lua，脚本由 Lua VM 解释）、**自带解释器执行 IL**（ILRuntime，纯 C# 实现的 IL 解释器）、**改造 IL2CPP 运行时使其支持解释 IL**（HybridCLR）。
- 选型要看：团队是否熟悉 Lua、性能预算、与现有 C# 代码的互操作成本、调试体验、平台审核风险、社区维护状况。
- 没有"最好"的方案，只有契合项目的方案。新项目若以 C# 为主且要求逻辑复用，HybridCLR 通常是首选；已有大量 Lua 资产则继续 Lua。

## 为什么 IL2CPP 不能直接加载新代码

IL2CPP 构建流程：C# 编译为 IL，IL2CPP 把 IL 转成 C++，再由平台编译器编译成原生库（Android 是 `libil2cpp.so`，iOS 是静态库链接进可执行文件）。发布后：

1. 包内没有 IL 的执行引擎（没有 JIT），元数据只是为反射保留。
2. 新下载的 dll 里的方法没有对应的原生机器码，没人能执行。
3. iOS 系统层面禁止匿名可执行内存页（W^X），所以也无法自己做 JIT。

细节可结合 C# 底层专栏的 4.1（Mono 与 IL2CPP 差异）与 4.2（泛型共享与 AOT 限制）。

## 平台政策关注点（概述，待核实）

- **Apple**：审核指南 2.5.2 大意是应用应自包含，不得下载、安装或执行会引入或改变应用功能的代码。业界对"通过解释器执行的脚本"的态度多年来有争议，实践中许多使用 Lua 热更的游戏过审，但这不是规则保证。要点是：热更只用于修复与内容更新，不得借热更改变审核时的功能定位。
- **Google Play**：开发者政策限制从 Google Play 之外的来源下载可执行代码（dex、so 等），对解释器或虚拟机中运行、且访问受限的代码有一定例外。
- 国内各 Android 渠道另有各自要求，上线前与渠道确认。

结论：把热更当作"修 bug 与内容迭代"的手段，保留合规风险预案（例如能够在审核期间关闭热更入口或服务端下发"审核版本号"）。

## 三类方案横向对比

| 维度 | HybridCLR | Lua（xLua/ToLua） | ILRuntime |
|---|---|---|---|
| 语言 | C#（几乎完整） | Lua | C#（子集，有适配限制） |
| 执行方式 | 修改后的 IL2CPP 运行时解释 IL，AOT 部分走原生 | Lua VM 解释，LuaJIT 在 iOS 不可用 | 独立的 C# 实现的 IL 解释器 |
| 与主工程互操作 | 同一运行时，类型互通，泛型/继承基本无需适配 | 通过绑定/反射桥接，成本高 | 跨域，需注册适配器与委托转换 |
| 性能 | 解释部分较慢，但优于一般脚本语言解释器（待核实，需实测） | Lua 解释快，但跨 C#/Lua 边界有开销与 GC | 解释执行，跨域调用开销大 |
| 调试 | 与 C# 接近 | 需要 Lua 调试器 | 需要专门支持 |
| 学习与迁移成本 | 低，写 C# 即可 | 需要掌握 Lua 与绑定机制 | 中，需了解跨域限制 |
| 维护状况 | 持续更新（待核实） | xLua 更新较少，ToLua 社区维护 | 更新较少（待核实） |

## 选型思路

1. **团队与代码**：已有大量 C# 逻辑并希望热更部分与未热更部分用同一套类型和工具链，选 HybridCLR。
2. **Lua 资产**：已有成熟 Lua 框架，或需要极致的热更灵活性（运行时即写即用），选 Lua。
3. **旧项目**：已经使用 ILRuntime 的项目，评估迁移成本后再决定是否切换。
4. **性能敏感模块**：战斗核心、物理、渲染相关尽量留在 AOT 的原生代码，热更层承载 UI 和活动逻辑。
5. **安全**：热更的 dll 或 Lua 文件同样可被逆向，需配合加密与校验，见 7.2。

## 常见坑

1. **只看性能跑分选方案**：解释部分的性能与热更逻辑占比相关，应对真实业务做压测。
2. **忽视 Unity 版本支持**：每个方案对 Unity 版本、脚本后端、平台的支持范围不同，升级引擎前先查兼容矩阵。
3. **选型后没划分 AOT 与热更边界**：边界不清会导致热更层调用大量未被保留的 AOT 泛型实例，见 4.3。

## 面试追问

**Q：为什么 iOS 上不能直接 `Assembly.Load` 新 dll？**
IL2CPP 没有 JIT 也没有 IL 执行引擎，加载进来的 IL 没有对应原生代码，系统也不允许运行时生成可执行代码。

**Q：HybridCLR 与 ILRuntime 的本质区别？**
HybridCLR 把解释器集成进 IL2CPP 运行时，热更代码的类型是运行时原生的类型系统的一部分；ILRuntime 是独立的解释器，热更类型对主工程是"外域"，需要适配器。

**Q：Lua 热更为什么比 C# 热更更不受平台限制？**
脚本是文本或字节码，由 Lua VM（C 代码，已随包编译）解释执行，不涉及生成原生代码。但仍受"下载并执行代码"的审核条款约束，只是实践中更常被接受。
