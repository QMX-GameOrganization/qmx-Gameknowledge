> 适用版本：与引擎版本无关。安全措施只能提高攻击成本，不能阻止有决心的逆向者；本页聚焦防御性设计，不涉及攻击实现。算法选型（SHA-256、AES、Ed25519 等）应参考当前通用安全建议。

## 要点

- 热更新的下载通道是攻击面：如果客户端会执行下载的代码或加载下载的资源，**不可信的内容 = 任意代码执行或资源被替换的风险**。
- 三层防护：**传输安全**（HTTPS）、**完整性与来源校验**（哈希 + 签名）、**存储保护**（加密、防篡改）。
- 哈希只能防损坏；防篡改需要**签名**：用私钥签名清单，客户端内置公钥验证，攻击者无法在不拥有私钥的情况下伪造清单。
- 加密主要提高逆向成本，不能当作安全边界。**真正的安全决策（数值、奖励、权限）必须由服务端校验**。
- 签名私钥只在构建/发布环境保存，不要进入仓库或客户端。

## 完整性与来源校验

### 哈希（防损坏、防缓存脏数据）

- 清单里记录每个文件的 SHA-256 或 MD5（MD5 仅防传输错误，不适合作安全用途）。
- 下载后计算并比对，不一致则删除重下。

### 签名（防篡改）

流程：

1. 构建完成后，用私钥对**清单文件**（包含所有文件哈希）生成签名。
2. 客户端先下载清单与签名，用内置公钥验证签名；通过后，再按清单中的哈希校验各个文件。
3. 因为清单是被签名保护的，文件哈希也就间接受保护。

```csharp
// 示意: 验证清单签名(使用 .NET 的 RSA / ECDsa 或平台库)
bool VerifyManifest(byte[] manifestBytes, byte[] signature, byte[] publicKey)
{
    using var rsa = RSA.Create();
    rsa.ImportSubjectPublicKeyInfo(publicKey, out _);
    return rsa.VerifyData(manifestBytes, signature,
        HashAlgorithmName.SHA256, RSASignaturePadding.Pkcs1);
}
```

要点：公钥可以内置在包里（可被提取，但它只能验签、不能签名）；密钥需要有轮换方案（新旧公钥并存的过渡期）。

### 传输安全

- 使用 HTTPS，避免中间人替换内容。
- 在需要更高保证的场景考虑证书固定（certificate pinning），但要有证书更换的升级方案，否则证书过期会导致全员无法更新。
- 不要关闭证书校验以“解决”测试环境的问题，并注意在正式构建中去掉相关的调试代码。

## 存储与加载保护

### 资源（AssetBundle）

- 防止直接解包：对 AB 做加密（整包 AES 或仅加密头部若干字节），加载时解密。
- 加载方式的选择（见 2.2）：`LoadFromMemory` 需要整包解密到内存，峰值高；`LoadFromStream` 配合解密流可边读边解密，内存更友好但实现更复杂。
- 简单的位异或、偏移头部等做法能挡住普通解包工具，但对有经验的逆向者作用有限。

### 热更 dll

- 热更 dll 本质是 .NET 程序集，很容易被反编译。
- 措施：代码混淆（符号重命名、控制流混淆，注意与反射和序列化的兼容）、dll 文件加密存储、运行时解密到内存后 `Assembly.Load`。
- 注意解密后的内存数据仍可被内存转储获取，所以只是提高门槛。
- 混淆工具需要保证不破坏 HybridCLR 等方案的元数据读取；改变前先在真机验证（待核实）。

### Lua 脚本

- 同理：加密存储、预编译成字节码（可读性降低，但不是加密）、加载器里解密。
- Lua 字节码与 Lua 版本和编译选项绑定，换版本要重新编译。
- 关键逻辑不要只靠 Lua 加密来保护。

## 防篡改与反作弊的边界

客户端上的所有校验都可能被绕过：

- 修改内存、Hook 函数、替换库文件，都会让客户端内的“校验通过”失去意义。
- 因此：**金币、背包、战斗结果、排行榜等必须在服务端校验**，客户端只是展示与输入端。
- 客户端防护的价值：提高成本、挡住批量脚本与低成本修改，配合服务端异常检测（数据不合理、行为异常）使用。
- 平台层完整性服务（如 Android 的 Play Integrity）可作为辅助信号（具体接入与能力以官方文档为准，待核实）。

## 日志与密钥管理

- 不在日志里输出密钥、签名、用户令牌。
- 客户端内置的解密密钥无法绝对保密：可以采用“包内一部分 + 服务端下发一部分”拼合，或每个版本使用不同密钥，缩短单个密钥泄露的影响面。
- 构建服务器上的私钥用 CI 的密钥管理功能存储，限制访问人员，操作留审计日志。

## 合规提示

- 热更新下载并执行代码，需注意应用商店条款（见 1.2），不要用热更绕过审核（例如更改应用核心功能）。
- 涉及用户数据的更新（隐私协议弹窗、权限说明）不得借热更绕过告知流程。

## 常见坑

1. **只做 MD5 校验就当作安全**：攻击者可以同时改文件与清单。必须签名。
2. **公钥/密钥硬编码并无轮换方案**：泄露或到期后无法更新。
3. **证书固定没有备用方案**：证书更换导致所有客户端无法更新。
4. **加密后性能没评估**：整包解密造成加载卡顿与内存峰值。
5. **把加密当作反作弊**：客户端逻辑可被绕过，需要服务端校验。
6. **混淆破坏反射/序列化**：真机崩溃，需要保留规则并测试。

## 面试追问

**Q：哈希校验和签名校验的区别？**
哈希用于检测传输损坏，攻击者可同时替换文件和哈希；签名用私钥签清单，客户端用公钥验证，攻击者没有私钥就无法伪造有效清单。

**Q：热更 dll 如何保护？**
HTTPS + 清单签名防篡改，存储加密、混淆提高逆向成本；但关键逻辑和校验仍应放在服务端。

**Q：客户端加密能不能防外挂？**
不能，只能提高成本。需要服务端对关键数据和行为做校验与异常检测。
