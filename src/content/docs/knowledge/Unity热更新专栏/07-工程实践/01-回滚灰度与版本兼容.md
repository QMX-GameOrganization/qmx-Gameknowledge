> 适用版本：与引擎版本无关的工程实践。具体阈值（崩溃率、灰度比例）取决于项目，文中数字仅为示例。

## 要点

- 热更新让问题上线更快，也让修复更快。**可回滚**和**可灰度**是把风险压低的两个基本能力。
- 版本兼容需要明确三类版本：**包体版本**（App 版本）、**热更代码版本**、**资源版本**。每次发布都要声明它们的兼容范围。
- 回滚的前提：旧版本文件仍在 CDN 与本地缓存里，客户端有“上一个稳定版本”的记录，启动流程能检测失败并自动切回。
- 灰度靠服务端下发：根据用户分组（用户 ID 哈希、渠道、地区、设备）返回不同的清单地址或版本号。
- 监控要覆盖更新各阶段的成功率、耗时、失败原因，才能判断是否需要回滚。

## 版本模型

```
App 版本        1.4.0         (商店包，含 AOT 代码与原生插件)
热更代码版本    code 52       (热更程序集)
资源版本        res 135       (AB / Addressables 内容)
```

兼容规则（示例）：

- `code 52` 要求 `App >= 1.4.0`（因为它依赖 AOT 里的某些接口）。
- `res 135` 要求 `code >= 50`（资源里的脚本引用了新类型）。
- 清单（见 1.3）里写明 `appVersionMin`、`codeVersionMin`，客户端按规则判断是否可以进入。

当 AOT 代码变化（新增或修改了热更代码依赖的接口、新增了需要桥接的签名），必须发整包并提升 `appVersionMin`，不要指望热更解决。

## 回滚机制

### 本地保留上一个稳定版本

```
persistentDataPath/
  hotfix/
    current/    本次已校验通过的版本文件
    stable/     上一个确认启动成功的版本文件
    state.json  { current: "code52_res135", stable: "code51_res133", bootOk: false }
```

流程：

1. 下载新版本到临时目录，校验通过后标记为 `current`，同时 `bootOk = false`。
2. 启动并成功进入主界面（或通过健康检查）后，把 `bootOk = true`，并将 `current` 提升为 `stable`。
3. 下次启动时如果发现 `bootOk == false`（上次启动没有成功），说明新版本有问题，自动切换到 `stable` 并上报。
4. 连续失败次数超过阈值，清理热更目录回到包内原始版本。

### 服务端回滚

- 清单入口指回旧版本即可，旧文件在 CDN 保持不删（文件名带哈希、只增不改，见 1.3）。
- 对已更新到问题版本的客户端，需要客户端有能力“版本号比服务端新也能降级”：不要只用 `>` 判断更新，而是用“等于服务端指定版本”判断。
- 紧急开关：服务端下发配置可禁用某模块或整个热更入口（审核期、重大事故时）。

## 灰度发布

分层策略：

1. **内部测试**：开发与测试账号指向测试清单。
2. **小比例灰度**：按用户 ID 哈希取模，例如 1% → 5% → 20% → 100%，每一档观察指标。
3. **按维度灰度**：渠道、地区、设备型号（先在高端机验证，再放到低端机），特定版本的 App。
4. **自动停止**：指标超过阈值（崩溃率、更新失败率）自动暂停放量。

实现方式：入口 `version.json` 由服务端动态生成，请求参数带上用户 ID、App 版本、渠道，服务端决定返回哪个清单。对 CDN 缓存的影响：入口文件不缓存，清单文件按版本缓存。

## 启动期健康检查与熔断

在启动流程里加入明确的“我已成功启动”信号：

- 热更代码加载成功、入口方法执行完毕、主界面显示、首个网络请求成功。
- 任何阶段抛异常，记录阶段名后走回滚逻辑。
- 记录崩溃（原生崩溃与托管异常）需要由崩溃上报 SDK 在下次启动时补报，同时本地标记 `bootOk` 状态。

熔断：同一热更版本启动失败超过 N 次，客户端停止尝试该版本并上报，避免用户卡在启动循环中。

## 监控指标

更新阶段：

- 入口/清单请求成功率与耗时。
- 下载成功率、平均速度、重试次数、失败错误码分布。
- 校验失败率（可能说明 CDN 缓存脏数据或文件损坏）。
- 各步骤耗时（定位更新慢的原因）。

运行阶段（按版本维度切分）：

- 崩溃率、ANR 率、启动失败率。
- 内存峰值、加载耗时。
- 关键业务成功率（登录、进入战斗）。

按 `app/code/res` 三个版本切片看指标，才能确认问题出在哪次发布。

## 发布流程建议

1. 构建并自动化冒烟测试（在真机或 IL2CPP 桌面 Player 上运行关键路径）。
2. 生成清单并记录三类版本、哈希、变更说明。
3. 上传到测试 CDN → 内部验证。
4. 上传到线上，灰度放量。
5. 观察指标，决定放量或回滚。
6. 归档该次发布的所有产物（包括 `addressables_content_state.bin`、符号文件、清单），以便后续增量和排错。

## 常见坑

1. **删除 CDN 上的旧文件**：灰度中的客户端或回滚目标不可用。
2. **只在服务端回滚，客户端不会降级**：客户端判断逻辑写成“比本地版本新才更新”，已更新到坏版本的用户无法回退。
3. **没有启动成功标记**：坏版本导致闪退，用户反复崩溃，无法自愈。
4. **兼容范围写在文档里，没有写进清单**：旧客户端拿到不兼容内容后崩溃。
5. **灰度分组不稳定**：每次启动随机分组，同一用户忽新忽旧。应基于固定用户标识。
6. **监控不区分版本**：看不出是哪次发布引入的问题。

## 面试追问

**Q：怎样设计热更新的回滚？**
保留上一个稳定版本，启动成功后才将当前版本提升为稳定；启动失败时自动切回；服务端旧文件保留，入口可指回旧清单；客户端用“等于服务端指定版本”的逻辑，允许降级。

**Q：灰度怎么做？**
服务端根据稳定的用户标识哈希分桶，按比例返回不同清单；分阶段放量，每阶段观察崩溃率等指标，异常时自动停止。

**Q：什么情况下必须发整包而不是热更？**
AOT 代码、原生插件、权限或 Player 设置变化，以及热更代码依赖的 AOT 接口变化。
