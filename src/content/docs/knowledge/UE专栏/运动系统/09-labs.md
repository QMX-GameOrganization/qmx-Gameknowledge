## 实验前保留什么

以下是可执行的学习实验设计，**本专题尚未进行 PIE、多人联机或性能实测**。先复制工程或建立版本控制检查点，记录引擎版本、角色蓝图、后端、关卡、网络模式与输入方法；每次只改变一个变量。

不要在两套角色使用不同动画、不同碰撞和不同网络配置时，用肉眼比较帧率后就归因于移动框架。

## 实验矩阵

| 实验 | 控制输入/环境 | 记录 | 判断目的 |
| --- | --- | --- | --- |
| 平地启动与制动 | 同位置、同按键时长、相同帧率设置 | 意图、实际速度、位移、模式 | 分离加速度、制动和动画过渡 |
| 持续顶墙 | 同墙面、同前进输入 | 实际位移、输入幅值、姿态 | 区分“有意图”与“实际移动” |
| 走出边缘后落地 | 同边缘、同速度 | 模式变化、竖直速度、落地时刻 | 理解模式转换与地面检测 |
| 滑行临界区 | 同助跑、蹲伏时机与坡度 | 提案速度、实际速度、蹲伏、模式 | 观察 380/200 条件与迟滞 |
| 翻越与中断 | 同障碍、同起点 | Trace、Chooser、Warp Targets、Montage 回调 | 检查选择、对齐和状态恢复 |
| 延迟与丢包 | 明确服务器/客户端数量及网络模拟配置 | 校正次数、误差、重放步数 | 验证自定义状态与预测 |

网络模拟设置随工具与版本变化，使用当前编辑器支持的 Network Emulation 配置，并记录具体值。先确认故障来自哪里，再决定是否调整平滑或容差。

## 出现问题时按层定位

1. **输入**：控制权正确吗？世界/局部方向转换对吗？输入是否被清空或重复消费？
2. **规则**：当前模式、速度限制、姿态和提案是否正确？
3. **环境**：碰撞通道、地面坡度、台阶、移动基座是否符合预期？
4. **同步**：服务器和客户端是否拥有重算所需的相同状态？
5. **表现**：实际运动正确后，再检查轨迹、动画数据库、根运动、IK 与相机。

调试输出也可能引入额外成本。先开足够定位问题的日志，测性能时再固定日志级别，避免比较不同观测开销。

## 什么情况下保留 CMC

已上线或接近交付、现有预测扩展成熟、技能依赖 CMC 语义、团队工具链围绕 Character 搭建时，保留 CMC 往往更可控。Mover 的结构变化不自动抵消迁移成本，也不提供未经测量的性能优势。

## 什么情况下适合试用 Mover

新项目需要多种运动规则组合，希望显式组织输入/状态/模拟边界，或者确有特定后端与网络物理需求时，可以用隔离原型验证。优先实现一个有代表性的动作链：移动 → 起跳 → 冲刺/击退 → 碰撞 → 落地 → 联网纠正。

## 迁移检查表

| 旧职责 | 在 Mover 中寻找的位置 |
| --- | --- |
| CMC 参数与 PhysCustom 中的规则 | 模式、共享设置、运动工具与扩展点 |
| SavedMove / 自定义移动数据 | 输入与同步状态类型、后端序列化与恢复契约 |
| 冲刺或 Root Motion Source | 评估 Layered Move / Effect / Mode，不做机械一对一映射 |
| Character 直接查询 | 玩法/动画接口与 CharacterMover 查询 |
| 普通 Montage 与根运动 | 支持 Mover 的播放与适配路径 |
| Tick 顺序假设 | ProduceInput、模拟、Finalize、动画更新之间的实际依赖 |

迁移验收应同时覆盖成功、拒绝、打断、死亡、瞬移、控制权变化与网络纠正，而不仅是“单机能跑”。最终选择以项目需求和验证结果为依据。
