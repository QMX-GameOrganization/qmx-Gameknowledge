## 为什么客户端先走

等待服务器往返后再响应输入，会把网络延迟直接变成操控迟钝。CMC 让自主代理先预测，并保留足够的历史，供服务器确认或客户端纠正。

![客户端预测、服务器确认或校正，以及未确认输入重放的时间线](/qmx-Gameknowledge/assets/ue-movement/prediction.svg)

这不是“客户端说自己到哪里，服务器就相信”。输入、时间、状态以及校验逻辑共同决定服务器接受什么。

## 四个核心对象与入口

| 源码符号 | 研究重点 |
| --- | --- |
| `FSavedMove_Character` | 保存哪些预测相关输入与起始信息，怎样重放 |
| `FNetworkPredictionData_Client_Character` | 未确认历史、待发送和待合并移动如何组织 |
| `ReplicateMoveToServer` | 本地预测与移动数据发送的衔接 |
| `ServerMove_PerformMovement` | 服务器如何使用收到的移动数据推进角色 |
| `ClientUpdatePositionAfterServerUpdate` | 在服务器更新后重放哪些未确认移动 |

本版本还有打包的网络移动数据通路；旧文章中的单个 ServerMove RPC 名称不能替代当前实现的完整调用链。

## 一个简化例子

客户端已经执行输入 100、101、102；服务器返回输入 100 对应的权威状态。如果需要纠正，客户端恢复到这个基准，再按顺序重放 101、102，推导出新的“现在”。已确认输入的清理、误差容差和移动合并等细节依实际实现而定。

普通位置平滑只是在表现层过渡误差；重放则重新计算后续模拟。两者目的不同，不能只靠插值解决错误的预测状态。

## 为什么自定义冲刺容易出错

假设冲刺期间提高最大速度，本地只改一个 `bIsDashing` 成员：服务器如果不知道冲刺输入，或客户端重放时读到“当前冲刺状态”而不是历史状态，双方计算就可能不同。

设计时需要回答：

- 冲刺请求属于输入还是权威结果？如何传送？
- 持续时间、冷却、方向如何恢复？
- 哪些移动可合并，哪些必须保留边界？
- 重放时能否重复触发音效、扣费或生成物体？

`FSavedMove_Character` 的扩展与自定义网络移动数据是相关入口，但具体方案需要结合技能架构，不能照抄几个压缩标志就认为所有状态都已同步。

## 自主代理与模拟代理不同

控制自己角色的客户端需要即时输入响应；观察其他角色的客户端通常依赖服务器状态和插值/平滑。不能要求所有网络角色都按本地输入预测，也不能用单机 PIE 的顺滑程度评价联机表现。

**自测：** 服务器位置正确，客户端为什么还反复拉回？检查影响模拟的状态是否完整、时间与模式是否一致，再看碰撞环境和移动基座等条件，而不是首先增大平滑参数掩盖误差。
