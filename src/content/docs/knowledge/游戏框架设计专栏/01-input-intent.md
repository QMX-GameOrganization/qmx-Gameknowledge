## 先记录输入，再解释行为

假设同一个空格键，在地面表示跳跃，在挂边时表示攀上。直接让两个系统各自检查 `SpacePressed`，就可能让一次按键触发两次行为。解决的起点是把“玩家按了空格”和“允许执行攀上”分开。

**输入快照**记录本次采样观察到的值和边沿，例如移动轴、当前是否按住蹲下，以及本次新增的空格事件。快照在本次处理期间只读，各系统看到相同的采样版本。输入层不应因为观察到换弹按键，就把武器事实写成 `IsReloading = true`。

**意图**把输入解释为玩法需求，例如移动向量、期望站姿、主动作请求、换弹请求。来源还可以是 AI、回放或网络命令。系统负责提交，后续统一规则负责决定本步如何处理。

```text
快照：CrouchHeld = false，SpacePressed(seq = 108)
解释：期望站立；提交主动作事件 108
FixedUpdate 按序判断：头顶受阻 → 暂不站起；挂边 → 事件 108 解释为攀上
执行：所属系统立即 TryCommit；接纳启动后更新事实并消费事件
未接纳：反馈暂缓，保留有效缓冲；不能把同一次挂边空格降为二段跳
```

“期望站立”与“现在已经站立”描述的是不同的事，必须能够同时保存。

## 持续值与事件要用不同契约

| 类型 | 示例 | 如何判断有效 | 保留到何时 |
| --- | --- | --- | --- |
| 持续值 | 移动轴、期望姿态、瞄准是否按住 | 本步已采样 / 已写入，不能只看值是否非零 | 新采样替换旧值 |
| 一次性事件 | 跳跃、换弹、切枪按下 | 有未处理且未过期的事件身份 | 消费、明确丢弃或超过 TTL |

`Move = (0, 0)` 是有效的“停止移动”，不能把零当成没提交。`CrouchHeld = false` 也有意义：它表达松键后希望站起。若只在非零、为真时写槽位，上一帧的移动或蹲姿请求就可能残留。

持续值可以每步都写，也可以带 `HasValue` / 采样版本区分“有效零值”与“本步未写入”。选择一种明确契约即可，不需要为所有字段增加复杂包装。

## 固定槽位固定的是结构

“固定槽位”表示预先约定有哪些意图字段及其载荷，不代表全游戏共用一个可变静态对象。

| 每角色槽位 | 载荷示意 | 合并 / 覆盖约定 |
| --- | --- | --- |
| Move | 有效标记、二维向量、采样版本 | 本角色选定的输入来源提供最终值 |
| DesiredPosture | 站立 / 蹲下 | 每步提交当前持续目标 |
| PrimaryAction | 事件序号、时间、上下文载荷 | 同一次事件由规则选择攀上或跳跃 |
| Reload | 事件序号、目标武器身份 | 按本步候选策略选取一个事件 |
| SwitchWeapon | 事件序号、目标槽 / 武器身份 | 明确本步取最早还是最新目标 |

schema 可以共享定义，但**每个角色实例各有自己的槽位内容、事件缓冲和处理记录**。角色 A 的跳跃不得覆盖角色 B 的跳跃。若同角色同时有玩家与 AI 输入，也应先确定当前控制来源，或规定来源合并顺序，不能靠谁最后运行碰巧决定。

固定槽位也不等于永远只允许保留一个历史事件。如果两次按键都应保留，可以用小队列存历史，再把本步候选投影到固定槽位。队列上限、溢出策略和本步取几个，都需要显式约定。

## 给一次性事件身份与寿命

可以从下面几个信息开始，不要求一开始就设计通用消息框架：

| 字段 / 记录 | 用途 |
| --- | --- |
| ActorId + Seq | 标识某角色的一次事件；多人或多来源时补足来源身份 |
| CreatedAt | 记录事件采样时刻，使用约定的单调时钟 |
| TTL | 最长等待时间，与 CreatedAt 使用相同时间基准 |
| Payload | 例如切枪目标；不要只保存“按了切枪” |
| 处理记录 | 区分待处理、上下文绑定、暂缓、已启动消费、最终拒绝、过期 |

`Seq` 在身份范围内递增，不能用“这一帧按下了”替代稳定身份。TTL 解决的是“还来得及响应吗”，不能代替消费记录；未过期的已消费事件仍然不能再次启动。

事件进入规则检查或交给执行器尝试，**不等于已经消费**。同步路径以 `TryCommit` 接纳并开始动作作为消费边界：执行器发布活动实例后，输入缓冲的所有者记录该事件已消费。若接纳的是带取消阶段的转换，也应建立实际过渡实例，由执行器负责推进，不能只是把裸请求留在外部队列就声称已开始。

本地守卫在启动前拒绝本次尝试，或当前阶段暂不允许时，可以返回 `Deferred`，在 TTL 内保留事件。只有显式最终 `Rejected` 才作为否决丢弃，过期则按 TTL 清理。动作已经开始后再失败或取消，不恢复旧输入，避免一次按键反复启动。延后计划中的预留也只是防重，不是最终消费，执行器尚未接纳时仍需按结果释放预留并保留或丢弃缓冲。

## 处理槽位清空，不等于消费缓冲

输入缓冲保存跨处理步的待处理事件，意图槽位只是本步的候选视图。典型过程如下：

```text
1. 输入采样：新事件进入本角色缓冲
2. 开始处理步：清空上一轮的临时槽位，持续目标重新写入
3. 从缓冲选择未消费且未过期的事件，填入本步槽位
4. FixedUpdate 按序检查并立即 TryCommit：启动才消费，暂缓保留，最终拒绝丢弃
5. 每项提交后发布所属事实；后续请求读更新结果，结束本步再清理临时槽位
6. 缓冲只移除已启动消费 / 最终拒绝 / 过期事件
```

第 5 步不能顺手把全部缓冲清空。反过来，如果第 4 步已经消费事件，第 5 步清槽位也不能把它变回“未处理”。

这里还要区分三种结果：

- **Started / 已接纳启动**：执行器建立活动实例并开始负责推进，消费事件；之后失败或取消不恢复旧输入。
- **Deferred / 尚未接纳、暂缓**：本地守卫未通过或条件暂未满足，事件仍在缓冲，可在 TTL 内按原有语义重试，不需要重新按键。
- **Rejected / 最终拒绝**：明确否决并丢弃；不因本步另一个动作后来失败而重跑。失效事件另按 TTL 过期清理。

不能仅凭“失败”决定消费还是重试，要看执行器是否已经接纳启动、返回的是暂缓还是最终拒绝。持续站起目标则无需依靠一次性事件缓冲存活。

## 低顶下站起：保留目标，不伪造结果

玩家松开蹲下键时，每步仍提交 `DesiredPosture = Stand`。规则发现头顶受阻，本步不安排站起，实际姿态保持蹲下。

当玩家走出低顶，下一步根据**仍存在的持续目标**重新判断，允许站起。这不是偷偷重放已经拒绝的一次性按键，也不是要求玩家再按一次松键。即使规则提前检查过空间，姿态系统真正扩大碰撞体之前仍要做最终检查；失败时反馈 `Blocked`，不能把活动事实提前写为站立。

## 挂边按空格：一次事件只归一个动作

推荐先保留“主动作事件”这一身份，再由规则根据当前事实选择攀上或跳跃。挂边时把这次空格绑定为攀上请求；绑定只是确定事件语义，不等于已经消费。如果为了展示多个候选而把它投影到攀上和跳跃，两个候选也必须共享同一个 `Seq`，遵守同一份上下文绑定与消费记录。

```text
挂边空格 108 → 解释并绑定为攀上 → TryCommit
               ├─ Started：发布攀上事实，消费 108；后续不再跳跃
               ├─ Deferred：仍保持挂边，保留 108；TTL 内可重试攀上
               └─ 最终 Rejected：丢弃 108
后续跳跃规则：108 属于挂边攀上，不能因启动未成功就降为二段跳
```

若攀上尚未被接纳，净空检查失败返回暂缓，应保持挂边事实，在 TTL 内保留同一攀上事件；持续受阻直至过期也不会自动改成二段跳。若上下文失效，则按明确策略最终拒绝或到期清理，不能悄悄改变该事件语义。若攀上已经启动后失败或取消，则按动作生命周期收尾，不恢复 108。

还要区分“尝试抓边”和“已经挂边后请求攀上”：空中自动抓边未被执行器接纳时，不能先改成挂边事实或吞掉玩家的跳跃缓冲。后续跳跃请求仍按实际状态判断；这与把已绑定的挂边攀上事件降级为二段跳是两回事。

## 自测

**问：每步清空槽位，为什么还会重复跳跃？** 因为跨步缓冲可能没有记录消费，同一个事件又被填回了槽位。

**问：停止移动能不能通过不写 Move 表达？** 只有接口明确把缺失定义为停止时才行；本教程选择显式写有效零值，便于区分遗漏提交和玩家松开。

**问：攀上空间检查失败就要消费空格吗？** 若尚未接纳且返回暂缓，应保留缓冲与挂边状态，在 TTL 内重试攀上；已启动后失败则不恢复输入。

**问：固定槽位是否证明没有 GC、一定更快？** 不能。载荷类型、队列实现和调度仍可能分配，需要独立测量。
