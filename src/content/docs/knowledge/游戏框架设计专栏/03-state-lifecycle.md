## 黑板可以共享读取，写入必须归属明确

黑板可以理解为角色各系统协作时交换数据的地方。它可以是几个普通结构，不必先做键值数据库。真正需要回答的是：每个字段代表什么、谁能写、其他系统读到的是哪一步的数据。

把所有字段放在同一对象，并不意味着所有系统都可以随意赋值。**系统和规则只允许写自己所属的数据域**；需要改变其他域时，提交意图、决定或反馈，由该域所有者处理。

| 数据域 | 典型内容 | 唯一写入职责 | 其他使用者 |
| --- | --- | --- | --- |
| 输入快照 | 轴值、按住状态、带身份的输入事件 | 输入采样层 | 意图生成系统只读 |
| 意图 | Move、DesiredPosture、Reload 请求 | 约定的意图生产者 / 来源合并器 | 规则只读候选 |
| 处理上下文与决定 | 本步事件绑定、提交结果、开始 / 取消决定；延后变体的预留计划 | 规则流程维护所属记录；执行仍走所属系统入口 | 后续规则读取更新记录与事实 |
| 移动活动事实 | 实际姿态、接地、挂边、实际位移 | 移动 / 姿态所属系统 | 武器、规则、动画只读 |
| 武器活动事实 | 当前武器、弹药、活动换弹实例与阶段 | 武器系统 | 规则、动画、UI 只读 |
| 执行反馈 | 已启动、尚未接纳暂缓、最终拒绝、取消确认及原因 | 执行该动作的系统，写所属反馈区 | 同步返回当前流程；后续生命周期反馈按约定汇入 |
| 动画输出 | 统一 Pose / 动画参数结果 | 动画策略与最终合成入口 | 展示层消费 |

表中的职责不是要求一行就建一个类。一个小型角色控制器可以实现多个职责，但读写边界仍应清楚。规则的 `Apply` 可以同步调用所属执行器 `TryCommit`，由执行器修改并发布事实，再返回结果；这是通过所有者协作，没有把事实写入权交给规则。若延后变体中多个规则需改变同一计划字段，也须通过明确顺序和受控接口合并，不能任意共享写入。

跨域禁止的是越权改事实，不是禁止协作。例如切枪规则可以把“取消换弹实例 41，并切向 B”的决定立即交给武器系统；真正把换弹事实从 Running 改为 Cancelling 或 Cancelled，仍由武器系统完成。

## 教学里的 isReloading 为什么看起来简单

一张教学图或短例子可能在换弹规则通过后直接写 `isReloading = true`。它通常省略了执行延迟与失败，用一个布尔值同时表达“本步计划换弹”和“实际上正在换弹”。可以把它理解为教学简化，不能由此推出所有系统都能写武器活动事实。

同步主路径可以让规则调用 `TryCommitReload`，成功启动后由武器系统发布 `ActiveReload`，后续规则就能直接读取更新事实。请求、活动事实与提交结果仍需分清，但不必为此强制建立独立计划层。只有开始动作必须延后时，才额外保存计划与预留：

| 字段示意 | 谁写 | 含义 |
| --- | --- | --- |
| WantsReload / ReloadRequest | 意图生产者 | 请求换弹 |
| PlannedWeaponAction（延后变体可选） | 规则流程 | 计划启动换弹，或切枪并取消旧实例；还未代表启动 |
| ActiveReload | 武器系统 | 实际已经启动的动作身份、阶段与状态 |
| ReloadResult | 武器系统 | Started、未接纳暂缓、最终拒绝、完成、取消确认等结果 |

同步路径中，后续规则读取已更新的 `ActiveReload` 与事件处理记录，避免重复启动；未接纳则保持原事实。延后路径才需要查看“当前活动事实 + 本步计划预留”，因为此时只查 `ActiveReload` 看不到尚未执行的安排。两条路径都不能把请求或预留直接伪装成已开始的事实。

若同步例子只用 `isReloading` 表示实际换弹状态，应说明它由武器系统在接纳启动后写入；它不能同时代替输入请求、可取消阶段和动作身份。关键是语义与写入权，不是要求所有项目都采用同样数量的字段或抽象层。

## 执行要有完整生命周期

系统接收决定后，至少要能区分“尚未接纳”“已经开始”“请求取消”“已经结束”。同步主路径可以直接走下面的流程，枚举不必照搬：

```text
请求 → 规则按序检查 → Apply 调用所属执行器 TryCommit
                       ├─ Deferred：尚未接纳，保留缓冲至 TTL 内下步重试
                       ├─ 最终 Rejected：丢弃事件
                       └─ Started：建立活动实例，消费事件 → Running / 实际过渡阶段
                                                          ├─ 正常完成 → Completed
                                                          ├─ 取消请求 → Cancelling → Cancelled
                                                          └─ 执行中失败 → Failed
```

“规则检查通过”不是“执行器已接纳”，“请求取消”也不是“取消已完成”。执行系统在真正进入活动阶段时发布事实，在结束时清理占用和临时资源，反馈原因。尚未接纳的本地守卫失败可以暂缓，不应一律消费；已经接纳启动后的失败或取消不恢复旧输入。临时不可用与最终拒绝必须在返回结果中明确区分。

同步主路径用事件身份与动作实例关联提交和反馈；持续移动目标可以保持有效，在多个物理步使用，但已启动消费的跳跃事件不能再次启动。若改用延后计划，还需为待执行决定设置身份和有效期，例如 `ActorId + StepId + DecisionId`，必要时附事实版本、目标和预期动作实例；预留阶段不代表消费，直到执行器接纳才结算启动。

## 用动作实例挡住旧回调

假设换弹 41 被取消后，玩家又开始换弹 42。旧动画事件或异步回调迟到，如果它只执行 `IsReloading = false`，就可能把 42 的状态清掉；如果它直接补弹，还可能把已经取消的动作结算一遍。

每次动作启动分配新的实例身份；回调携带实例身份，所属系统核对当前实例、阶段和是否已经结算。对象池复用角色时还要区分角色的生命周期代次，避免旧角色的回调命中新角色。

```csharp
// 教学伪代码：由武器系统接收完成消息，外部回调不直接写弹药事实。
// 实例身份匹配且阶段允许时，才结算一次；取消或重复回调都不能补弹。
void OnReloadCompleted(ActionId callbackId)
{
    if (activeReload == null || activeReload.Id != callbackId)
        return;

    if (activeReload.Phase != ReloadPhase.Completable || activeReload.Settled)
        return;

    activeReload.Settled = true;
    TransferReservedAmmo(); // 本例在完成阶段转移弹药；具体结算点由玩法约定。
    FinishReloadAndPublishResult(callbackId);
}
```

这不是要求每个动作都使用异步任务。即使只有动画事件，实例身份也能阻止旧消息污染新动作。若弹药在中途装填阶段已经转移，取消时还要按该玩法的资源规则收尾，不能在完成回调里再次补弹。

## 总状态机负责大边界，子系统保留各自状态

总状态机适合描述 Alive、Dead、Disabled 等角色级模式，或统一的控制权限与模式切换。它给规则提供门控，也可以发出取消相关动作的决定；武器和移动仍由自己的执行入口处理取消并反馈。

不要把“站立 + 行走 + 换弹”“蹲下 + 行走 + 换弹”都扩展成一个巨大的枚举。姿态、移动和武器存在可并存的状态，应保留各自的生命周期，用兼容规则连接。

| 层次 | 例子 | 主要职责 |
| --- | --- | --- |
| 角色总模式 | Alive / Dead / Disabled | 是否接收控制，哪些能力整体可用 |
| 移动与身体 | Grounded / Hanging、实际站姿、攀爬实例 | 位移与碰撞体不变量 |
| 武器 | 当前武器、换弹实例、可取消阶段 | 弹药、持有与武器动作生命周期 |
| 统一规则流程 | 允许移动换弹，禁止某些身体动作与切枪重叠 | 跨域兼容、事件归属与优先级 |

总状态切到 Dead 时，可以立即禁止新请求，但不要因此声称所有物理动作和异步资源已经清理完毕。需要同步停止还是等待取消确认，应在各执行契约中说明。

## Update 与 FixedUpdate：先承认不是一一对应

Unity 常规自动物理循环中，一帧可能没有 FixedUpdate，也可能有多个；这些固定步通常在该帧 Update 之前执行。不能写成“每次 Update 之后必定立刻执行一次 FixedUpdate”。也不能依赖不同 MonoBehaviour 的同名回调天然按需要排序。

输入采样位置还受 Input System 的动态 / 固定更新模式影响。当前讨论采用的主要协议是：**Update 采集并缓存输入，FixedUpdate 中统一整理意图、按序判断并立即 TryCommit 开始动作；每次提交后发布事实，后续请求读取更新结果。** 输入等待后续固定步才进入裁决，延迟需要结合固定步长和输入模式评估。

```text
渲染帧 A：FixedUpdate × 0..N（按既定流程处理此前缓存的输入）
          Update：采样输入 / 接收事件 → 更新持续目标、缓存一次性事件
          展示阶段：读取已确认事实，输出动画结果

后续渲染帧：FixedUpdate（如本帧安排了固定步）
            → 读取最新有效持续目标、未消费且未过期事件，整理本步意图
            → 请求 A：IsValid / CanApply → TryCommit → 发布所属事实与提交结果
            → 请求 B：读取 A 之后的最新事实，再检查、提交、发布
            → 按序处理其余请求，推进所属活动动作
            后续固定步继续使用持续目标；Deferred 事件在 TTL 内可重试
            已 Started 的一次性事件不重复启动
          Update：采集下一批输入，更新持续目标与事件缓冲
```

如果依赖物理模拟后的接地结果，应约定在模拟后采集，或清楚标记当前可用的是上一固定步结果；在 FixedUpdate 开头查询，不等于已经拿到本次模拟结束后的事实。

落实时至少确定这些边界：

1. **调度入口**：用明确的角色 FixedTick / 调度器调用顺序，保证逐项判断、提交与事实发布；不要让多个系统在各自回调中无序启动动作。
2. **跨步交接**：Update 写入的持续目标采用最新有效值；一次性事件进入每角色有界缓冲，以身份防重，不能被下一次 Update 简单覆盖丢失。
3. **有效性**：每次提交前核对角色、TTL、目标和动作实例；临时受阻可暂缓，最终无效则明确拒绝或过期清理，不能只返回一个含糊的“失败”。
4. **消费次数**：多个固定步可以使用同一持续目标；一次性事件只有未接纳时才能在 TTL 内重试，启动后只消费一次。没有固定步的渲染帧继续缓存事件，并遵守队列容量策略。
5. **反馈可见性**：`TryCommit` 返回前由所属执行器发布接纳后事实，供同一步后续规则读取；运行中失败再按生命周期反馈。不因某项失败重跑本步已最终拒绝的请求。

跨域转换还有额外依赖。例如切换动作要求先退出攀爬再启动武器动作，后者必须等待前者确认；同步调用返回并不意味着需要跨帧退出的动作已经结束。执行器可以接纳为实际过渡实例并发布 Cancelling，后续规则据此判断。普通移动与换弹允许重叠时则不必增加无意义等待。

## 可选时序：Update 裁决，后续阶段执行

如果实际需求要求 Update 先生成决定、后续 FixedUpdate 才执行物理动作，可以采用延后计划变体。此时在 Update 建立 `WorkPlan` 预留事件与通道，后续规则看预留；到执行阶段再调用所属执行器 `TryCommit`，接纳启动后发布事实并消费事件。

该变体还需处理计划身份、有效期、取消与队列容量：不能让多个 Update 覆盖尚未执行的一次性计划，也不能让多个固定步重复启动同一动作。尚未接纳返回暂缓时释放预留，保留 TTL 内的原语义输入；已启动后失败不恢复输入。不要在没有消费协议的情况下把两种时序混用。

同步主路径和延后变体均依靠有序检查、所属执行器本地守卫与明确反馈，不需要再加通用的“审核规则的审核器”。`WorkPlan` 是延后执行时的协调工具，不是所有角色框架都必须有的层。

## 动画策略只负责把事实变成统一 Pose

动画层读取实际姿态、速度、挂边事实和已启动的武器动作等信息，选择策略，再由约定的合成顺序输出统一 Pose / 动画参数。身体移动和武器动作可以在统一输出中分层表达，但多个策略不能无序覆盖相同结果。

动画完成事件可以作为反馈消息交给动作所有者，经实例和阶段核对后再更新事实。动画层不应仅因播放了“站起”就直接把碰撞体事实改为站立。

这里仅描述职责边界，不展开 Motion Matching、IK 或具体动画图实现，也不表示已经实现这些技术或完成任何工程重构。

## 用一条失败链路检查设计

```text
松开蹲键 → 持续目标为站立
FixedUpdate：站起规则检查 → 立即调用姿态系统 TryCommit
姿态系统：最终净空守卫受阻 → 尚未接纳，反馈 Deferred / Blocked
所属事实：仍然蹲着；后续请求读取这个真实姿态
下一处理步：读取蹲姿事实；站立目标仍在，再判断当前空间
```

这里没有任何系统越权：输入只表达目标，规则把决定交给所属执行器，姿态系统只在实际成功后更新姿态。若换成挂边空格触发的一次性攀上事件，尚未接纳时保留挂边事实与 TTL 内的攀上缓冲，不能改用它触发二段跳；**只有已接纳启动后的失败或取消，才按生命周期结束且不恢复旧输入**。显式最终拒绝与过期则各按对应原因清理。

## 自测

**问：统一黑板是否意味着谁方便谁就写？** 不是。共享读取与写入所有权分开，每个域都有约定的写入入口。

**问：切枪决定里写了取消，能立刻宣称旧动作不存在吗？** 不能。要看执行入口是否同步取消，还是需要等待确认。

**问：动作 41 的迟到回调能清理动作 42 吗？** 不能。身份、阶段与一次结算记录都必须匹配。

**问：完成这套拆分就证明速度更快吗？** 不能。本文只建立协作契约，性能需固定输入、编译环境和更新次数后实测。
