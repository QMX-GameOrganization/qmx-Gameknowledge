## 先用一个角色理解协作

玩家一边移动一边换弹，又按下切枪。输入系统知道按了什么，武器系统知道弹药和动作阶段，移动系统知道脚下与头顶的空间。怎样让它们协作，同时避免大家随意修改彼此的状态？

本专题以当前讨论采用的同步路径为主线：**Update 采集并缓存输入，各系统提交意图；FixedUpdate 中统一按明确顺序判断，每项通过后立即调用所属执行器的 TryCommit。执行器确认接纳并开始动作、发布更新事实后，再处理下一项请求。** 这里的“统一”指决策入口与协议统一，不要求所有功能塞进一个类，也不要求所有动作共用一个状态枚举。

```text
Update：采集输入 → 更新持续目标、缓存一次性事件
        ↓ 后续固定步读取
FixedUpdate：整理本步意图，按序处理各项请求
        ↓ 每项请求
IsValid / CanApply → Apply 调用所属执行器 TryCommit
        ↓
本地守卫通过并开始动作 → 所属系统发布活动事实，消费对应事件
尚未接纳则反馈暂缓或最终拒绝 → 按结果保留或丢弃事件
        ↓
下一项请求读取更新事实与本步处理记录
```

规则之间不必互相调用，但它们通过共享事实和本步处理记录形成顺序与数据依赖。规则也不是“只影响自己的独立脚本”：切枪的决定可能要求停止换弹，攀爬成功会改变身体活动事实。执行系统保留最终空间等守卫，规则检查通过不等于执行器必定接纳，更不等于整个动作已经完成。

若实际需求必须把裁决和执行分开，可以采用延后计划变体，用 `WorkPlan` 预留事件与通道，防止后续规则重复批准。同步逐项提交无需强制增加这层计划；两条路径均无需通用的“审核规则的审核器”，但都要保留所属执行器的本地守卫与结果反馈。

> 适用范围：以 Unity 角色玩法为背景的设计教程，时序说明参考 Unity 6 常规自动物理模拟与动态输入更新。具体 Input System 更新模式、自定义 PlayerLoop 和手动物理模拟需另外约定。文中的类型名、规则顺序、动作限制均为教学示例，不是某个项目的既定实现；代码是伪代码，未进行 Unity 编译、真实运行或性能测量。

## 三个词先分清

| 名称 | 含义 | 例子 |
| --- | --- | --- |
| 请求 / 意图 | 希望发生什么 | 希望站起、请求换弹、请求切到武器 B |
| 决定 / 计划 | 本步允许和安排什么 | 接受切枪，并安排取消当前换弹 |
| 活动事实 | 实际已经发生什么 | 角色仍蹲着、换弹实例 41 正在退出、武器 B 已切换成功 |

一个字段只能有约定好的含义。`WantsStand` 可以一直为真，但 `ActualPosture` 仍然是蹲姿；同步路径中的 `ActiveReload` 只由武器系统在接纳启动后发布。若采用延后路径，`PlannedReload` 获准也不代表换弹已经开始。

## 学完用这些问题自查

- 移动输入回到零、蹲下键松开，能否仍传递有效信息？
- 同一次空格事件为何不会既攀上又跳跃？
- 同一规则循环中，后面的规则读到的是原始快照还是更新后的工作状态？
- 切枪失败时，是否会错误地先取消合法的换弹？
- FixedUpdate 最终空间检查失败后，谁反馈、谁写事实、哪些请求允许下步再试？

这些问题比类名和接口数量更能检验边界是否清晰。架构整理方便解释与维护；是否减少分配、降低耗时，需要在真实项目中固定输入和测量口径后验证。
