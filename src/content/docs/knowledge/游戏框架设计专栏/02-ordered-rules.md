## 规则为什么需要顺序

上一章已经把输入变成意图。但玩家同一步提交攀上、跳跃、移动和换弹时，不能让每条规则只读最初快照，然后各自宣布“我合法”。即使每个候选单独可行，它们也可能争用同一事件或动作通道。

本专题的主要路径是在 FixedUpdate 中**按序判断一项，立即提交一项**。规则通过后调用所属执行器 `TryCommit`；执行器完成本地最终检查，接纳并开始动作，发布所属活动事实，然后才处理下一项。共享处理上下文包括最新事实、意图、事件绑定和消费记录，不必另建一套推演计划。

规则按显式顺序执行：一条规则通过并 `Apply` 后，后续规则必须看到提交结果和更新后的事实，而不是继续读取处理开始时的旧副本。规则可以不直接调用彼此，却仍通过这些数据产生依赖。只有证明读写集合不冲突时，才有依据讨论重排或并行，不能从“类之间没有方法调用”推导出规则独立。

## IsValid、CanApply、Apply 各做什么

这三个名称只是教学约定，重点是区分检查与生效。

| 阶段 | 主要问题 | 不应做的事情 |
| --- | --- | --- |
| IsValid | 候选是否存在、字段完整、目标身份格式有效、事件未过期？ | 缺少候选时仍继续访问载荷 |
| CanApply | 结合事实与前序决定，现在允许吗？事件和通道是否可用？ | 检查时偷偷消费事件、取消实际动作 |
| Apply | 同步路径调用所属执行器 TryCommit；延后路径才写计划与预留 | 绕过所属执行器直接改其他域事实，或把预留冒充已启动 |

检查应当只读，不靠调用次数产生副作用。`Apply` 可以把决定立即交给所属执行器，不是必须只写计划。真实碰撞体、弹药和活动动作仍由该执行器维护；`TryCommit` 成功表示动作已接纳启动，不表示整个动作已经完成。

## 主路径：同步逐项提交

```csharp
// 教学伪代码：在 FixedUpdate 内按注册顺序判断并立即提交。
// context 读取所属系统当前发布的事实，不冻结为整轮都不变的旧副本。
void ResolveFixedStep(StepContext context)
{
    foreach (var rule in orderedRules)
    {
        if (!rule.IsValid(context))
            continue;

        if (rule.CanApply(context))
        {
            var result = rule.Apply(context); // 内部调用所属执行器 TryCommit。
            context.RecordOutcome(rule, result); // Started 消费，Deferred 保留，最终 Rejected 丢弃。
        }
        else
            context.RecordNotApplicable(rule); // 按契约区分暂缓与最终拒绝，不自动吞输入。
    }
}
```

函数意图是说明顺序与可见性，实际实现可以很直接：少量明确规则加普通数据结构即可。执行器在返回 `Started` 前发布自己的活动事实，缓冲所有者再根据结果更新消费记录；`Deferred` 不得伪造启动事实。`IsValid` 跳过空候选不表示最终拒绝，发现过期或无效目标时则由约定入口清理并记录原因。遇到相同优先级，还应约定稳定的第二排序键，避免依赖容器枚举的偶然顺序。

## 用同一份工作状态走一遍

假设本步角色正在挂边，主动作事件为 108，允许攀上；同时有移动与换弹请求。以下顺序和限制**可配置，仅为示例，不是项目既定优先级**。

| 顺序 | 规则 | 读取什么 | Apply 后更新什么 |
| --- | --- | --- | --- |
| 1 | 生存 / 控制门控 | 是否死亡、是否被控制 | 禁用相关候选或通道 |
| 2 | 攀上 | 挂边事实、空间预查、绑定为攀上的事件 108 | TryCommit 成功则发布攀上实例并消费 108；暂缓则仍挂边并保留事件 |
| 3 | 跳跃 | 最新活动事实、事件语义与消费记录 | 108 已消费或仍绑定为攀上，本例都不能用它启动二段跳 |
| 4 | 移动 | 身体活动事实、移动方式与限制 | 所属执行器应用受攀爬约束的移动目标 |
| 5 | 换弹 | 最新武器与身体事实、兼容策略 | 若兼容且提交成功则发布换弹实例，否则按结果暂缓或最终拒绝 |

“身体通道”和“武器通道”是描述冲突的工具，不必马上搭建通用资源调度器。最小实现可以只是几组字段与明确条件。

攀上规则没有调用跳跃规则，但它通过所属执行器改变身体事实、影响事件记录后，已经影响了跳跃的可用性。后续规则若仍只看初始事实，就破坏了这条依赖。空中抓边未接纳时则不应提前写入挂边或消费跳跃事件，后续请求仍按实际事实处理。

## 移动与换弹可以并行

并非所有动作都要抢一个全局 `Busy`。在允许移动换弹的玩法中，移动处理身体位移，换弹占用武器动作；两者可以同时获准。这里的“并行”指玩法在时间上重叠，不意味着必须开两个线程。

换弹条件可以检查弹匣容量、备弹、武器身份、当前动作阶段和玩法兼容性。**不应无依据地加上“必须在地面”**：空中、蹲下、挂边是否允许换弹，都由该游戏的具体规则决定。需要限制时明确写出原因与条件。

统一规则处理解决的是条件与冲突如何集中表达，不是让所有功能彼此互斥。

## 同帧互斥与跨帧打断不是同一个问题

| 问题 | 要查看的状态 | 要产生的结果 |
| --- | --- | --- |
| 同帧互斥 | 本步已经接受了什么，事件和通道被谁占用 | 不重复接受冲突候选 |
| 跨帧打断 | 已运行的动作实例及其可取消阶段 | 取消 / 等待 / 拒绝，并安排后续执行 |

同帧互斥可以阻止换弹和切枪同时作为互斥的新动作开始，却不能自动结束上一帧已经启动的换弹。跨帧打断需要读取真实活动实例，例如“换弹 41，处于可取消阶段”，不能仅看本步 Reload 槽位是否为空。

取消也有完成时机。如果动作只能在特定帧退出，规则只能安排请求，武器系统确认退出后才能把通道视为实际释放。

## 切枪要先验证目标与可取消性

考虑当前正在换弹，玩家请求切到武器 B。危险顺序是：先取消换弹，再发现 B 不存在或当前阶段不能切枪。此时一个原本合法的动作被白白破坏。

推荐把切枪视为一个有前置条件的转换：

1. 验证目标 B 确实存在、当前仍可用，且不是无效或已失效身份。
2. 读取当前武器动作实例与阶段，判断是否允许取消；不允许时按策略拒绝或等待。
3. 两项通过后，`Apply` 立即把“切向 B + 必要时取消换弹 41”的决定交给武器执行器 `TryCommit`。
4. 武器执行器在真正改变活动状态前最终验证目标、当前实例与阶段；尚未接纳时返回暂缓或最终拒绝。
5. 验证仍通过后才取消和切换，发布新的活动事实并消费事件；需要延后退出时，接纳为一个实际过渡实例，保持过渡状态，确认退出后再开始新动作。

这里强调同一执行入口负责转换的一致性，不是声称跨多个异步系统的操作天然原子。若取消前最终验证失败，保留当前合法换弹，反馈尚未接纳的原因，并按暂缓或最终拒绝处理输入；若已经接纳并进入不可逆的取消过程，后续失败必须如实反馈并进入定义好的安全状态，不能伪造“换弹仍在继续”、擅自重启它或恢复旧输入。

当切枪规则排在换弹规则之前，前者成功提交后的切枪 / 过渡事实可以使后者本步不可用。若调整顺序，则要重新检查这些读写依赖，不能只改优先级数值就认为行为等价。

## 可选变体：必须延后执行时再引入 WorkPlan

若规则和执行不得不处于不同阶段，才需要在检查通过后把决定写入 `WorkPlan`，预留事件与通道。后续规则读取“活动事实 + 前序预留”，避免两个互斥请求同时获准；预留不是活动事实，也不代表输入已消费。

执行阶段再调用所属执行器 `TryCommit`：接纳启动后发布事实、消费事件并结算预留；尚未接纳返回 `Deferred` 时释放本次预留，在 TTL 内保留原语义事件；显式最终 `Rejected` 才丢弃。不要在一次检查失败后无限重放同一步计划，可以在下一步重新判断有效候选。

同步逐项提交时，后续规则直接读更新事实即可，不必强制增加 `WorkPlan` 或复制一套计划状态。只有“先裁决、后执行”的间隔才需要额外预留来表达尚未落地的决定。

## 不必再增加通用的“审核规则的审核器”

已经有确定输入、有序裁决、受控写入与执行反馈时，再增加一层对所有规则重新跑一遍的通用审核器，往往只是复制冲突判断，还容易出现两套标准。

同步逐项提交与延后计划两种路径都无需通用审核器，也都不能省略本地守卫。同步路径把最终检查放进当前这次 `TryCommit`；延后路径还需应对从裁决到执行之间的空间、目标和阶段变化。姿态系统扩大碰撞体前检查净空，武器系统消费弹药前确认动作实例和资源，都是执行职责。

两者回答的问题不同：规则决定“整体策略允许怎样做”，本地守卫确保“此刻实际操作仍满足该系统的不变量”。守卫失败要反馈尚未接纳、最终拒绝还是运行中失败，不能偷偷改写其他系统的事实或直接重新跑全部规则。

## 未接纳可暂缓，启动后失败不恢复输入

假设挂边空格 108 已解释为攀上。空间检查未通过和攀上已经启动后失败，是不同的结果：

```text
TryCommit 尚未接纳 → Deferred → 仍保持挂边，108 在 TTL 内可再次尝试攀上
TryCommit 接纳启动 → Started → 发布攀上实例，消费 108
                                      ↓ 后来失败 / 取消
                              按动作状态收尾，不恢复 108
显式最终 Rejected → 丢弃 108；TTL 到期则过期清理
```

无论暂缓还是启动后失败，都不能把这个已经绑定为攀上的事件降级为二段跳。暂缓后重试原有请求不等于重新放行本步已经最终拒绝的请求；最终拒绝不会因其他动作失败而自动补跑。尚未接纳的自动抓边也不应吞掉另一个合法跳跃候选，它没有建立挂边事实或取得该输入的消费权。

持续站起是另一种情况：低顶阻挡后，持续目标仍在，下一处理步可以重新判断。它依赖的是新一步的有效意图，不是本步失败后的隐式补跑。

## 自测

**问：规则没有互相调用，能随意交换顺序吗？** 不能。要检查它们通过共享工作状态形成的读写依赖。

**问：统一处理是否要求只有一个总动作能执行？** 不要求。移动与换弹可以占用不同通道，按兼容策略同时运行。

**问：规则同意切枪，为什么武器系统还要检查？** `TryCommit` 仍由武器系统保障目标、阶段和资源不变量；若延后执行，还要应对这段间隔内发生的变化。
