## 搜索结束不等于移动完成

搜索算法返回的是节点序列。Gameplay 还需要把它转换成角色可以执行的路径点，并处理移动过程中的变化：

```text
搜索节点
→ 反向读取 cameFrom
→ 反转为起点到终点
→ 压缩共线节点
→ 检查拐角和可通行空间
→ 交给移动执行器
```

搜索系统负责给出路径候选，移动系统负责速度、转向、碰撞和到达判定。两者之间使用明确的数据协议，避免移动器直接修改搜索内部状态。

## 路径重建

`cameFrom` 记录每个节点的前驱。到达目标后，从目标反向追溯到起点，再反转数组。追溯过程中要处理：

- 起点没有前驱。
- 目标不可达时没有完整链。
- 节点版本已经过期。
- 结果长度超过预分配容量。

路径点可以用节点 ID 表示，也可以在输出阶段转换成世界坐标。转换时统一格子中心、NavMesh 投影和高度采样规则。

## 路径压缩和平滑

相邻节点共线时，可以删除中间点。对于网格路径，还可以检查更远的两个点之间是否存在可通行直线，减少锯齿。

平滑检查需要使用与角色尺寸匹配的几何测试。单条射线只表示一个点的可见性，不能证明角色胶囊体可以通过。狭窄通道和拐角处应使用 CapsuleCast、多个射线或引擎导航系统提供的可行走检查。

## 路径缓存

路径缓存适合重复请求明显的场景，例如同一批单位向同一个据点移动。缓存键至少要包含：

- 起点区域或起点格子。
- 目标区域或目标格子。
- 地图版本。
- 通行规则版本。

地图障碍发生变化后，旧缓存必须失效。只用起点和目标做键，会把旧地图结果误用到新地图。

## 取消和失效

一个路径请求可能在完成前失效：角色被销毁、目标消失、场景切换、地图版本变化或用户发起新请求。请求需要有版本号或取消标记：

```text
requestVersion += 1
提交请求时记录 localVersion
完成回调前检查 localVersion == requestVersion
```

这个检查不能替代任务本身的释放和依赖管理。异步任务仍然要在拥有者销毁时取消或安全收尾。

## 使用 Unity 导航系统时的边界

使用 NavMesh、NavMeshAgent 或第三方寻路库时，仍然需要理解：

- 谁负责发起请求。
- 路径何时准备好。
- 路径是否可能被重新计算。
- Agent 和目标销毁时如何停止请求。
- 结果由谁转成移动意图。
- 表现层如何显示未完成、失败和重新规划。

引擎系统可以承担底层搜索，Gameplay 仍然需要承担请求生命周期、目标策略、预算和状态协作。

## 自测

- 为什么路径点压缩不能只用距离阈值？
- 地图发生一个障碍变化后，哪些路径缓存必须失效？
- 角色半径增大时，原先的直线平滑结果还能直接复用吗？
- 新路径请求到达后，旧路径的执行器如何安全停止？

## 练习

1. 为 A* 加入路径重建和共线点压缩。
2. 为路径请求加入版本号、取消和超时。
3. 比较未经平滑、共线压缩和视线平滑三种路径的拐点数。
4. 给移动执行器增加路径失效后的重新请求策略。
