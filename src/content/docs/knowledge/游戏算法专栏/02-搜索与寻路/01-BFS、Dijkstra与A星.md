## 先把地图变成图

寻路算法处理的不是“场景”这个概念，而是图：

- 节点表示可到达的位置或区域。
- 边表示一次允许的移动。
- 边权表示移动代价。
- 目标条件表示什么时候可以结束搜索。

网格地图的节点可以是格子，NavMesh 的节点可以是多边形，战术地图也可以把掩体、房间和路口作为节点。算法的选择取决于图是否隐式生成、边权是否相同、地图是否变化。

## 三种搜索的关系

| 算法 | 适用情况 | 特点 |
| --- | --- | --- |
| BFS | 所有边权相同 | 按层扩展，得到最少步数 |
| Dijkstra | 边权非负 | 每次扩展当前代价最小的节点 |
| A* | 有目标、可构造启发式 | 在 Dijkstra 基础上优先朝目标搜索 |

A* 的评价函数是：

```text
f(n) = g(n) + h(n)
```

`g` 是起点到当前节点的已知代价，`h` 是当前节点到目标的估计代价。启发式不高估真实代价时，A* 可以保持最优性。游戏中常用曼哈顿距离、对角距离或欧氏距离，具体取决于邻居规则和移动代价。

## 开放表和关闭表

典型 A* 维护：

- 开放表：已经发现但还没有展开的节点，按 `f` 排序。
- 关闭表：已经处理完的节点。
- `gScore`：每个节点当前已知的最小代价。
- `cameFrom`：路径重建所需的前驱节点。

伪代码：

```text
open.push(start, f(start))
gScore[start] = 0

while open 非空：
    current = open.popMin()
    if current == goal：重建路径并返回
    if current 已经处理过更优版本：跳过

    for neighbor in current 的可行邻居：
        nextCost = gScore[current] + cost(current, neighbor)
        if nextCost >= gScore[neighbor]：继续
        cameFrom[neighbor] = current
        gScore[neighbor] = nextCost
        open.push(neighbor, nextCost + heuristic(neighbor, goal))

返回不可达
```

C# 中的优先队列可以使用 `PriorityQueue<TElement, TPriority>`，也可以使用自定义堆。若不支持 decrease-key，可以把新优先级再次压入开放表，弹出时用 `gScore` 判断旧条目是否过期。

## 启发式要和移动规则一致

四方向移动通常使用曼哈顿距离。允许八方向移动时，可以使用对角距离或带对角代价的估计。若角色可以斜向移动，却仍然使用不匹配的启发式，搜索顺序和路径质量都会发生变化。

还要处理斜角穿越：如果两个相邻直角格都是障碍，禁止从它们的夹角穿过。这个规则需要在生成邻居时检查，不能等路径生成后再补救。

## 性能和结果的两个维度

A* 的性能不只由地图大小决定，还与以下因素有关：

- 障碍物分布。
- 启发式质量。
- 开放表实现。
- 是否重复请求相同或相近路径。
- 是否允许近似路径。
- 是否限制单次搜索展开的节点数。

Gameplay 中可以接受“下一帧继续搜索”的异步结果。搜索状态需要保存开放表、关闭标记、前驱和取消信息，并在场景或请求失效时安全结束。

## 常见坑

- 把世界坐标直接当作节点 ID，忽略坐标取整和地图边界。
- 只判断目标可走，忘记检查起点和中间邻居。
- 允许斜角穿越障碍。
- 优先队列中有旧条目，却没有在弹出时验证版本。
- 只比较平均耗时，忽略不可达地图和高密度障碍下的最差耗时。

## 练习

1. 在二维网格上实现四方向 BFS。
2. 为格子增加不同移动代价，改成 Dijkstra。
3. 加入曼哈顿启发式，改成 A*，比较展开节点数。
4. 加入不可达处理、路径重建、斜角限制和节点展开预算。
