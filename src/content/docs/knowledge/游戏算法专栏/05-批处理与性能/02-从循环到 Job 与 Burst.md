## 先判断算法是否适合并行

适合 Job/Burst 的工作通常具有这些特点：

- 输入和输出可以用连续数据表达。
- 每个元素的计算相对独立。
- 不依赖托管对象、UnityEngine API 或复杂虚调用。
- 写入位置明确，竞争可以避免或集中合并。
- 工作量足够大，可以覆盖调度成本。

一个很小的循环迁移到 Job 后，可能因为调度和同步变慢。迁移前先测量原始版本，并估算每次调度的工作量。

## 从对象循环提取数据

面向对象的单位通常包含 GameObject、MonoBehaviour、组件引用和表现对象。Job 需要的是可批量处理的数据：

```text
MonoBehaviour 层：收集输入和生命周期
数据层：位置、速度、目标索引、状态值
Job 层：批量计算距离、筛选、更新数值
提交层：主线程应用结果和表现变化
```

提取数据会产生同步和复制成本。数据层的所有权、读写阶段和回收时机需要写清楚。

## 依赖和结果可见性

Job 的结果只有在依赖完成后才能安全读取。常见链路是：

```text
收集输入 Job
→ 批量计算 Job
→ 归约或排序 Job
→ Complete
→ 主线程应用结果
```

过早 `Complete` 会让主线程等待，过晚读取会产生安全错误或使用旧数据。依赖链应与系统生命周期绑定，场景销毁时安排取消或完成。

## 并行写入

多个线程同时写同一个结果位置会产生竞争。解决方式包括：

- 每个元素只写自己的槽位。
- 使用 `NativeParallelHashMap` 的并行写入器。
- 每个线程写局部结果，之后做归并。
- 先生成事件，再由单线程按顺序提交。

并行容器解决的是写入安全，不能自动保证业务顺序和结果确定性。需要顺序时，加入稳定排序键或统一归并阶段。

## Burst 约束

Burst 适合纯数据、纯计算、分支可控的代码。托管对象、反射、部分虚调用和 Unity API 通常不能直接放入 Burst 路径。把不可 Burst 的部分留在边界层，避免为了迁移而重写整个系统。

## 什么时候停止迁移

出现以下情况时，需要重新评估：

- 工作量太小，调度成本超过计算成本。
- 数据复制和主线程回收占用大部分时间。
- 依赖链让主线程频繁等待。
- 业务分支复杂，Burst 版本难以调试。
- 性能瓶颈其实在资源、渲染或物理系统。

最终目标是降低稳定帧预算，而不是让代码都使用 Job 或 Burst。

## 练习

1. 把批量距离判断改写为 `IJobParallelFor`，比较不同批次大小。
2. 使用局部结果和归并阶段处理“每个单位写多个候选”的问题。
3. 记录 Job 调度、Complete、数据复制和主线程提交的独立耗时。
4. 对比普通 C#、Job、Burst 三种实现的最差帧和内存。
