## 先看访问模式

容器选择应该由访问模式驱动：

| 需求 | 常见选择 | 关注点 |
| --- | --- | --- |
| 按连续编号访问 | `T[]`、`NativeArray<T>` | 连续内存和边界检查 |
| 尾部增删 | `List<T>`、`NativeList<T>` | 容量和扩容 |
| 按键查找 | `Dictionary<TKey,TValue>` | 哈希、装箱、扩容和删除 |
| 去重 | `HashSet<T>` | 哈希质量和对象生命周期 |
| 按优先级取出 | 堆、优先队列 | 更新优先级和惰性删除 |
| 先进先出 | 队列、环形缓冲区 | 固定容量和溢出策略 |

复杂度只是第一层判断。Gameplay 中还要看分配频率、数据是否连续、对象是否经常销毁、是否需要在 Job 中访问，以及查询结果能否复用。

## 热数据和冷数据分开

一个单位可能包含位置、速度、生命、名字、装备、动画引用和调试信息。每帧移动只需要位置和速度，遍历时若把所有字段放在同一个对象里，会把不需要的数据带入访问路径。

可以把数据按更新频率拆开：

```text
热数据：位置、速度、当前状态、目标索引
中频数据：感知结果、技能冷却、路径游标
冷数据：名字、配置引用、调试信息、编辑器对象
```

在面向对象的 Gameplay 代码中，这种拆分可以先通过独立组件和数组实现。只有在 Profiler 证明数据访问是热点时，再考虑更强的数据导向改造。

## 容量和生命周期

`List<T>` 的扩容会分配新数组并复制旧元素。高频创建和销毁的单位集合应该提前设置容量，或者使用对象池和空闲索引表。

```csharp
var activeIds = new List<int>(expectedCount);
var byId = new Dictionary<int, Unit>(expectedCount);
```

容量只是减少扩容次数。它不会自动解决元素长期存活、引用未清理或场景切换后的泄漏。集合的拥有者、清理时机和移除规则仍然需要明确。

## 索引表和对象表分开

一种常见结构是用整数 ID 作为稳定索引：

```text
UnitId → dense index → 热数据数组
UnitId → managed view / GameObject
```

热循环只遍历 dense array。对象销毁时，把最后一个元素移动到空槽，并更新反向索引。这样可以避免频繁删除中间元素造成的大量搬移。

使用这种结构时要维护两个不变量：

- 每个有效 ID 都能通过反向索引找到唯一位置。
- 被移动的最后一个元素已经同步更新自己的索引。

## Unity 中的容器边界

- `List<T>` 和 `Dictionary<TKey,TValue>` 适合托管主线程逻辑。
- `NativeArray<T>`、`NativeList<T>` 和 `NativeParallelHashMap<TKey,TValue>` 适合有明确生命周期的批量数据。
- Job 不能直接安全地访问任意托管对象。
- Native 容器必须由明确的所有者释放，并在 Job 依赖完成后释放。

## 常见坑

- 只看 Big-O，忽略容器分配、哈希冲突和缓存局部性。
- 在循环里调用 `Dictionary` 查询，却没有确认键类型是否产生装箱。
- 删除元素后继续使用已经失效的索引。
- 对象池只复用 GameObject，却没有清理状态、事件订阅和异步回调。
- 用 Native 容器绕过托管分配，却忘记安排释放和 Job 依赖。

## 练习

1. 用 `List<int>`、`HashSet<int>` 和 `Dictionary<int, int>` 实现同一个目标集合，记录插入、删除、查询和遍历耗时。
2. 把 10 万个单位的热数据和冷数据拆开，比较遍历时间和内存占用。
3. 为一个会频繁生成和销毁单位的系统实现 dense array 加反向索引。
