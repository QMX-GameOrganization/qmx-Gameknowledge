## 视野判断应该分层

一个完整视野查询通常包含：

```text
距离范围
→ 阵营和状态过滤
→ 视野角过滤
→ 高度或遮挡点检查
→ 射线确认
→ 目标优先级排序
```

如果一开始就对所有目标发射射线，成本和调试难度都会快速增长。

## 射线命中多个对象

`RaycastAll` 可能返回多个命中结果。业务上需要明确：

- 是否只关心第一个实体碰撞。
- 触发器是否参与。
- 透明材质是否阻挡视线。
- 自己的 Collider 是否忽略。
- 命中结果是否需要按距离排序。

不要依赖返回顺序代表最近命中。若 API 没有提供排序保证，就显式选择最小距离结果。

## 目标点和高度

角色的脚部、胸口和头部可能得到不同遮挡结果。单个目标点的射线只能表达一个视线模型。可以根据玩法选择：

- 头部可见才算发现。
- 胸口可见即可攻击。
- 多个采样点中有一个可见。
- 使用 Collider bounds 的代表点。

采样点越多，结果越稳定，查询成本也越高。应把采样策略作为玩法规则明确下来。

## 视野结果缓存

感知系统可以缓存最近一次结果，并记录：

- 下一次更新时间。
- 当前目标。
- 目标位置版本。
- 地图或障碍版本。
- 上一次查询是否被打断。

远处 AI 可以低频更新，近处或战斗中的 AI 可以提高频率。结果缓存需要在目标销毁、阵营变化和场景切换时主动失效。

## 目标排序

目标优先级可以是一个可解释的评分：

```text
score = 距离权重 + 威胁权重 + 任务权重 + 可见性权重
```

评分前先完成硬过滤。排序只对少量候选执行，避免对整个世界排序。只需要最优目标时，可以使用线性扫描维护当前最佳值，不必构造完整排序结果。

- 目标点应该放在脚部、胸口还是头部？由什么决定？
- 感知结果缓存失效的条件有哪些？
