## 用三个变更请求检查设计

拿到一张 UML 图，类之间箭头很整齐，不代表设计有效。真正的检查是：需求变化时，规则会在哪一处修改，哪几处需要重新验证，调用方需要知道多少内部细节？

| 新需求 | 规则分散时 | 本专题的目标边界 |
| --- | --- | --- |
| 生命值不能超过上限 | 所有治疗点都补判断 | `Actor::heal` 维护统一约束 |
| 添加治疗技能 | 战斗循环追加类型分支 | 新增技能实现，在组装处注册 |
| 将减伤方式改为比例 | 所有攻击公式逐个修改 | 统一防御规则，验证相关调用 |

“新增行为不改战斗循环”并不等于“不改任何文件”。构造与注册具体技能的地方仍需认识新类型；存档、UI、本地化若要求新信息，也可能要扩展对应数据契约。要讨论的是影响面是否合理，而不是追求零修改的口号。

## 单一职责：按变化原因组织

角色维护生命值和受伤规则是一个合理的职责集合；把文件保存、网络连接、UI 排版、战斗计算全放进角色，会让不相关变化互相牵连。反过来，一个函数只有三行也不一定应拆成三个类。

可以先问：“调整这个规则的人，需要同时理解哪些无关模块？”如果改伤害必须知道按钮颜色，边界很可能值得调整。拆分后还要有明确协作协议，不能只是把一个大文件变成相互调用的很多小文件。

## 开闭原则：保护稳定流程，开放明确的变化点

稳定的战斗循环按顺序调用 `cast`；不稳定的技能效果由实现提供。这是本例的扩展点。但如果真实变化只是 100 种伤害数值，建 100 个派生类就不如配置表。如果每个技能都需要大量特殊访问，原接口可能过窄，不能为保住接口而偷偷暴露全部内部对象。

设计从已观察到的变化出发，避免预先构建万能插件系统。

## 依赖倒置与依赖注入不等于框架

战斗流程依赖 `Skill` 契约，而不是 `Fireball` 具体实现，这体现依赖倒置。由调用方把技能传进来，就是最朴素的依赖注入；不要求容器、反射或配置框架。

测试时可以传入一个很简单的假技能，检查流程是否真的调用了它：

```cpp
// 接口与第 9 章完整例子一致；需要先引入 Skill、Actor、ostream。
class CountingSkill final : public Skill {
public:
    explicit CountingSkill(int& calls) : calls_(calls) {}
    void cast(Actor&, std::ostream&) const override { ++calls_; }
private:
    int& calls_; // 借用；计数器必须比假技能活得更久。
};
```

把日志作为 `ostream&` 参数传入，练习时就能用 `ostringstream` 捕获输出，不必依赖屏幕。接口改变了一点点，却让验证更容易；这比引入一个庞大日志框架更适合当前规模。

## 不要把所有业务都变成继承

冷却、资源消耗和效果可以是独立维度。若每个技能都重复扣资源、查冷却和写日志，可以让施放服务处理共同流程，具体技能只产生效果。此时要定义失败结果、检查和生效顺序，防止半次施放。

设计模式的名字可用于交流，但先说问题：策略用于替换行为，工厂用于集中构造决策，观察者用于订阅变化。观察者还会引出取消订阅、回调顺序和引用寿命，不能只看到“解耦”两个字。

## 与已有 ECS 内容连接

面向对象关注对象边界与协作；数据导向关注数据布局、访问模式和批量执行。在工厂游戏中，单个配方或编辑器服务可以采用对象设计，大量传送带物品的更新则可能按组件和连续数组批处理。它们可以出现在同一个项目中。

虚接口增加间接调用和对象分散的可能性，但“改成 ECS 一定更快”也不成立。比较必须固定输入规模、规则、更新次数与编译条件，测量耗时、分配和缓存相关数据。本专题没有把架构整理当作性能测量。

继续阅读时可在左侧“ECS 学习 → 工厂游戏的实现”和“Unity-Job与Burst”中对照已有专题：重点比较对象如何标识、数据存在哪里、行为由谁批量执行。

**练习：** 设计一个火球数值配置，要求改伤害不新增类；再设计一个治疗技能，要求不改战斗循环。解释为什么两种需求采用不同扩展方式。
