## 角色有护甲，不是护甲的一种

```cpp
// 局部模型：护甲只负责把原始伤害换算为实际伤害。
struct Armor {
    int reduction = 0;
    int reduce(int raw) const {
        return raw <= reduction ? 0 : raw - reduction;
    }
};

class Actor {
    Armor armor_; // Actor has-an Armor：组合。
    int hp_ = 100;
};
```

本片段假设原始伤害和护甲非负；实际完整示例会校验。把护甲成员直接改成 `public`，就又让所有调用方承担数值合法性。封装边界可以是整个 `Actor`，也可以进一步是 `Armor` 自身；拆分类应服务于独立规则与复用需求，而不是为了让类数量多起来。

组合表达“由什么构成”或“使用什么协作对象”。成员是值时，生命周期通常跟随外部对象；成员是拥有指针时，由外部对象的所有权策略决定；只是引用时，外部对象并不拥有它。画关系图时，要把拥有与借用分开。

## 火球是一种技能：但必须满足契约

如果调用方只知道“技能可对目标施放”，火球、斩击、治疗都可以提供自己的实现。这里才可能需要公共继承：

```cpp
class Skill {
public:
    virtual ~Skill() = default;
    virtual void cast(Actor& target) const = 0;
};

class Fireball final : public Skill {
public:
    void cast(Actor& target) const override; // 在类外定义具体行为。
};
```

公共继承的关键不是“派生类能访问基类代码”，而是**调用方可以把派生对象当作基类对象使用，仍然得到契约允许的行为**。这通常称为里氏替换原则（LSP）。

如果 `Skill::cast` 承诺“任意合法角色都可以成为目标”，派生类却额外要求目标必须是某个特殊子类，并在其他情形崩溃，就破坏了可替换性。若确实有施放限制，应在接口契约中统一表达，例如 `canCast` 或返回明确失败结果。

## 为什么“飞行且远程且火属性”不宜一直向下继承

如果把特性组合全写进类型名，就会出现 `FlyingFireRangedEnemy`、`GroundIceRangedEnemy`……每个维度多一种取值，组合数都可能增长。共同实现也会散落在不同分支。

更自然的方案通常是：角色拥有移动策略、攻击方式、装备和属性配置。新增“冰属性”修改属性或伤害策略，而不是复制一条继承支系。组合的成本是对象协作、配置和间接调用变多，需要清楚安排所有权，不能假装它没有代价。

## protected、私有继承与多继承放在哪里

- `protected` 数据会让派生类依赖基类内部表示。基类修改字段时，多个派生类可能一起受影响。通常优先公开或受保护的受控操作，而非裸露可写字段。
- 私有继承不提供普通外部调用方所需的公共可替换关系，常用于实现技术。入门业务建模先用组合，遇到明确理由再研究它。
- C++ 支持多继承，会引出多份基类子对象、歧义和菱形问题。虚继承可共享某个虚基类子对象，但增加构造与对象模型复杂度。它和“虚函数”不是一件事。

本专题主线使用单继承的行为接口，避免让学习目标被复杂层次淹没。以后遇到多接口或既有框架，再带着真实约束分析。

## 设计练习

需求：怪物可以拿武器，玩家也可以拿武器，有些单位不会战斗。请不要先画 `WeaponActor`、`PlayerWeaponActor`。先回答：武器由谁拥有？装备槽是否允许为空？攻击需要知道角色全部内部状态吗？装备变化时哪些规则需要保持？

**参考方向：** 角色组合可选装备；武器提供攻击相关能力；战斗流程通过明确接口使用它。只有当不同单位确实能遵守同一能力契约时，再抽出共同接口。名词相似不能单独证明继承关系。
