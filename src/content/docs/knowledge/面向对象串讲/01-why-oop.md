## 先承认：过程式代码完全可以工作

假设我们写一个回合制游戏。最初只有一个角色和普通攻击，用结构体保存数据、函数执行规则，非常清晰：

```cpp
struct ActorData {
    int hp = 100;
    int armor = 8;
};

// 初版伤害规则；此处先忽略数值边界，下一章补齐。
void attack(ActorData& target, int damage) {
    target.hp -= damage;
}
```

这里不需要为了“面向对象”立即造一个 `ActorManagerFactory`。程序规模小、规则简单时，直接表达问题通常最好。STL 本身也大量使用值、算法、迭代器和泛型，而不是要求你继承 `vector`。

## 第一次变化：谁都能修改生命值

增加护甲以后，攻击函数开始计算减伤；技能代码可能又自己写一遍；陷阱直接 `target.hp -= 30`；UI 为了调试把生命值设成负数。问题不是 `struct` 这个关键字不好，而是**合法状态没有一个稳定的维护入口**。

```cpp
ActorData boss;
boss.hp = -999;         // 语法合法，业务状态却不合法。
boss.armor = -5;        // 所有调用方都要记住不能这样写。
```

如果不变量是 `0 <= hp <= maxHp`，那么每个修改点都必须遵守。只靠口头约定，修改点越多，检查成本越高。封装要做的，是把保证规则的责任集中到可以检查的边界。

## 第二次变化：分支开始四处生长

```cpp
enum class SkillKind { Slash, Fireball };

// 示意：不同界面和系统都根据同一个枚举分支。
// 战斗系统：switch(kind) 决定怎样施放。
// 提示系统：switch(kind) 决定如何描述。
// 消耗系统：switch(kind) 决定扣什么资源。
```

加入 `Heal` 时，要找到所有相关分支。漏改其中一个，编译也许仍通过，运行时才发现治疗技能在 UI 中叫“未知技能”。我们开始寻找一个边界：能否由技能自身提供行为，让战斗循环只负责“发起一次施放”？

这会引出多态，但不能立刻断言“所有 switch 都该删掉”。如果技能只是数值不同，可以用一份配置表和统一公式；如果类型集合固定且希望穷尽检查，可以考虑 `std::variant`；如果行为差异明显且需要独立扩展，虚接口才可能合适。

## 三大特性究竟在帮什么忙

| 概念 | 初学时容易记住的词 | 实际帮助 |
| --- | --- | --- |
| 封装 | private、public | 通过公开操作维护规则，让调用方少承担内部细节 |
| 继承 | 冒号、父类、子类 | 表达可替换的类型关系，复用只是可能的附带效果 |
| 多态 | virtual | 让调用代码依赖稳定契约，在运行时选择实际行为 |

抽象贯穿其中：调用者知道“它能施放”，不必知道“它怎样施放”。抽象不是越模糊越好，而是保留当前协作所需的信息，隐藏可以独立改变的实现。

## 什么才算一个对象

一个战斗对象可以同时拥有状态（生命值）、行为（受伤、治疗）和约束（生命值不越界）。但不是所有类都必须三者齐全：坐标可以是简单值类型，技能接口可以没有状态，服务可以协调其他对象。

从已有数据结构迁移时，可以这样理解：`vector<Actor>` 仍然负责顺序存储，`Actor` 负责单个角色的规则，战斗流程负责调用时机。它们是不同层次的职责，没有谁替代谁。

## 用需求检验意义

尝试在旧代码中加入“治疗不能超过最大生命值”。搜索所有 `hp` 写入点，并说明每个地方是否都要加判断。下一章把同一规则收进 `Actor::heal`，再比较需要记住的规则数量。

**自测：把 `hp` 改成私有，再提供 `setHp(int)` 原样写入，算完成封装吗？** 只改变了访问形式，未维护不变量。是否封装成功，要看外部能否绕过业务规则，而不只看有没有 getter/setter。
