> 适用版本：C# 9.0。Unity 的 `Awaitable` 为 Unity 2023.1 / Unity 6 之后提供（待核实具体版本），本篇不展开。Job System 和 Burst 在知识库的「Unity Job 与 Burst」专栏里讲。

## 要点

- 线程让多段代码同时运行。C# 里可以直接用 `Thread`，更常用的是 `Task`（任务）与 `async/await`。
- 多个线程同时读写同一份数据会出现**数据竞争**，用 `lock` 或原子操作保护。
- **Unity 的 API（`transform`、`GameObject` 等，只有 `Debug.Log` 这类少数例外）只能在主线程调用**。子线程只适合做纯计算、读写文件、网络，再把结果交回主线程。
- 速通阶段只要明白这几点，真正需要并行计算时再看 Job System。

## 开一个线程

```csharp
using System.Threading;

Thread worker = new Thread(() =>
{
    Console.WriteLine("子线程在加载资源...");
    Thread.Sleep(1000);                     // 模拟耗时
    Console.WriteLine("加载完成");
});
worker.Start();
Console.WriteLine("主线程继续执行");
worker.Join();                              // 等待子线程结束
```

输出里"主线程继续执行"通常先出现，因为两个线程是并发的，具体顺序不固定。

## 数据竞争与 lock

```csharp
int counter = 0;
object locker = new object();

void Work()
{
    for (int i = 0; i < 100000; i++)
    {
        // counter++;                       // 不加保护：读-改-写不是一步，结果会少于 200000
        lock (locker) { counter++; }        // 同一时刻只允许一个线程进入
    }
}

Thread a = new Thread(Work);
Thread b = new Thread(Work);
a.Start(); b.Start();
a.Join(); b.Join();
Console.WriteLine(counter);                 // 200000
```

只是做简单计数时，`Interlocked.Increment(ref counter)` 更轻量。`lock` 的对象应该是私有的专用对象，不要 `lock(this)` 或 `lock("字符串")`。

两个线程互相等待对方释放锁，就会**死锁**，程序卡住。避免办法是所有线程以同样的顺序获取锁，且持锁时间尽量短。

![不加锁时两个线程交错读写会丢失一次加一；加 lock 后顺序执行，结果正确](/qmx-Gameknowledge/assets/csharp/race.svg)

## Task 与 async/await

线程要自己管理创建和等待，`Task` 把"一件要做的事"抽象出来，配合 `async/await` 写起来像同步代码：

```csharp
using System.Threading.Tasks;

static int HeavyCalc()
{
    Thread.Sleep(500);                      // 假设很耗时
    return 42;
}

static async Task Main()                    // 控制台程序的入口可以是 async
{
    Task<int> task = Task.Run(() => HeavyCalc());   // 在线程池里执行
    Console.WriteLine("先做点别的");
    int result = await task;                // 等结果，等待期间不阻塞当前线程
    Console.WriteLine(result);
}
```

`await` 的含义是"这里要等，等完了再回来继续"，而不是阻塞线程。更详细的状态机原理属于进阶话题，这里先会用。

## Unity 里的规则

```csharp
// 以下为 Unity 代码示意
async void Start()
{
    string text = await Task.Run(() => System.IO.File.ReadAllText(path));  // 子线程读文件
    label.text = text;                    // await 之后回到了主线程（Unity 的同步上下文），可以安全使用 UI
}

void WrongExample()
{
    new Thread(() =>
    {
        transform.position = Vector3.zero;   // 错误：在子线程调用 Unity API，会抛异常
    }).Start();
}
```

规则总结：

1. **子线程里不碰任何 Unity 对象**。需要的数据先在主线程拷出来（`Vector3`、数组等纯数据），线程算完再把结果交回主线程使用。
2. 子线程交结果给主线程的常见办法：用线程安全的队列，主线程在 `Update` 里取出并处理。
3. WebGL 平台不支持多线程。
4. 要并行处理大量数据（寻路、碰撞、AI）用 Job System + Burst，而不是手写线程。
5. 协程（`yield return`）**不是**多线程，它依然在主线程分段执行，见 6.2 篇。

## 与 C++ 对照

| C++ | C# |
| --- | --- |
| `std::thread` | `Thread` / `Task.Run` |
| `std::mutex` + `lock_guard` | `lock` 语句 |
| `std::atomic<int>` | `Interlocked` 静态方法 |
| `std::async` / `std::future` | `Task<T>` / `await` |
| 数据竞争是未定义行为 | 不会崩溃，但结果不确定 |

## 动手试试

> **代码归属**：`【实验代码】`。本段只放进 `Assets/Speedrun/Labs/` 临时验证；要进入小游戏主线，请跟随后文或目录中的 `【主线实践】` 文章，在 `Assets/Speedrun/Game/` 重新接入并完成验收。

```csharp
using System.Threading;
using System.Threading.Tasks;
using UnityEngine;

public class ThreadDemo : MonoBehaviour
{
    async void Start()
    {
        int sum = await Task.Run(() =>                 // 在线程池里算
        {
            int s = 0;
            for (int i = 0; i < 100_000_000; i++) s += i % 7;
            return s;
        });
        Debug.Log($"计算完成：{sum}");
        transform.position += Vector3.up;              // await 之后回到主线程，可以安全使用 Unity API
    }

    [ContextMenu("子线程调用 Unity API")]
    void Wrong()
    {
        new Thread(() =>
        {
            try { Vector3 p = transform.position; }
            catch (System.Exception e) { Debug.LogError(e.Message); }   // 看看报的是什么
        }).Start();
    }
}
```

运行时观察：计算期间画面不卡（如果 Scene 里有动画可以更明显）；完成后物体上移一格。然后右键组件选"子线程调用 Unity API"，Console 会显示 Unity 拒绝在非主线程访问 `transform`。最后把 `Task.Run(...)` 去掉，直接在 `Start` 里同步算，感受主线程被卡住的程度。

## 项目应用决策：先分清 Unity 主线程和纯计算

Unity 的 `Transform`、`GameObject`、大多数 `UnityEngine` API 只能在主线程访问。可以放到后台线程的，是不依赖 Unity 对象的纯计算或文件/网络等待，例如生成一批寻路节点、解析存档文本；结果回到主线程后再修改场景。

- `Update`：短小、需要 Unity API 的主线程逻辑；
- `Task`/后台线程：可取消的纯计算或 IO；
- Job/Burst：需要大量数据并行处理时，转入对应专题。

不要为了“看起来异步”把几十次 `Task.Run` 放进每帧循环，也不要从后台线程直接改 `transform`。验收时让后台任务只返回数据，主线程统一应用结果，并在场景销毁时取消任务。

## 常见坑

- 在子线程调用 Unity API，抛出 `UnityException: ... can only be called from the main thread`。
- `async void` 里的异常无法被调用方捕获，会直接抛到同步上下文；尽量用 `async Task`，`async void` 只留给事件处理或 `Start` 这类入口。
- 在主线程对 `Task` 调用 `.Result` 或 `.Wait()`，可能造成死锁。
- 退出播放模式后，后台线程和任务仍在运行，访问已销毁的对象。需要用 `CancellationToken` 取消。
