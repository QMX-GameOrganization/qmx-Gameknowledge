## 怎么用这页

每题给出能直接口述的要点，不展开背景。建议按"先说结论，再补机制，最后说一个游戏里的实例"的顺序回答。标注"追问"的是面试官常见的下一问。难度分三档：A 必答，B 常追问，C 区分度题。

## A 档：必答

### Q1. 值类型一定在栈上吗？

不是。值类型实例的位置取决于它所在的宿主：

- 局部变量：栈或寄存器（JIT 可能整体拆成寄存器，称为 promotion）。
- class 的字段：内联在该对象的堆内存里。
- 数组元素：连续存放在数组对象内。
- 被 lambda 捕获的局部变量：提升到编译器生成的闭包类里，在堆上。
- 迭代器与 async 方法里跨 `yield`/`await` 存活的局部变量：保存在状态机字段里（状态机若是 class 则在堆上）。
- 装箱后：在堆上的新对象里。

同样"引用类型实例在堆上"基本成立，但要补一句：CoreCLR 在较新版本对不逃逸的对象开始做有限的栈分配，Unity 的 Mono 和 IL2CPP 没有（待核实）。

### Q2. 引用类型对象的内存结构是什么？

64 位 CoreCLR：对象头 8 字节（同步块索引、thin lock、哈希码），再是 8 字节 MethodTable 指针，然后是字段。引用指向 MethodTable 指针处，对象头在引用之前。最小对象 24 字节。Mono 与 IL2CPP 是 `klass` 指针加 `monitor` 指针共 16 字节，字段紧随其后。数组、字符串是变长对象，长度字段在 MethodTable 指针之后。

### Q3. 装箱和拆箱到底做了什么？

装箱（`box` IL 指令）：在堆上分配一个对象（头部加 MethodTable），把值拷进去，返回引用。拆箱（`unbox`）：检查对象的 MethodTable 是否匹配目标类型，匹配则返回指向装箱数据的托管指针，类型不符抛 `InvalidCastException`。`unbox.any` 在 `unbox` 后再取值（拷贝）。成本主要在分配、拷贝以及因此增加的 GC 压力，拆箱本身只是一次类型检查。

追问：装箱后修改装箱对象的值，原值变吗？不变，装箱是拷贝，二者互相独立。

### Q4. 哪些写法会隐式装箱？

- 值类型转 `object`、转接口类型（`IComparable c = 3;`）。
- 调用 `string.Format`/插值字符串时传入值类型（旧版本编译器或 `params object[]` 重载）。
- 值类型调用从 `object`/`ValueType` 继承来的未重写虚方法（`ToString`、`Equals`、`GetHashCode`）时，若 struct 未重写它们，通过 constrained call 可避免装箱；未重写时会装箱。
- 非泛型集合（`ArrayList`、`Hashtable`）。
- `foreach` 遍历 `IEnumerable<T>` 接口变量：`List<T>` 自带的 struct 枚举器通过接口使用时会装箱。
- 枚举作为 `object` 或在老版本 Mono 的 `Dictionary<EnumKey, V>` 默认比较器里（待核实现行 Unity 版本是否还存在）。
- 将值类型传给 `Action<object>`/`params object[]` 之类的参数。

### Q5. struct 和 class 怎么选？

struct 适合小的（通常不超过 16 字节）、逻辑上表示单个值、不可变、生命周期短的数据。class 适合需要共享身份、有继承与多态、体积较大的对象。选 struct 时若体积较大且频繁传参，复制成本反而更高；传参时用 `in`。游戏中常见的 struct：向量、四元数、颜色、ECS 的组件。

### Q6. `ref`、`out`、`in` 的区别？

三者都按引用传递变量的地址。`ref` 要求调用前已初始化，可读写；`out` 调用前可以不初始化，被调用方必须在返回前赋值；`in` 只读，编译器禁止在方法内给它赋值，是传大 struct 免拷贝的方式，但若 struct 不是 `readonly struct`，调用其成员时会产生防御性复制。

## B 档：常追问

### Q7. 为什么我给 List<Struct> 的元素赋值字段会编译报错？

`List<T>` 的索引器返回的是元素的拷贝（值类型的返回值），修改一个临时值没有意义，所以编译器报 CS1612。数组的元素访问是对元素变量本身的引用，所以 `arr[i].x = 1` 合法。解决办法：取出来、修改、写回；或用 `CollectionsMarshal.AsSpan(list)` 获取底层数组的 Span，直接修改元素。

### Q8. 什么是防御性复制？什么时候触发？

当编译器无法确认调用不会修改某个只读位置的值类型时，会先复制一份再调用成员，保证原值不被改。触发场景：`readonly` 字段的 struct 调用非 `readonly` 的方法；`in` 参数调用成员；`readonly` 属性返回 struct。避免方法：把 struct 声明为 `readonly struct`（所有字段只读，编译器就知道方法不会改），或把方法标 `readonly`。

### Q9. 可变 struct 有什么坑？

- 通过属性、`List` 索引器、`foreach` 迭代变量拿到的都是副本，修改不生效或编译报错。
- 装箱后再修改接口方法，改的是装箱对象，不是原变量。
- 放进 `readonly` 字段后调用修改方法，修改的是副本，不报错，只是静默无效。

建议 struct 默认不可变。需要就地修改时，通过 `ref` 返回或 `ref` 局部变量访问。

### Q10. struct 传参和返回的成本？

规则取决于调用约定。Windows x64 下大小为 1、2、4、8 字节的 struct 通过寄存器传递，其他大小由调用方复制到临时位置并传其地址；SysV x64（Linux、macOS，CLR 在 Unix 上遵循）可以把不超过 16 字节、字段分类合适的 struct 拆进两个寄存器。超过阈值的 struct 返回时通过隐藏的返回缓冲区指针。所以"struct 不超过 16 字节"既是微软设计准则，也是 ABI 友好的经验值。IL2CPP 下由 C++ 编译器按平台 ABI 处理。

### Q11. 值类型的默认相等性怎么实现？有什么问题？

`ValueType.Equals` 的默认实现：如果结构里没有引用字段、没有填充，并且字段类型适合逐位比较（排除浮点，因为 `0.0 == -0.0` 而位模式不同、`NaN != NaN` 而位模式相同），就直接按字节比较；否则用反射逐字段调用 `Equals`，很慢并且会装箱。`GetHashCode` 的默认实现也与字段构成有关，在不能按位处理时通常只取第一个非空字段参与计算，容易产生大量冲突（具体算法随版本变化，待核实）。结论：struct 作为字典键或频繁比较时，必须实现 `IEquatable<T>`，重写 `Equals(object)` 与 `GetHashCode`，用 `HashCode.Combine` 计算哈希。

### Q12. `==`、`Equals`、`ReferenceEquals` 的区别？

`==` 是运算符，默认对引用类型比较引用，对值类型没有默认定义（struct 需要自己重载）。`Equals` 是虚方法，语义由类型定义。`ReferenceEquals` 比较引用是否相同。`string` 重载了 `==` 与 `Equals` 为内容比较。Unity 的 `UnityEngine.Object` 重载了 `==`：对已被 `Destroy` 的对象，与 `null` 比较返回 true，但引用本身并非 null，所以 `?.` 和 `??` 对它无效。

### Q13. `object.GetHashCode()` 默认怎么来的？唯一吗？

默认实现 `RuntimeHelpers.GetHashCode`，值由运行时生成并存放在对象头（或同步块），之后保持不变，对象被 GC 移动也不变。它不是内存地址，也不保证唯一。一旦存了哈希码，对象头的 thin lock 空间就被占用，锁需要膨胀成同步块。

### Q14. string 为什么是引用类型且不可变？

不可变让字符串可以安全共享、可以作为字典键缓存哈希、可以被驻留（intern）。作为引用类型是因为长度可变且可能很大，值类型拷贝成本高。代价：每次拼接、`Substring`、`Replace` 都分配新对象。游戏里的对策：`StringBuilder` 复用、避免每帧拼字符串、用 `Span<char>`/`ReadOnlySpan<char>` 切片、数字转字符串缓存、UI 文本只在变化时更新。字面量会被驻留，运行时拼出的字符串默认不会，除非调用 `string.Intern`。

### Q15. 数组的内存布局和协变？

数组是引用类型，对象头加 MethodTable 后是长度字段，随后是元素。值类型数组元素连续内联；引用类型数组存放引用。引用类型数组支持协变（`Derived[]` 可赋给 `Base[]`），因此每次向引用类型数组存元素（`stelem.ref`）要做运行时类型检查，失败抛 `ArrayTypeMismatchException`；元素类型是 sealed 类时检查可以优化掉。多维数组 `[,]` 比交错数组 `[][]` 的访问慢，因为 JIT 对多维数组的优化较弱，游戏里普遍用一维数组加手算下标。

### Q16. `Nullable<T>` 装箱后是什么？

`int?` 有值时装箱得到装箱的 `int`，无值时装箱得到 `null` 引用。因此 `object o = (int?)null;` 之后 `o == null` 为 true；`o is int` 对有值的情况成立，没有"装箱的 Nullable"这种对象。

### Q17. 为什么 `Dictionary<TKey, V>` 对 struct 键要小心？

默认比较器 `EqualityComparer<TKey>.Default`：如果 `TKey` 实现了 `IEquatable<TKey>`，在 CoreCLR 中 JIT 对值类型实例化可以去虚化，调用无装箱；没实现则回落到 `object.Equals`，会装箱。在旧版 Unity Mono 上，枚举键是经典的 GC.Alloc 来源，常见做法是传入自定义 `IEqualityComparer<TKey>`（待核实当前 Unity 版本的实际表现）。

## C 档：区分度题

### Q18. `class` 的字段顺序是声明顺序吗？

不是。class 默认 `LayoutKind.Auto`，由运行时重排：引用字段通常放前面便于 GC 扫描，其余按大小从大到小，减少填充。含引用字段的 struct 实际上也使用自动布局，`Sequential` 不被遵守。需要稳定布局时（与 C++ 互操作、`Unsafe` 偏移计算），用只含 blittable 字段的 struct 加 `[StructLayout(LayoutKind.Sequential)]` 或 `Explicit`。

### Q19. 为什么 `ref struct` 不能装箱、不能作为类字段？

`ref struct`（如 `Span<T>`）可能包含指向栈的托管指针，若允许放到堆上，指针的生命周期就可能超出栈帧，造成悬垂。所以编译器限制它：不能装箱、不能是 class/普通 struct 的字段、不能用于 lambda 捕获、不能跨 `await` 或 `yield`（后续语言版本放宽了部分场景）、不能作为泛型参数（C# 13 起 `allows ref struct` 放开）。

### Q20. `is`/`as`/强转的成本？

它们都需要检查对象的 MethodTable。精确类型比较是一次指针比较；检查是否派生需沿继承链向上走；转接口需要在接口映射表里查找。.NET 5 起这些辅助函数由托管代码（`CastHelpers`）实现并有缓存。热路径里用 `sealed` 类可使类型检查退化成指针比较；用泛型或 `where T : struct` 可以避免转换。Unity 的 `GetComponent<T>` 本身比类型转换昂贵得多，应缓存。

### Q21. 泛型是怎么实现的？值类型与引用类型有什么区别？

CLR 的泛型在运行时保留（reified）。对每个值类型实例化（`List<int>`、`List<float>`）JIT 生成独立的机器码，因此能针对大小特化并内联；对所有引用类型实例化共享同一份代码（`List<string>` 与 `List<object>`），通过隐藏的泛型字典参数获取具体类型信息。IL2CPP 也是同理，只是在 AOT 阶段生成 C++ 代码，因此运行时才遇到的新值类型实例化无法生成，这是 AOT 平台上反射与热更常见的报错来源（见 4.2 节）。

### Q22. `stackalloc` 与栈大小？

`stackalloc` 在当前栈帧上分配，方法返回自动回收，不经 GC。线程默认栈大小是 MB 量级（主线程由系统决定，新建线程可在构造 `Thread` 时指定），超出会栈溢出，且 .NET 里栈溢出无法被 `catch`，直接终止进程。所以 `stackalloc` 适合小而固定上限的缓冲（几百字节到几 KB），大小不确定时先判断，超过阈值改用 `ArrayPool`。

### Q23. 深拷贝与浅拷贝，`MemberwiseClone` 做了什么？

`MemberwiseClone` 是 `object` 的受保护方法，按位复制对象字段到新对象：值类型字段复制值，引用类型字段复制引用，也就是浅拷贝。含引用字段的 struct 赋值同样是浅拷贝，容易造成"以为拷了一份，其实共享了内部数组"的 bug。

### Q24. 引用类型参数按值传递时，在方法里 `p = new Foo()` 外面变吗？

不变。传的是引用的副本，重新赋值只改副本。修改 `p` 指向对象的字段则外面可见。要让外面也变必须用 `ref`/`out`。

### Q25. `sizeof`、`Marshal.SizeOf`、`Unsafe.SizeOf` 的区别？

`sizeof(T)` 是编译期对非托管类型的大小（对自定义 struct 需要 unsafe 上下文）。`Unsafe.SizeOf<T>()` 返回 CLR 内存中的大小。`Marshal.SizeOf<T>()` 返回封送为非托管内存后的大小，如 `bool` 会按 4 字节计，含 `string` 的 struct 会按指针宽度计。做原生互操作时应该看 `Marshal.SizeOf`，做托管内存计算时看 `Unsafe.SizeOf`。

### Q26. `readonly struct`、`record struct`、`ref readonly` 返回值分别解决什么？

`readonly struct` 保证不可变，避免防御性复制；`record struct` 自动生成值相等性、`ToString`、解构，字段相等比较由编译器生成，避免了默认反射版 `Equals`；`ref readonly` 返回让你无拷贝地读取集合内的大元素。三者都是为了在保持值类型语义的同时减少拷贝和装箱。

### Q27. 泛型约束 `where T : struct, IFoo` 为什么能避免装箱？

IL 的 `constrained.` 前缀让 JIT 在 `T` 为值类型时，直接调用 `T` 上的接口实现，不必先装箱再走接口派发。加上值类型的泛型实例化独立编译，调用可被去虚化甚至内联，这是 C# 里最接近 C++ 模板静态多态的做法。

### Q28. 同一个 struct 放进 `object[]` 与放进 `T[]`，内存和性能差别？

`object[]` 每个元素都是装箱后的独立堆对象，内存是 `头+MT+数据` 乘元素个数，加上指针数组本身；访问要跳一次指针，缓存不友好，还给 GC 增加标记负担。`T[]` 是纯数据连续排列，缓存友好，GC 只需处理这一个数组对象（若 `T` 不含引用，GC 甚至不用扫描内容）。
