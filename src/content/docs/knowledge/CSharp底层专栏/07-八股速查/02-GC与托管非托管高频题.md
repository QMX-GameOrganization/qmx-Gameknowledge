> 适用版本：.NET 8/9 CoreCLR 的 GC 为基线；Unity 6000.x 的 Mono 与 IL2CPP（Boehm GC，默认开启增量 GC）单独标注。Unity 后续是否切换到 CoreCLR 运行时，以官方路线图为准，涉及处标"待核实"。原理对应专栏第 2、3、4 章。

## 怎么用这页

先背结论，再选一个自己项目里排查过的 GC 问题当例子，面试时能把原理和实践接起来。标 "Unity" 的题强调客户端项目的实际情况，没有标的是 .NET 通用原理。

## A 档：必答

### Q1. GC 怎么判断对象可回收？

可达性分析。从根集出发标记所有可达对象，不可达的就是垃圾。根包括：线程栈上的局部变量与参数（以及寄存器中的引用）、静态字段、GC 句柄（`GCHandle`、`DependentHandle`、弱引用的句柄表）、终结队列中的对象。.NET 不使用引用计数，所以循环引用不是问题。

### Q2. .NET 的分代 GC 为什么有效？

基于分代假说：多数对象很快死亡，存活时间长的对象会继续存活。堆分为 gen0、gen1、gen2，新对象分配在 gen0，回收 gen0 时只处理年轻对象，成本小。存活者晋升到更老的代。gen2 回收即完整回收。每代有分配预算（gen0 预算与处理器缓存大小等相关），预算耗尽触发相应代的回收，回收某代时同时回收它之下的所有代。

### Q3. LOH 是什么？什么时候用？

大对象堆（LOH）。大小 ≥ 85000 字节的对象直接分配到 LOH（阈值可配置）。它只在 gen2 回收时清理，默认不压缩（可以设置 `GCSettings.LargeObjectHeapCompactionMode` 要求下一次完整阻塞回收时压缩），容易碎片化。反复分配大数组是典型的 LOH 问题，例如每帧 `new byte[100000]`。解决：复用缓冲（`ArrayPool<T>`）、提前分配、分块。.NET 5 还加入了 POH（Pinned Object Heap），用 `GC.AllocateArray<T>(n, pinned: true)` 分配永久固定的数组。

### Q4. 什么是写屏障和卡表？

分代回收只扫描年轻代时，必须知道老代对象是否引用了年轻代对象。每次往引用字段写值时，JIT 插入写屏障代码：若被写入的新引用指向年轻代，就在卡表（card table）里把对应内存区域所在的"卡"标脏。年轻代回收时，除根集外还扫描被标脏的卡。代价是每次引用字段写入多几条指令，所以引用赋值比值类型写入更贵，这也是池化长寿对象后又频繁改其内部引用会拖慢 GC 的原因。

### Q5. GC 触发条件有哪些？

分配预算耗尽（最常见）；显式 `GC.Collect()`；系统内存不足的通知；`GC.AddMemoryPressure` 声明了外部内存压力。Unity 里还有：加载场景、`Resources.UnloadUnusedAssets` 触发的回收，以及增量 GC 下堆接近扩张时触发。

### Q6. 工作站、服务器、并发、后台 GC 的区别？

工作站 GC 面向客户端应用，单个堆；服务器 GC 每个核一个堆和 GC 线程，吞吐高但占内存。并发（后台）GC 让 gen2 回收的大部分标记阶段与用户线程并行，短暂的 gen0/gen1 阻塞回收仍可以插入。这些是 CoreCLR 的配置项（`System.GC.Server`、`System.GC.Concurrent`），Unity 的 Mono 与 IL2CPP 使用 Boehm GC，没有这些模式。

### Q7. Unity 的 GC 与 .NET 有什么不同？

Unity 的 Mono 与 IL2CPP 都使用 Boehm-Demers-Weiser GC：保守式扫描（栈和寄存器里看起来像指针的值就当引用，可能误保留对象）、非分代、非压缩（标记清除，不移动对象，因此有碎片）。回收是整堆工作，堆越大一次回收越慢。堆一旦扩张，向系统归还内存比较保守，所以内存峰值会长期保持。

### Q8. Unity 增量 GC 是什么？解决了什么问题？

增量 GC（Player Settings 里的 Use Incremental GC，新版本默认启用）把一次完整的标记工作切成多个小片，分摊到多帧，每帧在预算时间内工作，减少单帧卡顿尖峰。局限：写屏障等额外开销让整体吞吐变低；标记过程中被修改的引用需要重新扫描，如果分配速度超过 GC 推进速度，它会退化为一次性完整回收；最后仍有无法增量的阶段需要暂停主线程。可通过 `GarbageCollector.GCMode` 控制模式，`GarbageCollector.incrementalTimeSliceNanoseconds` 调整每帧时间片，`GarbageCollector.CollectIncremental` 手动推进。

追问：怎么手动控制 GC 时机？在场景切换、加载画面等可容忍卡顿的点主动 `GC.Collect()`；战斗中把 `GCMode` 设为 `Disabled` 并保证没有分配，结束后恢复（需要提前留够堆空间，否则会因无法扩张而崩溃，具体行为待核实）。

### Q9. 游戏里 GC.Alloc 的常见来源？

- 装箱：值类型转 `object`/接口、枚举做字典键（老版本）。
- 字符串：拼接、`ToString`、`string.Format`、插值字符串。
- 闭包与委托：捕获局部变量的 lambda 每次创建新委托和闭包对象，方法组转委托在老编译器下每次分配。
- LINQ 与迭代器：大量临时枚举器和委托对象。
- `foreach` 遍历接口类型集合（枚举器装箱）。
- `new` 临时 `List`/数组、`params` 数组。
- Unity API：返回数组的 API（`GetComponents`、`Physics.RaycastAll`、`Mesh.vertices`），应使用带结果列表参数或 NonAlloc 版本。
- 协程里的 `new WaitForSeconds`、每次 `yield return` 的 `StartCoroutine` 本身。

定位：Profiler 的 GC Alloc 列、Deep Profile、Memory Profiler 的快照对比。

### Q10. 零 GC 有哪些常见手段？

对象池、预分配和复用集合（`Clear` 而不是 `new`）、struct 替代 class、避免装箱、字符串缓存或 `StringBuilder`、`Span<T>`/`stackalloc`、缓存委托、`NativeArray`/`NativeList` 把数据移出托管堆、Job + Burst 处理批量数据。注意池化对象的写屏障与老年代引用问题。

## B 档：常追问

### Q11. 终结器和 Dispose 的关系？

`Dispose` 是确定性、显式的清理，终结器是 GC 之后的兜底。标准模式：`Dispose(bool disposing)` 中，`disposing` 为 true 时释放托管资源和非托管资源，为 false（终结器路径）只释放非托管资源；`Dispose()` 里调用 `GC.SuppressFinalize(this)` 让对象不再进入终结队列。含终结器的对象要多活至少一轮 GC，而且终结器线程只有一个，所以不要给每个小对象加终结器。

### Q12. 为什么推荐 SafeHandle？

`SafeHandle` 把句柄包装成有关键终结器的对象：封送时增加引用计数，保证 P/Invoke 调用期间句柄不会被其他线程 `Dispose` 或被 GC 提前终结；即使在线程中断、内存不足的极端情况下，也尽量保证句柄被释放。比自己持有 `IntPtr` 加终结器更安全。

### Q13. `GC.KeepAlive` 解决什么问题？

JIT 认为对象在"最后一次使用之后"就不再是根，哪怕它所在的方法还没返回。如果一个对象的终结器会释放原生资源，而原生调用仍在使用这些资源，对象可能在原生调用期间被回收并终结。`GC.KeepAlive(obj)` 放在使用之后，延长其可达范围。现代做法是使用 `SafeHandle`，由封送层保证存活。

### Q14. 什么是固定（pinning）？怎么做？有什么副作用？

固定指让 GC 暂时不移动某个对象，这样可以把它的地址交给原生代码。做法：C# 的 `fixed` 语句（作用域内固定）、`GCHandle.Alloc(obj, GCHandleType.Pinned)`（手动控制生命周期）、POH（永久固定）。副作用：固定对象会阻碍压缩，在其周围留下空洞，造成碎片；固定时间越长越糟。因此尽量短时固定，长期固定的缓冲用 POH 分配。Unity 的 Boehm 本来不移动对象，所以固定对 GC 无影响，但 `fixed` 语法与 `GCHandle.Alloc` 在代码层面仍然需要，以保证跨 .NET 实现的正确性。

### Q15. `GCHandle` 有几种类型？

`Weak`（弱，对象回收后句柄置空）、`WeakTrackResurrection`（对象被终结后复活仍可追踪）、`Normal`（强引用，阻止对象回收但不固定）、`Pinned`（强引用且固定）。用完必须 `Free`，否则泄漏。常见用途：把托管对象的标识传给原生回调（用 `GCHandle.ToIntPtr`），在回调里还原。

### Q16. 托管代码与非托管代码的区别是什么？

托管代码由 CLR（或 Unity 的 Mono/IL2CPP 运行时）管理：内存由 GC 管，有类型安全与边界检查，异常处理有统一模型。非托管代码（C/C++ 编译出的机器码）不受运行时监管，内存由程序自己管，指针可以任意操作。Unity 里 `NativeArray`、`UnsafeUtility.Malloc` 分配的是非托管内存，不受 GC 管理但被 C# 安全系统部分包装；Burst 编译的 Job 在语义上还是 C#，但生成的是无 GC 的原生机器码。

### Q17. P/Invoke 的调用过程和开销？

CLR 通过 IL stub 完成：参数封送（blittable 类型直接传，非 blittable 如 `string`、`bool`、数组要转换）、切换线程的 GC 模式（协作模式切到抢占模式，使原生调用期间 GC 能不等待该线程）、调用、恢复。blittable 参数调用的额外成本一般是几十纳秒量级，具体数值取决于平台（待核实）。`SuppressGCTransition` 特性可以省去模式切换，但只适用于极短、不会回调托管代码或阻塞的函数。Unity IL2CPP 在 AOT 阶段为每个 P/Invoke 生成 C++ 包装函数。

### Q18. 原生回调托管委托要注意什么？

- 委托必须被某个强引用持有，否则会被 GC 回收，回调时崩溃（`GCHandle.Alloc` 或存在静态字段里）。
- 在 IL2CPP 下，从原生代码调用的 C# 方法需要是静态方法，并标记 `[MonoPInvokeCallback(typeof(Delegate类型))]`，否则 AOT 无法生成反向封送的包装。
- 回调线程可能不是托管线程，需要注意线程附加。
- 回调里不要抛出异常越过原生边界。
- .NET 里更新的写法是函数指针加 `[UnmanagedCallersOnly]`，Unity 对其支持程度待核实。

### Q19. `string` 和 `bool` 在 P/Invoke 里为什么麻烦？

`bool` 默认封送为 4 字节 Win32 `BOOL`，与 C++ 的 `bool`（1 字节）不一致，应加 `[MarshalAs(UnmanagedType.U1)]` 或改用 `byte`。`string` 需要选择字符集与编码，封送时分配并复制，返回字符串时还涉及谁负责释放，容易泄漏。游戏中传大块文本或频繁调用时，应传 `byte*` 或固定的缓冲。

### Q20. Span<T> 是什么？为什么能降低 GC 压力？

`Span<T>` 是 `ref struct`，包含一个托管指针（或原生指针）和长度，表示一段连续内存的视图，可以指向托管数组、`stackalloc` 的栈内存、原生内存。对数组的切片不再复制数据、不分配对象。因为包含栈上可能存在的指针，它被限制只能存在于栈上，不能装箱、不能做类字段、不能跨 `await`。需要在堆上持有则用 `Memory<T>`。Unity 对 `Span<T>` 的可用性依赖版本与脚本后端（待核实），Burst 里通常用 `NativeArray` 或 `NativeSlice`。

### Q21. `unsafe` 指针和 `ref` 有什么区别？

`ref`（托管指针）是 GC 能识别的内部指针：即使指向堆对象的中间，GC 也知道它引用的是哪个对象，移动对象时会更新。`T*` 是非托管指针，GC 不追踪，指向托管对象时必须先固定。`ref` 只能用在栈上，类型安全，有边界与空检查保护；指针可以存储、做算术，没有保护。

## C 档：区分度题

### Q22. IL2CPP 与 Mono 的核心区别？

Mono 后端是 JIT（Android 上）或解释器（在 iOS 等禁止 JIT 的平台受限）运行 IL；IL2CPP 把 IL 转成 C++ 代码，再由平台编译器 AOT 编译成原生库。IL2CPP 的优势：性能一般更好、可平台化、更难反编译；限制：不能运行时生成新代码（`System.Reflection.Emit` 不可用），泛型值类型实例化必须在编译期可见，裁剪（Managed Code Stripping）可能删掉只通过反射访问的代码，需要 `link.xml` 或 `[Preserve]`。两者的 GC 都是 Boehm。热更新（如 HybridCLR）通过给 IL2CPP 补上解释器来绕开限制。

### Q23. 泛型共享是什么？为什么 AOT 报 "ExecutionEngineException: Attempting to call method ... for which no ahead of time code was generated"？

引用类型泛型实例化共享同一份机器码，值类型泛型每种实例化各有一份。AOT 编译时，只有在代码中能静态看到的实例化才会生成代码。如果通过反射（`MakeGenericType`/`MakeGenericMethod`）或运行时加载的程序集第一次用到某个值类型实例化，就没有预生成的代码，报上述错误。解决：在代码里显式引用该实例化让编译器生成，或使用共享引用类型实例化。

### Q24. 保守式 GC 的问题？

扫描栈和寄存器时，无法区分整数和指针，任何看起来像堆地址的值都被当成引用，造成误保留（对象本该回收却没回收），在 32 位平台更明显。优点是不需要精确的栈映射，实现简单。Unity 里这会让内存回收变得不可预测，并且无法压缩移动对象。

### Q25. 托管内存"泄漏"的常见形态与排查？

静态字段与单例持有、事件订阅未取消、缓存无上限、闭包长期持有、`Native*` 容器未释放、`RenderTexture`/`ComputeBuffer`/`Texture2D` 等 Unity 资源未销毁、`Resources.Load` 后未卸载。排查：Memory Profiler 抓取快照后对比两次差异，沿引用链找到根；.NET 上用 `dotnet-gcdump`、`dotnet-dump`、dotMemory。判断是托管泄漏还是原生泄漏：看 Profiler 中托管堆与原生内存的曲线。

### Q26. `GC.Collect()` 能不能乱用？

不应在常规路径使用。强制回收不会根据分配预算调优，反而会把短命对象提前提升，破坏分代假设。合理场景：场景切换、关卡加载后一次性清理，Unity 里与 `Resources.UnloadUnusedAssets` 一起使用；基准测试里获得干净的起点。

### Q27. 托管堆会不会归还内存给系统？

.NET 的 GC 会在回收后根据策略释放（decommit）空闲区域，并可通过配置（如 `GCConserveMemory`、`GCHeapHardLimit`）调整。Unity 的 Boehm 堆基本只增不缩，释放有限，所以托管内存峰值之后很难下降，内存预算要按峰值估算（待核实各版本的行为）。

### Q28. Unity 会迁移到 CoreCLR 吗？这对 GC 意味着什么？

会。Unity 官方论坛《Path to CoreCLR, 2026: Upgrade Guide》写明 Unity 6.8 将以 CoreCLR 取代 Mono，6.8 不再提供 Mono 选项；6.7 LTS alpha 已有实验性 CoreCLR 桌面 Player。CoreCLR 后端用 .NET 的分代压缩 GC（大对象阈值 85 KB）。官方同时说明 IL2CPP 的 Boehm GC 行为不变，所以 IL2CPP 目标平台仍按 Boehm 做预算（避免分配、控制堆大小）。回答时要点：区分后端；CoreCLR 下 gen0 便宜但大对象和固定对象仍要注意；增量 GC 在 CoreCLR 下是否有等价物待官方确认。
