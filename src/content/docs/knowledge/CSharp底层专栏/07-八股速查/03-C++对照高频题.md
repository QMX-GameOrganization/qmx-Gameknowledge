## 怎么用这页

前半部分是纯 C++ 底层题，后半部分是跨语言对比题。回答 C++ 题时先给语言规则，再给实现机制（对象布局、汇编层面做了什么），最后举游戏引擎里的用例。对比题则先说共同目标，再说两边的取舍。

## A 档：C++ 底层必答

### Q1. 虚函数是怎么实现的？

每个含虚函数的类有一张 vtable（函数指针数组，编译期生成，类的所有对象共享），对象头部有一个 vptr 指向它。虚调用编译为"取 vptr，按固定槽位下标取函数指针，间接调用"。vptr 在构造函数执行时设置：进入每一层类的构造时，vptr 先指向该层的 vtable，所以在基类构造函数里调用虚函数，调用的是基类版本，不会多态；析构同理。Itanium ABI 的 vtable 还包含 offset-to-top 与 RTTI 指针，MSVC 的 RTTI 信息放在 `vtable[-1]`。

### Q2. 什么时候基类析构函数必须是虚的？

通过基类指针 `delete` 派生类对象时。非虚析构会导致只调用基类析构，派生部分的析构被跳过，这在标准里是未定义行为。含虚函数的多态基类应该声明 `virtual ~Base() = default;`。不打算多态删除的基类可以用 protected 非虚析构。

### Q3. 多重继承的对象布局和代价？

每个有虚函数的基类子对象带自己的 vptr；把派生类指针转成非首个基类指针时，指针值会加上偏移；通过非首个基类调用被覆盖的虚函数，vtable 里是 thunk，先调整 `this` 再跳转。虚继承再增加 vbptr 或 vtable 中的 vbase offset，访问虚基类成员多一次间接寻址。游戏引擎里通常限制多重继承，只允许"一个实现基类加多个纯接口"。

### Q4. 智能指针各自适用场景？

`unique_ptr`：独占所有权，零额外开销，默认选择，可移动不可拷贝。`shared_ptr`：共享所有权，控制块含强/弱引用计数（原子操作）、deleter 等，对象指针加控制块指针共 16 字节。`weak_ptr`：观察 `shared_ptr` 管理的对象，打破循环，`lock()` 返回 `shared_ptr` 或空。`make_shared` 把对象与控制块一次分配，更快，代价是弱引用存在时对象内存要等控制块一起释放。

追问：`shared_ptr` 线程安全吗？控制块的引用计数操作是线程安全的；同一个 `shared_ptr` 对象被多线程读写不是；所指对象的并发访问也不是。

### Q5. RAII 是什么，解决什么问题？

资源获取即初始化：把资源（内存、文件、锁、GPU 句柄）的生命周期绑定到对象的生命周期，构造时获取，析构时释放。因为栈展开时会调用局部对象的析构，所以抛异常时资源也能释放，实现异常安全。典型例子：`std::lock_guard`、`unique_ptr`、自己写的作用域守卫（scope guard）。

### Q6. 左值、右值、`std::move`、`std::forward` 的区别？

左值有名字、可取地址；右值是临时值或将亡值。`T&&` 在具体类型下是右值引用；在模板参数推导场景下是转发引用（万能引用）。`std::move` 只是无条件转成右值引用的类型转换，本身不移动任何东西，真正的转移在移动构造/赋值里发生。`std::forward<T>` 按原始值类别有条件转换，用于完美转发。被移动后的对象处于"有效但未指定"状态，只能析构或赋新值。

### Q7. 为什么移动构造要标 `noexcept`？

`std::vector` 扩容需要把旧元素搬到新内存。为保证强异常安全，只有当移动构造不抛异常（`noexcept`）或类型不可拷贝时才会使用移动，否则退回拷贝（`std::move_if_noexcept`）。漏标 `noexcept` 会让容器扩容变成逐元素深拷贝，性能骤降。

### Q8. RVO 和 NRVO 是什么？

返回值优化：直接在调用方的返回槽构造返回值，避免拷贝或移动。C++17 起，返回纯右值（如 `return T{...};`）时强制消除拷贝（guaranteed copy elision），不要求类型可拷贝/移动。返回具名局部变量的 NRVO 仍是允许的优化而非强制，因此类型最好仍然可移动。`return std::move(local);` 反而会阻止 NRVO，应避免。

### Q9. 内存对齐是什么？为什么需要？

每种类型有对齐要求（`alignof`），对象地址必须是它的倍数。需要对齐的原因：部分硬件对未对齐访问会降速或触发异常；原子操作要求自然对齐才能保证原子；SIMD 指令（如 SSE 的 16 字节、AVX 的 32 字节）有对齐要求。结构体按成员最大对齐取整，成员间插入填充。调整手段：成员按大小降序排列、`alignas`、`#pragma pack`、`[[no_unique_address]]`（C++20）。

### Q10. `new`/`delete` 与 `malloc`/`free` 的区别？

`new` 先调用 `operator new` 分配内存，再调用构造函数；失败抛 `std::bad_alloc`（或用 `nothrow`）。`malloc` 只分配原始内存，失败返回 `NULL`，不调用构造。`delete` 先调用析构再 `operator delete`。`new[]` 对有非平凡析构的类型会额外存储元素个数（cookie），所以必须用 `delete[]` 释放，混用是未定义行为。`new` 可以重载，`placement new` 可在已有内存上构造对象，是内存池和 ECS 存储的基础。

### Q11. 栈和堆的区别？

栈：由编译器按函数调用自动管理，分配只是移动栈指针，速度极快，空间有限（MB 级），局部性好；堆：由程序或分配器管理，分配释放有开销，有碎片，大小受内存限制。C++ 中对象可以放栈上（自动存储期）、静态区、堆上，由代码决定；C# 中引用类型对象总是在托管堆上。

### Q12. 常见内存错误有哪些？

内存泄漏、重复释放（double free）、释放后使用（use after free）、悬垂指针/引用、缓冲区溢出、未初始化读取、对象切片、错用 `delete`/`delete[]`、栈上变量的地址逃出作用域。防御：RAII 与智能指针、容器代替裸数组、`std::span`/`string_view` 带边界信息、编译选项（`-fsanitize=address,undefined`）。

## B 档：常追问

### Q13. 怎么排查内存泄漏？

按平台选工具：Linux/macOS 用 Valgrind（`--leak-check=full`）、AddressSanitizer 的 LeakSanitizer；Windows 用 CRT 调试堆（`_CrtDumpMemoryLeaks`）、UMDH、Visual Studio 的诊断工具和堆快照；游戏引擎里用内建的分配跟踪，如 UE 的 `stat memory`、`memreport`、LLM（Low Level Memory Tracker），Unity 的 Memory Profiler 查看原生内存。思路：先确认是持续增长（快照对比），再用调用栈定位分配点，最后找释放路径缺失的原因。自研分配器时在 Debug 构建记录分配点调用栈。

### Q14. `malloc` 内部大致如何工作？

以 glibc 的 ptmalloc 为例：小块从按大小分类的空闲链表（fastbin、smallbin、tcache）取，大块由 `brk` 扩展的堆或 `mmap` 直接映射（默认阈值约 128 KB，动态调整）；释放时合并相邻空闲块，减少碎片；多线程用多个 arena 降低锁争用。tcmalloc 与 jemalloc 使用线程本地缓存和按大小分级的 span，减少锁和碎片。游戏引擎常自定义分配器（线性、栈式、池、伙伴系统），原因是可预测、低碎片、可统计。

### Q15. `const` 的各种含义？

`const int* p`：指向的数据不可改；`int* const p`：指针本身不可改；`const` 成员函数：承诺不修改对象的逻辑状态（`mutable` 成员例外）；`constexpr`：编译期可求值，是比 `const` 更强的承诺（`const` 可以在运行时才初始化）。常量引用参数 `const T&` 避免拷贝并绑定临时对象。

### Q16. `inline` 的真正含义？

`inline` 的主要语义是允许函数在多个翻译单元中有相同定义（放进头文件不违反 ODR），内联展开只是编译器可采纳的建议。实际内联与否由编译器按成本模型决定，与关键字无关；强制内联用 `__forceinline`/`__attribute__((always_inline))`。C# 对应的是 JIT 自行决定，加 `[MethodImpl(MethodImplOptions.AggressiveInlining)]` 是提示。虚函数调用通常无法内联，除非编译器能确定动态类型。

### Q17. 模板的实例化是怎么工作的？

编译器在使用点按具体类型参数生成代码（实例化），每种类型一份，所以没有运行时开销，可以内联，但可能造成代码膨胀；模板定义必须在使用点可见（通常放头文件）。SFINAE 与 C++20 concepts 用于约束可用类型。支持非类型模板参数（如数组长度）、全特化与偏特化。

### Q18. C++ 模板与 C# 泛型的区别？

| 项 | C++ 模板 | C# 泛型 |
|---|---|---|
| 实例化时机 | 编译期 | 运行时由 JIT（或 AOT）实例化 |
| 值类型 | 每种类型一份代码 | 每种值类型一份，引用类型共享一份 |
| 约束 | 鸭子类型，错误在实例化时暴露；concepts 改善 | 显式 `where` 约束，编译时检查 |
| 非类型参数、特化 | 支持 | 不支持 |
| 运算符 | 按类型直接调用 | 需要 `static abstract` 接口成员（C# 11）或泛型数学接口 |
| 运行时类型信息 | 擦除（只在编译期存在） | 保留（reified），`typeof(T)`、反射可用 |
| 代码膨胀 | 明显 | 值类型实例化膨胀，引用类型共享 |

### Q19. 虚函数调用成本主要在哪？

不在多读的一次 vtable 指针，而在无法内联、寄存器保存与恢复、间接跳转的分支预测。预测准确时开销很小，调用目标频繁变化时预测失败，惩罚是十几到几十个周期。优化手段：按具体类型批处理（数据导向设计）、`final` 辅助去虚化、CRTP 静态多态、LTO。

### Q20. 静态初始化顺序问题是什么？

同一翻译单元内全局/静态对象按定义顺序初始化，不同翻译单元之间顺序未指定。如果一个全局对象的构造函数依赖另一个翻译单元的全局对象，可能读到未初始化的值（static initialization order fiasco）。解决：函数内静态局部变量（Meyers 单例，C++11 起初始化线程安全）、`constinit`（C++20）。C# 的静态构造函数由运行时在首次访问前执行，没有跨文件顺序问题，但静态构造互相依赖时可能出现死锁或读到默认值。

### Q21. `std::function` 与 lambda 的开销？C# 委托对比？

lambda 是编译器生成的匿名函数对象类型，调用可以内联。`std::function` 做了类型擦除，调用经间接跳转，捕获数据小于内部缓冲区（SBO，容量依实现）时不分配堆，否则堆分配。C# 的 lambda 若捕获局部变量，会生成闭包类实例（堆分配），并为每次创建分配委托对象；不捕获的 lambda 会被缓存为静态委托，只分配一次。委托调用同样是间接调用，多播委托遍历调用列表。游戏里热路径每帧创建捕获 lambda 是 GC.Alloc 的常见来源。

### Q22. `std::vector` 与 `List<T>` 的扩容？

`vector` 的增长因子由实现决定（libstdc++ 与 libc++ 约 2 倍，MSVC 约 1.5 倍）；`List<T>` 容量不够时翻倍。两者扩容都要搬迁元素：`vector` 遇到非 `noexcept` 移动会拷贝；`List<T>` 内部是 `Array.Copy` 的块拷贝（引用类型只拷指针）。`vector` 扩容使迭代器、指针、引用全部失效；`List<T>` 的 enumerator 在修改后会抛异常（版本号检查）。已知元素数量时都应预留容量（`reserve`/`Capacity`）。

### Q23. `unordered_map` 与 `Dictionary` 的实现差异？

`std::unordered_map`（主流实现）是节点式链地址法：每个元素单独分配节点，桶数组存节点指针，扩容后元素指针与引用仍有效、迭代器可能失效。`Dictionary<TKey,TValue>` 把所有条目放在一个连续的 `entries` 数组中，用 `buckets` 数组保存链头下标，`next` 字段用下标链接，对缓存更友好、分配次数少，但扩容会搬迁整个条目数组。游戏里热点查询可以考虑开放寻址或 flat hash map（如 absl、robin_hood 等第三方实现）。

## C 档：区分度题

### Q24. C++ 异常与 C# 异常的实现与成本？

C++ 主流实现是表驱动的"零成本"模型：不抛异常时几乎没有运行时开销，抛出时查展开表，成本高（微秒级）。游戏引擎常禁用异常（`-fno-exceptions`），用返回码或 `Result` 类型。C# 异常在抛出时需要捕获栈跟踪并做两遍展开（查找处理器、再执行 finally），成本同样高，一般为数十微秒量级，.NET 9 起新的托管展开实现显著改善（待核实具体倍数）。Unity IL2CPP 下异常也带来额外代码体积，不要用异常做正常控制流。

### Q25. `dynamic_cast` 与 C# 的 `as`/`is` 有什么相同和不同？

都做运行时类型检查。`dynamic_cast` 依赖 RTTI（vtable 中的类型信息），指针转换失败返回空，引用转换失败抛 `bad_cast`，需要多态类型；游戏引擎常关闭 RTTI 并自建类型 ID。C# 的类型检查比较对象的 MethodTable，`as` 失败返回 null，强转失败抛 `InvalidCastException`，类型信息始终可用。

### Q26. Rule of 0/3/5 是什么？

规则 3：自定义了析构、拷贝构造、拷贝赋值之一，通常需要三者都自定义。规则 5：再加移动构造与移动赋值。规则 0：优先让成员用 RAII 类型（容器、智能指针）管理资源，类自身不写这些特殊成员，让编译器生成。C# 对应的问题少，主要是 `Dispose` 与 `Clone` 的语义管理。

### Q27. 对象切片是什么？

把派生类对象按值赋给基类对象，派生部分被截掉，虚函数行为也随之丢失：`Base b = derived;`。避免方法：多态类型通过指针/引用传递，把基类拷贝操作设为 `delete`。C# 没有这个问题，因为 class 的赋值传递的是引用。

### Q28. C++ `volatile` 与 C# `volatile` 有什么区别？

C++ 的 `volatile` 告诉编译器每次访问都要真实读写，不能优化掉，用于内存映射寄存器等场景，不提供线程间同步，也不保证原子。C# 的 `volatile` 字段访问带 acquire/release 语义，具有线程间排序的作用，但仍不保证复合操作的原子性（见 5.3 节）。多线程同步在 C++ 里应使用 `std::atomic`。

### Q29. 互操作时的 ABI 问题有哪些？

名字修饰：C++ 函数名会被修饰，导出给 C# 调用要用 `extern "C"`；调用约定：x64 下 Windows 只有一种，x86 下有 `cdecl`/`stdcall` 之分，`DllImport` 需要匹配；结构体布局必须逐字段一致（对齐、`bool`/`char` 宽度）；C++ 对象不能直接跨边界传递，需要通过 C 接口加不透明句柄；内存所有权要约定清楚，谁分配谁释放，别让 C# 去 `free` C++ 的 `new` 出来的内存。

### Q30. UE 里的 `UObject`、`TSharedPtr`、裸指针怎么共存？

`UObject` 派生对象由 UE 的 GC 管理，`UPROPERTY` 标注的成员才被 GC 追踪；非 UObject 的 C++ 对象用 `TSharedPtr`/`TUniquePtr` 或手动管理；`TWeakObjectPtr` 用来持有不影响 GC 的弱引用，访问前判断有效性。把 `UObject*` 放进普通 STL 容器或没有 `UPROPERTY` 的成员里，GC 看不到，对象会被回收并留下悬垂指针（见 5.2 节）。
