> 适用版本：C++17、Itanium C++ ABI（GCC/Clang）与 MSVC x64 ABI；.NET 8/9 的 CoreCLR 作为 CLR 参照；Unity 的 Mono 与 IL2CPP 单独标注。汇编片段是示意，具体指令随编译器、JIT 版本变化。无法确认的实现细节标"待核实"。

## 要点

- C++ 的非多态对象没有任何隐藏数据，`sizeof` 就是字段加对齐填充；有虚函数时在对象头部多一个 vptr，指向按类共享的 vtable。
- CLR 的引用类型对象固定带两个机器字的开销：对象头（同步块索引、锁位、哈希码）和 MethodTable 指针。64 位下空对象是 24 字节。Mono 与 IL2CPP 的头部布局不同：`klass` 指针与 `monitor` 指针都在对象指针之后，共 16 字节。
- 值类型本身不带头部，装箱后才有头部和 MethodTable 指针。
- 虚调用的成本主要来自间接跳转无法内联，以及分支预测失败，而不是多读的那一两次内存。
- 接口调用在 CoreCLR 里走 Virtual Stub Dispatch，单态时接近虚调用，多态时更慢。IL2CPP 的接口调用需要在 `interfaceOffsets` 里查找，细节见正文。
- `sealed`、`new` 出来的精确类型、`where T : struct` 的泛型实例化，都能让 JIT 把虚调用变成直接调用甚至内联。这与 C++ 的 `final`、LTO、模板单态化是同一类优化。
- 做 Native Plugin 或 Burst 互操作时，要让 C# struct 和 C++ struct 的 `sizeof`、`offsetof` 逐字段一致，`bool`、`char` 是最常见的错位来源。

## 对象布局

### C++：布局是 ABI 决定的

Itanium ABI（Linux、macOS、Android、主机平台的 Clang 工具链多数沿用）和 MSVC ABI 在细节上不同，共同点是：

- 非静态数据成员按声明顺序排列，每个成员按自身对齐要求补齐，整个类型的对齐是成员对齐的最大值，`sizeof` 向对齐值取整。
- 有虚函数的类，vptr 通常位于偏移 0。vptr 指向的 vtable 每个类一份，同一类的所有对象共享。
- Itanium vtable 在函数指针之前还有 offset-to-top 和 RTTI 指针，`dynamic_cast` 与 `typeid` 靠这里工作。MSVC 把 RTTI 信息放在 `vtable[-1]` 指向的 Complete Object Locator 里。

```cpp
struct A { virtual void f(); int a; };
struct B { virtual void g(); int b; };
struct C : A, B { int c; };

// Itanium x64：sizeof(A)=16, sizeof(B)=16
// C 内部 A 子对象在偏移 0（与 C 共用 vptr），B 子对象在偏移 16，有自己的 vptr
// 本文按 ABI 规则推导出 Itanium 下 sizeof(C)=32（复用 A 的尾部填充存放不了 B，但 c 落在 B 之后）
// MSVC 不复用基类尾部填充，推导为 40。以 static_assert 实测为准。
static_assert(sizeof(A) == 16);
static_assert(offsetof(C, c) > 16);   // offsetof 对非标准布局类型是条件支持，GCC/Clang 会警告
```

多重继承带来两个后果。第一，`C*` 转成 `B*` 时指针值要加偏移，这是编译器在转换处生成的 this 调整。第二，通过 `B*` 调用在 `C` 里被覆盖的虚函数，vtable 里放的是 thunk：先把 `this` 减回 `C` 的起点再跳转到真正的函数。虚继承还要额外的 vbptr 或 vtable 内的 vbase offset，访问虚基类成员多一次间接寻址。

这是游戏代码里"组件继承层级别太深、别多重继承"的底层原因：每个多态子对象多 8 字节，调用多一层调整。

### CoreCLR：对象头加 MethodTable

64 位 CoreCLR 的托管对象内存布局：

```
obj - 8 : 对象头（ObjHeader）：同步块索引 / thin lock / 哈希码，以及 GC 标志位
obj + 0 : MethodTable*            <- 引用指向这里
obj + 8 : 第一个字段 ...
```

要点：

- 引用指向 MethodTable 指针而不是头部，所以对象头是在引用"前面"的。
- 最小对象大小是 3 个指针宽（24 字节）。`new object()` 占 24 字节，原因是 GC 回收后要能把这块空间改写为 free object，需要容纳 MethodTable、长度字段等。一个 `int` 字段的 class 也是 24 字节：8 头 + 8 MT + 4 数据 + 4 填充。
- 数组在 MethodTable 指针后多一个长度字段（`int`，64 位下后面补 4 字节对齐）。
- `string` 是变长对象：8 头 + 8 MT + 4 长度 + 2×(n+1) 的 UTF-16 数据（含结尾 `\0`），再向 8 对齐。`"abc"` 占 32 字节。
- 引用类型字段默认由 CLR 自动重排：先放引用（便于 GC 扫描），再按大小降序放基本类型，把填充压到最小。`LayoutKind.Auto` 是 class 的默认值，Sequential 只对 struct 默认。含引用字段的 struct 实际上也被运行时按 Auto 处理，不能依赖声明顺序。

MethodTable 包含：基类型大小（`BaseSize`）、组件大小（数组或字符串元素）、标志位、虚方法槽数组、接口映射表、指向 `EEClass` 的指针（冷数据，如字段描述、布局信息）。可以把 MethodTable 理解成 C++ 的 vtable 加上 `type_info` 再加一部分 RTTI 的并集，但它是运行时由类型加载器构造的，而不是编译期常量。

### Mono 与 IL2CPP

Unity 两条后端的对象头不同于 CoreCLR：

```
obj + 0  : klass / vtable 指针
obj + 8  : monitor 指针（同步用，惰性创建）
obj + 16 : 第一个字段
```

即 64 位下头部是 16 字节，空对象 16 字节。数组在头部之后有 `bounds` 指针和 `max_length`（指针宽），元素从偏移 32 左右开始（待核实各版本）。IL2CPP 的 `Il2CppObject` 对应 `{ Il2CppClass* klass; MonitorData* monitor; }`。这意味着在 Unity 里统计"一个小对象有多大"，不能直接套用 .NET 文章里的 24 字节。

### 值类型没有头

`struct` 的实例就是字段的紧凑排列。放在局部变量里是栈或寄存器，放在 class 字段里内联在对象内部，放在数组里是连续元素。装箱时才在堆上建一个带头部和 MethodTable 指针的对象，把字段拷进去。所以 C++ 里 `std::vector<Vec3>` 与 C# 的 `Vec3[]` 同构，都是连续数组；`std::vector<std::unique_ptr<Foo>>` 与 C# 的 `Foo[]`（`Foo` 是 class）同构，都是指针数组加分散的堆对象。

## 虚调用的机器码

C++ 单继承虚调用：

```asm
mov rax, [rdi]         ; 取 vptr
call [rax + 16]        ; 调 vtable 第 N 个槽（槽位在编译期固定）
```

CoreCLR 类虚方法调用（x64 示意）：

```asm
mov rax, [rcx]         ; 取 MethodTable*
mov rax, [rax + 0x40]  ; 取 vtable chunk（具体偏移随 MethodTable 版本而异）
call [rax + 0x10]      ; 调槽位
```

CoreCLR 的 vtable 以 chunk 为单位存放（为了共享父类 chunk 节省内存），通常比 C++ 多一次取址。多一次 L1 命中的 load 只有几个周期，真正的代价是编译器无法越过调用点做优化：不能内联，寄存器要按调用约定保存，返回值要经过 ABI。

## 接口调用

C++ 没有接口分派问题，纯虚基类加多重继承就是接口，每个接口基类子对象自带 vptr。

C# 一个类可以实现任意多个接口，而接口方法在类的 vtable 里没有固定槽位（槽位随实现类不同而不同），所以运行时需要额外查找。

CoreCLR 使用 Virtual Stub Dispatch（VSD），调用点指向一个间接单元，经过三种 stub 演进：

1. lookup stub：第一次调用，进入运行时解析目标，同时生成 dispatch stub。
2. dispatch stub：单态缓存，比较对象的 MethodTable 与上次的是否相同，相同则直接跳转目标，不同则落到 resolve stub。
3. resolve stub：多态路径，用 (MethodTable, 接口槽) 做哈希查缓存表，缓存未命中再回运行时。

所以同一调用点总是同一个具体类型时，接口调用接近虚调用；调用点遇到很多种类型（如 `IUpdatable[]` 里混着十几种实现），就退化为哈希查表。.NET 8 起默认开启 Dynamic PGO，JIT 可以在热点调用点插入 guarded devirtualization：先比较 MethodTable 是否等于最常见类型，命中则直接调用（并可内联），否则回落到普通接口调用。

Mono 把接口方法编进 IMT（Interface Method Table）槽，冲突时走 thunk 链。IL2CPP 生成的 C++ 通过 `InterfaceFuncInvoker` 之类的模板做调用，大致流程是在 `klass->interfaceOffsets` 里找到接口对应的 vtable 偏移，再按槽位取方法指针（待核实当前版本的具体实现）。泛型虚方法和泛型接口方法在 IL2CPP 上更慢，因为需要在运行时按实例化类型查表。游戏里高频更新循环（`Update` 式的每帧遍历）如果走接口，建议在数据结构上按具体类型分桶，把热循环改成直接调用。

## 去虚化

| 条件 | C++ | CoreCLR JIT |
|---|---|---|
| 类型标记不可继承 | `final` 类或 `final` 方法 | `sealed` 类或 `sealed override` 方法 |
| 局部精确类型已知 | 栈对象、`new` 后立即调用，编译器可直接去虚化 | `new Foo().Bar()` 这类精确类型，JIT 可直接调用 |
| 全程序已知 | LTO、`-fwhole-program-vtables` | 不适用，但 Tiered PGO 可按运行时观察猜测并守卫 |
| 泛型 | 模板每类型实例化，天然静态分派 | `where T : struct, IFoo` 对每个值类型实例化独立代码，可完全去虚化并内联；引用类型实例化共享一份代码，仍是虚调用 |

把接口约束到值类型泛型参数上，是 C# 里最接近 C++ 模板静态多态的写法：

```csharp
interface IOp { int Apply(int x); }
struct Add1 : IOp { public int Apply(int x) => x + 1; }

static int Run<T>(T op, int[] data) where T : struct, IOp
{
    int s = 0;
    foreach (var v in data) s += op.Apply(v);   // 每个 T 单独编译，Apply 可以内联
    return s;
}
```

Mono JIT 对此的优化弱于 CoreCLR，IL2CPP 把泛型值类型实例化生成成独立的 C++ 函数，clang 在此基础上能内联，但 IL2CPP 自己的 Il2CppClass 初始化检查和空引用检查会留在函数内（待核实具体生成代码）。

## 值语义与引用语义

C++ 默认值语义：`Foo a = b;` 拷贝整个对象，要共享就显式用指针或引用。C# 的 class 默认引用语义：赋值只拷贝一个指针，别名关系是隐式的。这带来几个系统性差异：

- C++ 对象可以在栈上、静态区、堆上，生命周期由作用域或所有者决定；C# 的 class 实例一律在托管堆上（CoreCLR 在 .NET 9/10 对不逃逸的对象开始做有限的栈分配，Unity 的 Mono 与 IL2CPP 没有这个优化，待核实）。
- C++ 的 `const T&` 参数承诺不修改；C# 的 `in` 参数和 `readonly struct` 是对应物，但对 class 参数没有等价的"只读视图"。
- C++ 的"对象切片"在 C# 里不存在，因为 class 赋值不拷贝对象。
- 在 C# 里把大 struct 当参数传递，会产生栈拷贝（或经隐藏指针传递），应使用 `in`，且 struct 要标 `readonly`，避免触发防御性拷贝。

## sizeof、padding 与互操作

```cpp
struct S1 { char a; int b; char c; };    // sizeof == 12，a 后 3 字节填充，c 后 3 字节尾部填充
struct S2 { int b; char a; char c; };    // sizeof == 8
```

```csharp
[StructLayout(LayoutKind.Sequential)]
struct S1 { public byte a; public int b; public byte c; }   // Unsafe.SizeOf<S1>() == 12
```

对齐规则与 C++ 一致，所以这两个定义可以直接互相映射。需要注意：

- 使用 `Unsafe.SizeOf<T>()` 取 CLR 的内存大小，`Marshal.SizeOf<T>()` 取封送后的非托管大小，二者对非 blittable 类型不一定相等。
- C# `bool` 在托管内存里是 1 字节，但 P/Invoke 默认按 4 字节 `BOOL` 封送；`char` 是 2 字节 UTF-16，而 C++ `char` 是 1 字节。想要与 C++ 结构体按位一致，用 `byte` 与 `ushort`/`char16_t`，或加 `[MarshalAs]`。
- `LayoutKind.Explicit` 加 `FieldOffset` 可模拟 C++ `union`；两个字段重叠时，其中包含引用类型字段会被运行时拒绝。
- `#pragma pack(n)` 对应 `[StructLayout(LayoutKind.Sequential, Pack = n)]`；`alignas(64)` 没有直接对应物，只能用 `Size = 64` 或显式填充字段近似。
- 空类型：C++ 的空类 `sizeof == 1`，EBO（空基类优化）可使其作基类时不占空间；C# 空 struct 的大小也是 1。
- 面向 Burst 和 Job 的数据，要用 blittable 的 `struct`（只含基本类型和其他 blittable struct，Burst 对 `bool` 做了特殊处理），这样才能放进 `NativeArray`，并与 C++ 端按位共享。

## 常见坑

- 以为 C# `class` 的字段顺序等于声明顺序。引用类型默认 Auto 布局，不能用指针偏移硬算字段位置，要用 `[FieldOffset]` 或 `Unsafe.As`。
- 估算内存占用时忘记对象头，大量小对象（例如每个 8 字节数据一个 class）实际占用是数据的 3 倍。
- 把接口当作无成本抽象放进每帧热循环，且调用点是多态的，会落到哈希查表路径。
- 与 C++ 共享结构体时没对齐 `bool`/`char`，只在发布包出现崩溃或脏数据。
- 认为 C++ 的 `final` 一定去虚化。只有编译器能证明动态类型时才行，调用经过基类指针且没有 LTO 时，`final` 方法可以去虚化，`final` 类也可以，但只是"可以"，需要看汇编确认。

## 面试追问

1. C++ 里为什么构造函数中调用虚函数不会多态？回答要点：构造到某一层时 vptr 指向当前正在构造的那一层的 vtable，派生部分还没有构造；析构同理。
2. C# 对象为什么最小是 24 字节？要点：对象头 8 加 MethodTable 8，再保证至少能放下 GC 回收时的 free object 结构，等价于 3 个指针宽。
3. 多重继承如何影响指针值？要点：基类子对象偏移不为 0 时，派生类指针转换要加偏移，虚函数经由 thunk 调整 this。
4. C# 接口调用为什么比虚调用慢？要点：接口方法没有固定的 vtable 槽，需要经过 VSD 的 stub；单态缓存命中时差距小，多态调用点退化为哈希查表。
5. 怎样在 C# 里获得类似模板的静态分派？要点：泛型加 `where T : struct, I...`，让 JIT 对每个值类型实例化独立代码，从而去虚化与内联。
6. struct 与 class 在 Unity 的 IL2CPP 下最大的内存差异？要点：class 有 16 字节头，struct 没有；数组里 struct 连续存放，class 数组是指针数组。
