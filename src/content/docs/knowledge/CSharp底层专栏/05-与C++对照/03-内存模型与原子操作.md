> 适用版本：C++17/20 的 `std::atomic`；.NET 8/9 的 CoreCLR 内存模型（以 dotnet/runtime 仓库的 Memory-model 文档为准）；Unity Mono、IL2CPP 的行为单独标注，细节标"待核实"。

## 要点

- C++ 的数据竞争是未定义行为，同步靠 `std::atomic` 与 `memory_order`；默认 `seq_cst` 最强，`acquire/release` 是常用的低成本组合，`relaxed` 只保证原子性。
- .NET 运行时实际遵循的内存模型比 ECMA-335 强：普通读写可被重排，但 `Volatile.Read` 是 acquire，`Volatile.Write` 是 release，`Interlocked` 与 `Thread.MemoryBarrier` 是全屏障；对象引用的发布（赋值给共享位置）带 release 语义；有数据依赖的读不会被重排。
- C# 的 `volatile` 关键字只是让编译器给读写加上 `volatile.` 前缀，语义是 acquire 读 / release 写，不是 `seq_cst`，不能阻止"写后读"的重排，Dekker/Peterson 类算法仍然需要 `Interlocked` 或 `Thread.MemoryBarrier`。
- x86 是 TSO，只有"写后读"会被硬件重排；ARM 是弱序，读写之间多种组合都可能重排。很多只在手机上出现的并发 bug，源头在此。
- false sharing：两个线程各自写同一缓存行里的不同变量，缓存行在核间反复失效。解决方法是填充或对齐到缓存行，64 字节在 x86 上通用，Apple 芯片的缓存行更大（128 字节，待核实各型号）。
- `lock` 编译为 `Monitor.Enter/Exit`。CoreCLR 把 thin lock（线程 ID 与递归计数）放在对象头里，竞争时膨胀为同步块；哈希码也共用对象头，二者会互相影响。
- Unity 的 Job 安全系统靠调度时的读写依赖，避免两个 Job 同时写同一块 Native 内存，所以 Job 里一般不需要手写 memory_order，但并行写入、归约、自旋等场景仍然需要原子操作。

## C++ 的 memory_order

| 序 | 含义 | 典型用途 |
|---|---|---|
| `relaxed` | 只保证该原子变量自身的原子性与修改顺序 | 统计计数器 |
| `acquire`（读） | 之后的读写不能提前到它之前 | 获取锁、读取"就绪"标志 |
| `release`（写） | 之前的读写不能延后到它之后 | 释放锁、发布数据后置标志 |
| `acq_rel` | 读改写操作同时具备二者 | `fetch_add` 引用计数递减的末次判断 |
| `seq_cst` | 全局统一的总顺序 | 默认；需要多个原子变量之间的全序时 |

```cpp
std::atomic<bool> ready{false};
int data = 0;

// 生产者
data = 42;
ready.store(true, std::memory_order_release);

// 消费者
while (!ready.load(std::memory_order_acquire)) {}
assert(data == 42);       // release/acquire 配对建立 happens-before
```

`consume` 在标准里存在，但主流编译器把它按 `acquire` 实现，实践中不建议使用。

`seq_cst` 在 x86 上，读是普通 `mov`，写是 `xchg` 或 `mov + mfence`，代价在写。在 ARM64 上读写分别是 `ldar`/`stlr`，通常比 x86 的全屏障便宜。

## .NET 的内存模型

dotnet/runtime 仓库的 Memory-model 文档给出了运行时实际保证的规则，对比表：

| 操作 | .NET 的语义 | 对应 C++ |
|---|---|---|
| 普通读写 | 可重排，只保证单线程一致性；对齐的、不超过指针宽度的基本类型读写是原子的 | 非原子变量（竞争即 UB），但 .NET 中不是 UB |
| `Volatile.Read` / `volatile` 字段读 | acquire | `load(acquire)` |
| `Volatile.Write` / `volatile` 字段写 | release | `store(release)` |
| `Interlocked.*` | 全屏障 | `seq_cst` 的读改写 |
| `Thread.MemoryBarrier` | 全屏障 | `atomic_thread_fence(seq_cst)` |
| `Monitor.Enter` / `Exit` | 获取为 acquire，释放为 release | `mutex::lock/unlock` |
| 共享位置的引用赋值 | 相对于对象字段与元数据的写，是 release | 无直接对应 |
| 数据依赖读 | 保证有序 | 近似 `consume`，实际由硬件与 JIT 保证 |

几个重要结论：

1. 没有数据竞争未定义行为的说法。在 .NET 里，竞争读写只会读到某个写入过的值（对齐的小于等于指针宽度的类型），不会出现撕裂，不会让编译器随意推断。文档还规定编译器不能引入推测写、不能凭空新增读，但可以合并相邻的相同位置的普通读（所以"自旋等待普通字段"会被优化成死循环，必须用 `Volatile.Read`）。
2. 引用赋值带 release：先构造对象再把引用写到共享字段，其他线程读到非空引用后，能看到构造完成的字段值，无需显式屏障。这是 .NET 能让"无锁单例"和对象发布写得比 C++ 简单的原因。但文档同时说明，不要把它当通用的排序手段，编译器若证明对象没有共享，可以省掉这个 release。
3. 64 位以内的 `Volatile.Read<double>` 在 32 位平台才有意义：此时普通读写 `double` 可能撕裂，`Volatile` 与 `Interlocked` 保证原子。
4. 构造函数没有排序保证，静态构造函数的副作用在访问类型成员前可见。

C# 的 `volatile` 关键字的实现：运行时不识别它，C# 编译器对该字段的读写加 `volatile.` IL 前缀，JIT 据此生成 acquire/release 读写。常见误解是认为 `volatile` 等价于 Java 的 `volatile`（顺序一致）。写后读重排对 C# `volatile` 依然存在：

```csharp
// Dekker 风格：两个线程各自先写自己的标志再读对方的标志
volatile int a, b;
// 线程 1: a = 1; if (b == 0) { /* 进入临界区 */ }
// 线程 2: b = 1; if (a == 0) { /* 进入临界区 */ }
// 因为 volatile 写后跟 volatile 读允许被重排（store-load），两个线程可能同时进入。
// 需要在写和读之间加 Thread.MemoryBarrier()，或改用 Interlocked.Exchange 写。
```

## x86 与 ARM

| 重排类型 | x86（TSO） | ARM64 |
|---|---|---|
| 读-读 | 不重排 | 可能 |
| 读-写 | 不重排 | 可能 |
| 写-写 | 不重排 | 可能 |
| 写-读 | 可能（store buffer） | 可能 |

含义：

- 在 x86 上漏写 acquire/release 往往不会出问题，在 ARM（几乎所有手机、Apple 芯片、部分服务器）上才暴露。在编辑器（常为 x86 或 Apple Silicon）通过的并发逻辑，到 Android 真机上出错，常见原因是这个。
- .NET JIT 在 ARM64 上把 `Volatile.Read` 编译为 `ldar` 类带 acquire 的加载指令，在 x86 上编译为普通 `mov`。
- Unity 的 IL2CPP 把 C# 翻译为 C++，再由平台 C++ 编译器编译。C# 里的 `volatile` 字段访问会被翻译成相应的内存屏障加访问，不会变成 C++ 的 `volatile`（待核实各版本生成代码）。Mono 后端同样由 JIT 对 `volatile.` 前缀生成屏障。

## false sharing

```cpp
struct Counters {
    alignas(64) std::atomic<int> a;     // 各占一条缓存行
    alignas(64) std::atomic<int> b;
};
// C++17 可用 std::hardware_destructive_interference_size 取值，但它是实现定义常量，GCC 会提示 ABI 警告
```

```csharp
[StructLayout(LayoutKind.Explicit, Size = 128)]
struct PaddedInt
{
    [FieldOffset(64)] public int Value;     // 两侧各留 64 字节，避免与相邻对象同行
}
```

C# 里对象的对齐保证只有 8 字节，无法像 C++ 那样 `alignas(64)`，所以通常在数据两侧都留填充。.NET 自己的并发集合（如 `ConcurrentQueue` 的头尾索引）也采用这种填充。检测手段：性能计数器看缓存行失效、`perf c2c`（Linux）、VTune 的内存访问分析。

Unity 中最常见的 false sharing 场景是多个 Job Worker 并行往同一个 `NativeArray<int>` 的相邻元素累加计数。正确做法是每个线程使用独立的局部累加器（`[NativeSetThreadIndex]`），最后合并，或每个线程的槽位之间填充到缓存行。

## 锁与对象头

CoreCLR 的 `lock(obj)` 编译为 `Monitor.Enter(obj, ref taken)` 与 `finally { Monitor.Exit(obj); }`。对象头中同一个字承载几种互斥的状态：

- 空：无锁、无哈希码；
- thin lock：头部内嵌拥有者线程 ID 与递归计数，加锁用一次 CAS 完成，没有竞争时不分配额外结构；
- 哈希码：调用 `RuntimeHelpers.GetHashCode`/默认 `GetHashCode` 后，哈希码存入对象头；
- 同步块索引：出现竞争、`Wait/Pulse`、或同时需要锁和哈希码无法共存时，膨胀为同步块（`SyncBlock`），头部存其在同步块表中的索引。

因此：

- 对 `this`、`typeof(T)`、字符串或其他公开可访问的对象加锁是坏做法，外部代码也能锁同一对象，造成死锁或不必要膨胀。用私有的 `object` 字段或 .NET 9 的 `System.Threading.Lock` 类型（C# 13 的 `lock` 语句会识别它）。
- 对值类型加锁会装箱，每次锁的对象都不同，等于没锁。

Mono 在 `MonoObject` 的 `synchronisation` 字段中使用类似的 thin lock 设计，竞争时分配 `MonoThreadsSync`。IL2CPP 的 `Il2CppObject.monitor` 指向惰性创建的监视器数据，没有 CoreCLR 那样把哈希码和 thin lock 塞在同一个头的设计（待核实）。

## Unity Job 安全系统与内存序

Unity 的 Job 系统不要求开发者手写内存序，因为：

- 调度 Job 时，`JobHandle` 依赖决定先后；`Complete()` 之后主线程读取结果，前后由调度器与线程同步原语建立 happens-before。
- `NativeContainer` 的 `AtomicSafetyHandle` 在编辑器和开发构建中检查：同一容器同一时间只允许一个写 Job，或多个只读 Job，违反时抛异常。这是静态避免数据竞争的方法，不是内存序机制。
- 发布构建默认去掉这些检查，竞争会静默发生。

需要手写原子操作的典型场景：

- 并行写入同一容器（`NativeParallelHashMap.ParallelWriter`、`NativeList.ParallelWriter` 内部使用原子计数）；
- 用 `[NativeDisableParallelForRestriction]` 关掉检查后自己保证分区不重叠；
- 自己实现的归约或工作窃取。

Burst 支持 `System.Threading.Interlocked` 与 `Volatile` 的常见方法（待核实具体支持列表）。Burst 编译器基于 LLVM，遵守 LLVM 内存模型；在没有显式原子操作时，它可以像 C++ 编译器一样重排、合并普通读写，所以自旋等待普通字段在 Burst 里同样会被优化掉，要用 `Volatile.Read` 或 `Interlocked`。

## 常见坑

- 以为 `volatile` 等于 `seq_cst`。它只是 acquire/release，写后读仍会重排。
- 用普通 `bool` 字段做线程停止标志，循环被 JIT 提升为死循环。改用 `Volatile.Read` 或 `volatile`。
- 双检锁不加 `volatile`。在 .NET 的实际模型下，引用赋值带 release，读到非空引用就能看到构造完成的字段，但依赖该细节不如显式写 `Volatile` 清晰，Mono、IL2CPP 的行为未必与 CoreCLR 完全一致（待核实）。
- 在 x86 编辑器里验证无锁代码，直接发 ARM 手机。
- 用 `lock` 保护 struct 或字符串。
- Job 中多个线程写相邻元素，没有数据竞争但性能很差，原因是 false sharing。

## 面试追问

1. C# `volatile` 与 C++ `volatile` 有什么区别？要点：C++ `volatile` 只阻止编译器优化，不提供线程间同步语义；C# `volatile` 生成 acquire/release 访问，有线程间排序语义。
2. `Interlocked.CompareExchange` 的内存序？要点：全屏障，等价于 `seq_cst` 的读改写。
3. 为什么 ARM 上并发 bug 更多？要点：弱内存序允许读读、读写、写写重排，x86 只允许写读重排。
4. 如何证明 release/acquire 配对足够？要点：生产者先写数据后 release 写标志，消费者 acquire 读到标志，则数据写入 happens-before 消费者读数据。
5. false sharing 是怎么发现的？要点：多线程性能不随核数扩展，计数器显示大量缓存行失效；`perf c2c`、VTune；用填充或线程局部累加解决。
6. `lock` 的实现细节？要点：Monitor，对象头 thin lock，竞争时膨胀为同步块；不要锁公开对象。
