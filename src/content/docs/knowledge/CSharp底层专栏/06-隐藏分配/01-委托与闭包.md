> 适用版本:编译器行为以 Roslyn 为准;Unity 6000.x 使用 Roslyn,语言版本 C# 9.0(Unity 6000.2 手册),因此 C# 10/11 才加入的编译器优化(如方法组转换缓存)在 Unity 中不可用。委托对象大小以 CoreCLR 64 位为例,Mono/IL2CPP 的对象头与字段布局不同,待核实。

## 要点

- lambda 是否分配,取决于它捕获了什么:不捕获时编译器把它缓存在静态字段里,只在第一次创建一次委托;捕获局部变量或参数时,编译器生成闭包类(display class)并堆分配,每次计算 lambda 表达式还会新建一个委托对象。
- 闭包类在"被捕获变量的作用域入口"分配,而不是在 lambda 创建处。把捕获 lambda 写在方法中靠后的分支里,仍可能在方法一进来就分配闭包。
- 只捕获 `this` 的 lambda 不产生闭包类(编译为实例方法),但每次评估仍然新建委托。
- 方法组转换(`Foo(MyMethod)`)在 C# 11 之前每次评估都 `new` 一个委托;C# 11 起编译器对静态方法组缓存(版本归属待核实)。Unity 的 C# 9.0 下每次都分配。
- 本地函数不转成委托时不分配:捕获变量通过按引用传递的 struct 闭包传入。一旦转成委托,就退化为和 lambda 相同的分配行为。
- 多播委托(`+=`)每次组合都分配新的委托对象和调用列表数组,事件订阅在循环中频繁增删会产生持续分配;订阅者被发布者的委托引用,是最常见的托管泄漏来源。

## 委托对象本体

`Delegate` 与 `MulticastDelegate` 的实例字段(CoreCLR,示意):

| 字段 | 含义 |
|---|---|
| `_target` | 被调用实例;静态方法为委托自身(用于 shuffle thunk)或 null |
| `_methodBase` | 方法元数据缓存(反射用) |
| `_methodPtr` | 要跳转的函数入口 |
| `_methodPtrAux` | 辅助入口,用于静态方法的开放委托或虚委托 |
| `_invocationList` | 多播时的委托数组;单播为 null |
| `_invocationCount` | 多播时的计数 |

64 位 CoreCLR 上,对象头加方法表指针 16 字节,加上 6 个 8 字节字段共 64 字节。一个 `new Action(...)` 的代价就是 64 字节的堆分配加一次构造。Mono 与 IL2CPP 的 `Delegate` 在 Unity 类库中字段略有不同,精确大小待核实。

单播委托的调用 = 间接调用 `_methodPtr`,把 `_target` 作为第一个参数。绑定实例方法的委托(闭合委托)调用最快;绑定静态方法的委托(开放委托)在 CoreCLR 上要经过一次 shuffle thunk 调整参数,多一次跳转,所以"静态方法委托反而更慢"并不罕见。委托调用通常无法内联,开启 Dynamic PGO 后 CoreCLR 可对热点委托做 guarded devirtualization(见 2.1 节),Mono 与 IL2CPP 没有。

## 闭包类的生成

```csharp
int Sum(List<int> xs, int bias)
{
    int total = 0;
    xs.ForEach(x => total += x + bias);     // 捕获 total 与 bias
    return total;
}
```

编译器生成(示意,名字为编译器实际命名格式):

```csharp
[CompilerGenerated]
private sealed class <>c__DisplayClass0_0
{
    public int total;
    public int bias;
    internal void <Sum>b__0(int x) { total += x + bias; }
}

int Sum(List<int> xs, int bias)
{
    var closure = new <>c__DisplayClass0_0();   // 方法入口就分配
    closure.bias = bias;                         // 参数被提升成闭包字段
    closure.total = 0;
    xs.ForEach(new Action<int>(closure.<Sum>b__0));   // 再分配一个委托
    return closure.total;
}
```

两点值得记:

1. 被捕获的局部变量和参数,从此**住在闭包类的字段里**,方法自己对 `total`、`bias` 的读写也是访问堆字段,而不是寄存器。这会影响 JIT 优化,所以热路径里即使不分配,也尽量避免依赖被捕获变量。
2. 一次调用分配两个对象:闭包类实例和委托实例。

### 闭包在哪里分配

闭包类的实例在**被捕获变量声明所在的作用域入口**创建。

```csharp
void Handle(Foo foo, bool needCallback)
{
    if (!needCallback) return;                 // 即使这里返回,闭包也已经 new 出来了(参数 foo 的作用域是整个方法)
    Schedule(() => foo.Run());
}
```

当 lambda 捕获的是方法参数,闭包在方法入口就创建。若想让"不需要回调时零分配",把带捕获的部分挪到独立的方法或更小的作用域里:

```csharp
void Handle(Foo foo, bool needCallback)
{
    if (!needCallback) return;
    ScheduleCore(foo);                          // 闭包在 ScheduleCore 的入口分配,只在需要时发生
}
void ScheduleCore(Foo foo) => Schedule(() => foo.Run());
```

循环里的变量:`for` 的循环变量在整个循环里共用一个槽,捕获它的所有 lambda 看到同一个变量(经典坑);`foreach` 的迭代变量(C# 5 起)每次迭代是新变量,于是每次迭代分配一个新闭包类实例。

### 不捕获:静态缓存

```csharp
list.Sort((a, b) => a.CompareTo(b));           // 不捕获
```

生成(示意):

```csharp
[Serializable] [CompilerGenerated]
private sealed class <>c
{
    public static readonly <>c <>9 = new <>c();
    public static Comparison<int> <>9__0_0;     // 缓存的委托
    internal int <M>b__0_0(int a, int b) => a.CompareTo(b);
}

list.Sort(<>c.<>9__0_0 ?? (<>c.<>9__0_0 = new Comparison<int>(<>c.<>9.<M>b__0_0)));
```

第一次执行时 new 一个委托并缓存到静态字段,之后每次都复用,零分配。C# 9 引入 `static` 匿名函数:`static x => x + 1` 声明不允许捕获,编译器在你不小心捕获时报错,用来守住"零分配"这条线。Unity 的 C# 9.0 支持该语法。

### 只捕获 this

```csharp
class Enemy
{
    float _hp;
    void Register() => Events.OnTick += () => _hp -= 1;   // 捕获 this
}
```

没有闭包类,lambda 直接编译为 `Enemy` 的实例方法,委托的 `_target` 是 `this`。但每次执行 `+=` 这一行都会创建一个新委托(无法缓存,因为 target 是不同实例)。同时也意味着发布者对象一直引用这个 `Enemy`,见下文泄漏。

### 捕获 struct

```csharp
struct Ctx { public int Id; public void Run(Action a) => a(); }

void M(Ctx c)
{
    Action a = () => Console.WriteLine(c.Id);   // 捕获参数 c(struct)
}
```

被捕获的 struct 局部会被**提升成闭包类的字段**,即整个 struct 住进堆上。lambda 与外层方法共享同一个变量:lambda 对它的修改外层看得到,反之亦然。在 struct 的实例方法里 lambda 不能捕获 `this`(编译错误 CS1673),因为捕获的是它的拷贝而不是引用,需要时先复制到局部变量。

### 方法组转换

```csharp
void Tick() { }

void Register()
{
    Timer.Add(Tick);              // C# 9:每次 new Action(this.Tick)
}
```

Roslyn 在 C# 11 才引入方法组转换缓存(针对静态方法)。Unity 的 C# 9.0 下,上面每次执行都会 `new` 委托。绕开办法:

```csharp
readonly Action _tick;             // 实例字段缓存
Enemy() { _tick = Tick; }
void Register() => Timer.Add(_tick);
```

或使用静态只读字段缓存静态方法的委托。

### 本地函数

```csharp
int Count(int[] xs, int min)
{
    int n = 0;
    for (int i = 0; i < xs.Length; i++) Check(xs[i]);
    return n;

    void Check(int v) { if (v >= min) n++; }   // 本地函数,没有转成委托
}
```

本地函数被直接调用时,编译器把捕获变量放进一个 **struct 闭包**并按 `ref` 传入,不在堆上分配。一旦把本地函数转成委托(`Func<int> f = Check;`),它就变成堆上的闭包加委托。`static` 本地函数(C# 8)禁止捕获,可进一步固定零分配。

## 多播委托与事件

```csharp
public event Action OnTick;
OnTick += A;       // Delegate.Combine(OnTick, new Action(A))
OnTick += B;       // 再 Combine:新建多播委托,新建 _invocationList 数组(长度 2)
OnTick -= A;       // Delegate.Remove:再次分配
```

- `Delegate.Combine` 不修改原委托,而是新建一个带调用数组的 `MulticastDelegate`。N 次订阅的累计复杂度是 O(N^2) 的拷贝,每次都有新的数组分配。
- 调用多播委托时遍历 `_invocationList` 依次调用;其中某个订阅者抛异常,后面的订阅者不再被调用。
- `OnTick?.Invoke()` 的写法是先把字段读到局部,再判空调用,避免与取消订阅的竞态。
- 事件 `+=` 在运行时帧循环里反复增删(例如每次启用/禁用对象),会产生与订阅次数成比例的持续分配。需要频繁订阅的场景,考虑自己用 `List<T>` 或对象池维护监听者,而不是委托链。

### 事件泄漏

发布者(尤其是静态事件、单例、长寿命管理器)持有订阅者的委托,委托的 `_target` 引用订阅者对象,订阅者因此无法被 GC 回收。典型症状是:

- 已销毁的 `MonoBehaviour`(原生对象已没了)托管壳仍被静态事件引用,事件触发时回调进去,抛 `MissingReferenceException`。
- UI 面板反复打开关闭,每次都多订阅一份,回调次数越来越多,同时内存只增不减。
- 用 lambda 订阅后无法取消:`OnTick += () => ...` 每次是不同的委托实例,`OnTick -= () => ...` 删不掉。必须把 lambda 存到字段再 `+=` / `-=`。

规则:成对地写订阅与取消订阅,Unity 里放在 `OnEnable`/`OnDisable`;长寿命发布者用弱事件或显式 `Dispose` 订阅令牌;有疑问时在 Profiler 的 Memory 视图里查谁引用着该对象。

## 对照 C++

| 项 | C# | C++ |
|---|---|---|
| 无捕获 lambda | 编译为静态方法,委托缓存 | 可隐式转为函数指针,零开销 |
| 捕获的 lambda | 闭包类堆分配加委托堆分配(只要脱离栈就逃不掉) | 闭包对象是值类型,默认在栈上;放进 `std::function` 才可能触发堆分配(小对象优化内可免) |
| 捕获的语义 | 按引用共享变量(变量被提升到堆) | 显式 `[=]` 拷贝或 `[&]` 引用,悬垂引用要自己负责 |
| 生命周期 | GC 管理,事件持有会延长 | 值捕获拷贝拥有;引用捕获可能悬垂 |

最近的 CoreCLR 版本(.NET 9 起)的 JIT 在逃逸分析方面在逐步增强,可能对不逃逸的闭包与委托做栈分配,具体范围和版本待核实;Unity 的 Mono 与 IL2CPP 没有这类优化,按"总是堆分配"设计。

## 常见坑

- 在 `Update` 里写 `list.RemoveAll(x => x.id == id)`,捕获了 `id`,每帧一次闭包加委托。
- `button.onClick.AddListener(OnClick)` 在 C# 9 下每次评估都新建委托,在循环里反复调用就是一串分配。
- 方法参数被 lambda 捕获后,即使不走到 lambda 的分支也在方法入口分配闭包。
- 把 lambda 当作可取消的订阅。
- 静态事件订阅了对象实例,对象销毁后没取消。
- 误以为 `static` 方法的委托更快;开放静态委托在 CoreCLR 上需要 shuffle thunk,可能比实例闭合委托慢。

## 面试追问

1. **一个捕获了局部变量的 lambda 会产生几个对象?在哪一行分配?** 要点:一个闭包类实例,一个委托实例;闭包在被捕获变量的作用域入口分配(参数则在方法入口),委托在 lambda 表达式求值处分配;被捕获变量从此住在堆字段里。
2. **不捕获变量的 lambda 为什么没有分配?** 要点:编译器把它编译成嵌套类 `<>c` 的实例方法,并把委托缓存在静态字段里,首次用时创建一次;`static` lambda(C# 9)让编译器强制保证不捕获。
3. **方法组转换会分配吗?Unity 呢?** 要点:C# 11 前每次评估 `new` 委托;C# 11 起静态方法组被缓存;Unity 6000.x 是 C# 9.0,每次分配,需手工缓存到字段。
4. **事件为什么会造成内存泄漏?怎么排查和避免?** 要点:发布者的委托引用订阅者;长寿命发布者让订阅者不可回收;成对订阅取消订阅;lambda 订阅需存引用才能取消;用内存快照查引用链。
5. **多播委托每次 `+=` 发生了什么?** 要点:`Delegate.Combine` 新建多播委托和调用数组,旧的变成垃圾;累积为 O(N^2) 拷贝;热路径里不要频繁增删订阅。
6. **和 C++ lambda 的本质差别?** 要点:C++ 闭包是值类型对象,栈上无分配,捕获方式显式;C# 闭包是引用类型,捕获的是变量本身(按引用共享并被提升到堆),由 GC 管理。
