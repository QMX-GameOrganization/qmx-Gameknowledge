> 适用版本：示例基于 Unity 6（6000.x）的 `UnityEngine.Pool` 命名空间（2021.1 起提供）与 .NET Standard 2.1 的 `System.Buffers.ArrayPool<T>`。性能结论的方向性成立，具体数字请在目标设备上用 Profiler 实测。

## 要点

- 池解决的是**分配频率**和**初始化成本**，不是"让对象不被回收"。池化对象变成长寿对象，会增大存活堆（Unity Boehm 下直接增加每次标记的成本）。
- 值得池化的对象：创建昂贵（`Instantiate`、含大数组、带 Native 资源）、高频创建销毁、生命周期短且可复用。小而便宜的对象不值得池化。
- 池有四类典型事故：状态残留、忘记归还、重复归还 / 归还后继续使用、多线程竞争。
- 能 struct 化、能放进数组的数据，优先于"池化 class"：没有对象头、没有引用、没有写屏障、缓存友好。
- 临时大缓冲用 `ArrayPool<T>` 或 `NativeArray`；`List<T>.Clear()` 不释放容量，天然是一个复用缓冲。
- ECS 把这个思路推到极致：unmanaged 组件放在 chunk 里，不进托管堆；实体是整数句柄，创建销毁是 chunk 内的槽位操作。

## 什么时候池化

先看两个量：每帧分配次数 × 对象大小（决定 GC 频率），以及对象初始化的成本。

| 情况 | 建议 |
|---|---|
| 每帧产生几十个小 class 对象（事件参数、命令对象） | 先改 struct 或预分配数组，再考虑池 |
| 子弹、特效、伤害数字等需要 `Instantiate` 的 `GameObject` | 池化，收益来自跳过实例化与组件初始化，不仅是 GC |
| 临时 `List<T>` / `Dictionary` / `StringBuilder` | 用 `CollectionPool` / 字段复用 |
| 大数组缓冲（网络包、读文件） | `ArrayPool<T>`，避免 LOH 抖动（见 3.2） |
| 偶尔分配的对象（每几秒一个） | 不池化，成本不划算 |

池化的收益取决于存活堆。Boehm 非分代，池里闲置对象仍是全堆标记的一部分；一个 5000 个对象、每个带多个引用字段的池，会让每次完整标记多走一遍这张图。池的上限要设（`maxSize`），不能让它无限增长。

## 设计一个池

Unity 6 自带的 `UnityEngine.Pool.ObjectPool<T>` 已经覆盖多数需求：

```csharp
using UnityEngine;
using UnityEngine.Pool;

public sealed class BulletSpawner : MonoBehaviour
{
    [SerializeField] Bullet prefab;
    ObjectPool<Bullet> _pool;

    void Awake()
    {
        _pool = new ObjectPool<Bullet>(
            createFunc:      () =>
            {
                Bullet b = Instantiate(prefab, transform);
                b.OnExpired = _pool.Release;   // 方法组转委托只在对象创建时做一次
                return b;
            },
            actionOnGet:     b => b.gameObject.SetActive(true),
            actionOnRelease: b => { b.ResetState(); b.gameObject.SetActive(false); },
            actionOnDestroy: b => Destroy(b.gameObject),
            collectionCheck: true,      // Release 时检查重复归还；Release 构建可以关
            defaultCapacity: 64,
            maxSize:         256);       // 超出上限的归还会走 actionOnDestroy
    }

    public Bullet Fire(Vector3 pos)
    {
        Bullet b = _pool.Get();
        b.transform.position = pos;
        return b;
    }
}

public sealed class Bullet : MonoBehaviour
{
    public System.Action<Bullet> OnExpired;
    public void ResetState() { /* 速度、计时、拖尾、粒子等全部复位 */ }
}
```

注意 `b.OnExpired = _pool.Release` 放在 `createFunc` 里：方法组转委托在 C# 9 下每次执行都会 `new` 一个委托，如果写在 `Fire` 里，每次开火都会分配。池本身最容易引入这类隐性分配。

### 辅助池

`UnityEngine.Pool` 还提供 `ListPool<T>`、`HashSetPool<T>`、`DictionaryPool<TKey, TValue>`、`GenericPool<T>`、`LinkedPool<T>`。临时集合的标准用法：

```csharp
using UnityEngine.Pool;

void Collect()
{
    using (ListPool<Enemy>.Get(out List<Enemy> tmp))   // using 结束时自动归还并 Clear
    {
        FindEnemies(tmp);
        foreach (var e in tmp) e.Alert();
    }
}
```

## 四类事故

1. **状态残留**。归还时没有完整复位：速度、计时器、事件订阅、父子关系、动画状态、`TrailRenderer` 历史点、协程。症状是"第二次用才出 bug"。把复位集中到一个 `ResetState()`，并加测试：对象 Get → 乱改 → Release → Get，比较与全新对象的差异。
2. **忘记归还**。池不断 `createFunc`，要么超过 `maxSize` 后每次都在新建，要么内存持续上涨。给池加一个"借出计数"，Profiler 里监视借出数是否单调增长。
3. **重复归还 / 归还后继续使用**。同一个对象被归还两次，会被两个使用者同时借走，这是最难排查的一类。`collectionCheck: true` 在开发期必须开；归还后把外部持有的引用置空，或用句柄（索引 + 版本号）代替直接引用。
4. **多线程**。`ObjectPool<T>` 不是线程安全的。Unity API 本身只能在主线程调用；Job 里不能使用托管池。需要跨线程时，每个线程一个池（`[ThreadStatic]` 或线程局部），或使用 `System.Collections.Concurrent` 的容器，并接受锁的开销。

### 池把对象推进了老代（.NET）

在 CoreCLR 上，池里的对象很快晋升到 gen2。当池里长寿的容器对象（`List<Foo>`）被写入刚创建的年轻对象时，写屏障会标脏卡（见 3.2），下一次局部 GC 要扫描这些卡。因此：池里存放的对象应当尽量不包含指向新创建对象的引用字段；或者让池里的内容本身也是 struct。

### 池里的引用要及时清空

归还对象时，必须清掉它对其他对象的引用（目标、回调、父对象）。否则池里的闲置对象会让这些对象一直可达，造成"逻辑上已经销毁、实际上还占着内存"。

## struct 化

把 `class Particle { Vector3 pos; Vector3 vel; float life; }` 变成数组：

```csharp
public struct Particle
{
    public Vector3 Pos;
    public Vector3 Vel;
    public float Life;
}

public sealed class ParticleSystemLite
{
    Particle[] _items = new Particle[4096];
    int _count;

    public void Update(float dt)
    {
        for (int i = 0; i < _count; i++)
        {
            ref Particle p = ref _items[i];           // ref 引用数组元素，避免拷贝
            p.Pos += p.Vel * dt;
            p.Life -= dt;
        }
        // 移除死亡粒子：swap-remove，保持数组紧凑
        for (int i = 0; i < _count; )
        {
            if (_items[i].Life <= 0f) _items[i] = _items[--_count];
            else i++;
        }
    }

    public void Spawn(in Particle p)
    {
        if (_count == _items.Length) System.Array.Resize(ref _items, _items.Length * 2);
        _items[_count++] = p;
    }
}
```

收益：

- 4096 个粒子就是一个对象（数组），GC 只看到一个根；没有逐对象的对象头（典型每个对象 16 字节开销，64 位）。
- 数组连续，遍历时硬件预取有效，缓存命中率远高于散落的 class 实例。
- struct 数组内不含引用，卡表不参与，增量 GC 的写屏障不触发（写 `Vector3` 字段不是引用写入）。

注意事项：

- struct 不要太大。超过大约 16 字节后按值传递的拷贝开销显现，优先用 `ref`、`in` 传参；超过 64 字节要考虑拆分（SoA）。
- 避免在 struct 里放引用类型字段：一旦有一个引用字段，数组元素就需要被 GC 逐个扫描，失去"GC 看不到数组内部"的好处。
- 可变 struct 容易出错：从 `List<T>` 取出的是拷贝，`list[i].x = 1` 编译不过（CS1612）；改用数组并通过 `ref` 修改元素。
- AoS（结构体数组）与 SoA（每个字段一个数组）的取舍：一次访问多个字段用 AoS；只遍历少数字段（只更新位置）用 SoA，更利于 SIMD 与 Burst。
- `unmanaged` 约束的 struct（所有字段都是值类型）可以放进 `NativeArray<T>`，进一步脱离托管堆，并且能被 Job 与 Burst 使用。

C++ 对照：这就是 `std::vector<Particle>` 加 swap-and-pop 的惯用法。C++ 里 class 和 struct 差别很小，默认都是值语义、连续存储；C# 里 class 是堆对象 + 引用，所以"想要 C++ 的内存布局"必须显式选 struct 与数组。

## 数组与缓冲复用

### List 与字典

- `List<T>.Clear()` 对引用类型会把元素置空（避免保留引用），不会缩容；对 unmanaged 元素类型，`Clear` 仅重置 `Count`。预估容量并在构造时传入，避免扩容时产生的旧数组垃圾（以及大数组的 LOH 问题）。
- 逻辑上"每帧重建"的集合，把它放字段里，每帧 `Clear()` 再填充。

### ArrayPool

```csharp
using System.Buffers;

void Process(int needed)
{
    byte[] buf = ArrayPool<byte>.Shared.Rent(needed);   // 可能返回比 needed 更大的数组
    try
    {
        var span = buf.AsSpan(0, needed);               // 只用需要的前 needed 个元素
        Fill(span);
        Consume(span);
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buf, clearArray: false);
    }
}
```

注意：

- `Rent` 返回的数组长度可能大于请求值，内容**不保证为零**（可能有上一位使用者的数据），所以要用 `Span` 限定使用范围，并且在含敏感数据时设置 `clearArray: true`。
- 归还后不能再使用该数组。重复归还会让同一块内存被借出两次。
- 池里的数组在 CoreCLR 上落在 gen2 或 LOH，适合大缓冲；Unity Boehm 下适合避免大块分配造成的扩堆（见 3.3）。

### NativeArray 与 Allocator

`NativeArray<T>` 的内存来自原生分配器，不受 GC 管理，也不会被 GC 遍历。它的三种分配器与生命周期（`Temp` / `TempJob` / `Persistent`）在 Unity Job 与 Burst 专栏的"内存分配器与生命周期"一页有详细表格。与 GC 相关的要点：

- Native 内存零 GC 压力，但忘记 `Dispose` 就是泄漏，没有终结器兜底（见托管与非托管章节）。
- 把大块长期数据放 `Persistent` NativeArray，可以让托管堆保持小，从而让 Boehm 的每次标记变短。
- 托管数组与 NativeArray 之间的拷贝（`CopyTo` / `NativeArray.Copy`）有成本，设计数据流时要让数据只在一侧生长。

## 池与 GC 暂停、缓存局部性

| 维度 | 对象池 | struct 数组 |
|---|---|---|
| 分配频率 | 降到近 0 | 降到近 0 |
| 存活堆 | 增加（池里的对象常驻） | 只增加一个数组 |
| 标记成本（Boehm） | 增加（逐对象遍历） | 数组内无引用时，近乎为 0（仍需标记数组本身） |
| 缓存局部性 | 池内对象地址分散，取决于创建时间 | 连续，预取友好 |
| 写屏障 | 池内对象引用字段写入仍触发 | 值类型字段写入不触发 |
| 实现复杂度 | 需要复位 / 归还纪律 | 需要自己管理槽位与删除 |

结论：对 GC 与缓存都最友好的是"数据 struct 化 + 紧凑数组"，对象池是无法 struct 化时的次优方案，例如 `GameObject`、需要继承与虚调用的对象。

## 与 ECS 数据布局的关系

ECS（Unity Entities）把上面的做法系统化：

- 组件是 unmanaged struct，按 archetype 存放在固定大小（16 KB）的 chunk 里，同一 chunk 内同一类型的组件连续排列，天然是 SoA。chunk 的容量与大小以你所用的 Entities 版本为准（待核实）。
- 实体只是 `Entity { int Index; int Version; }` 这样的句柄，创建销毁就是 chunk 槽位的分配与 swap-remove，等价于一个内置的、带版本号的池。版本号解决了上面第 3 类事故（句柄过期后，旧引用能被检测出来）。
- 数据都在 Native 内存中，托管堆里几乎没有组件数据，GC 的标记成本不随实体数量增长。
- 托管组件（`class IComponentData`、`SharedComponent` 里的托管对象）会把数据放回托管堆并破坏 Burst 兼容性，只用于不得不引用 UnityEngine 对象的场合。

## 常见坑

- 池化小对象，反而增大存活堆和标记成本。
- 池的 `maxSize` 没设，峰值时涨上去之后永远不缩。
- 归还时只 `SetActive(false)`，没有复位粒子与拖尾，复用时出现"上一发子弹的拖影"。
- `ArrayPool.Rent(n)` 的返回数组长度被当作 n 使用，遍历到了脏数据。
- 把含引用的 class 放进 struct 数组，以为 GC 已经看不到它们。
- 在 Job 里使用托管池。

## 面试追问

1. 什么时候不该用对象池？ 要点：对象小而便宜、分配不频繁；池会增大存活堆（Boehm 下增加每次标记成本）；复位逻辑的 bug 风险高于 GC 成本。
2. 池化与 struct 化的取舍？ 要点：struct 数组无对象头、无引用、缓存友好、不触发写屏障；池适合必须是 class 的对象（`GameObject`、多态对象）；优先 struct 化。
3. 对象池最常见的 bug 是什么，如何防？ 要点：状态残留、忘记归还、重复归还、跨线程；防御：集中 Reset 并测试、借出计数监控、开启 collectionCheck、用索引 + 版本号句柄、线程局部池。
4. `ArrayPool<T>.Rent` 有哪些陷阱？ 要点：数组可能更长；内容不保证清零；归还后不可再用；敏感数据需 `clearArray`；大缓冲才划算。
5. ECS 的实体复用如何避免对象池的"过期引用"问题？ 要点：实体 = 索引 + 版本号，销毁时递增版本，旧句柄被检测为无效；数据在 chunk 里 swap-remove，保持紧凑。
6. 为什么池里放太多对象会让 Unity 的 GC 变慢，而 .NET 则表现不同？ 要点：Boehm 非分代，每次标记遍历全部存活对象，池里闲置对象也要遍历；CoreCLR 局部回收不遍历老代，但卡表与 gen2 回收仍有成本。
