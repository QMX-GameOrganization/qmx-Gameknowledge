> 适用版本：Unity 部分对应 Unity 6（6000.x）手册与 Memory Profiler 1.1.x；.NET 部分对应 .NET 8/9。配置项名称取自 Microsoft Learn 的 "Runtime configuration options for garbage collection"，默认值与可用性随版本、平台和 GC 模式（工作站 / 服务器）变化，文中标"待核实"的请以官方页面为准。Unity 的 Mono / IL2CPP 运行时不支持下文的 CoreCLR 配置项与 `GCSettings.LatencyMode`、`TryStartNoGCRegion`。

## 要点

- 诊断先于调优。先判断问题类型：分配率太高、存活堆太大、碎片、还是某一次完整回收的暂停；每种对应不同的工具和手段。
- Unity：Profiler 的 CPU 模块看 GC.Alloc 与 GC.Collect 的位置，Memory 模块看 GC Used / Reserved 曲线，Memory Profiler 包抓快照对比托管堆。
- .NET：`dotnet-counters` 看实时趋势，`dotnet-gcdump` 抓托管堆对象图，`dotnet-trace` / PerfView 看 GC 事件与暂停原因。
- CoreCLR 能调的旋钮：Server / Workstation、Concurrent、`GCConserveMemory`、`GCHeapCount` / 亲和性、`GCHeapHardLimit`、`GCLOHThreshold`；运行期用 `GCSettings.LatencyMode` 与 `GC.TryStartNoGCRegion`。
- Unity 能调的旋钮少得多：增量 GC 开关、`GarbageCollector.GCMode`、`CollectIncremental`、time slice，其余都靠少分配、小存活堆。
- 帧预算策略的原则：稳态不分配；必须发生的回收，放在玩家看不到卡顿的时间点。

## 从症状到工具

| 症状 | 可能原因 | 首选工具 |
|---|---|---|
| 周期性掉帧，时间轴上 `GC.Collect` 占几 ms 到数十 ms | 分配率高导致 GC 频繁；或存活堆大导致单次标记久 | Unity Profiler CPU 模块；.NET 看 `dotnet-counters` 的 `gen-0-gc-count`、`alloc-rate`、`time-in-gc` |
| 每帧 GC Alloc 列有值 | 稳态路径存在分配 | Profiler Hierarchy + Call Stacks（3.4） |
| 内存缓慢上涨，不回落 | 泄漏（静态引用、事件未注销、池无上限）或碎片 | Memory Profiler 快照对比；`dotnet-gcdump` 对比两次快照 |
| GC Reserved 很大，Used 很小 | 堆被偶发大分配撑大，Boehm 不归还 | Memory 模块的 GC Used / Reserved 曲线（3.3） |
| 偶发长时间卡顿，GC 次数不多 | 一次完整回收；终结器积压；SuspendEE 等待线程 | .NET：PerfView GCStats（区分 suspension 与 GC 时间）；Unity：Profiler 中单帧 `GC.Collect` |
| gen2 回收次数异常多 | LOH 抖动、对象过早晋升、池里放了大量短命引用 | `dotnet-counters` 的 `gen-2-gc-count`、`loh-size`；PerfView 的 GC Heap Alloc 视图 |
| 移动端被系统杀进程 | 托管堆 + Native 总量超限，脏页多 | Memory Profiler（含 Native 部分）；平台工具 |

## Unity 工具链

### Profiler

- **CPU Usage > Hierarchy**：按 `GC Alloc` 列排序，定位分配方法。`GC.Collect` 标记的出现位置和耗时就是 GC 暂停；增量模式下它会被拆成多个小块散落在多帧中。
- **Call Stacks**：在 Profiler 工具栏开启，GC.Alloc 样本会附带调用栈。Deep Profile 开销大，只作定性参考。
- **Memory 模块**：`GC Used Memory`、`GC Reserved Memory`、`GC Allocated In Frame`、`GC Allocation In Frame Count` 这类计数器，可以直接画出每帧分配曲线。
- 开发版 Player 连接真机，排除 Editor 自身分配的干扰。

### Memory Profiler 包

`com.unity.memoryprofiler`（1.1.x 系列）抓取整份内存快照，包含托管堆与原生内存：

- **Managed Heap**：看对象按类型的数量与大小、被谁引用（References 视图），能找出"本该释放的对象被静态字段、事件、协程持有"。
- **Compare**：先抓一份稳态快照，操作一遍（进入关卡再退出），再抓一份，比较差异，增长的类型就是泄漏候选。
- **Managed shell objects**：托管侧还活着、但对应的 Native 对象已被 `Destroy` 的壳对象，常见于持有 `UnityEngine.Object` 的静态引用（Unity 手册在 Managed memory 页面中提到了它与 `UnloadUnusedAssets` 的关系）。
- 碎片：关注托管堆各 block 的利用率；大量低利用率 block 意味着碎片或堆被偶发大分配撑大。

### 代码内的实时监控

```csharp
using Unity.Profiling;
using UnityEngine;

public sealed class GcMonitor : MonoBehaviour
{
    ProfilerRecorder _used, _reserved, _allocFrame;

    void OnEnable()
    {
        _used       = ProfilerRecorder.StartNew(ProfilerCategory.Memory, "GC Used Memory");
        _reserved   = ProfilerRecorder.StartNew(ProfilerCategory.Memory, "GC Reserved Memory");
        _allocFrame = ProfilerRecorder.StartNew(ProfilerCategory.Memory, "GC Allocated In Frame");
    }

    void OnDisable()
    {
        _used.Dispose(); _reserved.Dispose(); _allocFrame.Dispose();
    }

    void OnGUI()
    {
        GUILayout.Label($"GC used {_used.LastValue / 1048576f:F1} MB   " +
                        $"reserved {_reserved.LastValue / 1048576f:F1} MB   " +
                        $"alloc/frame {_allocFrame.LastValue} B");
    }
}
```

`OnGUI` 里的字符串插值本身会分配，只在调试面板里用，不要在零 GC 的测试里开着它。

## .NET 工具链

| 工具 | 用途 | 典型命令 |
|---|---|---|
| `dotnet-counters` | 实时计数器：`gc-heap-size`、`gen-0/1/2-gc-count`、`gen-0/1/2-size`、`loh-size`、`poh-size`、`alloc-rate`、`time-in-gc`、`gc-fragmentation` 等（名称随版本略有差异，待核实） | `dotnet-counters monitor --process-id <pid> System.Runtime` |
| `dotnet-gcdump` | 抓取托管堆对象图快照（类型、数量、大小、引用路径），不含对象字段值 | `dotnet-gcdump collect -p <pid>`；用 VS 或 PerfView 打开 |
| `dotnet-trace` | 采集运行时事件，可含 GC 事件与分配采样 | `dotnet-trace collect -p <pid> --profile gc-verbose` |
| PerfView | 分析 `.nettrace` / ETW：GCStats 汇总每次 GC 的代、原因、暂停时间；Heap Alloc 视图看分配调用栈 | GUI |
| `dotnet-dump` | 完整进程转储，用 SOS 命令（`dumpheap -stat`、`gcroot`）找根 | `dotnet-dump collect` |

阅读 GCStats 时的要点：

1. **Pause 时间 vs GC 时间**。长暂停可能来自等待线程到达安全点（suspension），而不是标记慢；两者的优化手段完全不同。
2. **Reason**：`AllocSmall`（gen0 预算耗尽）、`AllocLarge`（LOH 分配触发）、`Induced`（有人调了 `GC.Collect`）、`LowMemory`。大量 `Induced` 往往是业务代码在乱调 `GC.Collect`。
3. **Gen 与 Compacting / Sweeping**：确认 gen2 的比例以及是否在压缩。

运行时 API 同样能给出线索：

```csharp
using System;

static class GcStats
{
    public static void Snapshot()
    {
        TimeSpan pause = GC.GetTotalPauseDuration();           // .NET 7+：进程累计 GC 暂停时间
        long allocated = GC.GetTotalAllocatedBytes(precise: false);
        GCMemoryInfo info = GC.GetGCMemoryInfo(GCKind.Any);
        Console.WriteLine($"pause={pause.TotalMilliseconds:F1}ms allocated={allocated:N0} " +
                          $"lastGen={info.Generation} index={info.Index} " +
                          $"promoted={info.PromotedBytes:N0} fragmented={info.FragmentedBytes:N0}");
    }
}
```

把 `GetTotalPauseDuration()` 每帧做差，就能得到"这一帧里 GC 暂停了多久"，比通用采样更精确。

## CoreCLR 的 GC 配置项

配置方式：`runtimeconfig.json` 的 `configProperties`、环境变量 `DOTNET_xxx`（多数是十六进制值）、或程序集属性。常用项如下（来自 Microsoft Learn 的 GC 配置页；默认值与是否在 regions 下生效待核实）：

| 配置 | 作用 | 备注 |
|---|---|---|
| `System.GC.Server` | 服务器 GC | 客户端应用一般不用 |
| `System.GC.Concurrent` | Background GC | 默认开；关掉可省去后台线程与部分写屏障成本，gen2 变成阻塞式 |
| `System.GC.RetainVM` | 释放的 segment/region 留着不还 OS | 减少反复申请 |
| `System.GC.ConserveMemory` | 0 到 9，值越大越倾向压缩老代以降低内存占用 | 以 CPU 换内存 |
| `System.GC.HeapCount` | 服务器 GC 堆的数量 | 仅服务器 GC |
| `System.GC.HeapAffinitizeMask` / `System.GC.HeapAffinitizeRanges` / `System.GC.NoAffinitize` | 服务器 GC 线程与 CPU 的绑定 | 仅服务器 GC；容器或多进程共机时需要调 |
| `System.GC.HeapHardLimit` | 托管堆硬上限 | 容器化部署常用；超限抛 OOM |
| `System.GC.LOHThreshold` | 大对象阈值（默认 85000） | 见 3.2 |
| `GCgen0size` | gen0 预算的最小值 | 是否仍被当前版本采纳待核实 |

> 对 `GCHeapAffinitize*` 的说明：这类选项只对服务器 GC 有意义（每个堆一条 GC 线程，可固定在某个核上）。客户端的工作站 GC 没有多堆，不需要关心。

调优顺序建议：先通过减分配解决问题；只有当存活堆结构已经合理、症状仍在时才动 GC 配置。配置往往只是把代价从一个维度转移到另一个（内存 ↔ CPU ↔ 延迟）。

## 运行期延迟控制（仅 CoreCLR）

### GCSettings.LatencyMode

| 模式 | 含义 |
|---|---|
| `Batch` | 关闭并发 GC，吞吐优先 |
| `Interactive` | 默认（启用并发时）：Background GC |
| `LowLatency` | 仅工作站 GC：抑制 gen2 回收，除非内存紧张或显式 `GC.Collect`。适合短时间段 |
| `SustainedLowLatency` | 需要启用并发 GC：尽量避免阻塞式 full GC，可持续较长时间，但内存会涨 |
| `NoGCRegion` | 只读状态，进入 `TryStartNoGCRegion` 之后的值 |

`LowLatency` 用完要还原，它会让堆越涨越大：

```csharp
using System;
using System.Runtime;

GCLatencyMode old = GCSettings.LatencyMode;
try
{
    GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency;
    RunCriticalPhase();
}
finally
{
    GCSettings.LatencyMode = old;
}
```

### GC.TryStartNoGCRegion

在一段你能估计分配量的关键路径里，预先申请好内存，并保证期间不触发 GC：

```csharp
using System;
using System.Runtime;

static void RunWithoutGc(Action work, long expectedBytes)
{
    if (!GC.TryStartNoGCRegion(expectedBytes))      // 同时会预先提交这么多内存；失败时返回 false 或抛异常
        { work(); return; }

    try
    {
        work();
    }
    finally
    {
        // 如果期间分配超出，区域已被运行时结束并触发 GC，此时 EndNoGCRegion 会抛 InvalidOperationException
        if (GCSettings.LatencyMode == GCLatencyMode.NoGCRegion)
            GC.EndNoGCRegion();
    }
}
```

要点：

- 参数 `totalSize` 有上限（受堆布局与机器限制，具体值待核实），超限会抛 `ArgumentOutOfRangeException`。
- 进入区域时运行时可能先做一次 GC，来腾出所需空间；这次 GC 应安排在进入点，而不是关键路径内部。
- 超出预算时区域自动结束，随后正常 GC；`EndNoGCRegion` 的调用要先检查 `LatencyMode`。
- 有一个带 `disallowFullBlockingGC` 的重载，可以要求不要在进入时做完整阻塞 GC。

Unity 的对应物是 `GarbageCollector.GCMode = Mode.Disabled / Manual`（3.3），语义不同：它没有预提交内存和超限自动恢复，需要自己控制。

## 帧预算内的 GC 策略

以 60 fps（16.6 ms/帧）为例，目标是 **GC 不在玩家可感知的时刻让某一帧超预算**。

1. **减源头**：稳态零分配（3.4）。这是所有策略的前提。
2. **减存活堆**：在 Boehm 下，存活堆决定单次标记的总工作量；把大型常驻数据移出托管堆（NativeArray、ECS、StreamingAssets 按需加载）。
3. **安排时机**：
   - 加载界面、关卡切换、过场动画等"玩家不看帧率"的时刻，主动 `GC.Collect()`，并紧跟 `Resources.UnloadUnusedAssets()`（二者在大项目里可能耗时数秒，Unity 手册有提醒）。
   - 战斗等关键阶段前，预分配好所需内存，必要时设为 `Mode.Disabled` 或 `Manual`，阶段结束后恢复并回收。
4. **平摊**：保持增量 GC 开启，配合 `Application.targetFrameRate` / VSync，让 Unity 把 GC 时间放进空闲时间；需要精确控制时用 `CollectIncremental(预算纳秒)`。
5. **监控**：用 `ProfilerRecorder` 把 GC Used / Reserved 与每帧分配量放进调试面板和 CI；设阈值，越线就告警。
6. **服务端 / 工具链程序（.NET）**：工作站 + Concurrent；对延迟敏感的阶段使用 `SustainedLowLatency` 或 `NoGCRegion`。

一个常见的错误思路是"调大堆就能少 GC"。在 Boehm 下，堆越大，单次标记越久；在 CoreCLR 下，调大 gen0 预算能降低 gen0 频率，但每次暂停也会更久（更多存活对象需要拷贝），要看数据再取舍。

## 常见坑

- 看到 `GC.Collect` 就加 `GC.Collect()` 的"优化"，结果每帧一次完整阻塞回收。
- 在 Editor 里调优。Editor 的 Mono、域重载、编辑器分配都会污染数据。
- 只看平均帧时间，不看最坏帧。GC 问题几乎都体现在尾部。
- 在 CoreCLR 上长期使用 `LowLatency`，内存无限上涨。
- 认为 `GCHeapAffinitize*` 对客户端有意义。
- 把 `NoGCRegion` 当作"关闭 GC"，期望分配量不受控也没事。

## 面试追问

1. 线上发现偶发 200 ms 卡顿，怀疑 GC，你怎么确认和定位？ 要点：Profiler/trace 看那一帧是否有完整 `GC.Collect`；区分 suspension 与 GC 本身；看 GC 原因（分配触发还是 Induced）；用快照对比存活堆；确定是频率问题还是单次过长。
2. 工作站、服务器、Concurrent 的取舍？ 要点：WKS 用于客户端；SVR 每核一堆一线程，吞吐优先、内存高；Concurrent 只后台化 gen2，换取更短的 gen2 暂停，代价是额外开销且 gen0/gen1 暂停不变。
3. `SustainedLowLatency` 和 `NoGCRegion` 的区别？ 要点：前者是长期的"尽量避免阻塞式 full GC"，仍会有 GC；后者是预提交内存、在预算内完全不 GC，超限自动结束，只适合短且分配量可预估的区间。
4. Unity 里有什么办法控制 GC 时机？ 要点：增量 GC 开关与 time slice；`GCMode` Disabled / Manual；`CollectIncremental`；在加载点 `GC.Collect`；这些都受限于 Boehm 没有分代、不压缩。
5. 为什么"调大堆"不一定减少卡顿？ 要点：Boehm 下单次标记与存活堆成正比；CoreCLR 下 gen0 预算更大意味着单次回收更慢；真正有效的是减分配和减存活堆。
6. 如何发现内存泄漏？ 要点：稳态快照 → 操作 → 快照，比较增长的类型；沿引用链找到根（静态字段、事件、池、协程）；关注 Unity 的 managed shell objects。
