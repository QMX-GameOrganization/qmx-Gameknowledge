> 适用版本：本页以 .NET 8/9 的 CoreCLR 为主线（GC 实现在 `src/coreclr/gc/gc.cpp`）。Unity 当前默认的脚本运行时是 Mono / IL2CPP，使用的是 Boehm GC，不是这里描述的分代压缩式收集器，差异见 3.3。数值（预算、region 大小）会随版本与机器变化，文中标"典型值"或"待核实"的不要当成常量背。

## 要点

- CoreCLR 的 GC 是分代、可压缩、栈精确扫描的追踪式收集器；小对象 3 代（gen0/1/2），大对象单独一代（LOH，逻辑上称 gen3）。
- 分配是线程私有 allocation context 里的指针碰撞（bump pointer），热路径不加锁，代价接近几条指令；贵的是之后的回收，不是 `new` 本身。
- 一次 GC 的核心阶段是 mark、plan、relocate、compact，或 mark、plan、sweep。plan 阶段先模拟压缩，再决定真压缩还是清扫。
- 回收 gen N 时，gen 0..N 一起回收。老代到年轻代的引用靠卡表（card table）补根，见 3.2。
- 暂停的开销有两部分：挂起所有托管线程（SuspendEE）到达安全点的时间，以及标记与整理本身。Background GC 只能把 gen2 的标记与清扫移到后台线程，不能消灭 gen0/gen1 的暂停。
- .NET 7 起 64 位默认使用 regions 取代 segments，gen 成了 region 的属性，晋升可以不拷贝对象，内存也能以 region 为单位归还 OS。

## 根与可达性

GC 从根集出发做图遍历，不可达的对象就是垃圾。CoreCLR 的根包括：

| 根类型 | 说明 |
|---|---|
| 线程栈与寄存器 | JIT 为每个方法生成 GC info，描述在每个安全点哪些栈槽、寄存器里存着对象引用。因此栈扫描是精确的：不会把一个整数误认成引用 |
| 静态字段 | 类型加载时分配在 loader heap 或 pinned 区，是长期根 |
| GC handle | 强句柄、固定句柄（Pinned）、弱句柄（WeakReference 的底层）、`GCHandle.Alloc` 创建的都在这里 |
| 终结队列 | 带终结器的对象被单独登记，对象不可达后进入 f-reachable 队列，复活一次（见托管与非托管章节的 Dispose 一篇） |
| 老代对象（只在局部回收时） | 回收 gen0/gen1 时，不遍历 gen2，而是通过卡表找到"老代里指向年轻代"的引用，作为额外的根 |

精确扫描有一个直接后果：GC 可以移动对象。移动前后所有引用都能被改写，所以 CoreCLR 可以做压缩。Boehm 是保守扫描，栈上的任何整数都可能是指针，只能不移动（见 3.3）。这是两者所有行为差异的起点。

### JIT 对根的影响

JIT 只在"需要时"报告变量为活跃。Release 构建中，一个局部变量最后一次使用之后就不再是根，即使它的作用域还没结束：

```csharp
static void Probe()
{
    var big = new byte[1 << 20];
    var weak = new WeakReference(big);
    Use(big);                  // big 的最后一次使用
    GC.Collect();
    Console.WriteLine(weak.IsAlive);  // Release 下通常为 False；Debug 下为 True
}
```

Debug 构建（或附加调试器）会把局部变量生命周期延长到作用域结束，便于观察。不要用 `WeakReference` 的结果去验证"有没有泄漏"却不说明构建配置。

## 分配路径

```text
new Foo()
  -> JIT 内联的分配 helper（线程局部 alloc_context）
       alloc_ptr + size <= alloc_limit ?
         是 -> 返回 alloc_ptr，alloc_ptr += size       （无锁，几条指令）
         否 -> 慢路径：向 GC 申请新的 allocation quantum（典型 8 KB）
                 -> gen0 预算耗尽 -> 触发 GC
```

要点：

- GC 以 allocation quantum 为单位发放内存，典型约 8 KB，并整块清零（预热 CPU cache，也保证"新对象字段为 0"的语义）。BOTR 文档给出的数字是平均托管对象约 35 字节，一个 quantum 足以容纳很多对象。
- 剩余空间装不下下一个对象时，GC 把尾巴填成 free object，保证堆始终可线性遍历（"crawlable"），再换新的 quantum。
- 大对象（`>= 85,000` 字节）不走 allocation context，直接在 LOH 上分配，见 3.2。
- 内存分配的"便宜"依赖于压缩：压缩后 gen0 总是一段连续空间，下次分配又是指针碰撞。没有压缩的 GC（Boehm）退化为空闲链表分配，分配本身就贵得多。

C++ 对照：这相当于每线程一个 arena 的 bump allocator。`malloc` 要在空闲链表或 size-class 里找块，并可能加锁；托管堆把这个成本转嫁到回收阶段统一支付。

## 分代与预算

分代假设：大多数对象朝生夕死。把堆切成年龄段，频繁只回收最年轻的一段，就能让单次 GC 的代价正比于存活对象，而不是堆大小。

- gen0：新分配对象，gen0 和 gen1 合称 ephemeral（短命）代。
- gen1：在一次 gen0 GC 中存活的对象晋升到这里，充当 gen0 与 gen2 之间的缓冲。
- gen2：长期存活对象。gen2 GC 是 full GC，同时回收 LOH 和 POH。

每一代有一个分配预算（allocation budget）：这一代新增数据超过预算就触发该代的 GC。预算按存活率动态调整，存活率高就加大预算，期望下次死亡比例更好。gen0 的初始预算与 CPU 的 L3 缓存大小相关（典型值在几 MB 到几十 MB，随机器与配置变化，待核实），目的是让 gen0 尽量留在缓存里。

触发 GC 的因素不止预算：

- 碎片率高的代更值得回收。
- 机器内存负载过高时，GC 会更激进，避免整机换页。
- 短命代所在的内存快用尽时，更多做 gen1 以避免申请新空间。
- 显式的 `GC.Collect`、操作系统的低内存通知。

### 存活率才是成本

分代 GC 的单次成本约等于"标记存活对象 + 搬移存活对象"，死亡对象不付代价。所以：

- 大量短命小对象在 gen0 里的代价几乎只剩下分配本身，这就是 `new` 一堆临时 `List` 在服务端并不致命的原因。
- 真正糟糕的模式是"中等寿命"：对象活过 gen0 被晋升到 gen1，甚至 gen2，然后很快死亡。它们既付了拷贝成本，又把 gen2 撑大，触发昂贵的 full GC。典型例子：缓存淘汰策略做得差的对象、跨几帧的异步状态机。

## 四个阶段

下面是 `gc.cpp` 中一次 compacting GC 的主干（依据 BOTR 文档）：

```text
SuspendEE            挂起所有托管线程，到达安全点
generation_to_condemn 决定回收哪一代
mark_phase           从根开始遍历，标记存活对象（含卡表补根）
plan_phase           线性遍历堆，模拟压缩，算出每个存活片段的新地址与碎片；决定 compact 或 sweep
relocate_phase       更新所有指向被移动对象的引用（栈、寄存器、堆内引用、句柄）
compact_phase        按 plan 的结果拷贝对象
   或 sweep          把死亡空间连成 free object，挂入空闲链表
RestartEE            恢复托管线程
```

几点值得面试时说出来的细节：

1. plan 不是"先决定压缩再做"，而是先模拟。存活对象之间的间隙（plug 之间的 gap）如果足够小、整体碎片不高，会选 sweep，因为压缩要搬运数据。
2. relocate 之所以必须在 compact 之前，是因为引用的更新依赖 plan 阶段算好的新地址，不需要先拷贝。
3. mark 只访问存活对象，所以它不处理弱引用目标的死亡；弱句柄、终结队列在 mark 之后单独扫描。
4. 压缩会改变地址，所以 `fixed`、`GCHandle.Pinned`、`stackalloc`、非托管持有的指针都必须有固定或不可移动的保证，见托管非托管章节。固定对象会在 plan 阶段把压缩切成多段，大量固定会让压缩失效，表现为碎片。

## 工作站与服务器，Concurrent 与 Background

| 维度 | 工作站 GC（WKS） | 服务器 GC（SVR） |
|---|---|---|
| 堆 | 一个 | 每个逻辑核心一个堆 |
| GC 线程 | 触发分配的用户线程自己执行 | 每核一个高优先级专用 GC 线程，并行标记与压缩 |
| 取向 | 低延迟、小内存占用 | 吞吐量，适合多核服务器 |
| 客户端游戏 | 默认选择 | 一般不用：线程占核、内存占用更高 |

Concurrent GC（工作站默认开启）的实际含义是 Background GC：

- 只有 gen2 的收集可以在后台线程中并发进行（并发标记、并发清扫）。
- 后台 gen2 进行期间，用户线程若又耗尽 gen0 预算，可以触发一次前台（foreground）的 gen0/gen1 GC。前台 GC 与普通阻塞 GC 一样，需要挂起线程。
- 后台标记中途仍要至少暂停一次托管线程，用来完成标记收尾，之后才并发清扫。
- Background GC 以 CPU 换延迟：额外的写屏障与并发协调有开销，而且后台 GC 不压缩（只清扫）。

结论：它降低 gen2 的暂停长度，不降低 gen0/gen1 的暂停，更不会降低分配率。

## 从 segments 到 regions

经典的 segments 设计：启动时预留若干大块连续虚拟内存（segment），gen0/gen1 总在一个 ephemeral segment 里，晋升意味着对象留在原地、边界指针移动，或者拷贝到别的 segment。问题是 segment 大小固定，释放困难，LOH 与 SOH 难以相互借用空间。

Regions（.NET 7 起 64 位默认）：

- 堆由一批固定大小的 region 组成，每个 region 有自己的代标记（gen0/gen1/gen2/LOH/POH）。SOH 的基础 region 典型值是 4 MB，LOH 的是 32 MB（具体值随版本，待核实）。
- 晋升可以直接把 region 的代标记提升（整 region 提升），免去拷贝。
- 空闲 region 可以被重新分配给其他代，也可以 decommit 还给 OS，使得 SOH 与 LOH 之间的空间可复用。
- 虚拟地址预留更大（默认值与物理内存和平台相关，待核实）；不需要 segments 那样固定的 ephemeral 区。

对客户端程序的意义有限，了解即可：它改变的是内存归还与碎片行为，而不是"何时触发 GC"。需要回退到 segments 时，可以通过 `DOTNET_GCName` 加载随运行时分发的 segments 版 GC（clrgc 库；各版本是否仍随附，待核实）。

## 观测

```csharp
using System;

static class GcProbe
{
    public static void Report(string tag)
    {
        Console.WriteLine(
            $"{tag}: gen0={GC.CollectionCount(0)} gen1={GC.CollectionCount(1)} gen2={GC.CollectionCount(2)} " +
            $"allocThread={GC.GetAllocatedBytesForCurrentThread():N0} " +
            $"totalMemory={GC.GetTotalMemory(false):N0}");
    }

    public static void Details()
    {
        GCMemoryInfo info = GC.GetGCMemoryInfo();
        Console.WriteLine($"gen={info.Generation} compacted={info.Compacted} " +
                          $"pause={info.PauseDurations[0].TotalMilliseconds:F2}ms " +
                          $"fragmented={info.FragmentedBytes:N0} heap={info.HeapSizeBytes:N0}");
    }
}
```

`GC.CollectionCount(n)` 是"回收了至少 n 代的次数"，所以 gen2 的次数一定不大于 gen0 的次数。测一段代码的分配量，用 `GC.GetAllocatedBytesForCurrentThread()` 做前后差，比看 GC 次数稳定得多。Unity 的 Mono 没有 `GetGCMemoryInfo` 这类 API，只能靠 Profiler。

## 常见坑

- 在 Release 下用 `WeakReference` 检验泄漏，却在 Debug 下得出相反结论；两种构建的根集不同。
- 以为 `GC.Collect()` 能"释放内存"。它只回收，并不一定归还 OS；而且打乱了 GC 自己的预算与调优，会把一部分短命对象提前晋升。
- 把 `GC.Collect` 放进每帧循环里来"控制抖动"，每次都是一次 full blocking GC。
- 终结器、`GCHandle`、固定对象一多，压缩效果变差，gen2 越来越大。
- 服务器 GC 搬到客户端，反而因为每核一堆一线程拉高了内存占用与调度开销。

## 面试追问

1. 为什么 `new` 在 .NET 里比 `malloc` 便宜，代价转移到了哪里？ 要点：线程私有 allocation context 的指针碰撞、无锁；压缩保证了 gen0 连续；成本在回收阶段，与存活量成正比而不是与垃圾量成正比。
2. plan 阶段做什么，为什么不直接压缩？ 要点：线性扫描堆，计算存活片段（plug）与间隙（gap），模拟压缩后的地址与碎片；根据碎片率与搬运成本选择 compact 或 sweep；compact 需要 relocate 先更新引用。
3. Background GC 到底后台了什么？ 要点：只有 gen2 的标记与清扫；不压缩；gen0/gen1 的前台 GC 照样要暂停；以额外 CPU 与写屏障开销换 gen2 暂停变短。
4. 为什么 CoreCLR 能压缩而 Boehm 不能？ 要点：栈精确扫描依赖 JIT 生成的 GC info，引用可被改写；Boehm 保守扫描无法区分整数与指针，移动对象会破坏"疑似指针"的数据。
5. regions 解决了 segments 的什么问题？ 要点：固定大小连续 segment 难以释放与跨代复用；regions 以小块为单位，代是块属性，晋升免拷贝，空闲块可归还 OS 或在 SOH 与 LOH 之间复用。
6. 你如何确认一段代码对 GC 的影响，而不是凭感觉？ 要点：前后差 `GC.GetAllocatedBytesForCurrentThread`、`CollectionCount`、`GetGCMemoryInfo().PauseDurations`；Unity 里用 Profiler 的 GC.Alloc 与 GC.Collect 标记。
