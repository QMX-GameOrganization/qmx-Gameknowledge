> 适用版本：以 .NET CoreCLR（.NET 8 左右）的实现细节为参照，同时标注 Unity Mono 与 IL2CPP 的差异。Unity 6 的 C# 语言版本为 9.0。涉及具体字节数时均以 64 位平台为准，未能核实的标"待核实"。

## 要点

- "值类型在栈上，引用类型在堆上"是错误的概括。正确说法是：值类型的实例**内联存放在包含它的位置**里，引用类型的实例总是在托管堆上，持有者只存一个指针。
- 值类型的位置取决于上下文：局部变量（栈或寄存器）、类的字段（内联在堆对象中）、数组元素（内联在数组对象中）、被装箱（堆上独立对象）、被闭包或状态机捕获（变成堆上对象的字段）。
- 赋值和传参对值类型是按字节拷贝，对引用类型只拷贝指针。大 struct 的拷贝成本是线性的，这是 `in`、`ref` 和 `readonly struct` 存在的原因。
- GC 只关心"含有引用的位置"。不含引用字段的 struct 数组对 GC 是一块无需扫描的内存，这是 `NativeArray`/`stackalloc`/`Span<T>` 思路之外，纯托管代码里降低 GC 压力的基础。
- 与 C++ 对照：C# 的 `struct` 对应 C++ 的值语义对象，C# 的 `class` 近似"永远通过指针访问、析构由 GC 决定"的 C++ 对象。C# 没有对象切片，也没有 `struct` 的继承。

## 值语义和存放位置是两件事

C# 语言规范定义的是**语义**：值类型变量直接包含数据，赋值产生独立副本；引用类型变量包含对象的引用，赋值产生别名。规范从没有规定"栈"和"堆"，那是运行时的实现选择。

实际实现里，一个值类型实例可能出现在下面这些位置：

| 场景 | 实际位置 | 说明 |
|---|---|---|
| 方法局部变量 | 栈帧，或被 JIT 放进寄存器 | 不逃逸时 JIT 可以把 struct 拆成字段分别放寄存器 |
| 类的实例字段 | 堆对象内部，紧跟对象头和 MethodTable 指针之后 | 随宿主对象一起分配和回收 |
| 数组元素 `T[]` | 数组对象的元素区，连续排列 | `Vector3[]` 就是一块连续的 12 字节元素 |
| 静态字段 | 类型的静态存储区（CoreCLR 中非 GC 引用的静态数据在单独的区域，含引用的在堆上的对象里） | 细节随运行时而异 |
| 装箱 | 堆上新分配的对象 | 见 1.2 节 |
| 被 lambda 捕获的局部变量 | 编译器生成的 display class（引用类型）的字段 | 局部变量从栈"升级"到堆 |
| `async`/迭代器里跨 `await`/`yield` 存活的局部变量 | 编译器生成的状态机的字段 | Release 构建中状态机是 struct，但被装箱到 Task 后位于堆上 |
| `ref struct` 与 `Span<T>` | 只能在栈上 | 语言层面禁止逃逸到堆 |

所以面试时被问到"值类型存在哪里"，应该回答"取决于它被谁持有"。

```csharp
struct Particle { public float X, Y, Z; public int Id; }   // 16 字节，不含引用

class Emitter
{
    Particle _last;           // 内联在 Emitter 对象里，不是独立对象
    Particle[] _pool;         // 引用在 Emitter 里，元素连续存放在数组对象里

    void Tick()
    {
        Particle p = _pool[0];   // 拷贝 16 字节到局部变量
        p.X += 1;                // 只改了副本
        _pool[0].X += 1;         // 通过数组元素的地址直接修改（ldelema）
    }
}
```

注意 `_pool[0].X += 1` 能生效，是因为 IL 里数组元素访问用的是 `ldelema`（取元素地址），不是拷贝。而对 `List<Particle>` 做同样的事情会编译错误：`List<T>` 索引器返回的是拷贝，不是引用。

## 引用类型的真实结构

x64 上的一个 CoreCLR 引用类型对象：

```
         ┌─────────────────────┐ -8
         │ ObjHeader (8 字节)  │   同步块索引 / thin lock / 哈希码位
引用 →   ├─────────────────────┤  0
         │ MethodTable* (8)    │   指向类型描述
         ├─────────────────────┤  8
         │ 字段 ...            │
         └─────────────────────┘
```

引用本身指向 MethodTable 指针的位置，对象头位于引用的负偏移处。所以一个"空"对象在 CoreCLR x64 上是 24 字节：8 字节对象头、8 字节 MethodTable 指针、8 字节最小字段区（GC 回收后需要把这块内存改造成"空闲对象"，因此有最小尺寸）。详见 1.4 节。

Unity Mono 的 `MonoObject` 与 IL2CPP 的 `Il2CppObject` 都是"类指针 + 监视器指针"两个字，即 16 字节头，没有 CoreCLR 那种负偏移的头部。三种运行时的头部大小不同，不要用一种的数字去回答另一种。

引用类型的三个后果：

1. **访问多一次间接寻址**。读 `obj.field` 需要先解引用，缓存不友好；对象散布在堆上时每次访问都可能缓存未命中。
2. **有分配和回收成本**。分配走 GC 的分配上下文（CoreCLR 是线程本地的 bump pointer，很快），代价主要在之后的回收与标记。
3. **相等性默认是引用相等**，赋值只拷贝 8 字节。

## 数组：struct 数组与 class 数组

`Particle[1000]` 与 `ParticleClass[1000]` 的差别是 ECS 和数据导向设计的核心动机之一：

| 对比项 | `Particle[]`（struct） | `ParticleClass[]`（class） |
|---|---|---|
| 内存 | 一块连续区域，1000 × 16 字节 | 1000 个引用 + 1000 个独立对象，分散在堆中 |
| 遍历缓存命中 | 顺序访问，预取友好 | 取决于分配顺序，通常差 |
| 分配次数 | 1 次 | 1001 次 |
| GC 扫描 | 元素类型不含引用时，GC 完全不扫描元素区 | 每个元素都是引用，都要标记 |
| 元素可为 null | 否 | 是 |

"元素类型不含引用时 GC 不扫描"来自 MethodTable 里的 GCDesc：只有 `ContainsPointers` 的类型才带有描述哪些偏移是引用的信息。Unity 的 Boehm GC 是保守式扫描，没有 GCDesc 这套精确信息，但对不含引用的类型 IL2CPP 会使用不需要扫描的分配方式（待核实具体 API 与版本）。无论哪种运行时，结论一致：把热数据做成不含引用的 struct 数组，GC 压力最小。

## 赋值和传参的 IL 与 JIT 视角

对值类型，IL 使用的是整块拷贝指令：

- `ldloc`/`stloc`：整个值入栈、出栈（语义上的拷贝）。
- `ldobj`/`stobj`/`cpobj`：通过地址读、写、拷贝整个值。
- `initobj`：`default(T)`、`new T()`（无参构造）通常编译成它，等于把内存清零。
- `ldloca`/`ldflda`/`ldelema`：取地址，用来避免拷贝，是 `ref` 局部、`in` 参数的基础。

JIT（以 RyuJIT 为例）对 struct 的处理：

- **Struct promotion（结构体提升）**：不逃逸、字段数不多的局部 struct 会被拆成独立的标量变量放进寄存器，几乎等同于零开销。经典限制是 4 个字段以内，较新的 .NET 版本放宽了这一限制（待核实具体版本）。Unity Mono 的 JIT 优化弱得多，不能假设有同等的提升。
- **调用约定**：x64 Windows 下，大小不是 1/2/4/8 字节的 struct 按引用传递（调用者先做一份拷贝再传指针）；System V（Linux/macOS）下，≤16 字节的 struct 可以拆进两个寄存器传递，更大的放栈上拷贝。返回大 struct 则通过调用者提供的隐藏返回缓冲区。这就是"超过 16 字节的 struct 按值传递变贵"的底层来源。
- **IL2CPP**：struct 被翻译成 C++ 的 `struct`，传值和 C++ 一致，由 clang/MSVC 等 C++ 编译器按平台 ABI 处理，不经过 CLR JIT。

### 实践经验

小 struct（不超过 16 字节，如 `Vector3`+一个 int、`int2`、`Color32`）按值传递没有问题。更大的 struct（如 4x4 矩阵 64 字节）作为参数用 `in`（只读引用），作为返回值用 `ref readonly` 或输出参数，避免反复拷贝。注意 `in` 参数配合非 `readonly` 的 struct 会触发防御性复制，反而更慢，见 1.3 节。

## 与 C++ 对照

| 概念 | C++ | C# |
|---|---|---|
| 值语义对象 | `struct`/`class` 均可，栈上或任意位置 | 仅 `struct`，不能继承类 |
| 引用语义对象 | 指针/`shared_ptr`/引用，生命周期自己管 | `class`，GC 管理 |
| 拷贝 | 拷贝构造/赋值运算符，可自定义，可 `= delete` | 按位成员拷贝，不能自定义（没有拷贝构造） |
| 移动语义 | 有（`std::move`、右值引用） | 无，靠 `ref` 或不拷贝 |
| 只读传递 | `const T&` | `in T` / `ref readonly T` |
| 对象切片 | 基类按值接收派生类会切片 | struct 不能继承，不存在切片 |
| 平凡可拷贝 | `std::is_trivially_copyable` | `unmanaged` 约束（不含引用的 struct） |
| 数组 | `T[]`/`std::vector<T>` 元素内联 | `T[]` 元素内联；`List<T>` 内部是 `T[]` |

重要差异：C++ 里 `Foo f;` 默认在栈上且有确定的析构时机，C# 的 `class` 没有；C# 的 `struct` 可以有 `Dispose` 但不会被自动调用（`using` 除外）。

## 常见坑

1. **"struct 一定更快"是错的**。大 struct 的拷贝、频繁装箱、防御性复制都会让 struct 比 class 更慢。选择依据是大小、是否可变、是否需要多态、生命周期。
2. **可变 struct 放进 `List<T>`/属性/`readonly` 字段后修改无效**，因为拿到的是拷贝。见 1.3 节。
3. **struct 里含 `string`/数组字段不等于"值类型的全部好处"**：它含引用，GC 仍要扫描，拷贝时只拷贝引用，内容共享。
4. **`default(T)` 与无参构造**：C# 10 之前 struct 不能声明无参构造函数（Unity 6 用 C# 9），`new T()` 与 `default(T)` 等价，所有字段为零值。数组分配出来的元素也一样是零值，不会调用任何构造函数。
5. **以为 lambda 捕获的是值**：捕获的是变量本身，而且会把该局部变量搬到堆上的闭包对象里，是隐藏的 GC.Alloc 来源（见第 6 章）。

## 面试追问

**Q：值类型一定在栈上吗？**
不是。局部变量可在栈或寄存器，类字段和数组元素内联在堆对象里，装箱后在堆上，被闭包或状态机捕获后成为堆对象的字段。反过来，引用类型对象在 CoreCLR 的新版本中，JIT 对不逃逸的对象有限地做栈分配（逃逸分析），在 Unity 的 Mono/IL2CPP 上没有这种优化（待核实具体版本）。

**Q：`struct` 和 `class` 作为数组元素，对 GC 和缓存各有什么影响？**
struct 数组是一次分配、连续存储，遍历缓存友好，元素不含引用时 GC 不扫描元素区。class 数组是引用数组加分散对象，遍历多一次间接寻址，GC 要逐个标记。

**Q：大 struct 作为参数传递，底层发生了什么？**
调用约定层面会产生一次拷贝（或按引用传递调用者做过的拷贝），大小越大越慢。用 `in` 可传只读引用，但 struct 必须是 `readonly struct`，否则编译器为保证语义会在调用成员时插入防御性复制。

**Q：为什么 struct 不能继承？**
值类型实例内联存放且大小在编译期固定。允许继承就会出现 C++ 的对象切片和虚调用时布局不确定的问题。C# 选择让 struct 只能实现接口，接口调用值类型需要装箱或 `constrained.` 调用。

**Q：C# 的 struct 与 C++ 的 struct 最大区别是什么？**
C# struct 没有自定义拷贝/移动/析构，不可继承，不能取到稳定地址（GC 可能移动对象，除非固定），含引用字段时会参与 GC 扫描。
