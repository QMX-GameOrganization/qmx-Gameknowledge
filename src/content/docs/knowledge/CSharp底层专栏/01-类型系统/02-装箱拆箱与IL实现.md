> 适用版本：IL 指令语义属于 ECMA-335，三种运行时一致；对象大小以 CoreCLR x64 为例；编译器行为以 Roslyn 为准，Unity 6 使用 C# 9.0 语言版本。标注"待核实"的条目依赖具体 Unity/Mono 版本。

## 要点

- 装箱 = 在托管堆上新分配一个对象（对象头 + MethodTable 指针 + 值的拷贝），并返回该对象的引用。拆箱 = 检查类型后取得指向盒内值的指针，`unbox.any` 再把值拷贝出来。
- 盒子里的值是**独立副本**。通过接口修改盒内值，不影响原变量。
- 装箱发生在值类型被当作 `object`、`ValueType`、`Enum` 或**接口**使用时，也发生在 `params object[]`、`string.Format` 这类 API 的参数上。
- 泛型约束 `where T : struct, IFoo` 配合 `constrained.` 前缀，调用接口方法不装箱，是写零分配泛型代码的基础。
- 在 Unity 里，装箱是最常见的 `GC.Alloc` 来源之一，要靠 Profiler 的调用栈和 IL 反编译确认，而不是凭印象。

## IL 层面：box、unbox、unbox.any

C# 代码：

```csharp
int i = 42;
object o = i;      // 装箱
int j = (int)o;    // 拆箱
```

对应的 IL（Release，示意，局部变量编号可能不同）：

```
ldc.i4.s 42
stloc.0
ldloc.0
box      [System.Runtime]System.Int32
stloc.1
ldloc.1
unbox.any [System.Runtime]System.Int32
stloc.2
```

| 指令 | 语义 |
|---|---|
| `box T` | 分配 T 对应的盒子对象，把栈顶的值拷贝进去，栈顶替换为对象引用 |
| `unbox T` | 检查对象的类型恰好为 T（盒子里的类型必须精确匹配），把栈顶替换为**指向盒内值的托管指针** `T&` |
| `unbox.any T` | 对值类型等价于 `unbox` 加 `ldobj`，即取指针再把值拷出来；对引用类型等价于 `castclass` |

拆箱的类型检查是精确的：`object o = 1; long l = (long)o;` 抛出 `InvalidCastException`，因为盒子里是 `int`，不能隐式提升。必须写 `(long)(int)o`。

`unbox`（取指针）在 C# 里几乎看不到，编译器仅在需要原地访问盒内值时使用，例如对装箱的值调用方法时用的 `unbox` + `call` 序列。

## 盒子在内存里的样子

```
         ┌─────────────────────┐ -8
         │ ObjHeader           │
引用 →   ├─────────────────────┤  0
         │ MethodTable* (Int32)│
         ├─────────────────────┤  8
         │ int value (4) + pad │
         └─────────────────────┘   合计 24 字节（x64 CoreCLR）
```

即使装箱的只是一个 `int`，CoreCLR x64 上也是 24 字节，而不是 4 字节。盒子的 MethodTable 就是值类型本身的 MethodTable，`box.GetType()` 返回的就是 `typeof(int)`。Unity Mono 与 IL2CPP 的头部是两个指针（16 字节），盒子大小为 16 字节头加值，再按分配粒度取整。

装箱的成本有三层：分配本身、值的拷贝、之后的回收。频繁装箱会导致 Gen0 GC 频繁触发（CoreCLR），或者推高 Unity Boehm GC 的堆增长与触发频率。

## 隐式装箱的来源

按出现频率排序。判断是否装箱的最可靠方法是看 IL 里有没有 `box`，在 sharplab.io 或 ILSpy 里一看便知。

1. **值类型赋给 `object`/接口**：`IComparable c = 5;`、`List<IFoo>` 里放 struct。
2. **接口方法调用通过非泛型路径**：`void Use(IFoo x)` 传入 struct，调用点必须装箱。
3. **`params object[]` 与 `string.Format(string, object)`**：`string.Format("{0}", intValue)`、`Debug.LogFormat`、`Debug.Log("x" + obj)` 中 obj 为值类型。
4. **字符串插值与拼接**：取决于编译器版本。Roslyn 在 C# 10 引入了插值字符串处理器（`DefaultInterpolatedStringHandler`），可避免装箱；Unity 6 的语言版本是 C# 9，插值字符串走 `string.Format` 或 `string.Concat` 降级，带格式说明符的位置通常会装箱。具体降级结果请看 IL（待核实，因 Unity 内置编译器版本而异）。
5. **`Enum` 相关 API**：`Enum.ToString()`、`Enum.HasFlag`（旧运行时会装箱；.NET Core 2.1 之后 JIT 对 `HasFlag` 做了内联优化，Unity Mono 上请自行验证，待核实）、`Enum.IsDefined`、`Enum.GetValues`。
6. **非泛型集合**：`ArrayList`、`Hashtable`、`IEnumerable`（非泛型）。
7. **泛型集合用枚举/struct 做 Dictionary 键且没有合适比较器**：旧版 Mono 的默认枚举比较器会装箱；新的 Unity 版本是否仍然如此，要实测（待核实）。见 1.5 节。
8. **`foreach` 的枚举器**：`List<T>` 的 `Enumerator` 是 struct，`foreach` 直接用不装箱；但通过 `IEnumerable<T>` 接口变量遍历，枚举器会被装箱（Unity 老版本 Mono 编译器对 `foreach` 本身也有装箱的历史问题，现代 Roslyn 已修复）。
9. **委托绑定 struct 的实例方法**：`Action a = myStruct.Method;` 会把 struct 装箱，委托持有的是盒子。
10. **`ValueType`/`Enum` 基类方法的默认实现**：`struct.Equals(object)`、`GetHashCode()`（未重写时），调用者需传 `object`。

```csharp
interface ICounter { void Inc(); int Value { get; } }
struct Counter : ICounter
{
    int _v;
    public void Inc() => _v++;
    public int Value => _v;
}

var c = new Counter();
ICounter boxed = c;       // 装箱：boxed 指向盒子里的副本
boxed.Inc();
Console.WriteLine(c.Value);       // 0，原变量没变
Console.WriteLine(boxed.Value);   // 1，改的是盒子
```

这是装箱最经典的面试题，根因是"盒子是独立副本，接口调用作用在盒子上"。

## constrained 调用：怎样不装箱地调用接口

泛型方法里调用 `T` 的方法，编译器无法知道 `T` 是值类型还是引用类型，因此发出 `constrained. T` 前缀加 `callvirt`：

```csharp
static int Bump<T>(ref T x) where T : struct, ICounter
{
    x.Inc();          // IL: ldarg.0; constrained. !!T; callvirt ICounter::Inc()
    return x.Value;
}
```

CLR 在 JIT（或 IL2CPP 在生成代码）时按 `T` 的实际类型决定：

- `T` 是值类型且**自己实现了**该方法：直接 `call` 它的实现，用 `ref` 传的地址作为 `this`，不装箱，也不会改到副本。
- `T` 是值类型但**没有实现**该方法（继承自 `object`/`ValueType` 的默认实现，如 `ToString`）：先装箱再 `callvirt`。
- `T` 是引用类型：解引用得到对象，再 `callvirt`。

对于值类型，每个不同的 `T` 会产生独立的机器码实例（泛型特化），所以 `Bump<Counter>` 内部被 JIT 内联成对 `Counter.Inc` 的直接调用，没有虚调用开销。这是"把策略写成 struct + 泛型约束"这种零开销抽象技巧的基础（类似 C++ 的模板策略类）。

```csharp
var c = new Counter();
Bump(ref c);   // 不装箱，c.Value 变为 1
```

## Nullable<T> 与装箱

`Nullable<T>` 的装箱规则特殊：有值时装箱成 `T` 的盒子（不是 `Nullable<T>` 的盒子），没有值时装箱结果是 `null` 引用。

```csharp
int? a = null;
object o = a;           // o == null，没有分配
int? b = 5;
object p = b;           // p 的运行时类型是 System.Int32
bool t = p is int;      // true
```

因此 `a.GetType()` 对 `null` 的 `int?` 会抛 `NullReferenceException`：先装箱得到 `null`，再调用 `GetType`。

## 枚举的装箱

枚举是值类型。`enum.ToString()` 要反射查名字表，一般会有分配（返回字符串）和缓存查询；`Enum` 的静态方法参数是 `Enum` 类型，传入要装箱。游戏里常见的做法是启动时把枚举到字符串的映射生成成静态数组或 switch，不在热路径里调用。

`where T : struct, Enum`（C# 7.3 起支持）约束让泛型代码能不装箱处理枚举，借助 `Unsafe.As` 或 `Convert` 技巧取底层整数；在 Unity 6 的 .NET Standard 2.1 API 里 `Unsafe` 类的可用性取决于是否引入 `System.Runtime.CompilerServices.Unsafe`（待核实）。

## Unity 里的验证方法

1. Profiler 的 CPU Usage 视图切到 Hierarchy，打开 Call Stacks（Deep Profiling 不是必须），按 `GC.Alloc` 列排序，定位到具体调用栈。
2. Memory Profiler 抓快照，看托管堆里 `System.Int32`、`System.Single` 等"不该出现为对象的类型"的实例数量。
3. 用 ILSpy、dnSpy 或 sharplab.io 看编译后的 IL，查 `box` 指令。IL2CPP 项目也可以看生成的 C++：搜 `Box(` 相关调用（`il2cpp_codegen_box`/`Box`，具体名称随版本变化，待核实）。
4. 在测试里用 `GC.GetAllocatedBytesForCurrentThread`（CoreCLR）；Unity Mono 上可用 `Profiler.GetMonoUsedSizeLong` 前后对比，或者 `ProfilerRecorder` 订阅 `GC Allocation In Frame Count`。

## 与 C++ 对照

C++ 没有装箱的概念，最接近的是"把值类型对象包进 `std::any`/`std::variant`/`shared_ptr<void>`"，同样需要堆分配和类型擦除。C# 的特殊之处是装箱在语法上是隐式的，容易无意触发。C++ 模板在编译期为每个类型生成代码，对应 C# 泛型对值类型的特化，二者都能内联到直接调用；C++ 的虚函数调用对应 C# 对 `ICounter` 变量的接口调用（需要装箱的盒子，且是间接调用）。

## 常见坑

1. **在 `Dictionary<TKey,...>` 中使用自定义 struct 键而不实现 `IEquatable<T>`**：每次查找 `Equals(object)` 都会装箱参数，还可能走反射。见 1.5 节。
2. **用 `object` 做事件参数或消息总线载体**：每次发消息装箱一次。改用泛型消息 `Publish<T>(in T msg)`。
3. **日志**：`Debug.Log($"hp={hp}")` 即使日志级别被关闭，格式化和装箱也已经发生。用 `[Conditional("UNITY_EDITOR")]` 包装，或先检查开关。
4. **拆箱类型必须精确**：`(long)(object)intValue` 抛异常。
5. **把装箱当成纯性能问题**：它还会造成"修改的是副本"这类逻辑错误，如上面的 `ICounter` 例子。

## 面试追问

**Q：装箱时底层发生了什么？**
在托管堆分配一个对象，写入 MethodTable 指针（值类型自己的），把值拷进对象的数据区，返回引用。x64 CoreCLR 上 `int` 盒子占 24 字节。拆箱先检查 MethodTable 是否为目标类型，然后取盒内值的地址（`unbox`）或再拷出值（`unbox.any`）。

**Q：如何调用 struct 的接口方法而不装箱？**
通过泛型约束 `where T : struct, IFoo` 调用。编译器发出 `constrained.` 前缀，运行时对值类型 `T` 直接调用其实现，不装箱，同时因为每个值类型实例化出独立代码，能被内联。

**Q：`object o = (int?)null` 的结果是什么？**
`null`。`Nullable<T>` 无值时装箱为 `null`，有值时装箱为 `T`。

**Q：怎么在 Unity 里定位隐式装箱？**
Profiler 看 `GC.Alloc` 的调用栈，Memory Profiler 查托管堆里异常出现的基础类型对象，再用反编译器看 IL 里的 `box`。不要仅凭源码判断，因为编译器版本会改变降级结果。

**Q：为什么 `foreach` 遍历 `List<T>` 不装箱，遍历 `IEnumerable<T>` 变量会装箱？**
`List<T>.GetEnumerator()` 返回 struct 枚举器，`foreach` 使用模式匹配直接调用，不经过接口。通过 `IEnumerable<T>` 引用拿枚举器，只能调用接口方法 `GetEnumerator()`，返回类型是 `IEnumerator<T>`，struct 枚举器要装箱成接口。
