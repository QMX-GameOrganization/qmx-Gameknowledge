> 适用版本：Dying Light 1.55.0.0，ANM2 `FormatVersion` 为 42。依据 `DL1/Notes/DL1动画格式逆向.md` 第一到三、九、十二节。结论是“结构解码通过”，不等于“与原引擎姿态完全一致”。

## 要点

- 一份 ANM2 是一组“轨道”，每个轨道对应一根骨骼（或特殊的运动轨），每一帧存 9 个分量：旋转 3、位移 3、缩放 3。
- 旋转不用四元数，而用 3 个分量的 Cayley 编码，解码时再还原成单位四元数。
- 轨道与骨骼的对应靠名字哈希，不存字符串。
- 压缩数据分页存放。解码器最容易出错的是页表边界，这是作者花了最多精力校准的地方。

## 容器头（32 字节）

| 偏移 | 类型 | 字段 |
| --- | --- | --- |
| 0 | char[4] | `ANM2` |
| 4 | u16 | FormatVersion，DL1 为 42 |
| 6 | u16 | SamplerVersion，样本为 1 |
| 8 | u16 | FrameCount |
| 10 | u16 | TrackCount |
| 12 | u16 | PageCount |
| 14 | u16 | PageOffset |
| 16 | u32 | DeclaredLength，等于文件大小 |
| 20 | u32 | DurationKeyCount |
| 24 / 28 | u32 | 未知，原样保留 |

头后面是 `TrackCount` 个 `u32` 轨道描述符，再是 `PageCount` 个 `u16` 页帧跨度。页大小 0x10000。

注意 `SamplerVersion`：6846 份动画里有 331 份是 sampler0，头布局完全不同（帧数在 0x0A，轨道数在 0x0E，全局 base 字节数在 0x10 等）。作者为它写了独立的布局与解码器，而不是把字段改成 1 当 v1 处理。理由写在笔记里：sampler0 是原引擎明确支持的九分量骨动画，原引擎结构证据在 `engine_x64_rwdi.c:153073..153135` 与 `152444..152651`。

## 每个轨道每帧 9 个分量

```text
rotX rotY rotZ   // Cayley 向量
posX posY posZ   // 位移
sclX sclY sclZ   // 缩放
```

Cayley 向量到单位四元数：设 `s = x² + y² + z²`，则

```text
q.xyz = 2·r / (1 + s)
q.w   = (1 − s) / (1 + s)
```

可以直接验证它输出的是单位四元数。笔记里一个处决样本的运动轨旋转 Cayley = (0.00157073, 0.9984304, −0.0015708)，代入得到 (0.00157, 0.99999, −0.00157, 0.00157)，范数为 1，几乎是绕 Y 轴转 180 度。

```python
def cayley(x, y, z):
    s = x*x + y*y + z*z
    return (2*x/(1+s), 2*y/(1+s), 2*z/(1+s), (1-s)/(1+s))   # 单位四元数 (x, y, z, w)
```

由公式可推出 `w = cos(θ/2)`，所以 `|r| = tan(θ/4)`：旋转 180 度时 `|r| = 1`，上面样本的 0.9984 正是如此；`|r|` 只在 360 度才趋于无穷。用 3 个数表示一个旋转，没有冗余的归一化约束，适合压缩。这段推导是本专栏自己做的，笔记只给了公式；笔记也没有讨论为什么选 Cayley 编码。

## 轨道到骨骼：名字哈希

骨名不存字符串，用一个 32 位哈希：

```text
v = 0
对名称每个字符：小写后 v = (byte)c + 41 * v     // uint32 回绕
```

```python
def name_hash(name: str) -> int:
    v = 0
    for c in name.lower().encode("ascii"):
        v = (c + 41 * v) & 0xFFFFFFFF
    return v
```

实测：Jade 的 206 根骨骼名与 60 条轨道比对，命中 59 条；跑步样本 74 条轨道中 71 条唯一命中 Jade 的 entity。

没命中的轨道不是错误，而是特殊轨：

| 描述符 | 含义 |
| --- | --- |
| `0xCCC3CDDF` | MotionAccumulator（根运动累积），不能按骨名哈希处理 |
| `0x33D38632`、`0x9947260D` | 未识别，保留在产物元信息里 |
| `0x4723D1BD` | 另一条恒定定位轨，真实名字未证实，不匹配双方骨名，不重复应用 |

本专栏用上面的哈希对字符串 `MotionAccumulator` 做了计算，结果是 `0x9AE6877E`，不等于 `0xCCC3CDDF`。这印证了笔记的提醒：这条轨“不能对特殊轨直接套普通小写骨名 hash”，它是靠别的证据识别的，具体怎样识别笔记没有展开。

## 页表：最容易出错的地方

压缩数据分页，页内有一张表。笔记总结的规则，是在一次失败里修出来的：

- 页表长度严格等于 `firstWord × 8` 个 `u16`，**不能强行读至少 16 项**。否则首字为 1 的有效表之后会误读校准数据。
- 常量页（`packedCount = 0`）里，`index ≥ 2` 的压缩 slot 允许 `start = end`，校准区 `table[0]` 到 `table[1]` 仍要严格递增。
- 有压缩分量时 slot 必须非空，masks 的直接分量计数与有限浮点数独立验证。
- 最后一个终点可以是 4096（对应 65536 字节页末），中间 slot 不能是 4096，任何表项都不能大于 4096。

这些规则是用损坏负例反推出来的：降序、基础区重复、正 packed 空 slot、中间 4096、终点 4097、截断、count/mask 为 NaN、缺终点。

## 可信度怎么建立

| 验证 | 结果 |
| --- | --- |
| 全库审计 | 6846 份 ANM2、共 1,277,889 个整数帧，全部九分量为有限值，并记录原文件与解码 float32 的 SHA256 |
| 旧实现 vs 修正页表 | 通过数从 5926 升到 6515，新增 589；原 5926 与中间 6443 的解码哈希均未变化 |
| sampler0 | 331 份、76,988 帧，独立 C# 与独立 NumPy 按位 8 lane 解码，二阶预测积分，float32 乘加逐字节一致；跨 slot/page 边界的 889,824 个分量差为 0 |
| 损坏负例 | 12 个真实损坏样本全部被拒绝 |
| 局限 | sampler0 的小数时间插值没有原引擎 oracle，`Sample` 非整数明确 `NotSupported`，不猜插值 |

另有一项很重要的反例：一个“合法但被改过的位流”被解码器接受了，并且输出哈希改变。作者的结论是：解码器不能替代可信来源的 SHA 完整性。也就是说，解码成功不等于数据可信。

## 性能测量

多页 300 帧 74 轨的样本，对首、中、末整数帧做 `Sample`：约 211 到 247 微秒，每次当前线程托管分配 146,152 字节。作者没有虚构性能通过阈值，只记录实测。这个分配量对每帧调用不友好，读者若要做运行时版本，应缓存解码后的 slot，而不是每次分配。

## 值得学的点

- **旋转压缩用 Cayley 三元组**，解码公式简单，可单位化验证。
- **名字用哈希，查找用一次性表**。运行时不比较字符串。
- **边界规则从负例中提炼**。每条页表规则都对应一类损坏样本，这样规则不是拍脑袋。
- **统一的审计管线**。全库扫描、哈希记录、旧新结果对比，改了解码器就能回归。

## 常见坑

- 把 `SamplerVersion` 当作可随意改写的字段。
- 把整数帧解码当成完整播放：小数时间插值、原 FPS、最终游戏姿态都是另外的问题。
- 从 `m_melee_fighter_a_run_loop_01` 的 37 帧推断“循环不含端点”。笔记指出 37 帧包含循环端点，视频每圈使用前 36 帧。
