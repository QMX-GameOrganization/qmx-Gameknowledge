> 适用版本：Dying Light 1.55.0.0。本章讲方法与结构，具体例子在后续各章展开。

## 要点

- 数据驱动的引擎里，同一个字段会被多处代码以不同方式读取。声明只说明“有这个参数”，行为在消费它的函数里。
- 这套逆向资料把每个机制拆成三块：**声明**（Data0）、**消费者**（反编译函数）、**教学实现**（C# 内核）。三块分开存放、分开验证。
- 好的代码设计也遵循同一原则：数据提供方和数据使用方只通过一个窄接口交换快照，各自可以独立替换。

## 一个字段的三重身份

以玩家的 `StairHeight(0.51)` 为例：

| 层 | 内容 | 证据等级 |
| --- | --- | --- |
| 声明 | `walk_player.phx` 里写了 0.51，通用默认是 0.35 | ① 原声明 |
| 消费者 | 脚本回调经 Walk 槽 `+0x320` 写入对象 `+0xac0`；核心根据接触高度与前进方向决定是否抬高向上速度 | ② 静态消费核对 |
| 教学实现 | 教学内核只记录已定位的分支结论，不声称完整台阶系统已还原 | 明确边界 |

如果只看第一行，会以为“台阶高度 0.51 米，低于它的台阶都能上”。第二行说明它并不是简单的高度阈值，而是进入一个根据接触高度和速度决定的辅助分支，其实际执行方式是调整物理体速度，不是直接改 Transform。

## 枚举同步是数据与代码的契约

`.def` 文件的头部有两条原话：

```text
//Keep this synchronized with EAIMainGoalRule enum!
$ShouldDie                         (i, 3)
...
//keep synchronized with EModuleType
$ZOMBIE_LOGIC_MODULE        (i, 37)
```

这说明脚本侧的数字 ID 与 C++ 枚举必须一一对应。这对逆向有两个后果：

- 在二进制里能用同一个 ID 找到“名称表”。教材里就是用 `0x18009faf0` 的名称 getter（输入减一后索引 77 项表）把函数与规则名对上的。
- 不同版本的枚举数值不能直接平移。教材举过例子：当前版本 `BlastDamageMul = 0x106`、`MaxHealth = 0x2be`，而旧反编译里的数字 ID 不能套这份枚举，更不能拿 `0x104` 在两个版本里互相指代。

## 窄接口：提供者与接收者

运动提交是最干净的例子（详见 4.1）。游戏层并不直接改物理体，而是提交三项数据：期望世界速度、加速度标量、减速度标量。教学版把它写成一个只读快照加一个接口：

```csharp
public readonly struct MotionRequest
{
    public Vector3 WorldVelocity { get; }
    public float Acceleration { get; }
    public float Deceleration { get; }
    // 构造函数略
}

public interface IMotionReceiver
{
    void Submit(MotionRequest request);
}
```

要点在设计意图里：

| 代码 | 目的 |
| --- | --- |
| `readonly struct` 与只读属性 | 一次请求是不可变快照，构造后不能逐项修改 |
| `IMotionReceiver.Submit` | 发送方只依赖提交契约，物理后端查证后可以替换 |
| 提供方 `BuildRequest` | 决定“想要什么”；接收方决定“怎么作用到实际运动” |

教材还特意注明：接收到请求不等于实际达到该速度。这正好对应原作的分层：玩法层提交目标，物理层经加减速、接触、台阶辅助之后才得到真实速度。

## 值得学的点

- 在自己的项目里也把配置、消费、验证分三处存放。配置里的值只代表“设计师想要”，不是运行时结论。
- 给跨版本或跨模块使用的枚举写明“与某某同步”的注释，并在加载时校验数量。
- 让接口只传值不传引用：快照类型（值类型、只读）可以在帧间缓存、回放、做单元测试。

## 常见坑

- 用声明值做数值推理。比如把 `WalkAcceleration(-1)` 当作“加速度为 -1 米每二次方秒”，会得到荒谬的结论，实际是“跳过限速阶段”的标记。
- 在多个版本的反编译文本里按偏移互相对照。教材多次强调：原反编译与当前 DLL 的地址布局分别记录，不互相套偏移。
