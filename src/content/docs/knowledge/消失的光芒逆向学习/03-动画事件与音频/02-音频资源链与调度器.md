> 适用版本：Dying Light 1.55.0.0，只覆盖四个核心效果银行 `all_in_maps_1/2/3/persistant.csb`（共 5107 个样本）。不涉及音乐、对白与 DLC。依据 `DL1/Teach/Audio/音频资源与事件链教学.md`。

## 要点

- 声音资源链是：银行 `.csb` → 单样本 FSB5（Vorbis 编码）→ 用游戏自带的 `fmodex64.dll` 解码成 PCM → 脚本里的 `SoundGroup` 把样本组织成可随机选择的组。
- 导出的 PCM 是最终声音的输入，不是最终混音。随机变体、音调变化、距离衰减、遮挡、总线、HDR 都在运行层。
- 调度器的任务是“在动画时钟跨过事件帧时发出声音”，和 3.1 的事件时钟同一个思路，但这里更强调**零分配**。

## CSB 银行的结构

四个银行共同的结构经过全表校验：

| 位置 | 字段 | 说明 |
| --- | --- | --- |
| 0..63 | 零字节 | 四银行逐字节验证 |
| +64 | u32 表偏移 | 均为 76 |
| +68 | u32 条目数 | 分别 1636 / 967 / 1458 / 1046 |
| +72 | u32 | 未解释，保留原值 |
| 每条 +0 | 64 字节零结尾 ASCII 名称 | 原样保留 |
| 每条 +64 / +68 | u32 内容偏移 / 长度 | 全表逐段连续，完整覆盖银行 |
| 每条 +72..87 | 四个 u32 | 含义未证明 |

每个条目含一个单样本 FSB5 版本 1，编码 15（Vorbis）。解析器检查 `60 + sampleHeadersSize + nameTableSize + encodedDataSize == 条目内容长度`，并检查 FSB 样本头 `uint64` 高 30 位的帧数（`sampleHeader >> 34`）与 FMOD 解码出的帧数一致。这里的“帧”是每声道同一时刻的一组采样，和视频帧无关：

```text
PCM 字节数 = 音频采样帧数 × 声道数 × 每样本字节数
时长秒数 = 音频采样帧数 ÷ 采样率
```

例：`bone_break_01` 解为单声道 PCM16、48000 Hz、20944 帧，即 41888 字节、0.436333 秒。

## 为什么不用 ffmpeg

本地 ffmpeg 直接打开这种 FSB 会报 `Not yet implemented in FFmpeg, patches welcome`。作者没有绕过断言，而是把这条失败记进 `first_errors.json`，改用游戏自带 `fmodex64.dll`，通过 `ctypes` 调原生接口：

```text
System_Create → SetOutput(NOSOUND) → Init
  → CreateSound(CREATESTREAM | OPENONLY) → GetSubSound(0)
  → GetFormat / GetLength / GetDefaults → ReadData
  → Sound_Release → System_Release
```

细节：`OPENONLY` 避免打开流时预读造成开头缺失；`ReadData` 取解码后的 PCM；`GetLength(PCMBYTES)` 给读取预算；每个返回值都检查，非零立即带操作名报错。接口接收 ANSI 文件名，所以输出目录里用 ASCII 相对路径并恢复调用前的工作目录。解码器路径、SHA256 与真实版本都写入清单，不下载外部二进制。

## 脚本层：名字不是最终混音

`scripts/audio/hdr_snd_groups.scr` 声明 `SoundGroup`，组内的 `Sound` 是具体样本名；组属性包括 Volume、Bus、MinDistance、MaxDistance、RollOff、PitchRange、实例上限。例如 `walker_male00_idle_calm` 含六个男性丧尸待机样本，`beretta_shot` 含三个开火变体。所以“一个事件播放一个 WAV”是错误的理解：事件播放的是组，组选变体。

匹配规则也是个小工程：ASCII 大小写归一，优先完整名称；只有未匹配具体样本且以 `.wav` 结尾时才去掉后缀，因为银行里确实有名称本身含 `.wav` 的条目，不能无条件去后缀。脚本存在混合文本编码，索引用 Latin-1 做可逆字节视图读取 ASCII 结构符号，既不丢弃非法字节，也不声称注释的原编码就是 Latin-1。

## 动画事件与音频时间换算

事件帧相对当前 SeqTrack 片段起点。展示视频的源范围是 2..45（背后处决）与 0..62（肘击），换算为：

```text
源动画帧   = SeqTrack 起始帧 + 局部事件帧
视频时间   = (源动画帧 − 视频首源帧) ÷ 30
音频放置帧 = 视频时间 × 48000
```

背后快速处决的三个声音落在 0.1 / 0.6 / 0.8 秒，肘击落在 0.2 / 1.1 秒。注意 `GIVE_GRAB_DAMAGE` 不是声音事件，不要把它的帧误当声音帧。

## 教学调度器 AudioEventScheduler

```csharp
public void Advance(double TargetFrame, List<ScheduledSound> OutputList)
{
    if (!double.IsFinite(TargetFrame) || TargetFrame < PlaybackFrame)
        throw new ArgumentOutOfRangeException(nameof(TargetFrame));
    OutputList.Clear();
    int FirstCycle = Loop ? Math.Max(0, (int)Math.Floor(PlaybackFrame / ClipFrameCount)) : 0;
    int LastCycle  = Loop ? (int)Math.Floor(TargetFrame / ClipFrameCount) : 0;
    for (int Cycle = FirstCycle; Cycle <= LastCycle; Cycle++)
        foreach (var Event in EventList)
        {
            double EventFrame = Cycle * (double)ClipFrameCount + Event.Frame;
            if (EventFrame > PlaybackFrame && EventFrame <= TargetFrame)
                OutputList.Add(new ScheduledSound(EventFrame, Event));
        }
    PlaybackFrame = TargetFrame;
}
```

要点：

- 条件是 `上一时钟 < 事件时钟 <= 当前时钟`，与 3.1 同源。更新从第 14 帧直接跳到 22 帧也不会漏掉 15 和 21 的事件。
- 循环 clip 使用持续递增的播放时钟，每圈的事件时钟是 `圈序号 × 帧数 + 局部帧`，多圈更新也按序分发。
- `Seek` 只设置时钟，不追放被跳过区间的旧声音；反向播放必须显式 `Seek` 并另行定义事件语义。
- 调用方**预建并复用**输出 `List`。`Advance` 清空后写入本次事件，避免每帧创建集合与数组。教材实测 50,000 次推进期间当前线程托管分配为零。事件最多时仍可能扩容，应在初始化阶段按预算预留容量。

## 值得学的点

- **资源链分层写成独立步骤**：容器解析、解码、脚本关联、预览合成各一个脚本，每步输出带哈希的清单。
- **失败的工具链保留为证据**，再换方案，而不是悄悄换掉。
- **音频调度用输出缓冲区参数**而不是返回新数组，这是 Unity 里常见的无 GC 写法，对应 C# 底层专栏的“隐藏分配”。

## 常见坑

- 把导出的单个 WAV 当成游戏里实际听到的声音。
- 条件写成 `当前帧 == 事件帧`，会在掉帧时漏声音。
- 对循环 clip 只检查本圈内的事件，一次跨多圈时会漏。
- 把 `GIVE_GRAB_DAMAGE` 的帧误作声音事件帧。

## 练习

1. 给片段增加两个同帧声音，检查两个都触发，顺序稳定。
2. 更新故意按 0 → 4 → 17 → 40 跳跃，验证结果与逐帧推进一致。
3. 修改片段裁切起点，检查源帧与局部帧的转换，而不是直接改音频素材时长去掩盖错误。
