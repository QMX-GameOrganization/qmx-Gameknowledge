> 适用版本：Dying Light 1.55.0.0。依据 `DL1/Teach/Logic/进阶教学.md` 第 8 节与 `QuestGraph.cs`。AND/OR 的**结构**有原证据；同一 Tick 内的调度顺序、OR 取消副作用、父任务激活、存档恢复没有实测，属于教学策略。

## 要点

- 一个任务是一串阶段，阶段有类型（`started quest guard`、`go to`、`wait`、`talk`、`checkpoint`……），还可以嵌套 `AND`/`OR` 组合，组合里有多条路径，每条路径又是一串阶段。
- 三种节点就够了：**叶节点**（真正等待或执行）、**顺序节点**、**并行节点**（AND/OR）。
- 叶节点是任务系统与游戏世界之间的边界：它只传原阶段数据给宿主，由宿主决定如何查询世界。

## 数据：以 Voltage 为例

`quests/slums/slums_sq_voltage_quest.xml`：

```xml
<Quest name="__Voltage_helper_02" parent="AirDrop02" pxsl_line="17">
    <Phase type="started quest guard" name="_" quest_name="AirDrop03" finished="true" pxsl_line="18" />
    <Phase type="go to" name="Voltage - Helper 02 - Blake" distance="10000" show_locations="false">
        <Destination>
            <QuestObject class="SpawnPoint" name="QuestHelper_SP_Blake" />
        </Destination>
        ...
```

教材选中该任务的四个根阶段：`started quest guard`、`go to`、`OR`、`checkpoint`。`OR` 下有两条路径：`talk(Blake)` 与 `started quest guard(Voltage)`。组合类型定义在 `quests/_underlay/phases_struct_defs.xml`（`AND` 在第 3 行，`OR` 在 12 行附近）。

一个小细节：节点上的 `pxsl_line` 是源生成信息，不是当前文件的行号。教材用 XML 解析器给出的真实行号，避免引用错位。另一个细节：`phases_struct_defs.xml` **不完整**（例如没有 `started quest guard`），所以不能靠这份文件的缺项推断游戏不支持某种阶段类型。

## 教学实现

```csharp
public interface IQuestLeafHost { bool ExecuteOrCheck(QuestPhase Phase); void Cancel(QuestPhase Phase); }
public interface IQuestNode     { bool Tick(); void Cancel(); }

LeafNode:      未完成且未取消时 Complete = Host.ExecuteOrCheck(Phase); 完成后不再执行
SequenceNode:  while (Next < N && Nodes[Next].Tick()) Next++;  return Next == N;
ParallelNode:  AND → 每条路径都 Tick，全部完成才算完成
               OR  → 按声明顺序 Tick，第一个完成者胜出，取消其余路径
```

| 类型 | 设计意图 |
| --- | --- |
| `IQuestLeafHost` | 世界查询、对话、传送、检查点等语义由宿主实现；节点只传原 `Phase` 数据 |
| `LeafNode` | 等待条件可跨 Tick 查询；完成后记住结果，已完成动作不重复 |
| `SequenceNode` | 当前阶段完成后推进；同一个 Tick 内允许连续完成多个即时阶段 |
| `ParallelNode AND` | **每条路径都更新**，不能用短路的 `All`，否则后面的路径永远不更新 |
| `ParallelNode OR` | 教学策略按声明顺序更新，任一路径完成立即取消其他等待路径 |
| `Cancel` | 停止推进并通知活动叶节点；清理对话/交互等待由宿主负责 |

AND 那一行是个典型陷阱。下面两种写法行为不同：

```csharp
// 错：All 短路，第一条没完成就不再 Tick 后面的路径
Complete = NodeList.All(Node => Node.Tick());
// 对：先全部 Tick，再判断
Complete = NodeList.Select(Node => Node.Tick()).ToArray().All(V => V);
```

## 自测（教材）

- 初始前置为 false 时，`go to` 不执行；
- 前置完成后到 `OR` 等待；
- `Voltage` 条件完成可结束并取消谈话等待；
- 重复 Tick，`checkpoint` 仅执行一次；
- 另构造 AND 测试，必须两边都完成；
- 未知叶接口抛异常。

## 故障策略（教学宿主工程设计）

后续的叶课程补充了一条终止故障策略：宿主完成回调若已经产生副作用后抛异常，保存并原样重抛首个错误；后续 Tick 不重做回调；允许 `Cancel` 停止该叶。教材明确这**不是原引擎异常策略**，也没有通用回滚，不会撤销宿主已经提交的副作用。

## 值得学的点

- **三种节点覆盖大多数任务/行为树需求**，并且都只有 `Tick` 与 `Cancel` 两个操作。
- **叶节点把世界访问隔离到宿主接口**，图本身不依赖具体游戏对象，因而可以脱离游戏测试。
- **AND 要全部更新**，这是“并行”与“短路”之间的常见坑。
- **幂等**：完成后不再执行，取消后不再推进，重复取消无害。

## 常见坑

- 把取消当作回滚。取消只停止等待，不撤销已发生的副作用。
- OR 取消其它路径的时机与原引擎不一定一致，不能据此声称还原了原调度。
- 以为 `talk`、`checkpoint` 就是个返回 true 的小动作（见 7.2）。
