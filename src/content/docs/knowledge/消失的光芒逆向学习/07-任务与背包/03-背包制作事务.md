> 适用版本：Dying Light 1.55.0.0。依据 `DL1/Teach/Logic/进阶教学.md` 第 7 节与 `CraftingInventory.cs`。教学背包每种物品只保留一个聚合堆叠，多格背包、随机词条、存档、维修提交均未实现。

## 要点

- 制作要么完整成功，要么背包完全不变。不能出现“扣了材料但产物放不下”。
- 实现手法：**在一份候选副本上完成所有扣除与加入，所有约束都通过后，用一次赋值替换真实库存**。
- 配方里的某些数值语义没有证实，教学代码不猜，而是让调用方显式注入“产量策略”。

## 原声明

`collectables.scr` 里的医疗包蓝图：

```text
Item("Craftplan_MedKit_Large_Healing", CategoryType_Collectable)
{
    RequiredItem("Craft_Alcohol", 1);
    RequiredItem("Craft_Gauze", 1);
    CraftedItem("Medkit_HealthPackLarge", 1, 2);
    ...
}
```

`inventory.scr` 里的物品定义：酒精和纱布的 `MaxStackCount` 都是 999999，医疗包是 99。教材原样使用这些数据，不改成“看起来更合理”的常用堆叠上限。`CraftedItem(…, 1, 2)` 的两个数原样保存，本轮没有查证它们与普通/升级产量的关系。

## 实现

```csharp
public bool TryCraft(RecipeDefinition Recipe, int Batches, Func<RecipeOutput, int> YieldPolicy)
{
    if (Batches <= 0) throw new ArgumentOutOfRangeException(nameof(Batches));
    int Yield = YieldPolicy(Recipe.Output);
    if (Yield <= 0) throw new InvalidOperationException("产量策略必须明确返回正数量");

    var CandidateDict = new Dictionary<string, int>(CountDict);          // 候选副本
    foreach (var Group in Recipe.IngredientList.GroupBy(Item => Item.Id))   // 同名材料合并
    {
        int Required = checked(Group.Sum(Item => Item.Count) * Batches);
        if (Required <= 0) throw new InvalidDataException($"配方数量不合法 {Group.Key}");
        int Existing = Count(Group.Key);
        if (Existing < Required) return false;                          // 材料不够：库存未动
        CandidateDict[Group.Key] = Existing - Required;
    }
    int OutputCount = checked((CandidateDict.TryGetValue(Recipe.Output.Id, out int Current)
                               ? Current : Count(Recipe.Output.Id)) + checked(Yield * Batches));
    if (OutputCount > DefinitionDict[Recipe.Output.Id].MaxStackCount) return false;   // 放不下：库存未动
    CandidateDict[Recipe.Output.Id] = OutputCount;
    CountDict = CandidateDict;                                          // 唯一提交点
    return true;
}
```

逐处设计意图：

| 位置 | 意图 |
| --- | --- |
| 构造函数 | 复制初始库存和物品定义，校验每个单堆叠数量不超上限 |
| `Count` | 已定义且未持有返回 0；**未定义物品明确失败**，不混淆两种情况 |
| `YieldPolicy` | 调用方明确决定产量；课中测试选择原第一参数，但这是教学策略，没有偷偷猜两个数的语义 |
| `CandidateDict` | 在独立数据上扣材料、加产物，失败时不替换真实库存 |
| `GroupBy(Id)` | 合并同一物品的多个需求，避免分散检查导致总消耗超出持有量 |
| `checked` | 批次乘法和产量加法溢出报错，不能溢出成负数绕过上限 |
| `CountDict = CandidateDict` | 所有约束通过后只有一个提交点 |

`GroupBy` 的必要性举例：配方列了两行“铁 2”，库存只有 3。逐行各检查一次“有 2 个”都会通过，但总需求 4 个超出，只有合并后才暴露。

## 自测（教材）

- 做一批后材料各减 1，医疗包增加 1；
- 材料不够时库存完全不动；
- 已有 99 个医疗包时制作失败且不消耗材料；
- 把产量策略改成 `int.MaxValue` 应当溢出，且没有半提交。

## 事务的两种常见写法

| 写法 | 优点 | 代价 |
| --- | --- | --- |
| 候选副本 + 单点替换（本章） | 实现简单，任何失败都零副作用 | 需要拷贝；库存很大时有成本 |
| 先检查后修改（两阶段） | 无拷贝 | 检查和修改之间的状态不能变；检查逻辑要与修改逻辑保持一致，容易漂移 |

教学背包只有少量物品，拷贝的成本可以忽略。如果真实库存有成千上万条目，可以改成“记录补丁列表，全部校验后再应用”，思路相同。

## 值得学的点

- **单一提交点**：所有修改汇聚成一次赋值，把“失败路径”的复杂度降到零。
- **溢出检查**：背包、经济系统是溢出漏洞的重灾区，用 `checked` 或饱和运算。
- **不确定的数据通过注入策略解决**，而不是写进常量。
- **合并同类项再检查**，避免“分别通过但总量超标”。

## 与已有笔记的联系

这个“先在副本上算，再一次性提交”的做法，与 ECS 学习专栏“06 系统与时序”里“先接收/锁定输入，再按固定阶段统一推进”的思路相近：目的都是不让半途状态被其他系统观察到。

## 常见坑

- 一边扣材料一边检查产物容量，失败时已经扣掉了材料。
- 对同一种材料的多条配方行分别检查。
- 把 `CraftedItem` 的第二个整数当作产量。
- 用 `int` 累加大量批次，静默溢出为负数。
