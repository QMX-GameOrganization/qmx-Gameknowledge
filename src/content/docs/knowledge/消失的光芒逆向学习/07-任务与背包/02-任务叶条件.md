## 要点

- 教材把 3,219 个声明（595 个 guard、1,572 个 go to、1,052 个 wait）里的 3,207 个成功编译成叶谓词，12 个因为含 `complete_challenge` 被明确拒绝。
- 其余 67 种阶段类型没有实现，遇到就抛“未支持”，不假装。
- 三个叶谓词都很小，但每个都有一个容易写错的细节。

## started quest guard：两道门

任务状态有三个值：0 未开始、1 进行中、2 已完成。三个布尔标志 `started`、`finished`、`started_but_not_finished` 组合出判定：

```csharp
bool RequiresNonzero = Started || StartedButNotFinished;
if ((State != 0) != RequiresNonzero) return false;                        // 第一道门：是否开始
return Finished ? State == 2 : !StartedButNotFinished || State != 2;      // 第二道门：完成状态
```

本专栏用这段表达式复算了教材的真值表：

| 组合（started / finished / started_but_not_finished） | 状态 0 | 状态 1 | 状态 2 |
| --- | --- | --- | --- |
| true / false / false | false | true | true |
| true / true / false | false | false | true |
| true / false / true | false | true | false |
| false / false / false | true | false | false |
| false / true / false | false | false | false |

结果与教材一致。结论有一条很反直觉：**`finished=false` 本身并不排除已完成任务**（第一行状态 2 为 true）。要“已开始但未完成”，必须用 `started_but_not_finished`。

原生函数链：RTTI 类 `FUN_1812d6370` → `FUN_180dd97e0`，字段绑定 `quest_name +0x90`、`started +0xA0`、`finished +0xA1`、`started_but_not_finished +0xA2`；真正的判断在 `FUN_180dd9ef0`（`gamedll_x64_rwdi.c:1576339`），读目标 virtual `+0x88` 的状态。

构造器 `FUN_180dd9cb0` 明确把 `started` 初始化为 true，另外两个布尔从原全局读取，静态初值未查证。所以接口强制传入 `QuestGuardDefaults`，教材宿主显式选择 false/false，不伪装为已验证的原默认值。

## go to：有符号半径

```csharp
return (Radius >= 0) == (Math.Abs(Radius) - Distance >= 0);
```

| 半径 | 含义 |
| --- | --- |
| 正 | 距离 ≤ 半径才通过（到达） |
| 负 | 距离 > |半径| 才通过（离开） |

本专栏复算：半径 2、距离 2 通过；半径 −2、距离 2 **不通过**（严格大于）；半径 −2、距离 3 通过。**用一个符号位复用同一字段表达“到达”和“离开”两种语义**，既省字段，又保证两者在边界上互斥。

细节：普通目标分支读双方世界位置算三维距离；区域目标分支使用区域虚函数提供的距离，涉及有效性与内外部结果，所以接口用显式 `QuestDestinationMetric`，不强行当成欧氏距离。原判断缺失目标时可能走直接完成分支，教学选择 **fail fast**：未绑定的真实关卡对象抛异常（这是教学选择，非原行为）。`distance=0` 会在激活时读目标默认半径，宿主必须显式绑定 `DefaultRadius`。

## wait：本地游戏时钟

```csharp
StartTime = World.GameTime;                                       // 激活时记录
bool Expired = Duration - (World.GameTime - StartTime) < 0;       // 严格小于
```

- 剩余时间 = `duration − (now − start)`，**严格 < 0** 才算到期。`duration=0` 在激活同刻剩余为 0，不完成，后续时间为正才结束。本专栏验证：duration 5，在 5.00 时不到期，5.01 到期。
- 原 XML 有 18 条零时长和 1,034 条正时长 wait；负时间没有真实样本，工具明确拒绝，不静默归零。
- 完成 gate 由宿主以 `IsWaitCompletionAllowed` 提供；gate 关闭期间时钟继续前进，重新打开时沿用原 start，不重新倒计时。游戏暂停靠宿主停止推进 `GameTime`。
- 取消处理器析构本地 watch；教学核把 watch 字段内联进叶，用 `WatchActive`/`WatchReleaseCount` 验证“启用/关闭只一次”。

教材实测：已激活的 local wait 50,000 次 Tick 在 .NET 10 上托管分配为 0。

## checkpoint 与 talk：停在边界外

| 阶段 | 为什么没实现 |
| --- | --- |
| checkpoint | `FUN_180dc52c0` 登记当前 checkpoint 并保存先前引用；`FUN_180dc55f0` 在三个引用有效等条件下恢复先前引用；涉及任务层级、checkpoint 历史和世界处理器，不是“返回 true 并写存档” |
| talk | `FUN_180db70d0` 并非对话完成的 bool：它查询 group、speaker、可用 dialog、NPC 与玩家状态；`FUN_180db9d90` 配置临时标志与 dialog manager，还可能进入 `FUN_180e001f0`；有还原 NPC 标志、清理提示的路径 |

教材的判断：继续机械抄虚函数调用没有足够收益，现有本地 DLL 的相关地址与反编译文本不一致，需要旧版本 vtable/对象布局和世界服务。于是保留原 Destination 并抛未支持。

## 激活与完成链

`FUN_180d15440`（`:1462867`）在定义存在且状态为 0 时，经 `FUN_180d165c0` 写状态 1，再调根 phase virtual `+0x508`；父指针不存在且 virtual `+0x28` 不允许时提前返回。`FUN_180d15950`（`:1463108`）对状态 2 幂等返回，普通完成分支调 phase virtual `+0x510` 后写状态 2。教材没有把这几行 setter 冒充完整的任务激活/完成服务，而是通过 `TeachingQuestWorld.SetQuestState` 注入状态。

## 值得学的点

- **用一个表覆盖所有标志组合**，比用几个例子更可靠：教材对全部 24 个状态/flag 组合与原控制分支的转写逐一比较。
- **符号编码语义**（有符号半径）。
- **严格比较与零时长的边界**要显式写测试。
- **未实现就抛异常**，不要为了“跑通”返回 true。

## 常见坑

- 把 `finished=false` 理解成“还没完成”。
- 把游戏暂停实现成关闭 gate：gate 与时钟是两件事。
- 把原 setter 的几行代码当作完整任务服务。
