> 适用版本：Dying Light 1.55.0.0。依据 `DL1/Teach/Logic/教学.md` 的 0.1、0.2、1.1a 与第 2 节。原函数 `FUN_180aaa0e0`、`FUN_180ab2c40`、`FUN_180e07c40` 为反编译文本中的位置，C# 命名与分组是教学设计。

## 要点

- 玩家的运动在原作中是**分层提交**的：玩法层决定想要的速度，物理层决定实际速度。两层之间只传三项数据。
- 玩法层有多种“来源”：动画运动增量、模块给出的速度或目标位置、跳跃模块提供的高度。统一提交后由物理体消费。
- 教学版把“请求”做成不可变快照，把“接收方”做成接口，提供者与消费者互不持有对方的状态。

## 原作里怎样走

物理回调 `FUN_180aaa0e0` 调用 `FUN_180ab2c40`。后者根据玩法状态选择模块提供的速度、目标位置或动画运动来源，统一提交给 Walk。

| 反编译位置 | 行为 |
| --- | --- |
| `gamedll_x64_rwdi.c:1096535–1096569` | 动画分支：通过 AnimBind 与采样接口取运动增量，再除以时间步得到速度。动画不仅是视觉播放 |
| `1096579–1096661` | 非动画分支：包含**游戏层**的速度平滑，与物理层的加减速参数是不同环节 |
| `1096715–1096719` | 局部速度转世界向量，经 `FUN_180e07c40` 提交到 Walk 虚槽 `+0x2d0` |
| 随后的 `+0x300 / +0x310` | 加速、减速标量接口。反编译存在浮参丢失，不能按表面参数列表翻译 |
| `FUN_180c716b0`（`1365048`） | 跳跃：明确计算 `目标Y = 当前Y + 高度`，所以该字段叫高度量，不是初速度 |

“动画驱动的位移”这一点值得停一下。很多游戏用 Root Motion，把动画里的位移直接写到 Transform。这里不是：它读动画的增量，除以时间步，**变成速度**，交给物理体去走，这样碰撞仍然生效。

## 教学版：三项数据的快照

```csharp
public readonly struct MotionRequest
{
    public Vector3 WorldVelocity { get; }   // 世界空间期望速度，米每秒
    public float Acceleration { get; }       // 米每二次方秒
    public float Deceleration { get; }       // 米每二次方秒
    public MotionRequest(Vector3 WorldVelocity, float Acceleration, float Deceleration)
    { this.WorldVelocity = WorldVelocity; this.Acceleration = Acceleration; this.Deceleration = Deceleration; }
}

public interface IMotionReceiver { void Submit(MotionRequest Request); }
```

提供方（教学里的 `PlayerMotionLesson`）把输入转换成请求：

```csharp
var LocalVelocity = new Vector3(Input.Move.x, 0f, Input.Move.y) * MoveSpeed;
var YawRotation   = Quaternion.Euler(0f, transform.eulerAngles.y, 0f);   // 只取水平朝向
var WorldVelocity = YawRotation * LocalVelocity;
return new MotionRequest(WorldVelocity, Acceleration, Deceleration);
```

设计意图：

| 代码 | 目的 |
| --- | --- |
| 方向乘 `MoveSpeed` | 无速度单位的输入变成米每秒；手柄轻推的幅度被保留 |
| 只取 Y 朝向 | 俯仰、侧倾不会让水平请求带上竖直速度；Transform 缩放不进入速度 |
| 局部到世界的转换 | 对应原作 `FUN_180ab2c40` 里的局部速度转世界向量 |
| `readonly struct` | 请求是帧内快照，传值不会被后续修改 |

## 输入采样的时序

教学版把输入拆成独立快照：

```csharp
public readonly struct PlayerInputSnapshot { public Vector2 Move; public bool JumpPressed; }
```

读取输入在 `Update`，使用 `WasPressedThisFrame()` 得到按下边沿；运动请求在 `LateUpdate` 构造，保证先读后用。这里有一个提醒：`WasPressedThisFrame` 同帧多次调用不会自动“消费”按下状态，读取快照也不会清除它。接入 `FixedUpdate` 物理步时，要重新约定“一次性请求”的缓存与消费，否则一个跳跃按下可能在多个物理步里重复执行。

作者还特别声明：原作具体的输入采样阶段、按键缓存规则尚未查清，不声称复原了原输入系统。

## 值得学的点

- **提供者与消费者之间只传不可变快照**，这让运动逻辑可以做离线单元测试。
- **动画位移转速度而不是直接写 Transform**，让物理碰撞对动画位移同样生效。
- **“请求”不等于“结果”**。日志里看到的 `WorldVelocity` 不代表角色已经到达该速度。
- **输入边沿与持续按住分开**，并把“消费”的时机作为设计问题明确提出。

## 与 ECS 学习专栏的对应

在 ECS 里，同样的结构可以对应：输入系统写一个单例或实体上的 `MotionRequest` 组件，运动系统读取它并更新 `Velocity`、`Position` 组件。提交时序、谁清除一次性请求，这些问题在 06 系统与时序一章里也出现过。

## 常见坑

- 把请求当成立即位移：本课的 `TraceMotionReceiver` 只打印，不移动对象。
- 在 `Start` 里反复查找组件。教学代码统一在一个 `Init`/`InitComponents` 里缓存。
- 直接把 `CharacterController` 当成原作实现：教材明确说那只是演示，已暂停作为正式路线。
