> 适用版本：以公开反编译 `gamedll_x64_rwdi.c` 为准。依据 `DL1/Teach/Logic/Equipment/装备声明与实例耐久.md`。实际维修事务（扣材料、增加已用次数、RepairLuck 随机分支）、`use` 的完整脚本展开、制作产量均**未实现**。

## 要点

- 一把武器有两个层次：**定义**（物品声明里的 Condition 上限、可维修标志、维修材料）与**实例**（背包里这一把的当前耐久、已用维修次数）。不要混成一个状态对象。
- 声明是脚本命令逐条写入定义对象，其中有“后写覆盖”的标量，也有“累加”的材料表，两者规则不同。
- 夹取、损耗、可维修判定各对应一个原函数，表达式很小，可以逐行复刻。

## 定义侧：脚本命令的字段操作

`inventory_gen.scr` 里 `Melee_ShortKnifeCGen` 第一条声明含 Condition 40、CriticalCondition 12、Reparable true、RepairPart 金属零件 1、AllowedRepairs 3。同名还有两条声明，Condition 分别为 32 和 12——三条记录教材全部保留，没有猜变体选择规则。

| 命令 | 原函数 | 行为 |
| --- | --- | --- |
| `Condition(x)` | `FUN_180695b90`（`:615028`） | 把同一个数写入定义对象 `+0x250` 与 `+0x254`，两字段的独立作用未证明 |
| `Reparable(b)` | `:615105–615108` | **先清 bit0，再按布尔写 bit0**，其余标志位保持不变 |
| `RepairPart("A;B", n)` | `FUN_180681dc0`（`:609693`） | 用分号拆名字，对每个名字写入 n；已存在的在 `:609889` **加上**本次数量 |
| `RepairPotency(x)` | `:613386–613393` | 输入夹到 [0, 1]，NaN 得到 0 |

对应教学调用：

```csharp
var Definition = new EquipmentDeclarations(-1, -1, -1, 0, 0xa4);
Definition.ApplyCondition(40);
Definition.ApplyReparable(true);
Definition.ApplyRepairPart("Craft_MetalScrap", 1);
Definition.ApplyRepairPart("Craft_MetalScrap;Craft_Nails", 2);
Definition.ApplyRepairPart("Craft_Nails;Craft_Nails", 1);
// 金属 1+2 = 3，钉子 2+1+1 = 4（重复名字逐次累加）
```

教材用一个初始标志 `0xa4` 证实修改 `Reparable` 只影响 bit0。

**标量字段可以后写覆盖，材料表不行**，这是读脚本时最容易漏的差别。另一个边界：空名称（如 `"Craft_Nails;"`）的原行为没有证明，教学入口先拒绝再修改，不无依据地忽略空项。

## 实例侧：赋值、损耗、判定

| 函数 | 规则 |
| --- | --- |
| `FUN_180654800`（`:587093`）实例赋值 | 只有 clamp 标志开启**且**定义上界大于零，才把请求值夹在 [0, 上界]；其它情况直接写入请求值 |
| `FUN_180654bc0`（`:587224`）损耗 | 定义上界非负时计算 `current − amount`，结果夹到 [0, current]，再进入开启 clamp 的赋值阶段；负 amount 不会增加耐久；上界小于零时不执行 |
| `FUN_180654de0`（`:587344`） | 定义可维修标志 **且** `current < bound` |
| `FUN_180654d00`（`:587292`） | `used < allowed` |
| `FUN_1807108c0`（`:669880`）维修显示 | 实例 condition > −1 且允许次数 > 0 才准备显示，剩余 = 允许 − 已用，**不加下限钳制** |

算例（教材）：

```csharp
var Instance = new EquipmentInstanceSnapshot(20, 2);          // 当前 20，已用维修 2
Instance.ApplyConditionAssignment(50, 40, true);               // 请求 50，上界 40，clamp 开
// Current = 40，Used = 2（赋值不是维修，不改已用次数）
Instance.ApplyConditionLoss(6, 40);                            // 当前 40 → 34
```

关闭 clamp 时请求 50 会原样保留 50；上界非正时请求负数也原样保留。

两个对实现者很有价值的细节：

- **NaN 行为不同**：`RepairPotency` 是比较分支，NaN 得到 0；实例 setter 原样保留 NaN。教材专门保留这个 IEEE 比较差异，并说明这不表示脚本里存在 NaN 输入。
- **显示层不兜底**：剩余次数可以算出负数，教材说应由实例创建和维修事务证明来源，不能靠显示层隐藏。

## 没有闭合的部分

实际维修函数 `FUN_180654c20`（`:587263`）已找到：通过条件后，它按参数决定是否增加 `+8` 已用次数，再夹取输入强度并乘定义上界。但 `587279–587284` 含不能直接运行的 `movmskps` 反编译表达式和丢失的浮点调用参数。教材没有猜整数舍入或最终恢复值，也没有提前提交那次计数增加。

另外 `CraftedItem("Medkit_HealthPackLarge", 1, 2)` 的两个整数仍原样保留，`CraftingMaster` 和 `craftingexpertise` 两个技能与这两个产量参数的选择链也没有证实。

## 值得学的点

- **定义/实例分离**：配置数据不可变，实例状态可变。你的物品系统也应如此，存档只存实例。
- **声明语义要区分“覆盖”与“累加”**，写测试各覆盖一种。
- **夹取条件写在函数里的组合布尔**，不要简化成“永远夹”。
- **宁可不实现，也不猜**：遇到反编译表达式丢参数，就停在这里并写明。

## 常见坑

- 以为 `Condition` 的两个字段是冗余的而只写一个。
- 把 `Reparable(false)` 实现成清空整个标志字节。
- 把 `ApplyConditionAssignment` 当作维修完成。
- 把显示的剩余次数钳制到 0，掩盖上游错误。
