## 要点

- 每个数值属性维护四个量：**基值、累计加值、累计倍率增量、当前值**。
- 当前值 = `(倍率增量 + 1) × 基值 + 加值`。多个倍率修改**相加**成增量，不连乘。
- 撤销效果不靠“减回去”，而是清零所有临时槽，然后重新应用仍有效的列表。
- 布尔属性用一个字节的两位：bit0 是当前值，bit1 是默认值，清理时从 bit1 恢复 bit0。

## 反编译里的原型

`FUN_180b696f0`（`gamedll_x64_rwdi.c:1214590`）的核心如下，字段名是本专栏按教材的偏移表加的注释：

```c
// param_2 是一条修改记录：+0x10 = value_mul，+0x14 = value_add；param_3 = 栈数
// 属性记录：+0x08 当前值，+0x0c 基值，+0x10 累计加值，+0x14 累计倍率增量
if (属性->虚函数+8() != 0) {                          // 返回值非零才修改，含义未核实
    add  = (float)stack * 修改记录->value_add + 属性->累计加值;
    属性->累计加值 = add;
    属性->当前值   = (属性->倍率增量 + 1.0) * 属性->基值 + add;
    mul  = (float)stack * 修改记录->value_mul + 属性->倍率增量;
    属性->倍率增量 = mul;
    属性->当前值   = (mul + 1.0) * 属性->基值 + add;
}
```

这与教材的 C# 内核逐行对应：

```csharp
public void Apply(float ValueAdd, float ValueMul, short StackCount)
{
    AddValue = StackCount * ValueAdd + AddValue;
    RefreshValue();
    MultiplierDelta = StackCount * ValueMul + MultiplierDelta;
    RefreshValue();
}
private void RefreshValue() => Value = (MultiplierDelta + 1) * BaseValue + AddValue;
```

两处细节：

- 加值和倍率各自累加，且各刷新一次当前值，教材称之为“保留原函数的赋值顺序”。最终结果与顺序无关，保留顺序是为了让复刻与原函数的中间状态一致。
- 栈数是**有符号**数（`short`）。没有额外夹到零，原表达式允许负值。生命、伤害、速度是否设下限，交给消费者。

## 算例

基础值 100：

| 修改 | 结果 |
| --- | --- |
| `value_add = 120`（Painkillers 对 MaxHealth） | 220 |
| 倍率增量 0.25，加值 20 | 145 |
| 上一行再叠 Painkillers | 265 |
| 倍率增量变 0.5（再叠一个 `value_mul = 0.25`），加值 20 | 170 |

本专栏用代码复算了这四个数：220、145、265、170，与教材一致。

## 布尔属性

教材描述：布尔字段的 bit0 是当前值，bit1 是默认值，其余位保持原样。`Apply` 只写 bit0，所以同一属性多次写入时**最后一次生效**，没有 OR 叠加，也没有按栈数缩放。`ResetModifier` 从 bit1 恢复 bit0。

对应反编译（`FUN_180b69790`，`1214614` 起）里的位运算：

```c
*(byte*)(slot + 8) = *(byte*)(slot + 8) & 0xfd;                         // 清 bit1
*(byte*)(slot + 8) = (b & 1) * 2 | (*(byte*)(slot + 8) & 0xfe) | (b & 1); // bit1=b, bit0=b
```

教材对 256 种输入字节独立穷举了这个表达式，验证“保留高六位、只改最低两位”。

同一个函数还透露了属性槽的**分区布局**：循环遍历 0 到 0x408 的槽位，`id−1 < 0x376` 的是数值属性，`id−0x379 < 0x88` 的是布尔属性，`id−0x403 < 5` 的是另一类（含释放内存的调用，疑为字符串类）。这是本专栏读反编译得到的观察，教材没有这样总结，三类的含义也未核实；枚举编号跨版本不能平移。

## 配置接入与 Refresh

`AttributeBank` 通过宿主注册的名称找状态槽，名字区分大小写，**没注册的属性直接失败**，不会静默当作 0。`Refresh` 的顺序：

1. 清空全部数值槽和布尔覆盖；
2. 应用无期限列表（原偏移 `+0xf0`）；
3. 应用限时列表（原偏移 `+0x108`）。

数值属性在两个列表之间共同累计；布尔属性按这个顺序覆盖。

## 为什么要“清零重算”

| 做法 | 问题 |
| --- | --- |
| 加上去，到期再减回去 | 乘性加成无法精确还原；浮点误差随次数累积；撤错层 |
| 清零，再重放仍有效的列表 | 始终从权威输入出发；顺序固定；可审计 |

代价是每次刷新的开销与（属性数 + 修改条目数）线性相关。教材明确没有给性能预算，只记录了测量值：复用重载下，两个真实 buff 同时存活，输出容量 4，预热 256 次后调用 50,000 次，每次推进 0.0001 秒，当前线程托管分配实测 0 字节。

## 值得学的点

- **四槽模型 + 全量重算**是 RPG 属性系统的稳妥基线，调试时只需看四个数。
- **倍率相加、加值相加**，让多层加成的结果与应用顺序无关，也便于 UI 展示“+25%”。
- **布尔覆盖最后写入生效**，规则简单到可以背下来。
- **未注册就失败**，把拼写错误尽早暴露。

## 常见坑

- 把倍率连乘。教材：两个修改量各自累加，不连续相乘。
- 把 `skill` 的 `change="x0.25"` 自动当作同一规则，消费桥尚未证实。
- 混用“修改记录”和“属性记录”的字段：同样的 `+0x10`，在修改记录里是 `value_mul`，在属性记录里是累计加值。
- 以为 `Value` 是游戏里最终读到的值。个别 getter 会依外部状态再乘缩放。
