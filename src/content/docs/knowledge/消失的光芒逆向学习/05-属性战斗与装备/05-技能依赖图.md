> 适用版本：Dying Light 1.55.0.0。依据 `DL1/DL1Source/Data0/data/skills/common_skills.xml` 与 `DL1/Teach/Logic/SkillGraph.cs`、`EffectDispatcher.cs`。教学内核只实现**单级技能**的学习；多级、效果叠加、存档均未实现。

## 要点

- 技能是一张有向无环图：一个技能可以要求若干前置技能、若干分类等级、若干技能点。
- 声明里的“效果”是字符串（效果 ID + 原始 `change` 值），教学内核不解释它，只把整组原样派发给显式注册的处理器。
- 加载时就检测成环与缺失前置。图在构造时被验证，运行期才不必处理脏数据。

## 数据：`common_skills.xml`

本专栏用命令行统计：该文件含 98 个 `<skill`，分五类：

| 分类（`cat`） | 数量 | 技能点类型 |
| --- | --- | --- |
| fighter | 23 | Fighter |
| runner | 24 | Runner |
| driver | 23 | Driver |
| status | 24 | Status |
| reputation | 4 | Reputation |

其中有 83 处 `skill_req` 前置声明。一个典型条目：

```xml
<skill id="Stunning" cat="fighter" tier="3" max_level="1" desc_params="kick_trauma;P;M:Stunning"
       skill_points="1" skill_points_type="Fighter">
    <level_req type="Fighter" value="3"/>
    <skill_req id="StunAttacks"/>
    <effect id="ConfusionProbabilityKick" change="0.10"/>
</skill>
```

文件开头有两行说明：`tier` 标记技能菜单中的位置（等于按钮 id）；`desc_params` 是用分号隔开的参数表，首项永远是图标，`NODE` 表示六边形背景，`P` 表示被动技能。这说明同一份数据兼做玩法定义和 UI 布局，数据驱动的另一面是一个字段承载多个关注点。

## 内核：构造即验证

```csharp
public SkillGraph(IEnumerable<SkillDefinition> SkillList, Dictionary<string,int> LevelDict, Dictionary<string,int> PointDict)
{
    SkillDict = SkillList.ToDictionary(Item => Item.Id);
    // ... 复制等级与技能点字典
    var Active = new HashSet<string>(); var Complete = new HashSet<string>();
    foreach (string Id in SkillDict.Keys) Visit(Id, Active, Complete);
}

private void Visit(string Id, HashSet<string> Active, HashSet<string> Complete)
{
    if (Complete.Contains(Id)) return;
    if (!Active.Add(Id)) throw new InvalidDataException($"技能前置成环 {Id}");
    foreach (string Required in SkillDict[Id].RequirementList)
    {
        if (!SkillDict.ContainsKey(Required)) throw new InvalidDataException($"技能 {Id} 缺少前置 {Required}");
        Visit(Required, Active, Complete);
    }
    Active.Remove(Id);
    Complete.Add(Id);
}
```

这是标准的三色 DFS：`Active` 是“正在访问”（灰），`Complete` 是“已完成”（黑）。在访问一个节点期间再次遇到灰色节点，就是环。`Complete` 同时起到记忆化作用，每个节点只展开一次，整体 O(V+E)。

## 学习的事务检查

```csharp
public bool CanLearn(string Id)
{
    var Skill = SkillDict[Id];
    return !LearnedHashList.Contains(Id)
        && Skill.RequirementList.All(LearnedHashList.Contains)
        && Skill.LevelRequirementList.All(Item => LevelDict[Item.Type] >= Item.Level)
        && PointDict[Skill.PointType] >= Skill.Cost;
}

public SkillEffect[] Learn(string Id)
{
    if (!CanLearn(Id)) throw new InvalidOperationException($"技能不可学习 {Id}");
    var Skill = SkillDict[Id];
    if (Skill.MaxLevel != 1) throw new NotSupportedException($"本课只实现单级技能 {Id}");
    PointDict[Skill.PointType] -= Skill.Cost;
    LearnedHashList.Add(Id);
    return Skill.EffectList;
}
```

设计意图：

- 四个条件缺一不可：没学过、前置齐全、分类等级达标、技能点够。
- `Learn` 的“检查与扣点”在一个方法里完成，没有半成功状态。
- 遇到多级技能**明确抛 `NotSupportedException`**，而不是默默按单级处理。这是“不假装支持”的又一个例子。
- 返回效果列表，而不是内部直接应用，让调用方控制何时、怎样生效。

## 效果派发：原字符串，不解释

`EffectDispatcher.Apply` 的合同：

- skill 的 `change` 不被当数学公式解释，**原样**交给明确注册的处理器；
- 先确保整组效果都有处理器，再开始派发——一个未知 ID 会让整组都不派发，不会出现“前一半生效、后一半抛异常”的情况；
- 没有默认处理器，不吞未知效果；
- 一次派发内处理器自己抛异常时，跨处理器回滚不在合同内。

为什么不解释？因为 `change="x0.25"`（例如 `Health1` 对 `MaxHealth`）的消费桥在原生代码中没有找到，对应的原函数 `FUN_180e69cb0` 在现有反编译文件里标记为 `Unable to decompile`。所以 5.1 的倍率规则不会被自动当作它的语义。

## 值得学的点

- **图在构造时验证**：成环和缺失前置是数据错误，越早报越好。
- **三色 DFS**：游戏里的科技树、任务依赖、构建依赖都能直接套。
- **效果走注册表**，原始字符串保留。扩展新效果只需注册，不改图。
- **先全量校验，再开始修改**：派发效果时的原子性做法。

## 常见坑

- 用递归深度限制代替环检测，会在深图上给出误导性的栈溢出。
- 把技能点扣除放在效果成功之后，失败时留下“点已扣、效果没生效”。
- 把 `desc_params` 当作纯 UI 数据忽略，导致导出时丢失 `P`/`NODE` 语义。
