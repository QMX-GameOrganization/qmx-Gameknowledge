> 适用版本：当前安装版 `gamedll_x64_rwdi.dll`（SHA256 以教材记录为准，开头为 `59f4399c…`）。本章用的是**机器码**，不是旧反编译 C，二者地址不通用。依据 `DL1/Teach/Logic/AI/原生AI条件与查询边界.md`。恢复范围仅限 `ZombieLogicModule` 与 `InfectedLogicModule` 的死亡、光照条件组合，不是完整 AI。

## 要点

- 对 C++ 虚函数多的模块，**RTTI + 虚表**是最可靠的锚点：类名、虚表地址、每个虚槽的函数入口都能独立确认。
- 要证明“这段函数就是 ShouldDie”，需要一条证据链：名称表 → 工厂 → 虚表 → wrapper → 模块虚槽。
- 光有静态阅读不够。教材把原函数的机器码复制到独立进程里执行，用模拟的虚调用回调驱动，得到“原始实现的真实输出”，再与 C# 对拍。
- 世界查询（感知、导航、句柄）这些深层依赖没有恢复，所以接口里留着“宿主必须提供”的口子。

## 证据链

| 步骤 | 地址或位置 | 作用 |
| --- | --- | --- |
| 名称 getter | `0x18009faf0` | 输入减一后索引 77 项表，把规则 ID 变成名字 |
| 工厂 | `0x180268d30` | 用同一枚举域，把 ID 写到规则对象 `+8`，把对应 RTTI 的虚表写进对象 |
| 死亡 wrapper | `0x180264140` | 从状态对象 `+0xd58` 取模块，调模块虚槽 `+0xd20` |
| 光照 wrapper | `0x180266b20` | 从 `+0xd60` 取模块，调虚槽 `+0xd70` |

两个模块的主虚表和函数入口：

| 类型 | 主虚表 | 死亡 D20 | 光照 D70 |
| --- | --- | --- | --- |
| `ZombieLogicModule` | `0x18146d860` | `0x1802fdbb0` | `0x180084840` |
| `InfectedLogicModule` | `0x181459878` | `0x1802d29a0` | `0x1802d2ef0` |

导出工具验证了“工厂的 ID 写入、虚表地址、虚表首方法与 wrapper 完全一致”。wrapper 的无效模块分支不是可靠的 `false` 返回，所以教学核**要求宿主提供有效查询域**，不去模拟原无效指针行为，也不补成功兜底。

## 死亡条件

两个模块先对 actor 虚槽 `+0x368` 的 int32 结果做一次无符号区间判断：

```csharp
int Classifier = Queries.ActorVirtual368();
if (unchecked((uint)(Classifier - 7)) <= 9u) return false;       // 7..16 全部返回 false
```

这是编译器常用的区间判断技巧：`(uint)(x − 7) ≤ 9` 等价于 `7 ≤ x ≤ 16`，一次比较搞定上下界。本专栏用 −40 到 40 的整数以及 int32 的两个极值验证过这个等价关系。教材提醒：不能把这个分类器猜成“已死亡枚举”，也不能把后面的 `F20` 改写成 `Health <= 0`，因为 `F20` 的更深实现涉及多个 actor 句柄、标志与其它调用，没有恢复。

差异：

- `Zombie`：区间外调用一次 `F20` 并返回该结果。
- `Infected`：`F20` 为真时**再调用一次** `F20`，第一次为假就直接返回假。

这两次调用不能缓存成一个值。教学接口因此能观察 `true, false` 序列的最终 false 与调用次数。

## 光照条件

`Zombie` 的 D70 只有 `xor al,al; ret`（永远 false）。`Infected` 的光照函数范围 `[0x1802d2ef0, 0x1802d2fe5)`，共 245 字节，**跨 unwind 分片**，不能只读首个 unwind 块就声称全函数恢复；需要按 PE 的 CHAININFO 合并分片。

按顺序的查询（均为十六进制标识，保留原短路顺序）：

| 顺序 | 接口 | 已证明的原访问 |
| --- | --- | --- |
| 1 | `AiDataBool250` | actor `+9c0` 的 getter `233c60` key `0x250`，读动态值或默认值 |
| 2 | `GoalField84` | actor `+cb0` 句柄，校验或 `2a61b0` 解析，再读 `+84` |
| 3 | `ModuleByte4C4` | 模块 `+4c4` |
| 4 | `ModuleVirtual9F8` | 模块虚槽 `+9f8` |
| 5 | `ActorDd8Nested2C8Byte10` | actor `+dd8` 句柄，经 `+2c8` 指针读 byte `+10` |
| 6 | `ModuleVirtualF28` | 模块虚槽 `+f28` |
| 7–9 | `ModuleByte182/183/184` | 模块 `+182/+183/+184` |

逻辑：第 1 步为假则返回假；第 2 步分类器**严格等于 `0x26`** 则立即返回真，不再访问后续查询；否则要求 4C4 非零、9F8 为假、嵌套 byte 为零、F28 为真，最后 182/183/184 按顺序任一非零才为真。

教材有意**不给这些未知量取语义名**：不能叫“UV 晕眩”“看到玩家”“手电筒照到”。key `0x250` 属于这次 AIData getter 域，不能借用另一份属性表里的 `LookAimVertSpeed_Pad` 名称。

## 机器码 oracle

验证死亡条件时，作者的做法很值得学：

1. 把两个原函数（分别 56 和 78 字节）完整复制到独立 Python 进程的可执行内存里，**零指令 patch**；
2. 导出时先验证：函数内没有 RIP 相对数据访问、没有直接外部 call，所有直接跳转都在复制的函数范围内；
3. 间接调用（虚调用）指向模拟对象的虚表，虚表项是 Python 回调；
4. 80 组输入覆盖 int32 极值、区间边界、四种 `F20` 返回序列；
5. 原机器码的结果、调用顺序与 C# 内核对拍，一致。

边界声明：这是 **mock 回调条件下的验收**，不能计成原 AI 的世界运行。光照函数的 768 组 C# 检查（8 个 bool/byte 门限组合 × Goal 0x25/0x26/0x27）是源码条件组合验收，**没有运行光照机器码 oracle**。

导出过程中的首个错误被保留：工厂失败分支跳向共享 epilogue，超出选取的成功 case 摘录。修正方式是让工厂证据显式记录外部跳转，而复制死亡函数与完整光照函数仍严格要求直接跳转在本函数内，没有放宽断言。

## 停在哪里

`ShouldAttack`（ID 31）的规则与 RTTI 链已定位，但 `Zombie` 和 `Infected` 的 `C80` 都进入 `0x180309010`，继续调用较深的共享实现 `0x1802c0c00`。收益低于已经闭合的死亡/光照，所以本轮停在定位。`ShouldReactOnHit`（ID 15）只记录规则和虚槽 `B58`。

## 值得学的点

- **RTTI + 虚表**：逆向 C++ 游戏时的第一把钥匙。
- **区间判断技巧**：反编译里 `(uint)(x − a) ≤ b` 要读成范围检查。
- **机器码 oracle**：把原函数当黑盒执行，比“读懂再重写”更不容易错。
- **保持原短路顺序和调用次数**：查询可能有副作用或开销，次数本身是行为的一部分。
- **宿主查询接口**：`INativeDeathQueries`、`INativeLightQueries` 把“已恢复的条件逻辑”和“尚未恢复的世界读取”分开。

## 常见坑

- 把 `0x26` 这样的魔数命名成猜测的含义。
- 只看函数首个 unwind 块就当全函数。
- 把 mock 条件下的 oracle 通过，读成“AI 已还原”。
- 缓存 `F20` 的结果，改变了 `Infected` 的调用次数。
