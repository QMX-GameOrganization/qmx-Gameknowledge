> 适用版本：Dying Light 1.55.0.0。依据 `DL1/DL1Source/Data0/data/ai/` 下的 `.def`/`.scr`，以及 `DL1/Teach/Logic/AI/原生AI条件与查询边界.md`。**本章讲的是结构，不是完整 AI：寻路、攻击执行、状态调度均未还原。**

## 要点

- AI 的“想做什么”由一组**主目标规则**（`Should…`）表达，每条规则是一个返回 bool 的条件，有固定的整数 ID。
- AI 的“能做什么”由一组**功能模块**（攻击、受击、死亡、光照反应……）提供，每个模块有类型 ID。
- 具体怪物的强弱与感知参数不在代码里，而在一串用 `!include` 继承的参数预设里。

![AI 规则与模块](/qmx-Gameknowledge/assets/dl1/dl1-ai-rules.svg)

## 规则表：`ai_main_goal_rules.def`

文件开头一句话：`//Keep this synchronized with EAIMainGoalRule enum!`。内容是 `$名字 (i, ID)` 形式：

| ID | 规则 | ID | 规则 |
| --- | --- | --- | --- |
| 2 | ShouldLieDead | 15 | ShouldReactOnHit |
| 3 | ShouldDie | 21 | ShouldReactOnDanger |
| 9 | ShouldReactOnFinisher | 31 | ShouldAttack |
| 12 | ShouldReactOnBurn | 41 | ShouldBeginGrab |
| 13 | ShouldReactOnElectorcution | 48 | ShouldReactOnLight |
| 14 | ShouldReactOnPoison | 57 | ShouldExplode |

ID 最大为 77，其中 23 和 38 空缺。从名字能读出这套规则覆盖的行为面：死亡、跌倒、起身、燃烧、感电、中毒、受击、迷惑、躲闪、危险、警戒级别、攻击、抓取、爆炸、尖叫召唤其他丧尸、夜间攻击性、逃跑等。

## 模块表：`ai_modules.def`

开头同样有同步提示：`//keep synchronized with EModuleType`。例如：

| ID | 模块 | ID | 模块 |
| --- | --- | --- | --- |
| 3 | ELECTROCUTION_MODULE | 21 | DEATH_MODULE |
| 7 | ATTACK_MODULE | 22 | HEALTH_MODULE |
| 11 | LIGHT_REACTION_MODULE | 37 | ZOMBIE_LOGIC_MODULE |
| 15 | HIT_REACTION_MODULE | 38 | INFECTED_LOGIC_MODULE |
| 20 | GRAB_MODULE | 41 | VOLATILE_MODULE |

表里还有 `BURNING`、`BLEEDING`、`KNOCK_DOWN`、`DODGE`、`STAMINA`、`ARMORED_LOGIC`、`SPITTER_LOGIC` 等。这是典型的**组合式**设计：一个怪物类型 = 一组模块的选择。`zombie_ai_module_presets.def` 给出了几种常用模块集合的代号：

```text
ZOMBIE_AI_MODULE_STANDARD       = "0"
ZOMBIE_AI_VOLATILE              = "1"
ZOMBIE_AI_SUICIDER              = "2"
ZOMBIE_AI_TRANSFORM_SUICIDER    = "3"
ZOMBIE_AI_FACE_MIMICS           = "4"
```

## 规则到目标的有序表：`*_goal_rules_generic.scr`

条件（规则）怎样变成行为（目标）？答案在各阵营的 `goal_rules` 脚本里，例如 `ai/zombie/zombie_goal_rules_generic.scr`（42 行）：

```text
Rule(GoalLieDead,       ShouldLieDead)
Rule(GoalDie,           ShouldDie)
Rule(GoalHolding,       ShouldHoldPlayerGrab)
Rule(GoalReactOnFinisher, ShouldReactOnFinisher)
Rule(GoalFall,          ShouldFall)
Rule(GoalBeginGrab,     ShouldBeginGrab)
Rule(GoalReactOnBurn,   ShouldReactOnBurn)
Rule(GoalReactOnHit,    ShouldReactOnHit)
...
Rule(GoalReactOnLight,  ShouldReactOnLight)
Rule(GoalAttack,        ShouldAttack)
Rule(GoalAvoidAiRegion, ShouldAvoidAIRegion)
Rule(GoalReach,         ShouldQuestMove)
Rule(GoalKeepAlive,     ShouldKeepAlive)
```

每行把一个目标（`Goal…`）和一个条件（`Should…`）配对。从书写顺序可以看出一种**优先级排布**：死亡、躺尸、被抓、处决反应排在前面，攻击靠后，`KeepAlive` 垫底像是兜底项。同一个目标可以被多条规则引用（例如 `GoalReach` 对应任务移动和中止夜间攻击，`GoalIdleBehave` 对应强制待机、尖叫、等待导航）。人类阵营（`human/`）和感染者（`infected/`）各有自己的表，另有 Boss 战专用表。

教材对“表里谁先赢”的态度要注意：教学策略是**死亡优先于攻击、首个满足的规则被选中**，并明确写着“首满足优先是教学策略”，原引擎的选择算法没有确认。也就是说，脚本里的顺序本身是事实，“按顺序取第一个满足者”是推断。

这个设计的好处是：改 AI 行为只需调整这张表的顺序或增删行，不用动代码。

## 参数预设：继承加差量

`ai/zombie/` 下有 130 个文件，其中 83 个 `.scr`、成对的 `.dat`，且 86 个文件名含 `custom_preset`。以 `biter_policeman` 为例，预设只有几行：

```text
!include("zombie_data_custom_preset_anim_set_c.scr")

ParamFloat("damage_mul", 1.34)       // Final damage = Ml_Baton_AI.damage * damage_mul
ParamFloat("health_mul", 2.25)       // 基础生命来自曲线 'zombie_health' 再乘此值
ParamFloat("head_health_mul", 1.0)
ParamFloat("stamina_to_health_ratio", 0.22)
```

基础参数表（`zombie_data_params.scr`，757 行）定义视距、听觉、反击概率等，例如：

| 参数 | 值 |
| --- | --- |
| `sight_range_calm` / `sight_range` | 10.0 米 |
| `sight_range_mul_at_night` | 1.0 |
| `sight_angle_at_min_dist_calm` / `at_max_dist_calm` | 160 度 / 70 度 |
| `grab_counterattack_prob` | 0.8 |
| `hearing_sensitivity` | 1.0 |

注释里直接写单位与含义，如 `//[m]`。数值怎么进入决策，见 6.3。

## 规则怎样在二进制里找到

教材用一条完整链证明“规则名属于这段函数”（针对当前安装版 DLL，SHA256 以教材记录为准）：

1. `0x18009faf0` 的名称 getter：输入减一后索引 77 项表。
2. `0x180268d30` 的工厂使用同一个枚举域，把 ID 写到规则对象 `+8`，把对应 RTTI 的虚表写进对象。`ShouldDie` 是 ID 3，`ShouldReactOnLight` 是 ID 48。
3. 导出工具验证：工厂写入的 ID、虚表地址、虚表首方法与 wrapper 完全一致。

细节见 6.2。

## 值得学的点

- **条件拆成独立规则对象 + 整数 ID**。AI 主循环只问“哪条规则成立”，具体判定交给规则对象，新增行为不改主循环。
- **模块组合代替继承**：一个怪物 = 一组模块 ID，用预设代号复用。
- **参数预设的差量继承**：数十个变体只写差异。
- **枚举同步注释**：这是脚本层与代码层的约束，值得放进自己的项目，并在加载时做数量校验。

## 常见坑

- 以为规则 ID 连续。23 和 38 是空缺，数组下标不能直接当 ID。
- 假设 `Zombie` 与 `Infected` 的同名规则行为相同。两个模块各有独立实现（见 6.2）。
- 看到 `ZOMBIE_LOGIC_MODULE` 就推断普通丧尸一定走全部分支：类型名不能独立证明某个具体角色采用了哪些分支。
