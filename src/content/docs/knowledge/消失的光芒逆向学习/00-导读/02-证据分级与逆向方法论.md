> 适用版本：Dying Light 1.55.0.0。分级名称取自 `DL1/Teach/索引.md` 的“查证状态”表述，图中的编号是本专栏整理的。

## 要点

- 逆向最容易犯的错，是把“看到字符串”当成“理解了算法”。这套素材用分级来防止这件事。
- 一个结论至少要回答三个问题：声明是什么、哪个函数消费它、有没有被独立验证过。
- “教学设计”单独成类。教学代码里的射线布局、积分方式、策略取舍，都是作者自己的选择，不能冒充原作行为。

## 五级证据

| 级别 | 含义 | 本项目里的例子 |
| --- | --- | --- |
| ① 原声明 | `.scr` / `.xml` / `.def` 写了什么 | 玩家 `walk_player.phx` 声明加速、减速均为 -1，台阶高度 0.51 |
| ② 静态消费核对 | 反编译函数或当前 DLL 指令里能找到读取者 | `FUN_180b696f0` 里的属性累加表达式 |
| ③ 独立内核验证 | 教学 C# 与独立 Python/NumPy 复写逐位一致 | 128 组 binary32 逐步舍入对照 |
| ④ 机器码 oracle | 原函数字节复制到独立进程执行，虚调用走 mock | 死亡条件 80 组输入对照 |
| ⑤ 原作对照 / Unity 实测 | 在游戏或 Unity 里运行比对 | 多数结论尚未到达，保持“待验收” |

每一级都不能替代上一级。教材里反复出现的限定语很典型：“静态核对不等于原游戏行为实测”“测试向量不是整款游戏覆盖率”“通过检查数不等于学员掌握程度”。

## 三条纪律

**不为让结果好看而放宽断言。** 属性教材记录过一次失败：根工程整合时，零分配断言曾失败一次，后来补了实际字节数诊断，用 12 个新进程重跑通过，但首次失败的原因没有定位。作者保留了失败日志，没有改阈值、测量循环或工具链，也没有把原因归给 JIT 或 GC。

**保留首错。** 动画解码里有一个例子：`Necksnap` 候选首次解码失败，错误是 `ANM2 page0 table offsets not strictly increasing`。作者没有把失败吞掉，而是追到页表读取规则（页表长度应为首字乘 8 个 u16，不能强行读至少 16 项），修正后 589 份原本失败的动画通过。首错日志与修正前后的哈希对比都留在证据目录里。

**明确停止位置。** 例如 `ShouldAttack` 的规则与 RTTI 链已经定位，但两个模块都进入同一个较深的共享实现，继续追的收益低于已经闭合的死亡/光照条件，于是文档写明“停在定位，不交猜测的攻击逻辑”。

## 为什么要这么麻烦

反编译文本里有大量“看起来能用”的东西：

- 反编译器丢浮点参数（教材提到 `FUN_180ab2c40` 附近的加减速接口“存在浮参丢失，不能按表面参数列表翻译”）。
- `(int)(float)` 这样的表面转换，实际机器码是 `cvt` 之后的 `movss`，数值并不被截断。
- 同一个 `+0x10` 偏移在“修改记录”和“数值属性记录”里意义相反（一个是 `value_mul`，一个是累计加值）。

只靠字符串和表面表达式，这些都会写错。分级的作用，是让读者在引用某个公式时，知道它踩在哪一级上。

## 值得学的点

- 在文档里用固定句式区分“原作事实 / 教学设计 / 仍未知”。每一节都这么写，读者不用猜。
- 结论带 ID（例如 `LocalAxisAcceleration`），证据 JSON 里按 ID 存原文摘录、哈希、行号。切换会话后不需要重读全部反编译。
- 进度台账只记状态：待讲、已给代码、待用户验收、用户确认通过。AI 自己的测试通过不等于学员通过。

## 常见坑

- 把“通过 207 个检查”读成“还原了 207 个机制”。检查数是教材自己的验收项数，不是游戏覆盖率。
- 用 `native` 函数名里的关键字推断语义。教材明确说过，字符串锚点“不能当算法证明”。
