## 端口不是一个抽象函数，而是带空间信息的槽位

`ItemAcceptorComponent` 的槽位包含：

```text
pos       相对建筑的位置
direction 从哪个方向接收
filter    可接受的物品类型
```

`ItemEjectorComponent` 的槽位还保存：

```text
item      当前待发出的物品
progress  物品离开发出点的进度
cachedTargetEntity / cachedDestSlot / cachedBeltPath
```

因此连接匹配同时检查三件事：位置相邻、方向相反、物品类型可接受。

## 连接什么时候计算

输出系统不会每个 tick 都在地图上搜索下游目标。`ItemEjectorSystem` 会在实体或相关组件变化时重建缓存；`StaleAreaDetector` 用受影响区域限制重算范围。

```text
建筑放置/删除/旋转
→ 找到受影响区域
→ 清理旧缓存
→ 重新匹配端口
→ 正常 tick 直接使用缓存
```

这是一种“静态拓扑、动态状态分离”的设计。

## Unity ECS 的建议数据

```csharp
public struct Port : IBufferElementData
{
    public Entity ConnectedEntity;
    public byte Direction;
    public int ItemFilter;
    public byte Kind; // Input / Output
}

public struct TopologyDirty : IComponentData {}
```

`TopologyRebuildSystem` 只查询 `TopologyDirty` 实体；`TransferSystem` 不负责寻找邻居，只消费已经生成的连接。

## 为什么不要让端口互相直接调用

直接调用会让更新顺序决定结果：先处理的输出可能占满接收槽，后处理的输出永远失败。更稳定的做法是把连接结果写入结构化状态，再由统一系统按照固定顺序提交传输。

不过 shapez.io 对单机工厂采用了更简单的局部尝试：输出端调用目标的 `tryAccept`，成功返回 `true`，失败则保留物品。它没有复杂的全局握手，也能得到稳定的背压。
