## 第一阶段：单链

只实现：

```text
Producer → 一条 BeltPath → Receiver
```

限制条件：

- 一种物品。
- 一个配方。
- 一个输入口和一个输出口。
- 传送带只有直线段。
- 物品用 `BeltPathItem` 缓冲，不创建独立 Entity。

验收：生产器能持续生产；接收器满后路径逐渐堵塞；清空接收器后运输恢复；固定时间步下结果可复现。

## 第二阶段：速率和容量

加入：

```text
Producer.OutputRate
Receiver.InputRate
BeltPath.Speed
BeltPath.Spacing
InputCapacity / OutputCapacity
```

记录实际吞吐量，确认它等于限制项中的最小值，而不是由渲染帧率决定。

## 第三阶段：拓扑变化

加入直线、转弯和拆除：

```text
放置带段 → 合并路径
删除中段 → 拆分路径
旋转带段 → 标记拓扑脏并重建
```

每次重建后检查物品顺序、路径长度和末端连接没有丢失。

## 第四阶段：竞争与分流

最后再加入多个输出连接一个输入、分流器和合流器。此时再决定是否需要 Proposal/Reservation；单链阶段不应提前承担这个复杂度。

## 建议的验证表

| 场景 | 观察结果 |
| --- | --- |
| 接收器空闲 | 生产、运输、接收连续发生 |
| 接收器满 | 末端物品停止，阻塞向上游传播 |
| 生产器输出槽满 | 生产器暂停，不丢失成品 |
| 删除中间带段 | 路径拆分，物品状态可解释 |
| 清空接收器 | 阻塞逐 tick 消退，生产恢复 |
| 两个输出竞争 | 结果符合明确的顺序或公平策略 |

## 最终原则

先复现 shapez.io 的简单正确模型：路径、间距、末端尝试、失败停留。等测试证明模型正确，再将路径物品布局、拓扑重建和多路仲裁分别优化。不要在第一版同时引入独立物品实体、全局请求总线和复杂预留协议。
