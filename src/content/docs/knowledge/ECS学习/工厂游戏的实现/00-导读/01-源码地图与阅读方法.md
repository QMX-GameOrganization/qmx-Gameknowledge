## 先看哪几类文件

```text
src/js/game/entity.js                         Entity 基础对象
src/js/game/entity_components.js              组件注册与组件集合
src/js/game/entity_manager.js                 实体查询与生命周期
src/js/game/components/belt.js                单段传送带组件
src/js/game/belt_path.js                      连续传送带运行时路径
src/js/game/components/item_acceptor.js       输入槽定义
src/js/game/components/item_ejector.js        输出槽和输出中的物品
src/js/game/systems/belt.js                   带段拓扑和路径重建
src/js/game/systems/item_ejector.js           输出交付与失败重试
src/js/game/systems/item_acceptor.js           接收动画和消费表现
src/js/game/components/item_processor.js      生产/加工状态
src/js/game/systems/item_processor.js         处理器更新
```

## 推荐阅读顺序

先看组件，知道“实体身上有哪些数据”；再看系统，知道“谁修改这些数据”；最后看 `BeltPath`，理解项目为性能做的特殊聚合。

```text
Entity / Component
  → Acceptor / Ejector
  → BeltComponent
  → BeltPath
  → EjectorSystem / BeltSystem
  → ProcessorSystem
```

## 源码中的分层

| 层 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Entity | 身份、组件容器、生命周期 | 具体生产规则 |
| Component | 可序列化的状态和静态配置 | 跨实体调度 |
| GameSystem | 遍历一类组件、修改运行时状态 | 保存每个建筑的全部逻辑 |
| BeltPath | 连续路径上的物品、长度和末端交付 | 建筑放置规则 |
| Map/Topology | 查找相邻实体、方向和连接 | 每 tick 的物品移动 |

## 读源码时要区分两种代码

很多方法同时服务模拟和渲染。例如输出槽里的 `progress` 既表示物品正在离开器件，也用于绘制浮动物品。分析时先问：这个字段会不会改变“能否传输”的结果？如果不会，它属于表现辅助状态，不要把它混进核心传输协议。

## 关键阅读问题

- 一个物品当前由谁拥有？
- 传输失败时物品留在哪里？
- 连接是在每帧查找，还是拓扑变化时缓存？
- 速率由显式计数器表示，还是由距离和移动速度产生？
- 多个输入竞争时，谁决定优先级？
