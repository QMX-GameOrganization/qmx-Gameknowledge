> 适用版本：C# 9.0。Unity 行为以 2021 LTS 到 Unity 6000.x 的 Mono/IL2CPP 为准。

## 要点

- 语法和 C++ 的 `try`/`catch` 相似，多了 `finally`：无论是否出错都会执行，常用于收尾。
- C# 没有 `noexcept`，也没有异常规范；`throw` 出的对象必须是 `Exception` 的子类。
- **异常是处理意外的，不是流程控制**。能用 `if` 或 `TryParse` 判断的，不要靠抛异常。
- 在 Unity 里，`Update` 中抛出的异常不会让游戏崩溃，只会打印红色错误，并且**这一帧该方法后面的代码不再执行**。下一帧还会继续调用，同样的错误刷屏。

## 基本写法

```csharp
try
{
    string text = ReadSaveFile();           // 假设可能抛异常
    int hp = int.Parse(text);
    Console.WriteLine($"hp={hp}");
}
catch (FormatException e)                   // 先捕获更具体的
{
    Console.WriteLine($"存档格式错误：{e.Message}");
}
catch (Exception e)                         // 再捕获更宽泛的
{
    Console.WriteLine($"未知错误：{e.Message}");
}
finally
{
    Console.WriteLine("读档流程结束");       // 一定会执行，哪怕上面 return 了
}
```

`catch` 从上到下匹配第一个合适的，所以要**从具体到宽泛**排列，顺序反了编译器会报错。

## 常见异常，认一下就行

| 异常 | 典型原因 | 游戏里的场景 |
| --- | --- | --- |
| `NullReferenceException` | 对 `null` 调用成员 | 物体被销毁后还在用它，没拖引用 |
| `IndexOutOfRangeException` | 数组下标越界 | 背包格子编号超出范围 |
| `ArgumentOutOfRangeException` | `List` 下标越界、参数不合法 | 同上，针对 `List` |
| `KeyNotFoundException` | `Dictionary` 取不存在的键 | 按物品 ID 查配表 |
| `InvalidCastException` | 强转到不兼容的类型 | 错误的向下转换 |
| `DivideByZeroException` | 整数除以 0 | 浮点除零不抛，得 `Infinity` |
| `FormatException` | 解析字符串失败 | `int.Parse("abc")` |

`NullReferenceException` 是 Unity 开发里的第一大异常。C++ 里空指针解引用是未定义行为，C# 里则稳定地抛这个异常，并附带出错的行号，调试反而容易。

## 主动抛出

```csharp
static void TakeDamage(ref int hp, int amount)    // ref 见 2.4
{
    if (amount < 0)
        throw new ArgumentException("伤害不能为负数", nameof(amount));
    hp -= amount;
}
```

在 `catch` 里想把异常继续向上抛，写 `throw;`，**不要写** `throw e;`：后者会重置调用栈，丢掉出错位置。

## 自定义异常

```csharp
class InventoryFullException : Exception
{
    public InventoryFullException(string msg) : base(msg) { }
}
```

这里用到了类和继承，暂时看懂形状即可，学完第 3、4 章再回来。游戏项目里更常见的是返回 `bool` 或结果枚举，自定义异常用得不多。

## 什么时候不该用异常

异常的**抛出**很慢（要收集调用栈），远比一次 `if` 判断昂贵。每帧都可能触发的情况（例如"按键是否按下"、"字典里有没有这个键"）要用条件判断：

```csharp
if (!table.TryGetValue(itemId, out var item))     // 返回 false，不抛异常
    return;
```

## 在 Unity 里用到它

- Console 里的红色条目就是未处理的异常，点击它，下方会显示**调用栈**，双击栈里的某一行可以跳到对应代码。
- `NullReferenceException` 最常见的原因是 **Inspector 里的引用没拖**：字段显示为 `None`，运行时使用它就会报错。
- Unity 不会因为 `Update` 里的异常而崩溃，但那一帧该方法后面的代码被跳过，下一帧又重复报错，Console 被刷屏。
- `try/catch` 适合放在解析存档、读写文件、解析网络数据这类"可能失败"的地方，不要包整个 `Update`。

## 动手试试

```csharp
using UnityEngine;

public class NullDemo : MonoBehaviour
{
    [SerializeField] private Rigidbody body;      // 先故意不拖

    void Start()
    {
        Debug.Log(body.mass);                     // 会报 NullReferenceException
    }
}
```

1. 挂到一个物体上点 Play，在 Console 里双击报错，确认跳到了 `body.mass` 这一行。
2. 给物体加上 `Rigidbody` 组件并拖进字段，再运行，错误消失。
3. 把 `Debug.Log(body.mass)` 包进 `try { } catch (NullReferenceException) { Debug.LogWarning("没拖 Rigidbody"); }`（需要 `using System;`），观察红字变成了黄色警告。

## 项目应用决策：异常是失败边界，不是流程控制

玩家输入、Inspector 配置和存档内容可以先验证，适合用返回值和提示处理；文件损坏、资源缺失、网络不可用等跨层失败，才适合抛出并在边界处捕获。不要在 `Update` 里用 `try/catch` 包住正常分支，也不要捕获后什么都不做。

主线项目的规则是：底层方法说明失败原因，上层决定显示“无法读取存档”还是回退到新游戏；开发期保留堆栈和上下文，发布期再做用户可读提示。验收要覆盖空引用、坏存档和缺少组件三类失败，并确认游戏仍能回到可操作状态。

## 常见坑

- 空的 `catch { }` 吞掉所有错误，之后现象诡异却没有任何日志。至少要 `Debug.Log` 一下。
- 在 `Update` 里 `try/catch` 一个每帧都会出错的调用：既慢又掩盖问题。先修根因。
- 在协程里抛异常，协程会静默终止，后面的逻辑不再执行（第 6.2 篇会再提到）。
- 用 `throw e;` 导致丢调用栈。
